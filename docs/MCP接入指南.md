# MCP 接入指南（随发行版附带）

> 本文件随发行包落在 `docs/MCP接入指南.md`。
> 目的：说清 RuPix 对外提供什么、任意支持 MCP 的 AI 客户端要怎么接、接完怎么验收。
>
> **本包不含 MCP 适配器，也不含任何脚本。** 发行版交付的是 `rupix.exe`、`decoders/*.dll`、
> 清单、许可与文档。MCP 协议由**仓外独立适配器**承担，需要单独获取，或按本文 §二 的契约
> 自行实现。因此安装 RuPix 与是否安装 Python / 其它脚本运行时**无关**。

## 一、它是什么、不是什么

RuPix 本体不实现 MCP 协议，不常驻、不监听端口、不弹 GUI 窗口、不进单实例闸门。
它只提供四个**不开窗也能调用**的命令行动词；MCP 会话由独立适配器持有：

```
AI 客户端 ──stdio JSON-RPC──> 独立适配器（仓外组件，本包不提供）
                                  └─每次 tools/call 起一个短命 rupix.exe ──一行 JSON──> 回适配器
```

- 适配器不是 RuPix 的一部分：可以独立发版、独立安装、独立选语言与协议栈，
  协议栈 / JSON-RPC / SDK 都不进本包，也不编进 exe。
- 每个 AI 客户端各自起一个适配器，客户端关掉它就没了；这不是全局后台服务。
- 四个动词全部只读：不改设置、不联网；目录输入与出像素的三个动词不写盘。
  `--list` 吃压缩包时会展开到 `<exe>/temp/`，是唯一例外（见 §二）。Win10 与 Win11 行为一致。

## 二、宿主契约（这才是本包真正提供的东西）

| 动词 | 参数 | 返回 |
|---|---|---|
| `--list` | 目录**或压缩包** | 该目录 / 包根层里 RuPix 认得的图清单；与 GUI 翻页同源，包输入见下表后说明 |
| `--metadata` | 文件 | 大小 / 时间 / 后缀 / EXIF 六行 / orientation；**不解码** |
| `--thumbnail` | 文件 | 240×180 框内缩略图的 PNG（base64 内联） |
| `--render` | 文件，可选 `宽 高` | 按框渲染的 PNG（base64 内联）、原图尺寸与帧数；缺宽高按原尺寸 |

**`--list` 认压缩包（m305）**：把 `.zip` / `.cbz` / `.7z` / `.rar` / `.cbr` / `.tar`
等容器路径直接传给 `--list`，宿主展开它的**根层**到 `<exe>/temp/rupix-zip-*/L*/`，
再按与 GUI 同一份清单规则回条目。此时 `dir` 是落盘后的层目录，`entries[].path` 是落盘
后的真实文件路径，可原样交给 `--metadata` / `--thumbnail` / `--render`；响应多出
`archive:true`、`skipped`（认得出但打不开的条数）、`truncated`（层级预算是否截断）
三个字段。目录输入时这三个字段**不出现**，响应与旧版逐字节一致。
`truncated` 为真表示包内**层级树**被建树预算截断（子包 >64 / 512 MB / 20 000 节点 / 32 层）；
`entries` 仍是完整的根层清单，没列全的是左侧文件树里的子层结构。

- 只列**根层**：包内子目录 / 子包不在 `entries` 里，命令面没有「包内定位」语法；
  要翻子层走 GUI 的左侧文件树。
- 这是命令面**唯一写盘**的一条路（其余三个动词与目录输入仍零临时文件）。展开目录与
  GUI 共用、由 RuPix 在 GUI 退出时统一清理；**适配器不要自行删这些路径**，它们要活到
  随后那次 `--render`。纯无头部署（永不启 GUI）时，残留按 `rupix-zip-` 前缀由运维清理。
- 只读介质上「不写盘」的前提对包输入不成立：写不进 `temp/` 会回 `code=3`。

- stdout **恰好一行 JSON**：`{"ok":…,"cmd":…,"code":…,<各动词自有字段>}`；
  日志只走落盘 sink，不混进 stdout。
- 退出码 `0` 成功 / `2` 参数错 / `3` 读文件或解码失败 / `4` 上限拒绝
  （清单 10000 条、像素 3200 万），与响应里的 `code` 同值。
- 像素在 `png_b64` 字段，`mime` 恒为 `image/png`；调用方把它解成标准 MCP
  `{ "type": "image", "data": "<base64>", "mimeType": "image/png" }` content block 即可，
  **不需要转码、不需要落临时文件**。文本类动词直接塞 text content。
- `--list` 认哪些后缀**取决于 `decoders/` 里已装的 DLL**（见 §六）。
- 没有 `open` 动词、没有写操作、没有逐帧动词、没有窗口控制 —— 这是设计，不是缺漏。

> `rupix.exe` 是 GUI 子系统程序，调用方必须自己重定向 stdout 才能读到那一行。
> JSON 一律 UTF-8；用 `cmd` 的 `>` 重定向时留意代码页，路径含非 ASCII 字符时
> 建议由程序化调用方（`subprocess` / `Process` / 管道）按字节捕获。

## 三、接进 AI 客户端

1. 先取得或实现一个适配器：把 §二 四个动词映射成 MCP 工具。**这一步不在本包内完成**。
2. 在客户端的 MCP 配置里加一条 stdio server，指向**你放置的适配器**：

```json
{
  "mcpServers": {
    "rupix": {
      "command": "<适配器运行时绝对路径>",
      "args": ["<适配器入口绝对路径>"],
      "env": { "PYTHONIOENCODING": "utf-8" }
    }
  }
}
```

`env` 一行只在适配器确实以 Python 实现时才需要；换别的语言就按它的运行时填。
路径里的反斜杠在 JSON 里要写双份，或整条改用 `/`。本文不写死任何机器专属路径。

| 客户端 | 配置入口 |
|---|---|
| Claude Desktop / Cline / Cherry Studio 等 | 配置文件里的 `mcpServers`，或图形界面「添加 MCP Server → stdio」 |
| WorkBuddy | `~/.workbuddy/mcp.json` 的 `mcpServers`，条目需带 `"type": "stdio"`；加完在连接器管理页的自定义连接器入口点「信任」，必要时重启客户端 |

3. 重启客户端，确认工具列表里出现适配器注册的工具。**看到工具 = 握手成功**；
   没看到就先按 §五 单独验宿主命令面，把「宿主坏了」和「客户端没配好」分开。

**参考映射**（某个适配器的实现示例，**不是 RuPix 契约**，换适配器就可能变）：

| 工具 | 宿主动词 | 必填参数 | 返回 |
|---|---|---|---|
| `rupix_list` | `--list` | `dir` | text |
| `rupix_metadata` | `--metadata` | `path` | text |
| `rupix_thumbnail` | `--thumbnail` | `path` | image + text |
| `rupix_render` | `--render` | `path`，可选 `width` + `height` | image + text |

工具名、入参 schema、annotations、错误语义都由适配器决定；稳定不变的是 §二 那四个动词。
适配器应把工具内失败做成 `isError: true` + 可读文本，协议级失败才用 JSON-RPC `error`。

## 四、换一个 AI 来验收：把下面这段原样发给它

> 前提：已按 §三 接好适配器，工具列表里能看到它注册的工具。
>
> 请只用适配器提供的 `rupix` 工具做一次接入验收，逐步报告你的实际观察，不要猜：
> 1. 先列出可用工具，报告名字和各自必填参数。
> 2. 对目录 `<换成你机器上一个真实存在的图片目录>` 调列目录工具，报告条数和前两个条目名。
> 3. 挑其中一张调元数据工具，报告 `size`、`ext`、`orientation`。
> 4. 对同一张调缩略图与渲染工具（渲染给 `width=320`、`height=240`）。
>    请确认你收到的是**图片**而不是一段文字描述，并报告 `width` / `height` / `bytes` 与 `natural`。
> 5. 故意请求一个不存在的文件，确认返回错误，把错误文本原样贴出来。
> 6. 最后回答：全程有没有弹出 RuPix 的图形窗口？有没有任何一步需要你写文件？
>
> 任何一步失败就停下，原样贴出错误文本，不要自行改用别的方式绕过。

**预期**：工具齐全；列目录条数与目录里图片数一致；缩略图与渲染都返回可显示图片且
`bytes` 自洽；第 5 步错误文本里能看到 `code=3`；全程无窗口，写盘口径见 §二。
若第 4 步只拿到文字，多半是客户端没把 `image` content block 交给模型 —— 那是客户端的
呈现问题，先按 §五 验宿主，确认 `png_b64` 能解出真 PNG 再回头查客户端。

## 五、不依赖 AI 也能验：直接跑宿主命令面

在发行目录里用调用方重定向 stdout，逐个跑：

```
rupix.exe --list "<某个图片目录>"        > out-list.json
rupix.exe --list "<某个压缩包>"          > out-list-archive.json
rupix.exe --metadata "<某张图片>"       > out-meta.json
rupix.exe --thumbnail "<某张图片>"      > out-thumb.json
rupix.exe --render "<某张图片>" 320 240 > out-render.json
```

四个检查点：

1. 每个文件**恰好一行**合法 JSON，`ok:true` / `code:0`；
2. 退出码与 `code` 同值（缺参数应得 `2`，不存在的文件应得 `3`）；
3. 解出 `png_b64` 后前 8 字节应为 PNG 签名 `89 50 4E 47 0D 0A 1A 0A`，
   且实际字节数与 `bytes` 一致；
4. 全程不弹窗口；目录与像素动词不产生临时文件（`--list` 吃包例外，见 §二）。

这四步过了，宿主侧就是好的；剩下的问题都在适配器或客户端配置。

| 红在哪 | 多半是 |
|---|---|
| stdout 一行都读不到 | 调用方没重定向 stdout（GUI 子系统），或读了 stderr |
| `code=3`「扩展名无人认领」 | `decoders/` 为空或少了对应 DLL，见 §六 |
| 中文路径变乱码 | 调用方按系统码页解了 UTF-8 stdout，应按字节捕获 |
| 工具列表空 / 握手超时 | 客户端 `command` / `args` 指向的适配器路径不对，或没重启 / 没信任 |

## 六、额外安装的解码器，MCP 能不能用？

**能，而且这是设计本身。** 无头命令面与 GUI 是**同一枚 exe、同一条解码链**：入口在一切
分支之前统一装配 `install_decode_stack()`，再由 `<发行目录>/decoders/*.dll` 动态并出格式表。
适配器每次 `tools/call` 起的是一个短命进程 —— 所以**新装、替换或删掉一枚解码器 DLL，
下一次调用就生效，不必重启适配器或客户端**。`--list` 认哪些后缀也会跟着变。

内置只有矢量的 `resvg`（管 `svg` / `svgz`）；**位图全部由解码器 DLL 提供**。
本包 8 枚 DLL 的实测：

| 样本 | 结果 |
|---|---|
| AVIF / JXL / TIF / PNG / JPG / HEIC / PSD | 成功出像素；HEIC 640×480 按 320×240 框缩到 120×90 |
| GIF 2 帧 / APNG 3 帧 | 成功，`frames` 回帧数，**像素只回第一帧** |
| 把 `decoders/` 换成空目录 | 上述位图全部 `code=3`「扩展名无人认领」，只有 SVG 仍能解 |
| 只留 `modern` 一枚 DLL | 只有 `avif` / `heic` / `jng` / `jxl` 能解；`--list` 认出的后缀从 16 种缩到 4 种 |

四个诚实边界：

1. **只有第一帧**：命令面没有逐帧动词，`frames` 只告诉你总帧数。动图 / 多页要看第 N 帧得走 GUI。
2. **`--metadata` 不解码**：它只回 `size` / `mtime` / `ext` 与 EXIF 六行 + orientation；
   EXIF 先读文件头 256 KiB，找不到再补读至 12 MiB，更深处拿不到是防御性上限。
3. **GUI 的解码器设置不作用于命令面**：`rupix.ini` 里的 `decoders_disabled` / `decoders_preferred`
   由 GUI 运行时装载，无头路径在它之前就返回了；命令行 `--safe-mode` 则在统一入口生效。
   想在 MCP 侧少认一种格式，就该动 `decoders/` 目录，而不是改 ini。
4. **RAW 样本**：几个 RAW golden 样本是裁切片，`raw` 解码器会报「文件已损坏」；
   错误来自解码器内部、不是「无人认领」，用完整的 RAW 原片才能验这条格式。

## 七、安全边界

- 四个动词只读；命令面不开端口、不注册服务、不碰注册表，写盘范围见 §二。
- 路径必须是本机真实存在的文件或目录；上限（清单条数、像素总量）由宿主拒绝，回 `code=4`。
- 单客户端 stdio 形态，不是全局后台服务：多个 AI 客户端各起各的适配器，彼此不共享状态。
  把整包拷到只读介质也能用（诊断物与缓存写不进去时静默降级）；但 `--list` 读包
  需要能写 `temp/`，只读介质上这一路会回 `code=3`。

## 八、随包文件与契约漂移

`docs/` 下与本主题相关的**只有本文**，另有 `decoders.json` / `plugins.json` / `update.json`
三份清单与两份许可。真源是 `main/docs/MCP接入指南.md`，由部署脚本复制进发布目录并校验
「存在 / UTF-8 / 非空 / 落地字节同源」；**不要手改发布目录里的副本**，下次部署会覆盖。

★ **分仓形态下有一处风险**：宿主改了 JSON 字段或退出码语义，仓外适配器不会自动变红。
适配器一侧应当自带契约漂移判据（起真实 exe 跑四个动词、断言字段与退出码），
这是唯一能在改完宿主当场发现不一致的地方。本包不替适配器承担这件事。
