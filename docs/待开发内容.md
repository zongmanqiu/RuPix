## 一、值得做的两条

### 1.1 平移上限的「衣角」在顶缘会藏进自绘标题栏

**现象（可观察的错）**：把一张比视口大的图往下拖到底（看图的上缘），再推到极限，
主画布**看起来整块是空的**——图没画错，是那 24 dp 衣角被自绘标题栏吃掉了。
往下缘拖没有这个问题（底部没有整幅遮挡）。

**根因（源码核实，不是推测）**：`src/core/viewer/zoom.rs::pan_limits` 拿
`self.view.2 / self.view.3`（视口宽 / 高）当基准，而 frameless 窗的标题栏 chrome
画在画布上方约 33 dp **之内**，`view` 含那一块 ⇒ 上限比真实可见区多算了一条标题栏。

**修法**：公式不动，**换输入**——上限基准从窗高换成扣掉标题栏的内容高。
牵动的是 m206 那一版裁决（上限 = (视口 + 图)/2 − 24dp 的基准），所以不自行改，
**等一句话拍板**。

**判据现成**：`build/pan_probe.ps1` 用鸟瞰小地图的视口矩形读数（夹具中部封顶 50% 灰，
白矩形可数值提取）——修完直接对比"推到顶缘时视口矩形上边是否 ≥ 0"。

**为什么它排在第一位**：这是全清单里**唯一一条能指出「用户看见的东西是错的」**的条目，
其余要么是观感、要么是量了没收益。

### 1.2 EXIF 覆盖率缺口：256 KiB 之后的拍摄信息显示为空

**现象**：JPEG / PNG / TIFF 的 EXIF 落在 256 KiB 之后时，属性窗的「拍摄信息」整段为空
（相机 / 镜头 / 曝光 / 焦距 / GPS 六行全空）。文件本身有 EXIF，我们不显示。

**来历**：m104 把读取上限从 12 MiB 收到 256 KiB，理由是**属性窗开着时每翻一页，UI 线程
要白读、白分配 12 MiB**（12 MiB 档实测 4.2–4.7 ms，256 KiB 档 23–25 µs）。这是一次
有意的"拿覆盖率换帧预算"——**它不是 bug，是记账记下来的缺口**。

**必须先量再决定**（顺序不能反）：

1. 造一批"EXIF 落在 256 KiB 之后"的真文件，量**这类文件的真实存在率**。
   本机 94 枚带 EXIF 语料里最深的一枚非 HEIC 只到 19,087 B，**一枚越界都没有**——
   但那是本机语料，不能代表用户相册。
2. 存在率低（比如 <0.5%）⇒ **维持现状**，把缺口写进文档，不再挂账。
3. 存在率不低 ⇒ **首选分档，不是回退**：解码路继续用 256 KiB（那是热路径，每张图都走），
   只在**用户主动打开属性窗**时读深档（一次性、用户已经接受了 12 MiB 那 4 ms）。
   这条路的代价接近零，且不把 12 MiB 摊回翻页。

**为什么它排在第二位**：缺口是真的，但**今天没有任何证据它能命中用户的实际文件**。
先量，别先改——这与 `待办.md §18` 的 ⑮/⑯ 同一个规矩（有数才谈结论）。

## 四、编码线与编辑套件（原 §一～§七，保留分析、收窄口径）

> 这一节回答「如果将来要用原格式保存 / 要裁剪，得付什么」。**它不构成开工许可。**

### 4.1 共同依赖：今天到底有什么编码能力

| 落点 | 现状 |
|---|---|
| 依赖 | `Cargo.toml` 里 `png = "0.18.1"` 是**正式依赖** |
| 宿主编码 | `src/platform/clipboard.rs` 两份：`encode_png`（剪贴板，`Fastest` / RGBA）与 `encode_png_compact`（另存，`Balanced` + 全不透明转 RGB，8 MP 省约 8 MB） |
| 唯一出口 | `src/ui/chrome.rs::start_save_png` —— 后台线程「合成 → 编码 → 写盘 → 回执」；`src/ui/canvas.rs` 给默认名 `原图主名.png`，对话框标题「另存为 PNG」，写的是**用户另选的路径**，不碰原图 |
| 编辑态 | `src/core/viewer/edited.rs` 的覆盖账本只有 `(w, h, RGBA8)` + 还原用的 original；`whole_image_for_plugin` 返回的 `ForPlugin` 只有 `path / w / h / rgba / orient`，**没有帧号页号、没有元数据** |
| 插件侧 | 通道调色插件的「另存为（PNG）…」走宿主同一出口；色阶插件自己产 PNG 字节。插件进程外也可自带编码器写文件，宿主零改动 |
| 解码侧 | ABI 的导出全是只读：`iv_probe` / `iv_render` / `iv_render_raw` / `iv_render_region` / `iv_caps` / `iv_metadata` / `iv_export_svg`（末者是 SVG 文本导出），**没有 encode / write 面** |

★ 一句话：**「有编码器」和「有多格式编码体系」不是一回事**。今天有的是前者（PNG 一枚），
`待办.md §24` 为「另存」引第二枚编码器的提议也逐一判废过（JPEG 无 alpha / 有损、
WebP / AVIF 违轻量、BMP / TGA 比 PNG 大、GIF 静态打不过 PNG、TIFF / PDF 看图器不排版、
SVG 换壳位图）。

### 4.2 「保存」有三种口径，问题从这里分叉

| 口径 | 含义 | 需要什么 | 现状 |
|---|---|---|---|
| **A 导出编辑结果** | 新建文件、格式自由、不碰原图 | 一枚编码器 | ✅ 涂鸦走这条：任意格式解得开就能涂，一律另存 PNG |
| **B 覆盖 / 更新原文件** | 存完仍是原格式、别的软件当原图用 | §4.3 那六层 | ❌ 未做，当前架构连落点都没有 |
| **C 旁路叠加** | 原文件永远不动，编辑存成独立笔画层 / 差异层，加载时叠加 | 零格式编码器 | ❌ 未做；代价是「发给别人」仍要合成一次，又回到 A |

**用户 2026-10-31 拍板走 A**（`待办.md §24` 原文：不管原图是什么格式，只要解得开就能涂鸦，
涂完一律另存 PNG）。所以"涂完不能按原格式保存"不是漏实现，是为了避开 B 的全部代价
而选的产品口径。

### 4.3 选 B 的成本：不止「每种格式一枚编码器」

| 层 | 卡点 |
|---|---|
| 像素编码 | N 种格式 N 枚编码器；宿主还要撞 `待办.md §26④`「把任何编解码库编进 exe」永久不提供（现有 PNG 那一枚是复制 / 编辑结果导出的既有例外） |
| 容器 | GIF / APNG / WebP 动画 = 多帧 + 延时 + 循环；TIFF / PDF / MPO = 多页。解码只得到**当前这一帧的 RGBA8**，按原格式写回去，动画与多页直接没了 |
| 元数据 | EXIF / ICC / 方向 / XMP / 位深 / 色度采样 / HDR：另存路径里这些零命中，编辑覆盖也不带 ⇒ 信息在解码时就没进来，写不回去 |
| 保真 | JPEG 从 RGBA8 再压一次 = 再损一代；要无损只能走 DCT 系数域局部改，那是另一套算法，不是「加一枚编码器」 |
| 矢量 | SVG 涂完还存 SVG，笔画是矢量层、底图只能嵌位图，文件比 PNG 还大 |
| ABI | 要按格式回写就得给只读 ABI 加编码面、bump 版本、每枚 DLL 各自实现，与「DLL 只负责解码 / 位图不内置」的架构相撞 |

**裁剪比涂鸦还远一步**：它改变像素网格，而 `image.write` 契约要求「收到的与回传的都是同一尺寸」
（`src/core/viewer/edited.rs` 卷首）。所以裁剪**走插件 editor 路线连 A 都走不通**；
**走宿主显示层变换路线（像旋转 / 镜像那样）则不碰契约**——这正是 §4.4 收窄的那条。

### 4.4 三条各自的准入（口径已收窄）

不是「格式保真」这一格。**

### 4.5 编辑套件（裁剪 + 缩放尺寸）—— 用户点名「以后再做」

> 用户原话方向：「这些图片编辑类的，整合到一起，然后写入待开发内容，以后再做。
> 如果要做，也是和图片的简单编辑一起做——包括 PNG/SVG 两种格式的涂鸦、裁剪、缩放尺寸。」
> 来源语境：23 条清单 #19（调整尺寸后重新保存）单独做被判「没意义」，整编入此套件。

**范围**：涂鸦（已有，不重做）＋ **裁剪** ＋ **缩放尺寸**，一套统一的「简单编辑」入口；
输入 PNG 与 SVG（SVG 走宿主 resvg 已栅格化的像素，不拖该依赖进插件）。

**为什么单独的 #19 判废**：只改尺寸落一个新文件，UX 断裂（临时文件 + 新窗），作为独立功能
无消费场景；作为编辑套件的一个能力才有意义。

| `image.write` 同尺寸契约 | 对宿主路线不适用 | 走宿主路线则**不必改契约**；走插件 editor 路线必须改，不推荐 |
| 第二枚编码器（`§24` 逐格式判废） | PNG 一枚既有例外 | 套件输出仍**只出 PNG**（`Balanced` + 去 alpha 既有口径），不新增编码器 |
| SVG 保存形态 | 未决 | 涂 / 裁 / 缩后的 SVG 存什么：① 包一层 `<image>` 嵌回栅格（保留 `.svg` 后缀，矢量信息已断）；② 转 PNG。二选一或都给，**需拍板** |

**实现路线倾向**（届时先验证再动工）：沿用涂鸦的宿主显示层变换路线——裁剪 / 缩放都是
纯几何变换，与已有旋转 / 镜像同族，另存走 `start_save_png` 同一出口；8 MP 闸与超大图另存
的内存代价在动工前实测。**本文件不排期**，重开由用户点名。

## 五、窗口外发光 / 外部阴影（立项待评估，不排期）

参考同机 `.ex/优秀项目/pecia` 的做法（用户点名「类似 pecia 那种外部阴影」）：
它不是调 DWM，而是**另开一枚垫在主窗下面的分层伴生窗口**
（`WS_EX_LAYERED | WS_EX_TRANSPARENT | WS_EX_NOACTIVATE | WS_EX_TOOLWINDOW`），
用 `UpdateLayeredWindow` 画一张比主窗四周各大 9px 的预乘 BGRA：1px 抗锯齿边框环 +
高斯渐变外发光（σ=3、边缘 alpha 约 45/255、颜色跟随边框 ⇒ 深色主题下是白色轮廓光）。
随移动 / 缩放 / DPI / 圆角变化重算；进程级开关默认开。参考源码实测记了三个坑：
`CS_DROPSHADOW` 在无边框窗上不出阴影、DWM 会丢掉自绘边带、阴影必须对齐
`GetWindowRect` 而不是 `EXTENDED_FRAME_BOUNDS`。

**RuPix 的难点**：主窗本身就是逐像素分层（`WS_EX_LAYERED` + `UpdateLayeredWindow`，
不调 `LWA_ALPHA`），已有 alpha 通道，但**窗口矩形固定 ⇒ 发光画不到窗外**。两条路：

| 路线 | 做法 | 代价 |
|---|---|---|
| A 扩主窗 | 四周各留 9px padding，在同一张位图里画发光 | 所有 `view` 坐标、命中、拖动、鸟瞰、缩略图条、DPI、最大化 / 全屏全量重算 |
| B 伴生窗口 | 照参考项目另开一枚 HWND 垫在后面 | 不动布局，但要新建窗口类、z 序、move/resize/show/hide/minimize/DPI 全事件同步、多开时每窗一份、关窗销毁 |

两条路都要处理：整窗默认 75% 半透明与阴影的叠加、极简 / 放映 / 全屏态要不要关发光、
每窗一份的生命周期。粗估 **500–900 行 + 框架补丁 + 配置键 + 设置页开关 + 门禁测试**。

**收益**：纯观感——让无边框半透明窗在浅色壁纸上边界更清楚。**暂缓理由**：看图器追求沉浸，
发光压在深色图上会抢画面；用户一贯按「低占用 / 极简」取舍；且它与按钮归类是两条独立的轴，
混做必然返工。**重开时先出一张深 / 浅桌面 × 白图 / 黑图的对比图再拍板**，本文件只立项、不排期。
