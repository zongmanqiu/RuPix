## 一、共同依赖：今天到底有什么编码能力

| 落点 | 现状 |
|---|---|
| 依赖 | `Cargo.toml` 里 `png = "0.18.1"` 是**正式依赖** |
| 宿主编码 | `src/platform/clipboard.rs` 两份：`encode_png`（剪贴板，`Fastest` / RGBA）与 `encode_png_compact`（另存，`Balanced` + 全不透明转 RGB，8 MP 省约 8 MB） |
| 唯一出口 | `src/ui/chrome.rs::start_save_png` — 后台线程「合成 → 编码 → 写盘 → 回执」；`src/ui/canvas.rs` 给默认名 `原图主名.png`，对话框标题「另存为 PNG」，写的是**用户另选的路径**，不碰原图 |
| 编辑态 | `src/core/viewer/edited.rs` 的覆盖账本只有 `(w, h, RGBA8)` + 还原用的 original；`whole_image_for_plugin` 返回的 `ForPlugin` 只有 `path / w / h / rgba / orient`，**没有帧号页号、没有元数据** |
| 插件侧 | 通道调色插件的「另存为（PNG）…」走宿主同一出口；色阶插件自己产 PNG 字节。插件进程外也可自带编码器写文件，宿主零改动 |
| 解码侧 | ABI v6 的导出全是只读：`iv_probe` / `iv_render` / `iv_render_raw` / `iv_render_region` / `iv_caps` / `iv_metadata` / `iv_export_svg`（末者是 SVG 文本导出），**没有 encode / write 面** |
| 规模 | 发布清单 8 枚解码器 DLL，覆盖的后缀由各自 `formats` 字段按动态并集给出；位图一律不内置，DLL 只负责解码 |

★ 一句话：**「有编码器」和「有多格式编码体系」不是一回事**。今天有的是前者（PNG 一枚），
`docs/待办.md` §24 为「另存」引第二枚编码器的提议也逐一判废过（JPEG 无 alpha / 有损、
WebP / AVIF 违轻量、BMP / TGA 比 PNG 大、GIF 静态打不过 PNG、TIFF / PDF 看图器不排版、
SVG 换壳位图）。

## 二、「保存」有三种口径，问题从这里分叉

| 口径 | 含义 | 需要什么 | 现状 |
|---|---|---|---|
| **A 导出编辑结果** | 新建文件、格式自由、不碰原图 | 一枚编码器 | ✅ 涂鸦走这条：任意格式解得开就能涂，一律另存 PNG |
| **B 覆盖 / 更新原文件** | 存完仍是原格式、别的软件当原图用 | §三 那六层 | ❌ 未做，当前架构连落点都没有 |
| **C 旁路叠加** | 原文件永远不动，编辑存成独立笔画层 / 差异层，加载时叠加 | 零格式编码器 | ❌ 未做；代价是「发给别人」仍要合成一次，又回到 A |

**用户 2026-10-31 拍板走 A**（`docs/待办.md` §24 原文：不管原图是什么格式，
只要解得开就能涂鸦，涂完一律另存 PNG）。所以"涂完不能按原格式保存"不是漏实现，
是当年为了避开 B 的全部代价而选的产品口径。

## 三、选 B 的成本：不止「每种格式一枚编码器」

| 层 | 卡点 |
|---|---|
| 像素编码 | N 种格式 N 枚编码器；宿主还要撞 §26④「把任何编解码库编进 exe」永久不提供（现有 PNG 那一枚是复制 / 编辑结果导出的既有例外） |
| 容器 | GIF / APNG / WebP 动画 = 多帧 + 延时 + 循环；TIFF / PDF / MPO = 多页。解码只得到**当前这一帧的 RGBA8**，按原格式写回去，动画与多页直接没了 |
| 元数据 | EXIF / ICC / 方向 / XMP / 位深 / 色度采样 / HDR：另存路径里这些零命中，编辑覆盖也不带 ⇒ 信息在解码时就没进来，写不回去 |
| 保真 | JPEG 从 RGBA8 再压一次 = 再损一代；要无损只能走 DCT 系数域局部改，那是另一套算法，不是「加一枚编码器」 |
| 矢量 | SVG 涂完还存 SVG，笔画是矢量层、底图只能嵌位图，文件比 PNG 还大 |
| ABI | 要按格式回写就得给只读 ABI 加编码面、bump 版本、每枚 DLL 各自实现，与「DLL 只负责解码 / 位图不内置」的架构相撞 |

**裁剪比涂鸦还远一步**：它改变像素网格，而 `image.write` 契约要求「收到的与回传的都是
同一尺寸」（`src/core/viewer/edited.rs` 卷首；§24 里 8 MP 闸不抬的理由正是这条）。
所以裁剪在当前契约下 **连 A 都走不通**，先改契约才谈得上编码。

## 四、三条各自的准入与重开条件

| 条目 | 当前状态 | 卡在哪 | 重开要回答 |
|---|---|---|---|
| **快速图像转换**（A→B 换格式 / 转 PDF / 转 SVG） | ⏸ 挂起，归在编码相关组以后再考虑 | 产品裁决：`docs/产品定位与边界.md`「不做导出 / 格式转换这条能力线」+ `docs/待办.md` §26④ 永久不提供 | ① 导出能力线裁决是否松动；② 第二枚编码器的轻量判废是否被新量化证据推翻。**两问没松动，有多格式编码能力也不投入** |
| **涂鸦** | ✅ 已交付，出口只有 PNG（口径 A） | `docs/待办.md` §24 用户拍板 + 逐格式判废 | 若要改成按原格式保存 ⇒ 先答 §三 六层，再选型 B 或 C；不改口径则无需任何动作 |
| **裁剪** | ❌ 永久不提供 | `docs/待办.md` §26④ 硬边界；且 `image.write` 同尺寸契约、像素网格都过不去 | 先松动产品裁决 **且** 改「回传必须同尺寸」的契约；JPEG 无损裁剪属 DCT 系数域操作，不是通用编码器能给的 |

**三条方向不同，别用「等编码器」统一解锁**：
#4 是换容器，可以不动像素（某些格式间理论上还能字节级转封装）；涂鸦 / 裁剪是改了像素再存，
必然重编码、§三 的保真问题全冒出来。**共用的是「像素 → 文件」这一格，不是「格式保真」这一格。**
即使多格式编码能力到位，#4 卡产品裁决、涂鸦卡 §24、裁剪卡 §26④ ⇒ 都不自动放行。
