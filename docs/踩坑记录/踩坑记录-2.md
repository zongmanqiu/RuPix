### K48 —— 配对测量忘了同相：dcache 开着比"解码 vs 本地重采样"，结论方向整个反过来 **［2026-10-19 已根治：整套磁盘解码缓存撤除，见 K68 与 `HISTORY.md`］**

- **现象**（2026-10-17 C 路线验收）：同一进程里把"老规矩三次整解"与"C 一次整解 + 两次本地
  换档"配对，第一次跑出来是 **老规矩 0.50s vs C 1.39s**——按这个数 C 是倒退，该直接毙掉。
- **根因**：配对两侧**不同相**。老规矩那一侧复用了同进程前面刚跑完的解码，`dcache` 全命中，
  量到的是"读 140 MB 缓存"（≈0.05s/次）而不是"解一次码"（≈0.35s/次）；C 那一侧则把
  `pump` 的静默窗（400ms）也算进了画面耗时。两个偏差叠加，足以把结论翻面。
  重跑（`RUPIX_NO_DCACHE=1` + 计时改成"等到上屏位图到达该档为止"）才是
  **TIFF 1.94s→1.60s、JPEG 3.98s→2.30s**。
- **另一处同族错误**：计划里我写过"≥100% 状态的工作集从 531 MB 降到 150–290 MB"，那是
  **推理不是实测**——100% 以上时显示档就等于原图档，`base + image + 框架纹理` 三份一样
  少不了，与今天持平；中间档反而多一份原图 base。已在 本仓历史记录 §7.4b 更正。
- **解法（规矩）**：① 配对两侧必须**同一开关状态、同一热度**，跑之前先声明缓存/预热怎么处理；
  ② 计时要量**用户等的那件事**（"画面到达这一档"），不要量"探测器静默了多久"——探测窗会把
  几十到几百毫秒的固定偏差按步数累加；③ **没测出来的收益不写进文档**，写"待测"。
- **同类**：一次探针里混用"真解码路径"与"缓存命中路径"作对比，等于拿两个不同的机器比。
  同相性是配对比较唯一的前提，`RUPIX_NO_DCACHE=1` 这类开关存在的意义就是它。

### K49 —— "放大看不清"的第三层在渲染滤镜：量到中间状态对，不等于最终像素对

- **现象**（2026-10-17 第二次报障）：同一张 6055×6055 的 TIFF，用户放大到底仍只见马赛克糊面，
  而别的软件能看清每一个像素格。上一轮刚把解码链修通并用探针实测过"上屏位图 = 原图档"，
  于是排查顺序自然落在自家 `viewer` / `decode` 里"还有哪一处阉割"。
- **根因不在自家代码**：`draw_image` 的观感链路有**三层**可归因——①解码给了哪一档、
  ②上屏位图多大、③位图铺进更大的框时用什么插值。前两层这次都是对的（原图档、1 源像素
  = 1 位图像素），缺陷是第三层：windui 的 D2D `draw_image` 把 `DrawBitmap` 的
  `interpolationMode` **写死 LINEAR**（矩形裁剪与圆角 layer 两个分支各写死一处），
  双线性把相邻源像素混成中间色，方块棱角在数学上不可能出现。第三层在 `.3rd/`，
  不在"查自己的调度与档位"的怀疑半径里。
- **解法（规矩）**：① 观感类报障的判据必须下到**最终呈现的像素**，不能停在中间状态——
  位图尺寸对得上而画面仍旧糊，这轮的教训就是这个死角。能读回像素的通路（D2D
  `offscreen::OffscreenBackend`，与窗口后端同一个 `D2DCanvas`、只把呈现目标换成 CPU 可读的
  离屏位图）比读代码强得多：一条"同一次运行、只差一个标志"的两臂对照，二十分钟就把责任层
  钉死（未声明臂 32 个像素里 16 个混合色，声明臂 0 个）。② 改完之后要**数同一常量的出现次数**：
  `grep` 到 `draw_image` 里两处 `DrawBitmap` 各自写死，就知道"只补一处"会复发，测试也得跟着
  分两条（矩形一条、圆角一条）。③ 修渲染缺陷先划**影响半径**：全局"放大即用最近邻"会把
  非整数 DPI 下的矢量图标一起拖进最近邻（18dp 图标在 125% 下物理 22.5px，已算放大），
  整套 UI 变锯齿——所以做成逐图 opt-in，而不是顺手把默认值改了。
- **同类**：任何"最后一公里"的观感问题（字形 hinting、色彩管理、缩放滤镜、抗锯齿模式），
  责任常落在被调用的第三方渲染层里一个写死的常量上；自家数据链全绿只是必要条件。
  与 K46 同一句话的另一半：**先做可测量的判据再动手**——而判据要量在用户真正看见的那一层。



### K50 —— 消掉一处白拷后读数没动：那说明归因错了，而不是"还有别的没查到"

- **现象**（2026-10-17 B1 内存批次）：探针 ⑩ 那一步"只喂一份自造的 `Decoded` 给 `apply`，
  量 `install` 在交出去那份之外又留几份"读出来是 **+141.5 MB**，正好等于一份整图，
  于是账记在 `derive_of` 的 `base.to_vec()` 白拷头上（那处确实存在，也确实该消）。
  M1 把它改成 `Arc` 共享之后重跑：**⑨ 从 421.7 降到 281.5（少了 140，说明 M1 生效了），
  可 ⑩ 的 +141.5 一分没动**。两处读数交叉起来只有一个解释：那 141.5 从来就不是白拷，
  是**另一处**同样大整图级的东西，而我把它笼统算进了已经查到那一处。
- **根因（位置很隐蔽）**：`Loaded::nav_thumb_rgba` 这名字写的是"缩略"，整图路线里装的
  却是 **base 本身**（6055×6055）；`rebuild_image` 又**无条件**拿它调 `nav_image_of` →
  `transformed`，而 `transformed` 对恒等变换也要 `to_vec()`（注释里明写"上屏层要独占缓冲"）。
  于是鸟瞰那份是**第二份整图像素**，每次缩放/换档都重拷一遍，UI 层 `nav_img` 还为它单独
  上传一份预乘 Pixmap（再 140 MB + 0.09–0.14 s）。`install` 里那条
  `.filter(|_| d.region.is_some())` 说明作者本来知道"整图态不需要它"，但 `rebuild_image`
  没有同一条闸——**同一个语义在两个地方各写一半，一处守了一处没守**。
- **解法（规矩）**：① **改一处就重跑同一支探针**，读数不动即归因作废，必须重新查，
  不许写"剩下的算解码路径/瞬时"这种兜底口径混过去。真正定位靠的是两个**独立**读数交叉
  （⑨ 的常驻 vs ⑩ 的自留量），单看一个数怎么算都自洽。
  ② 凡是"`xxx_thumb` / `xxx_small`"这类**带尺寸含义的字段**，要钉一条判据说它实际多大：
  本轮补的测试直接断言鸟瞰那份 `(512, 384)` 且 `!= (2000,1500)`，缩放前后 `gen` 不变
  （变了就是又拷了一遍），旋转后才换轴——名字与实现从此对不上就会红。
  ③ 共享/独占要用**指针判据**（`Arc::ptr_eq`）而不是"逻辑上应该只有一份"。
  ④ 一处语义要**收敛到一个守门处**：`nav_image_of` 现在自己封顶 512，`rebuild_image`
  只管"什么时候值得重画"，调用点不再需要各自补 filter。
- **同类**：K48（配对不同相会把结论翻面）与 K49（中间层量对了不等于最终像素对了）是同一
  族错误：**用一个自洽的数字代替一条能推翻自己的判据**。能"改前/改后各跑一次、看哪个数
  动了"的探针才配叫查账；本轮 ⑩ 那条历史读数（+141.5 → +2.4）就是留在探针注释里的证据。

### K51 —— 把活儿挪到别的线程后，探针没泵那条通道：实现到位却"画面永不到达"

- **现象**（2026-10-17 M2 换档异步化）：`tick` 的本地换档改成"只投递给 `sv-level` 线程，
  结果由 `poll_levels` 换上"之后，探针 ⑨ 的判据如果还只泵解码回包 `Done`，缩放那几步
  就永远等不到画面换档——读起来像"异步化把功能做坏了"，而实际是**探测器漏泵了新通道**。
  同一条坑的反面更危险：`Viewer` 在真实主循环里由 `runtime` 每 16 ms 轮一次，
  只要 `runtime` 那一处忘了接（或接了却把返回值吞掉），单测全绿、真机上画面停在旧档不动，
  表现与"根本没实现"一模一样。
- **根因（结构性的）**：一条链路上有两个"完成时刻"——活儿干完 vs 结果被搬上屏。
  异步化只把前者提前了，后者要靠**另一条通道**被泵、并且把"画面变了"送回标脏链路。
  本项目静止不重绘（没人标脏就不合成），所以漏掉返回值的失败模式是**静默**的。
- **解法（规矩）**：① 新增任何异步通道时，**同一批**改动里要把三处一起接上：调用方的泵
  （`runtime` 的轮询）、返回值进标脏链（这里靠 `#[must_use]` 让漏接编译期就报警）、
  以及**探针/测试的等待条件**。② "停稳"判据必须写成**用户等的那件事**（本例：上屏位图
  到达期望尺寸 + 换档信号数够），不是"探测器安静了 400 ms"——K48 记过一次，这次是同一
  条坑的异步版。③ 线程要**懒起**：`Viewer::new` 不起 `sv-level`，首次异步换档才起——
  单测与探针一次会造几十份 Viewer，每份挂一条就是几十个僵尸。
- **同类**：一切"把 UI 线程的活儿挪走"的改动（M2b 的预乘上传、区域重渲、预读）都受这条约束：
  **移动的是执行，判据也得跟着移动**，否则量到的是探测器自己的盲区。

### K52 —— 框架注释写着"O(窗口)"不等于它就是那一帧的钱：三条假设被同一支探针打回

- **背景**（2026-10-17 拖动鸟瞰 CPU ~5%）：我连着提了三条听起来都很合理的归因——
  ① 鸟瞰那份是原图尺寸，每帧采样 36 MP 很贵（M9 的额外 CPU 收益）；
  ② `draw_image` 每帧新建并填充一块**整窗** `Mask`，`.3rd/.../render/skia.rs:703-715`
  自己都写明"也就是说本函数整体仍是 O(窗口)"，所以这是税；
  ③ 改成"只画可见区切片"（B4）能把每帧成本砍到窗口大小。
- **实测（`examples/paint_cost_probe.rs`，生产入口 `SkiaCanvas`，目标 800×600，n=40/200，报中位）**：
  鸟瞰 6055²→160×120 **0.43 ms**、512²→160×120 **0.37 ms**（差 0.06 ms，不是瓶颈）；
  整窗 `Mask` 新建+扫描线填充 **0.064 ms**；省掉 Mask 直连 tiny-skia **8.76 ms** vs
  走 `draw_image` **10.3 ms**（只省 1.5 ms）；而"900×700 可见区切片 → 1600×1200 裁进窗"
  **9.9 ms ≈ 整源那一臂的 9.6 ms**。三条假设**同时作废**。
- **真机制**：成本**随目标像素数线性**——~20 ns/目标像素（铺底只要 0.27 ns/像素，差 70 倍），
  与源尺寸、与倍率（200%/400%/800%）、与滤镜（最近邻 vs 双线性）都无关；
  把**宿主 crate** 也从 `opt-level="z"` 提到 3，同一臂 10.0 → 6.3 ms（−37%），代价是
  exe 4.35 → 5.32 MB（+0.98 MB）。也就是说这笔钱花在 tiny-skia 的缩放混合循环上，
  而那个循环因为泛型入口**单态化进我们这一侧**（`Cargo.toml` 那条注释早就写过这件事，
  我只顾着引用它的结论，没去量我们这一侧还在 z）。
- **解法（规矩）**：① **注释、计划、上一轮的自己**写的成本说法都只是**假设**，要落进
  账本必须先有对应的那一臂；② 分臂要按"能推翻谁的假设"来设计，而不是按"想证明什么"来
  设计——本探针之所以能救回来，是因为它同时跑了源尺寸/目标尺寸/倍率/滤镜/mask/优化档
  六个旋钮的对照，而不是只量"一帧多久"；③ 证伪要**就地收回**：本轮把"鸟瞰那份太大所以
  慢"与"整窗 mask 是税"两句从我自己的叙述里撤掉，并把 B4 的收益从"省 CPU"改成
  "省常驻（未测）"。
- **同类**：K49（中间层量对了不等于最终像素对）、K50（消掉一处白拷后读数没动＝归因错）、
  K48（配对不同相结论翻面）。这一条补的是**"引用来源不明的成本故事"**——
  包括引用自己昨天写的那句。
- **★ 更正（同一天，见 K53）**：本条"真机制"里那句"循环因为泛型入口**单态化进我们这一侧**，
  所以要把宿主 crate 也提到 3"**归因错了**。实测五档：`z`+fat LTO 9.7 ms、`s`+fat 9.6 ms、
  `3`+fat 6.9 ms、`thin` 9.5 ms、**`z`+关 LTO 7.1 ms**——最后一档宿主仍然停在 `z`，光栅却已经
  快了 26%。所以决定的不是"宿主那一侧的档位"，而是 **fat LTO 在链接期把依赖位码按宿主
  profile 的 `opt-level` 重编了一遍**，`[profile.release.package.*]` 的例外整个被冲掉。
  提宿主到 3 只是绕过它的代价最贵的一种方式（+0.98 MB），关掉 LTO 更便宜（+0.55 MB，
  且不止救回 tiny-skia：整窗铺底 0.130 → 0.048 ms）。

### K53 —— `[profile.release.package.*]` 的 opt-level 例外会被 `lto = true` 静默冲掉

- **现象**（2026-10-17，拖动鸟瞰 CPU 5–6.5%）：`Cargo.toml` 里写着"光栅化内核按速度优化"
  ——`tiny-skia` 与 `windui` 两箱单独提 `opt-level = 3`，而 `examples/paint_cost_probe.rs`
  量出来那条循环的表现和"根本没提"一样（生产@200% 一臂中位 9.7 ms）。
- **根因**：`lto = true`（fat）把依赖 crate 的 LLVM 位码合并进**最终链接的那一级**再跑一遍
  优化流水线，用的是宿主 profile 的 `opt-level`（这里是体积优先的 `"z"`）；
  `[profile.release.package.*]` 只决定"各箱自己那一遍"的档位，位码一旦被合并就作废。
  五档配对实测（同一臂中位，交替顺序、各 3–5 组）：
  | 配置 | 中位 ms | `rupix.exe` |
  |---|---|---|
  | `z` + `lto = true`（原状） | 9.7 | 4,345,856 |
  | `s` + `lto = true` | 9.6 | 4,609,536 |
  | `z` + `lto = "thin"` | 9.5 | 4,724,224 |
  | **`z` + `lto = false`** | **7.1** | 4,924,928 |
  | `3` + `lto = true` | 6.9 | 5,322,752 |
  前两档是关键对照：**宿主档位从 `z` 换成 `s` 一点都不影响光栅**，而"提 3"两档都影响——
  说明生效的是**链接那一级**的档位，不是各箱自己的例外。`lto = "thin"` 也冲（ThinLTO 同样
  重跑跨箱内联），所以"改 thin 就能保住例外"的想法也是错的。
- **解法**：`lto = false`。整条软光栅路径一起回来，不止例外那两箱：整窗铺底 0.130 → 0.048 ms、
  1:1 blit 3.67 → 2.06 ms、生产@200% 一帧 10.3 → 7.7 ms、鸟瞰 0.37 → 0.27 ms。
  代价两条：① exe 4.35 → 4.92 MB（+13%，跨箱内联没了）；② **一次性**的安装路径略慢——
  `mem_chain_probe` 配对（各 2 次、顺序翻转）放大 200% 那一步墙钟 1.03 → 1.07 s、
  UI 忙 0.155 → 0.175 s（`image` 箱的采样循环丢了 LTO 内联）。常驻内存两档**逐字节相同**
  （283.6 / 296.3 MB）。拖动是每帧、安装是一次，所以换。
- **同类**：K07（解码库在 `z` 下慢 4.6 倍，解法是"给那箱提 3"——**在开着 fat LTO 的
  workspace 里那条解法不成立**，解码器侧若无 LTO 才有效）；K52（引用注释/旧结论当证据）。
  规矩：**凡靠 `[profile.release.package.*]` 提档位的，必须先确认 `lto` 是关的**，
  否则例外只是一句注释；验证要用"同一臂配对"，不能只看 exe 体积没涨就当生效。
### K54 —— 共享桌面上 `SetCursorPos` 造不出"用户在手拖"：测量台必须自带一条"不该有读数"的对照臂

- **现象**（2026-10-17 拖动 CPU 专项）：我写了支 PowerShell 台子自己起实例、合成鼠标拖动、
  读进程 CPU，跑出"15 秒 459 帧、每帧 6.9 ms、5.6%"——看着完全成功。用户三条反驳全中：
  ①**这台桌面上不止一个 agent 在动鼠标**，`SetCursorPos`/`mouse_event` 用的是**同一根全局
  光标**，我这 15 秒随时被人抢走，帧可能是别人晃出来的；② 滚轮事件按**光标落点**投递，
  落到别的窗口上就等于**根本没放大**（用户："放大倍数是否有影响？感觉不够啊"）；
  ③ 我用 `Stop-Process` 收尾 → 那是 `TerminateProcess`，**会话戳来不及删**，用户下次启动
  就撞上"RuPix 上次异常退出"的弹窗——**我的测试替他伪造了一次崩溃**。
- **根因**：读数没有自我否定能力。"帧数很多"不等于"我那次拖动发生了"；一台只报"读到了什么"
  的台子，永远分辨不了真动作与噪声。
- **解法**（前四条在 `.temp/drag_cpu_rig3.ps1`，后两条是 rig4 补的；`temp` 是一次性区，
  引用前先确认脚本还在，不在就照这里的判据重写）：
  1. 输入用 **`PostMessageW` 直接投给自家 HWND**：windui 的客户区坐标是从 `lParam` 解的
     （`platform/win32/mod.rs` 的 `handle_pointer` / `handle_wheel`），所以完全不碰光标、
     不怕窗口被遮；CPU 只取**自己 PID** 的 `TotalProcessorTime`，别人的负载进不来。
  2. 每台子配一条**"动作没发生时应读到 0"的对照臂**：只发 move 不发 down、且**不放大**——
     pan 被夹在 0（M6 的 `nav_drag_only_repaints_when_pan_actually_moves` 正是这条判据），
     所以对照臂应当**零帧**。实测对照臂 0–2 帧为干净、17–410 帧即污染，整轮作废重跑。
  3. 收尾一律 **`WM_CLOSE`**，绝不 `Stop-Process`：宁可可等 8 秒，也不留下假崩溃现场。
  4. **手速 / 鼠标回报率是这条曲线的自变量**：不钉住它，"5% vs 3.5%"就只是两次不同的拖动，
     不能进同一张表。钉住之后量到的律是：**一次投递的鼠标消息 = 一次整窗重绘**
     （120/s 时 frames/move = 1.00），超过系统合污能力才封顶（300/s 时只投递进 124 帧/s，
     frames/move = 0.41）。
  5. ★ **上面那条对照臂的判据本身有 bug（rig4 撞出来的）**：在鸟瞰点上"只 hover 不放大"
     读到了 **10 帧 / 0.04%**——那不是别人的光标，是 chrome 的 hover 态被我自己的 move
     改脏了，正常应用行为。**噪声地板要改成"一条消息都不投的那几秒"**（rig4 实测 0 帧），
     那才是"没人碰它"的定义；"投了消息却以为没投"不是对照。
  6. ★ **两种坐标约定不能混**：客户区消息 `lParam` 是**物理**像素（`handle_pointer` 直接
     `(lparam & 0xffff) as i16` 交给按逻辑坐标运算的命中代码），`WM_MOUSEWHEEL` 的 `lParam`
     是**屏幕**像素（`handle_wheel` 自己 `ScreenToClient`）。rig3 把 `client/scale` 塞进
     `lParam`，只有 scale=1.00 才碰巧不错位（rig4 把 dpi/scale 打成一行再也不敢假设）。
     倍率要**投递滚轮**、锚点用屏幕坐标，才谈得上"这一臂放大到了几 percent"。
- **同类**：[[feedback-evidence-driven]] 的"未测≠PASS"管的是没测就不许说通过；这一条管的是
  **测了但测的是自己造的现象**。判据要能证伪自己——否则 459 帧只是探针在数自己的心跳。

### K55 —— 一臂里 TAIL 掉回稳态不够判"那是换档余波"：配对复跑把一半结论顶掉了

- **现象**（2026-10-17 M8 倍率/面积专项，`.temp/drag_cpu_rig4.ps1`）：七个臂的表里，35% 那一臂
  每帧 6.42 ms，比左右两臂（16% 的 3.49、91% 的 3.35）贵一倍。同一臂的 HEAD 是 7.63 ms、
  TAIL 掉回 3.03 ms，我据此写下"这是连滚 8 格后的**换档余波**，2.6 s 沉降没等完，不能算进
  倍率的账"——听起来很顺，因为那个倍率确实正处在往原图档升级的路上。
- **为什么这个判法不成立**：限速落地后同一支台子、同一组臂复跑，35% 那一臂 HEAD 6.47 /
  TAIL **6.77**、中位 6.74 ms——**稳态就是贵一倍**。同一次运行里"末段掉回便宜档"只说明
  **那一臂内部发生过一次跳变**，跳变的方向可能是"余波退了"，也可能是"终于升级到了更贵的
  档"。拿一条 TAIL 当"余波"的证据，等于把两种相反的解释各挑一个顺眼的。
- **解法**（三步，都可照抄）：
  1. 判"这是不是暂态"要在**配对方阵**里判：同臂至少两次独立运行（这里是关限速 / 开限速
     两轮），中位数复现就是稳态属性，不许用一次运行的首尾差解释掉。
  2. 报"暂态"必须同时报**它朝哪个方向收敛**：TAIL 比 HEAD 便宜 ⇒ 可能是余波；TAIL 比
     HEAD 贵 ⇒ 是刚跳进更贵的那一档。第一轮那条 TAIL 恰好朝便宜方向，纯属运气。
  3. 结论落文档时把**被顶掉的那一半**写在原地划掉，别另起一段：K52/K53 是这么办的，
     这一条照同样格式办（计划 §B2 的 M8 表已就地更正）。
- **顺带钉住的两件事**（同一次复跑读出来的，都不显眼但会误导下一个人）：
  - 35% 那一档确实贵一倍，机制未查（怀疑是 2–3× 降采样带选的档位与滤镜最费）——**记为
     待办线索，不许写成结论**。
  - 本项目的**空闲工作集裁剪**（`platform::working_set`，启动 2s/10s 各一刀 + 空闲 1.5s
     再一刀）会让 `WorkingSet64` 在臂间跳 1 ↔ 385 MB。所以**测量台里的工作集不是内存判据**，
     要看内存就用 §二·b 那支受控探针（它按份记账，不看系统工作集）。
- **同类**：[[K52]]（框架注释的"O(窗口)"不是那一帧的钱）与 [[K53]]（opt-level 例外被 LTO
  冲掉）都是"机制故事讲得顺、被一次配对实测顶掉"。这一条的特别处在于**证据是我自己造的**：
  HEAD/TAIL 是我为了诚实才加的读数，结果它反过来把我带偏了一次。

### K56 —— 没有 WinDbg 也能把自家 .dmp 解到源码行：`debug = 1` 是那条真正缺的开关

- **现象**（2026-10-17 崩溃取证收尾）：`.dmp` 写出来了、`crash.log` 里 RVA/基址/线程名都齐，
  但拿 Python + `dbghelp` 去解时一路是 `err=87`、函数名空、行号 0；`crash.log` 的栈回溯里
  自己的帧全是 `rupix_lib::platform::crash_evidence::seh_filter` 这种"看着对但下一帧就断"的样子。
  参考项目 CurSeen 的踩坑记录第二十二节早就写了同一个坑，我仍然重新踩了一遍。
- **根因（三条，各自独立，凑齐才能解到行）**：
  1. **`[profile.release]` 只有 `strip = true`、没有 `debug`** ⇒ PDB 里**没有本 crate 的行表**
     （实测两个 pdb 里 `.rs` 文件名命中 **0**、私有函数名 `nav_pan_to` 命中 **0**，只剩
     `seh_filter` 这类公开符号）。★ **`strip` 与 `debug` 不是一回事、不能互相替代**：MSVC 下
     调试信息只进 PDB 不进 exe，实测 `rupix.exe` 4,956,672 → 4,956,160（−512 B，落在链接噪声里），
     pdb 7.8 MB → **21.3 MB**。开了 `debug = 1` 之后 `crash.log` 的回溯直接长出
     `crash_probe::main` + `at …\examples\crash_probe.rs:36`——**不依赖任何外部工具**。
  2. **`SYMOPT_DEFERRED_LOADS` 会把 pdb 打不开伪装成"这个地址解不出"**（都是 err 87）。
     诊断期把 0x04 摘掉，装载失败就在 `SymLoadModuleEx` 当场报，不再往下追错方向。
  3. **结构体字段表不要照抄文档名**：本机实测 `IMAGEHLP_LINE64` 是
     `SizeOfStruct(4)+pad(4)+Key(8)+LineNumber(4)+pad(4)+FileName(8)+Address(8)`——按
     "Size/FileNumber/LineNumber/Column/Address/FileName" 排会把 `Key` 当成行号，症状正是
     "文件名对、行号 0"。`SYMBOL_INFO` 的 `SizeOfStruct` 要给 **88**（给 80 直接 err 87）。
- **解法 / 定式**：
  - 发布配置固定 `debug = 1`（`Cargo.toml` 里已写死理由）。要函数名去 `crash.log` 拿，
    **不要**为了解 dump 里的名字而升 `debug = 2`（公开符号表齐全但 pdb 还要涨，收益已被
    `crash.log` 覆盖）。
    - **★ 勘误（m129，见 K135）**：这段的前提是"`crash.log` 里有函数名"，而 m129 实测那时
      `crash.log` 里全是 `<unknown>`——名字与地址一起是空的。函数名解不出的真因是
      `dump_sym.py` 的 `SYMBOL_INFO` 少四个字段，不是 `debug = 1` 缺公开符号；
      修好之后 `debug = 1` 名字齐全，`debug = 2`（74.2 MB）**收益为零**。
      结论"别升 2"仍然成立，但理由换了：不是"用不上"，是"本来就有"。
  - 离线读 dump 用 `build/dump_sym.py`：`python build\dump_sym.py <报告或转储>`（m129 起只需一个参数，
    脚本自己按指纹在 `.temp\symbols\` 里认 pdb；老写法 `<dump> <exe>` 仍然兼容）
    → 打印异常码/异常地址/**RVA**/出错地址读写、`CONTEXT` 的 rip/rsp/rbp/rax/rcx/rdx、
    线程名、exe 记的 pdb 名，最后 **地址 → `文件:行`**。
  - 三条硬偏移：`MINIDUMP_EXCEPTION` 里 `ExceptionAddress` 排在 `NumberParameters` **之前**
    （整条 152 字节）⇒ `ThreadContext.DataSize` 在流起始 **+160**、`.Rva` 在 **+164**，读错的
    症状是"寄存器全 0、栈回溯哑掉"；`ModuleList` 每条 **108** 字节；`ThreadNamesStream` 的
    条数在**首字**。
  - **配对判据只认「exe 字节数 + TimeDateStamp + 同次构建」**：`CvRecord` 的头部宽度在不同
    dump 里见过两种写法，按文档拼出来的 GUID/age 是假数（实测 age 解出 ASCII `in_s`）——
    所以我让脚本**只捞以 `.pdb` 结尾的字符串**，不报 GUID。假 GUID 比没 GUID 坏。
  - pdb 归档要有上限：一枚 21.3 MB，`deploy.py` 现按 `.temp/symbols/` 留最近 **5** 枚。
- **同类**：[[K53]]（构建配置静默决定运行时能力）、[[K55]]（判"暂态"要配对复跑）。
  本条的形状与它们一样：**"工具不好用"其实是配置少一行**，而报错信息一点不像。

### K58 —— SEH 隔离层要按**责任**分类，不是按"能不能吞"

- **现象**：坏解码器的三类事故共用一句「解码器出错，已隔离」，其中两处是错的：
  ① 递归爆栈（`STATUS_STACK_OVERFLOW`）不在吞并码表里 → `EXCEPTION_CONTINUE_SEARCH`
  → 进程 abort，窗口无声消失，还不算解码器故障、不拉黑（V7）；
  ② 网络盘掉线 / U 盘被拔 / 文件被截断（`EXCEPTION_IN_PAGE_ERROR`）被当解码器故障计三振
  → 冤枉一个健康解码器，日志还把它说成解码故障（V8）。
- **根因**：吞并表按"哪种异常能吞"设计，没按"这次到底谁的错"设计；而**不能降级**与
  **不该记账**是两件事。
- **解法 / 定式**：
  - `seh_shim.c` 返回**类别**而不是笼统的 `-1`：`SEH_DECODER_FAULT` / `SEH_MEDIA_FAULT`；
    Rust 侧 `platform::seh` 有同值的 `SEH_MEDIA` 与 `MediaFault` / `SehFault` 两个标记类型。
    ★ **这是同一份契约的两个书写处**，C 那边 include 不到 Rust 常量，改一边必须改另一边。
  - 吞栈溢出之后**必须**调 `_resetstkoflw()` 重新武装守护页，否则下一次深递归不再报栈溢出，
    而是直接跑出栈尾踩后面的内存——那比不抓更坏。能抓住是因为处理体在 `__except`
    （出事帧已全部展开、那块栈已归还），换成 `__finally` 就活不下来。
  - 实测现象：单测里爆栈会打印 `thread … has overflowed its stack` **两行**，断言照过、
    进程照活。那是 **Rust std 自己的**栈溢出处理器（先于我们的过滤器跑，重画守护页后
    原样再抛一次），不是我们的失败——别看见它就以为自己没接住。
  - 三振口径同理：文档、日志、UI 文案都写「**连续** 3 次」，代码却是会话内累计且无复位路径
    （V10）。一张坏图一次动作能烧掉 2 次（嗅一次 + 解一次），于是"平时好好的解码器"整场会话
    被拉黑、那个格式静默无人认领、**不重启不解黑**。定式：任何"计数 + 阈值"都要问一句
    "连续还是累计"，并把复位路径写出来。
- **同类**：[[K42]]（句柄类型混淆只能靠前置校验）、[[K57]]（文档与代码的裂缝）。

### K59 —— 缓存键少了"由谁解出"，读写各拷一份整图 **［2026-10-19 已根治：整套磁盘解码缓存撤除，见 K68 与 `HISTORY.md`］**

- **现象**：磁盘解码缓存（`core::dcache`）的键只有 路径 + 文件 mtime + 长度 + 目标框 + 帧号。
  换掉一个 DLL、或升级宿主本体（RGBA 归一、EXIF 方向补转、缩放档位**全在宿主里**）之后，
  旧条目照样命中——屏幕上还是**上一版解码器**画出来的像素。同时 `load` 用 `fs::read` 整读
  再 `bytes[HEADER..].to_vec()`，`store` 先拼一个 `头 + 整图` 的大 Vec：一次 40MP 命中要在峰值
  同时握住两份 160 MB，写侧也一样。
- **根因**：缓存被当成"文件内容的函数"，而它其实是"**解码器**与文件的函数"。拷贝那半边是
  顺手写法的默认成本，没人对着 160 MB 量级看过一眼。
- **解法 / 定式**：
  - 键里并入**解码器身份**：`decoders::catalog::decoder_stamp()`（exe 自身 + `decoders/` 每个
    DLL 的 名字·大小·mtime，只做 `metadata()`，不加载 DLL），经 `core::decode::set_decoder_stamp`
    注入（core 不能 import decoders，走既有的"运行期注入点"形状）。装配时装一次、
    用户点「重新扫描」时刷新。
    （**m117 注**：本条上方那道横幅说的"整套磁盘解码缓存撤除"之后，`core::dcache` 与这两枚函数
    （`decoder_stamp` / `set_decoder_stamp`）**都已不在仓里**——这里是"当时这么修过"的叙述，不是现行入口；
    **定式仍然有效**：缓存的键要含"由谁算出这个值"，否则换实现后旧条目静默命中。）
  - 代价要讲清：升级那一次全员未命中，旧条目等按龄/总量清理退场——**比拿错像素便宜**。
  - 读侧改成"头单独小读 + 像素 `take(need).read_to_end` 进最终缓冲"，写侧改成
    `File::create` 后两段 `write_all`。半截文件的自愈判据不变：长度必须**正好** = 头 + 像素。
  - 顺手补的自洽闸：解码器申报的 `bytes_needed` 必须与它自己报的宽高相称
    （`≤ 像素 × 16 + 1 MiB`，16 = 最宽的 `PF_RGBA_F32`）。绝对上限只看总量，看不见
    "100×100 却报 160 MB"这种小图大要价。
- **同类**：[[K56]]（结构体字段表要实测不能照抄文档）、[[K58]]（同一契约的多个书写处）。

### K60 —— 两个语义不同的 bool 在同一处透传：一次按键被分发两遍

- **现象**（两条，同一段代码）：① 从第 92 帧连按 91 下 `,`，画面只退 1 帧；② 修掉①之后，
  按一下 `,` 反而退**两**帧（`帧 6/100` → `帧 4/100`）。①的症状掩盖着②：那时重复分发两次
  算出的是同一个目标，看着像只生效一次。
- **根因**：
  - ①目标帧号以"屏幕上这一帧"为基准算，而后退一步可能要付一次「重建 + 快进」，这期间
    `loaded` 还是旧帧 → 连按每一下都算出同一个目标。定式：**步进型操作的基准必须是"在途
    目标"，不是"已上屏状态"**；帧上屏（`install`）时清掉在途标记，让位给屏幕。
  - ②`Viewer::step_anim` 返回的 bool 说的是"画面当场换了没"（重绘提示），
    `exec_action` 的 bool 说的是"这个键消费了没"（分发契约）。`Action::FramePrev` 那两臂
    把前者原样透传成后者 ⇒ 画布 `on_event` 报"没消费" ⇒ windui `App::on_key` 接着走
    `App::on_shortcut` 第二遍，同一个键执行两次。两个 bool 语义不同、类型相同，编译器一声不响。
- **解法 / 定式**：
  - 那个 bool 在生产里**没有任何读者**（两颗按钮丢弃返回值，快捷键层是唯一读者且读错了语义）
    —— 能删的返回值就删，别留一个"两种契约都能读"的 bool 让下一层猜。消费位改由
    `exec_action` 明写 `true`，动作臂一律不透传被调函数的返回值。
  - "消费"位报错的通用症状：**同一次按键执行两遍**。幂等动作（旋转、适应窗口、开关）看不出来，
    只有步进型动作（逐帧、缩放步进、不透明度步进）当场翻倍。改过这类动作就要数一遍分发次数。
- **这台机器的按键探针口径**：`PostMessage` 投 `WM_KEYDOWN` 会被 windui 消息循环里的
  `TranslateMessage` 合成一条 `WM_CHAR`。探针若再显式补投一条 `WM_CHAR`，一次"按键"就有两条
  字符事件（旧探针正是这个形态，它测出的"一下两帧"里有一半是自己造的）。要么只投
  keydown+keyup（等价于一次真实按键），要么只投 WM_CHAR，**不许混**。
- **数分发别看像素**：信息条要鼠标悬在浮条上才出，而桌面与别的 agent 共享一个光标、不能动全局
  鼠标。用 `RUST_LOG=warn,windui=trace,rupix_lib=debug`（日志落 `rupix.log`；**2026-10-19 起这枚文件改名 `temp\rupix-<今天>.log`**，见 K72）数
  `handle_key` 进了几条；终点判据用 `RUPIX_DECODE_TRACE=1` 数**真正落地的解码次数**——
  那才是"用户看到走了几帧"。
- **同类**：[[K54]]（测量台要自带对照臂）、[[K58]]（同一契约的多个书写处）、[[K42]]（类型混淆只能靠前置校验）。

### K61 —— 单帧贵一倍：先找"换了哪条路径"的二值开关，不要解释成"数据变大了"

- **现象**：同一张 6055² 图、同一个 784×561 窗口、同一支 `drag_cpu_rig4`，拖动时
  `image` 单帧中位 **35% 那档 7.00 / 6.31 ms**，而 16%、91%、286% 三档全是 3.0–3.3 ms。
  不是"越深越贵"（那条轴早就量过，是视口面积），是**中间某个倍率单独贵一倍**。
- **先排掉两个便宜的解释**：①档位来回震荡——整轮 `[decode-trace]` 只有 2 条、`rebuild`
  只跑 2 次，档没动过；②那一档多画了东西——每一档都是 3 次 `draw_image`（主图 + 鸟瞰 +
  视口框）。两条都排除之后才把几何打进日志，唯一剩下的变量是**源尺寸与目标框是否恰好相等**：
  贵的一臂 `src=2131² / dst=2130²`，便宜的一臂 `src=5526² / dst=5526²`。
- **根因**：`.3rd` 里那条"物理尺寸与源图相差 1 像素以内吸附 1:1"的判据写成了严格
  `< 1.0`，而它自己的注释承诺"±1 误差也在此吸收"——差**恰好** 1 px 落在门外。命中吸附 →
  `Transform::identity()` + 整数平移，tiny-skia 走逐行 blit；差 1 px → `scale=0.99953`
  的双线性，逐像素 4 抽头。**宿主每帧都在造这个差**：档位按 `ceil` 请求、上屏矩形按
  `round` 取整。已修（补丁 13），两臂同改。
- **定式**：
  - **台阶来自路径切换，不来自数据量**。数据量是连续的，成本跟着它走只会渐变；看到
    一倍/几倍的台阶，去找那个二值开关（一个比较符、一条 `if`、一次缓存命中与否），
    不要去编"这一档的数据就是更大"的故事。
  - **测不出差错的判据等于没有判据**。上游那条同名测试用一张**纯红**源图，1.125 倍
    双线性把纯红摊出来还是纯红，断言永远不可能失败——判据写错时它一声不响。补的测试
    一律用**有接缝**的源图（左红右蓝，插值必出中间色），并且带一条"不该吸附的那臂必须
    >0"的反面对照；再加一次"把改动改回去、看它是否真的红"的落地校验（本次：两臂各 9 个
    混合像素，FAILED）。
  - 跨会话的数字只作旁证，判定用**同一轮内的分臂**（[[K50]]）：本补丁的签收数是修完之后
    那一轮里 35% 档 3.31 ms 与 16/91/286% 的 3.12–3.36 ms 落在同一条线上。
- **同类**：[[K54]]（测量台要自带对照臂）、[[K52]]（引用别人——包括自己上一轮——写的成本故事不算依据）、[[K50]]（配对口径）。

### K62 —— "只有画出来才被悬停到，只有被悬停到才画"是个死锁

- **现象**（2026-10-18 读代码抓到，用户没报过）：极简模式的设置说明写"隐藏标题栏/工具栏/
  信息条，**悬停显示**"，实际是信息条**永远悬不出来**。
- **根因**：显示条件是 `show_info = hover_info`，而 `hover_info` 由 `activity()` 拿
  `info_rect` 判——`info_rect` 是 `draw` 每帧"我真的画了"才回写的那块矩形，没画时恒为
  零矩形（这个设计本身是对的：命中区必须等于所见区）。于是：没显示 → 没有矩形 → 悬不到 →
  不显示。开关的输入是它自己输出的函数，**不动手就永远解不开**。
- **解法 / 定式**：让它的显隐跟着**另一个已经有独立判据的**浮层走（这里选标题栏：状态现在
  就画在标题栏右端，`hover_title` 由指针坐标直接算，不依赖任何"画没画"）。定式：
  **凡"悬停才显示"的浮层，其显示条件里不许出现"它自己上一帧被画过"**；要联动就联动到
  位置类判据（指针几何）上，别联动到产物上。
- **顺带同一处的另两条**：① 标题栏是**直绘**的，框架的省略号截断住在 `Label` 控件里
  （windui 那份 `ui/text_fit` 是 `pub(crate)`，宿主够不着），所以长文件名会**折行画到图片上**
  ——直绘方必须自己管宽度（`clip_text`）；② 量宽用 12 号、画用 13 号，胶囊比字窄一圈、
  居中的字两头溢出。
  **量与画必须同一份 `TextStyle`**，否则"按文本自适应宽度"这件事本身就是假的。
- **同类**：[[K60]]（两个语义不同的 bool 透传）、[[K54]]（判据要能真的失败）。

### K63 —— 跑完 clippy/test 不等于产物变新：`deploy.py` 只搬不建

- **现象**（2026-10-18，差点据此记下一张假签收）：改完信息条落位 → `cargo clippy --release
  --all-targets` 0 警告 → `cargo test --release --lib` 228 绿 → `deploy.py` 报 `deploy OK`
  → 真机截图里信息条**还在老位置**。第二张"改后"截图其实出自**上一版** exe。
- **根因**：`build/deploy.py` 只做"把 `.temp/target/release/rupix.exe` 原子换名搬到
  `.build/`"+ 解码器核对，**它不编译**。而 `cargo clippy` 只检查不产出二进制，
  `cargo test --lib` 只建 lib 与测试目标、**不建 `rupix` 这个 bin**。于是部署链上出现了一个
  "全绿但搬走的是陈旧产物"的空档。
- **解法 / 定式**：收摊动作里 `cargo build --release` 是**独立的一步**，不能被 clippy 或
  test 顶替。判据用时间戳，不用感觉：`ls -l --time-style=+%H:%M:%S .build/rupix.exe
  .temp/target/release/rupix.exe` 两处都必须是刚刚那一次。真机取证前先看这两行，
  再看截图——**一张来自旧二进制的"改后"截图比没有截图更糟**。
- **同批撞到的另一条**：`.build/rupix.exe.old` 报 `PermissionError（拒绝访问）`＝部署时
  程序还开着（旧文件改名要等句柄释放）。脚本化流程里"关窗"必须排在 deploy **之前**，
  而且失败的那一步要重跑一次才算数（这次就是第一次 deploy 失败、第二次才 OK，
  而中间那次截图是旧的）。
- **同批撞到的第三条（当场清掉）**：从**仓库根**跑 `cargo test --manifest-path main/Cargo.toml`
  会在 `main/` 里长出 493 MB 的 `target/`——`.cargo/config.toml` 的 `target-dir =
  "../.temp/target"` 是**按当前目录**解析的，不在 `main/` 下就等于没写。cargo 一律
  `cd main` 之后再调；收摊扫一遍 `find main extension -name target`。
- **同类**：[[K50]]（配对口径与"测的是不是生产产物"）、[[K53]]（构建配置改变实测结论）。

### K64 —— 用 PowerShell 改带中文注释的配置文件，默认码页会把键粘进上一行注释

- **现象**（2026-10-18，D 项取证时）：探针脚本要按不同窗口尺寸开窗，用
  `Get-Content -Raw` + `-replace` + `Set-Content -Encoding UTF8` 改 `.build/rupix.ini` 的
  `window_w`。跑完窗口还是 800 宽——键"没生效"。
- **根因**：Windows PowerShell 5.1 的 `Get-Content` **按 ANSI 码页**解码，而这份 ini 的注释是

  `# 固定尺寸档…）\nwindow_w=800` 粘成一行 → 整条键被当成注释 → 应用按"看不懂的值回退默认"
  静默走默认宽（这条回退是文件头写明的契约，不是缺陷；缺陷在我这边）。
- **解法 / 定式**：**读写都显式指定编码**——`[System.IO.File]::ReadAllText($p,[Text.Encoding]::UTF8)`
  + `WriteAllText($p,$t,(New-Object Text.UTF8Encoding($false)))`（`$false` = 不带 BOM）。
  改完**要回读核对**：本例的判据是数一数字符串里还有几行 `^window_w=` 这类键（`keys=5` 才对，
  粘行时只有 4）。同类症状"设置没生效"先看文件本身，再看解析器。

### K65 —— "信息条自己在动"有两个来源：纵向换档（必须消）和横向跟着文本滑（可以留）

- **背景**（2026-10-18）：用户先报"屏幕不够大时这些信息会上升一行，不好"，我把它修成
  "状态只有一个家：标题栏右端"。当天用户复核时的原话是"状态要不要搬到标题栏，我不确定"——
  最后拍板"并进浮条"。**换位置这件事本身不是病灶**，重做一遍才把两条判据分清楚：
  ① 同一个信息只有一处；② 它**占的格子不能把按钮挤出档位**。**只做 ① 不做 ②，抖还在**——
  暂停动图会多出"· 帧 47/100"，实测文本从 82 px 涨到 153 px，浮条居中布局下
  **整排按钮横移 71 px**，那还是"在动"，只是从"上下跳"变成"左右跳"。
- **② 的第一版开错了药**：我把格子做成**定宽**（照最坏输入算死），当天用户复核的原话是
  "没有自适应宽度啊？感觉像是固定宽度了，信息右侧有一大片空白"。**病灶是"换档"，不是"变宽"**——
  定宽把两件不同代价的东西一起禁了：纵向跳档（真不可接受，压住画面）和横向滑动（居中浮条的
  固有性质，代价小得多）。正解是**格宽贴着文本走，档位却按"满格"判**：文本变化只让按钮排
  左右滑，永远不让信息换行。**判据要挑到"最小够用"那一条**，宽一档就把可接受的代价一起禁掉。
- **上限照哪条量**：照**永不许截断的那一条**，不照日常那条。帧号是屏幕上唯一载体
  （AGENTS §八.7），所以文本框必须装得下最坏输入：`1234/1234 · 100% · 帧 1234/1234` 实测
  207 px、`1234/1234 · 4000×3000 · 载入中…` 实测 **209 px（后者才是上界）** → 文本框上限 212、
  满格 241（`INFO_CELL_MAX` 由 `info_cell_w(INFO_TEXT_MAX)` **推导**：左内边距 8 + 文本框 + 6 +
  分隔线 1 + 6，不写死）。
  ★ 第一版就是写死的 224 = 14+207+3，结果**文本框只剩 198 px，比最坏串还窄 9 px**——
  而 `draw_text` 的 rect 宽**同时就是折行宽**（两后端都把 `rect.w` 交给排版器），
  症状不是截断而是**浮条里长出第二行**，把 40 px 高的胶囊撑坏。这条现在由单测拿真实
  DWrite 排版守着（`the_status_cell_actually_fits_the_worst_string`），改文案格式 / 改字号
  当场跑红——**宽度这种数不能只活在注释里**。探针留在 `examples/text_measure.rs`。
  再往上的病态输入（一个目录 12345 张 → 232 px、一张图 12345 帧 → 237 px）**故意不兜**，
  那种串走 `clip_text` 收成省略号：宁可少看一位数，也不给所有人多付 25 px 浮条宽。
- **自适应买回来一条新优先级**：满格 241 + 9 颗 346 = 587 px 才放得下，动画三颗再加 111 px
  → 698。窗口不够宽时**让谁**？定案：**状态 > 动画按钮 > 留白**——按钮还有 `,` `.` `P`
  与右键菜单两条退路，状态没有第二处；再窄（<587）才退回浮条上方那一整行。
  降级顺序必须**单调**（宽→窄：12+格 → 9+格 → 9+整行），否则拖窗口时信息会来回跳。
  ★ 档位**只按满格判、不按本帧实际格宽判**，否则"文本变长"本身就能触发换档——那正是这一条
  要修的病。鸟瞰图避让同理读 `cell_reserve`（满格），不读本帧格宽：它跟着滑没关系，
  跟着跳就有鬼影。
- **把错误从状态通道摘掉，要回头查剩下的那处会不会说谎**：错误原来在状态栏与画面中央各写
  一遍，删掉状态栏那份之后，`loaded` 永远不来的失败态会卡在"8/197 · 载入中…"——
  **一句本来无害的话，在唯一载体身上就是假话**。改成失败时只留位置号。

  DirectWrite 软硬两后端都按 `rect.w` 自动折行、纵向仍居中，所以"让宽"就是全部改动，
  **不要自己写折行**（先读 windui 软/硬两后端的排版入参——`DWriteEngine::draw` 与 D2D 的
  `draw_text` 都把 `rect.w` 当换行宽、纵向另按 metrics 定位——再决定要不要动手）。

  别拿一张图去读代码；③`.build/` 与 `.temp/` 一样是共享的（本轮 `ls .build/rupix.exe` 有一瞬

  所以"exe 是我的"这句话每次都要**当场**用 md5 + 时间戳重证，不能引用十分钟前的结论。
- **★ m100 补（同一课的第二枚 API：`CopyFromScreen` 也护不住）**：那条教训当时是 `PrintWindow`
  被别家 overlay 污染；m100 换成正经的"取我自己的 `GetWindowRect` → 抓那块屏幕区域"，

### K66 —— 预读"早就在写"，但 12 次翻页里 10 次被自家判据扔掉：单测夹具走的正是那条漏网分支

- **现象**（2026-10-19，用户报"切图还有卡顿感，是不是没做预加载"）：预读从 m34 起就是
  ±2 张、方向感知、视口档、256 MiB 预算，代码在、日志在、缓存也在填。可是拿 6 张大图
  （19–37 MP 未压缩 TIFF）真机连翻 12 次，三种间隔（0.36 s / 1.0 s / 2.5 s）读数**完全一样**：
  `预读命中 2`、`预读位图过小（视口已变），丢弃重解` 10 次。也就是每翻一张都在
  "后台已经解好了 → 门口被扔 → 现解一遍 130–260 ms" 的路径上走一遍，用户感觉就是没有预读。
- **根因①（判据与 fit 的几何不相容）**：`use_prefetched` 的"够用"判据拿缓存位图的
  **两条边**分别比视口框的 90%。但 fit 从不裁切，一张图装进框里**永远只有一条边贴住框**，
  于是这条判据等价于要求"图片长宽比 == 窗口长宽比"。混尺寸目录里只有恰好同比例的那张
  能活下来——实测那 2 次命中正是 5600×4200 撞进 800×600 的窗口。窗口 16:9、图 4:3 之类
  的常见组合全部被扔。**判据连"比框还大"的那份也扔**（441 < 561×0.9），所以它不是"保守"，
  是**反着筛**。
- **根因②（首解框继承了上一张）**：`desired_pixels()` 的 `natural × 倍率` 用的是 `self.loaded`，
  而换图窗口期 `loaded` 为防闪**故意还停在上一张**。于是新图的首解框是**上一张的显示尺寸**：
  748×561 的窗口里紧跟在 4000×6000 后面的 6400×3600 只解到 374×210（本该 748×421），
  首屏白糊一倍；更糟的是它把根因①的比较基准一起带偏，形成"预读按视口框解 → 判据按
  视口框比 → 驳回 → 重解按上一张的框"，越补越糊。
- **为什么 243 条单测一条都没红**：`step_uses_prefetched_neighbor_without_new_decode` 的夹具
  是 `natural (4,4)` + 位图 `4×4`——命中走的是 `at_native` **那条逃生门**，`enough` 那条分支
  **从来没被执行过**。夹具只要"尺寸相等"就绕开了整个档位问题。**定式：测"缓存里那份比原图小"
  这件事，夹具必须自己就是"比原图小"**（新增 `prefetched_tier()` 专门造这种形状），
  并且要配一条**反向**用例（窗口拉大一倍后仍然必须驳回），否则判据一改就没人守。
- **解法**：①"够用"改成与**这张图此刻按视口框解出来会有多大**比
  （`fit_dims(natural, viewport_pixels())`），与 `tick` 里那条 `whole_image` 判据同一口径；
  ②`desired_pixels()` 只在 `loaded.path == 清单当前项` 时才参与计算，否则退回视口框
  （清单为空时维持老算法——合成上下文与 `decode_target_is_clamped_before_it_is_cast` 靠它）。
  两处都在基座，**零 ABI、零解码器改动**，所有格式一起受益。
- **改后实测**（同一样本目录、同样三臂）：命中 **12/12**、驳回 **0**，0.36 s/次 的连翻也全命中；
  原图档升级照旧落地（6 条 `[原图档升级]` 回包），1:1 清晰度没有回退；单文件首开
  `tiff_100M.tif` 仍是 290 ms / 561×561，没有多出一次解码。
- **顺带结掉的一个猜想**：用户提的"预读 0–3 张可设"里，**深度不是瓶颈**——三种间隔都是
  12/12 命中，把窗口开深没有可测收益；真正卡住 0.14 s/次 那种狂翻的是**串行的一枚解码线程**
  （每张 TIFF 视口档 130–210 ms，队列排不过来）。所以"0=关"是个有真实用途的开关，
  "1–3"是给一个已经不存在的瓶颈加旋钮。
- **同类**：[[K54]]（断言要能真的失败）、[[K45]]（预读的尺寸账要按**视口档**算，不是原图档）、
  [[K65]]（共享桌面上先固定环境再读代码）。

### K67 —— 会话戳把"另一枚还活着的实例"读成"上次异常退出"：用户每次开机都被弹一次

- **现象**（2026-10-19 用户报障）：每次单开 `rupix.exe` 都弹「检测到上次运行未正常结束 …
  上次会话：pid=25844 启动于 …」，而那句里的 pid **此刻还在任务管理器里活着**。
  用户的第一反应是"提示是很久以前的旧数据，怎么不失效"——这条直觉完全正确，只是
  原因不在"旧数据没清"，在**判据本身错**。
- **根因**：`open_session()` 的判据是 `rupix.run` **文件在不在**。可"戳存在"有两种含义：
  ①上次进程没走到 `close_session`（真异常）；②另一枚 RuPix 正在运行、戳是它刚刚写的。
  旧代码把两者当一件事。而②在本机不是假设：取证时 `tasklist` 里有**三枚** `rupix.exe`、
  `GetWindowTextLength` 全为 0（窗口已销毁、进程滞留），`EnumWindows` 也找不到可打的窗口。
   windui 的命名互斥体随窗口销毁释放 ⇒ 新进程被 `claim_instance` 判成"首实例"、
  正常走完 `run()` ⇒ 读到那枚活进程的戳 ⇒ 弹提示。**一张小文件承载了两种语义**，
  与 [[K60]]（两个语义不同的 bool 在同一处透传）同族。
- **解法**：判定前先**认人**——解析戳里的 pid，`OpenProcess(PROCESS_QUERY_LIMITED_INFORMATION)`
  + `GetExitCodeProcess == STILL_ACTIVE` 判活，再 `QueryFullProcessImageNameW` 核镜像路径
  **等于本 exe**。两条都要过才算"并发实例"：只看 pid 活不活会被 **pid 复用**骗到
  （陈旧戳的号可能已经属于别的程序 ⇒ 该弹的不弹）。判成并发就三件事都不做：
  不弹提示、不覆写它那枚戳、退出时不删它。反向用例进单测（`live_sibling_requires_same_exe_image`：
  自己的 pid → 真；`pid=4` 活着但不是本 exe → 假；越界号不存在 → 假）。
  代价写在注释里：这一改可能"少弹一次"，而崩溃取证另有 `crash.log` / `.dmp` 两条
  独立证据链，不靠这枚戳，所以宁可少弹。
- **顺带查清的一条**：次级实例**不会**覆写/删除戳——`open_session` 在 `rupix_lib::run` 里，
  而 `main.rs` 的 `claim_instance` 闸门在那之前就 return 了。我最初写的"交接口把别人的
  戳删掉"是**臆测**，读了调用链才否掉。定式：写根因之前先把**执行顺序**读出来，
  别按"常识里的单实例实现"推断。
- **"很久以前"那半句是第二个 bug**：判据修好还不够，用户那句直觉另有出处——戳里那句时间
  由 `panic_guard::civil_from_secs` 按 **UTC** 输出。取证对照：本地 `03:07:40` 启动的
  pid 25844，戳里写 `2026-10-18 19:07:43`（差 8 小时、还跨到前一天），于是**八分钟前**
  那枚活实例看着像隔天留下的旧数据。定式：凡是给人读的时间，口径要跟用户手里的对照物
  （任务管理器 / 资源管理器）一致；"日志只要能排序"这种内部理由不该顺带决定 UI 文案。
  换算改成实测 `GetLocalTime − GetSystemTime` 的偏移（自带夏令时，不必读时区表），
  两条不变量进单测：偏移是整分钟且不超 ±14 h；负偏移跨到前一天时不许格式化出负时分。

### K68 —— 我只算了时间账就推荐"保留并修好磁盘缓存"：漏了形态账与定位账

- **现象**（2026-10-19，用户问"缓存是不是该删"）：我第一轮回答"数据不支持删，建议把
  写盘挪出关键路径"。用户回问的其实是另一件事——"我们不是已经判定没人像我们这么做吗"。
  去翻 旧项目调研 才发现：**做磁盘缓存的四家存的全是压缩受限档**
  （mimageviewer = SQLite+WebP 缩略图；luminous = `{res}_{sha256}.webp` 且小图不写；
  LightningView = QOI、限 1920 宽、24 h TTL；sriv = 缩略图磁盘缓存），
  另有几家明写"无缓存"（showme / imgvwr / lightview / stiv 只在内存留 1 张）。
  我们存的是**未压缩整图 RGBA**，一张顶格 140–160 MB，量级差 10–30 倍。
- **根因（我的方法问题）**：我只做了一张**同机配对时间表**（写 +214 ms / 命中省 99–343 ms），
  就得出"收益是真的 ⇒ 留着"。时间表答不了"该不该存在"，因为它缺三样：
  ①**覆盖面**——键含窗口框，默认 800×600 窗口的视口档只有 1.26 MiB，够不到 2 MiB 落盘门槛，
  最常走的那条路根本吃不到缓存；能落盘的只有"放大/按 `1` 过的原图档"。
  ②**上界性质**——我测的"热读 62 ms"是那份 `.bin` 刚被本进程写过、还在**系统文件缓存**里，
  真冷盘（尤其这包被拷到 U 盘跑）会把收益吃掉甚至倒贴。
  ③**定位账**——便携应用把最多 2 GiB 未压缩位图堆在 exe 同级目录，跟着同步盘/U 盘到处走，
  与"轻量、内存与菠萝持平"是直接冲突的；这条不在时间表里。
- **解法 / 定式**：性能问题答"值不值"要交**三份账**：时间表（同相配对）、覆盖面
  （这条路径今天真走得到吗）、定位/形态（参照里同一件事长什么样、和本项目的公理冲不冲突）。
  缺任何一份就别急着说"建议保留"。撤除的判据最终也不是"没收益"，而是
  **"收益的形态不对"**：留着 = 长期背着一个参照实践里没人用的磁盘形态。
- **附带收获**：为了量这笔账临时建过一个三臂基准（OFF / 冷=解+写 / 热=读回，逐轮台账），
  是**先建后删**的正例——数字留在 本仓历史记录 与 `HISTORY.md`，
  功能撤了探针也跟着撤，不给仓库留一具依赖已死模块的尸体。
- **同类**：[[K48]]（配对忘了同相，结论方向反）、[[K45]]（算错账加出来的限制）、
  [[K50]]（消掉一处后读数没动 = 归因错了）、[[K65]]（取证前先固定环境再读代码）。

### K69 —— 核查清单里"列而不行"的第二例：clippy 有 warning 也退 0，`-D warnings` 才是门禁

- **现象**（2026-10-19，按桌面版总纲 §16 机检本仓）：`AGENTS.md` §九第 4 行写着
  `cargo clippy --all-targets` → 判据"exit 0，第一方源码零 warning"。翻 `main/build/*.bat`
  六步流程，**没有任何一步跑 clippy**。而 clippy 的退出码在只有 warning 时是 **0**——
  所以就算有人手工跑它，"exit 0"也证明不了"零 warning"，这行判据本身是假的。
- **同类的先例**：`cargo fmt --check` 在 2026-10-17 撞过同一个坑（当时两个文件已经漂了

  这条规矩**。
- **根因**：核查清单是给人读的，读的人会把自己"记得跑过"当成"跑过"。只有能失败的东西

- **解法 / 定式**：
  1. 静态类判据一律进 `2_scan.bat`（现在是 [1/5]…[5/5] 五步），新增判据时**同步改

  2. clippy 写成 `cargo clippy --all-targets --release -- -D warnings`——把 warning 升级成
     error，退出码才等于判据；
  3. 新门禁装完必须**当场证明它能失败**（总纲 §2.1 那句"没验证过的门禁多半是假绿"）。
     这次的证明不需要人造 fixture：新写的 `env_report` 自己撞出一条
     `manual_c_str_literals`，带 `-D warnings` 直接 `error: could not compile`，
     不带就只是一条 warning。
- **附带收获**：`-D warnings` 装上的第一小时就抓到自己人，说明它有用；同类地，
  `deploy.py` 新加的 RT_VERSION 门禁也用三臂验过（无资源 fixture → 拒 / 版本喂错值 → 拒 /
  正常 → 过），见 [[K70]]。
- **同类**：[[K63]]（跑过 clippy/test ≠ 产物变新）、[[K13]]（脚本静默跳过 = 假绿）。

### K70 —— 加 VERSIONINFO 的第一个坑：`rc.exe` 没有 SDK 的 include 路径

- **现象**（2026-10-19）：照常见写法在 `assets/version.rc` 里 `#include <winresrc.h>`，
  `rc.exe` 直接编不过——`embed_resource` 调 `rc.exe` 时只把 `$OUT_DIR` 当 `/I` 传（它的
  MSVC 分支实测就是 `/fo 输出 /I out_dir` 再叠调用方给的 include），**不会**注入
  Windows SDK 的 `um`/`shared` 目录；而在普通 shell（不是 VS 开发者提示符）里
  `INCLUDE` 环境变量本来就是空的。结果：`manifest_optional()` 把它降级成一条 cargo 警告，
  版本资源静默缺席——现象与"忘了跑 rc"完全一样。
- **正解**：模板里不 include 任何东西，把用到的三个符号按 SDK `um/verrsrc.h` 的字面值写死
  并在文件头注明出处（`VS_VERSION_INFO=1`、`VOS_NT_WINDOWS32=0x00040004L`、`VFT_APP=0x1L`、
  `VFF_MASK=0x3fL`）。头文件在 `Windows Kits\10\Include\10.0.26100.0\um\verrsrc.h`，
  要改就去读它，别猜。
- **另外两个小坑**：
  1. **中文显示串**要 `#pragma code_page(65001)`，同时 `Translation` 用 `(0x804, 0x4b0)`，
     否则资源管理器"语言"列显示成英语；早期版本我图省事把 Cargo 的中文 description
     做了 ASCII 过滤，结果 FileDescription 变成 `RuPix  Windows  decoders  DLL SVG` 这种
     掉字句子——**过滤不是编码方案，是掩盖**。
  2. 读回校验时**别按 2 字节步长扫 UTF-16 字符串**：VERSIONINFO 的键对齐到 4 字节，
     相对块起始可能是**奇偏移**，按步长扫会把 `,CompanyName` 这种带半截前缀的串当成键名，
     于是"键齐全"的检查假红。正确做法是整串比对（`"FileVersion".encode("utf-16-le")+NUL`
     在不在字节里）。
- **定式**：给 exe 加/查嵌入资源时，**门禁要解析 PE 的 `.rsrc` 本身**（`deploy.py` 已有
  叶子遍历，加一个 type==16 的判据即可），别用"构建没报 warning"当判据——`manifest_optional`
  存在的意义就是把失败变成不失败。


### K48 —— `vx` 恒为 0 养出的隐藏假设：贴左后整块界面错位、命中却在原位 **［2026-11-08 已根治］**

- **现象**：缩略图条从底部挪到左侧之后，关闭按钮等标题栏按钮**画在偏左的位置**，但鼠标悬停
  屏幕右上角仍然是关闭按钮、也真能关窗；底部浮条同样整体左移。用户的原话是
  「显示效果和实际效果不同」——这是坐标系错位的标准描述。
- **根因**：`chrome::paint` 与 `filmstrip::paint` 各有一个
  `let local = |x, y, w, h| (x - vx, y - vy, w, h)`，而画布（`core::paint_node` 以 `abs`
  递归、**不做 translate**）要的正是**绝对**坐标。于是两份都错、但错法不同：
  chrome 的几何是**相对**视口（`title_btn_rect` / `btn_rect` / `pill` 都从 0 起算）⇒ 该
  `+ vx`，写成 `- vx` 就整块左移 2×vx；filmstrip 的几何本来**就是绝对**（`layout` / `panel`
  内部已加过 `vx`）⇒ 一个像素都不该挪，减一次就左移 1×vx。
  命中测试那边是 `pos - view.0`（绝对 → 相对），与**相对几何**自洽 ⇒ 一直是「对的」。
  两处减法都因为底条时 `vx/vy == 0` 而侥幸无害，**藏了整整一个功能周期**。
- **解法**：chrome 侧统一走 `to_canvas(view, rel)`（`+ vx`，与 `hit` 的减法互逆）；
  filmstrip 侧 `local` 退化成恒等；顺带修 `above.ix` 与悬停提示夹紧里「相对 + 绝对」混用。
- **三条防线（都做了「改回旧写法必红」的负向验证）**：
  1. `what_is_painted_is_what_gets_hit_when_the_origin_is_not_zero`——**故意用 `vx = 112`**；
  2. `painted_cells_land_on_the_absolute_rects`——缩略图格必须落在 `layout` 的绝对矩形上；
  3. `paint_moves_geometry_through_to_canvas_only`——源码级 `include_str!` 断言，
     因为「`to_canvas` 的单测绿了」**不等于**「`paint` 真在用它」（第一版就是被这点骗过）。
- **两条通用教训**：
  - 某个坐标/参数长期恒为 0 时，代码里会**长出一批「0 也无所谓」的假设**。凡是引入会让它
    非 0 的改动（这里是把缩略图条挪到左边 ⇒ `view.x` 变成 112），先全仓搜 `- vx` /
    `- view.0` / `- origin`，逐个问「这个 0 是语义还是巧合」。
  - 纯函数的单测通过，**不代表调用点接对了**。接线用的东西（转换、分派、开关）要么收成
    唯一入口（编译期强制），要么单独钉一条源码/结构断言。
- **附带的坑**：往 `#[allow(...)]` 与 `fn` 之间插入新函数，会把属性「吃」到新函数头上，
  原函数立刻 clippy 红（`too_many_arguments (11/7)`）。插代码前先看锚点上方有没有属性行。

### K49 「秒退」不一定是崩溃：默认关窗的双击把标题栏也吃了

- 现象：用户报「刚刚遭遇了一次秒退，不知道什么原因」。日志里**没有 panic、没有异常退出**，
  只有 `[close] id=1 ... close_to_tray=true action=Close`，启动到关闭 3 秒。
- 根因：`double_click` 默认 `1 = 关窗`（对齐菠萝），而双击分支当年**没区分区域**。
  用户想「双击标题栏最大化」→ 窗口直接收了。
- ★ 判据：**遇到「秒退」先看日志尾部有没有 `[close]`**。有 `[close]` 就是正常关窗路径
  （有人在替你点关闭）；一条日志都没有才轮到查崩溃/被系统杀。
  `.build/temp/rupix-<date>.log` 每段会话都以「=== RuPix 会话开始 ===」起头，按它切分最省事。
- 修法：标题栏恒 `Maximize`（纯函数 `double_click_action`），范围判据复用
  `Chrome::in_title_strip`，别新造一份。
- ★ 又一次「纯函数绿 ≠ 接线对」：`title_bar_double_click_always_toggles_maximize` 只钉判据，
  所以另配 `double_click_wiring_asks_the_title_strip_first`（`include_str!` 源码锚点）。
