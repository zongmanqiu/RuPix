### K98 —— 一条"防连按"的握手永远走不到：删掉判据用例照样绿；而它挡住了一个真会锁死的口子

- **现象**（m74）：「复制当前（PNG）」改走后台线程时，第一版给每枚复制编了号
  （`copy_seq: Arc<AtomicU64>`），线程写剪贴板前问"我还是最新的那一枚吗"，轮询收回执时
  也只认最新代号——防"连按两次，慢的那枚把快的那枚盖回去"。给这条写回归用例时按惯例做变异：
  **把 `if seq != newest { continue; }` 整行删掉，用例照样 PASS**。
- **根因**：那条判据**不可达**。第二枚在 `copy_display` 里先被 `copy_in_flight()` 拒成
  `Busy`，登记根本发生不了 ⇒ 代号永远不推进、通道里永远只有一枚回执；而用例为了造出"旧回执"
  只能连投两次，第二次投递**换掉了通道**，旧 `Sender` 发送直接失败——测试送进去的那枚旧回执
  从来没有进过队列。用例绿的是"通道被换掉"这件事，不是"代号过滤"那件事。
- **判据与修法**：整条编号链当场删除（字段 + 两个方法 + 线程侧判断 + 轮询过滤），
  `Receiver<(u64, Result<…>)>` 收成 `Receiver<Result<…>>`，三处 `Arc`/`AtomicU64`/`Ordering`
  import 一并没了；单飞这件事由 `copy_busy` 一处承担，并在 `copy_in_flight` 的注释里写明
  "这一位就是单飞闸"。重写后的用例改钉**能走到的**行为：成功只从 `Ok` 回执来说、说完闸就放开、
  被换掉的线程送不进来（`send` 返回 `Err` 本身就是断言）。
- ★ **删掉编号反而露出一个真会锁死的口子**：`try_recv` 的错误原先一律读成"还在等"，
  而 `Sender` 被丢弃且没发回执（只有那一枚线程半路 panic 才会这样）正是这条错误。
  于是 `tick_copy` 永远返回 `Waiting`、在飞位永久占住——此后每次复制都被"还在进行"拒掉，
  **屏幕上一句下半句都没有**，用户只能重启。现在按 `TryRecvError::Disconnected` 分开处理：
  如实报一条失败并把闸放开，用例 `a_dead_thread_unarms_the_gate_instead_of_waiting_forever` 钉住。
- **教训**：一条判据如果**删掉之后用例还绿**，那它要么没被钉住，要么根本走不到——两者都要当场查清，
  而"走不到"的处置是**删掉它**，不是留着当保险；不可达的保险还会盖住它旁边那条错误分支。

### K99 —— 排表基准取"落地时刻"就把成本变成了慢放；数日志时认错 `src=` 会读出假缺陷

- **现象**（m75）：一张标 25 fps（每帧延时 40 ms）的 GIF，屏上实测只有 **13.3 fps**（640×480）/
  **9.1 fps**（3 MP @适应窗口）。而 UI 线程是干净的（放动图时 `WM_NULL` 往返最大 8.5 ms、`over20=0`）——
  **不是卡顿，是慢放**。帧间隔 75 / 110 ms 恰好 ≈ 每帧成本 28 / 61 ms **+ 40 ms 延时**。
- **根因**：`install` 里排下一帧写的是 `anim_next_at = 落地时刻 + 延时`。这一句的意图是"别排队堆积"
  （同一时刻只留一个在途请求），这一点它做到了；但它顺手把**上一帧的解码成本转嫁给了下一帧的等待**，
  于是周期成了 `成本 + 延时`。同一段注释里还写着"帧率完全跟随文件自带延时"——**两句互相否证，
  而两句都没被量过**。
- **判据与修法**：把"发请求的闸"和"这一帧该显示的时刻"拆成两个字段。闸（`anim_next_at`）仍由
  `tick_anim` 触发时清空 ⇒ 在途请求永远只有一个，原设计要保的性质一分不丢；时间线
  （`anim_due_at`）跨帧续接：`due = 上一帧的 due + 延时`，落后时 `.max(now)` 夹住（欠的不补等）。
  周期于是变成 `max(延时, 成本)`。三条"看着像下一帧、其实不是"的守卫缺一不可：**档位升级**
  （同一帧重解，帧号没变）、**换图**（旧图欠的账会让新图第一帧立刻开跑）、**暂停恢复**
  （恢复处只排闸不排线的话，下一帧找不到基准，整段播放悄悄退回慢放）。
- ★ **顺带一条读数纪律**：同轮第一次算"按键到落地"得到 460 ms，差点写成"翻一张图等半秒"。
  读日志才发现那行是 `[main-latency] src=decode bitmap=1920x1080`——**m58 故意推迟的原图档升级**；
  首帧走的是 `src=prefetch` 命中，按键即换。"`数标签行数 = 上屏次数`"这类判据，
  **不分辨 `src=` 与 `bitmap=` 就会把后台补档读成用户等待**。
- **教训**：凡"到点做下一件事"的排表，先问一句基准是**上一件事发生**还是**上一件事该发生**——
  前者把耗时加进周期，后者才守时；而"守时"与"不堆积"从来不冲突，是两个字段各管一件事。
  另一面：注释里写的性能承诺（"帧率完全跟随文件延时"）必须有读数，否则它会带着"已经做到"的
  假象活很多轮。
### K100 —— 把"参考项目的门禁"读成了"本仓的缺项"：立项前必须先 grep 本仓确证它存在

- **现象**（m76）：立案时给 m76 写了三件事——① 清 20 个 `[待核]`；② `deploy.py` 把许可原文拷进 `.build/`，
  缺失即红；③ 清掉 `AGENTS.md` 里四把不存在的工具（`gen_licenses.py` / `sync_assets.py` / `boot_check.py` /
  `check_deps.ps1`）和"§九 第 6 条断言 `build\licenses\` 非空"。开工前 grep 了一遍本仓：
  **③ 那四把工具名与那条判据在 `main/AGENTS.md` 里根本不存在**（§四 列的七把工具全是真的，§九 十一行里没有
  `licenses` 一字）；它们只出现在 参考项目自己的文档，以及本仓历史记录 那张
  **"对照 curseen / pecia"的比较表**里。② 则撞上 2026-10-19 用户明确的封存裁定（`待办 §14`「不要管 `.build/` 的事情」，
  那一段末尾本来就写着"别下一轮当新发现再翻出来"）。**三条里两条前提是假的**，只有 ① 成立。
- **根因**：读对照表时**没分清"对方有什么"与"我们缺什么"**。m19 那张表的列名是"参考项目的做法 ⇒ 我们的缺口"，
  抄着抄着，左列的具体文件名被当成了右列的缺陷证据；再加上"许可合规"这个词一进来，`.build/` 那一档封存
  根本没被想起来——**立项的动作少了"确证存在"这一步**，而不是想法本身离谱。
- **判据与修法**：从对照表 / 旧审计里取候选，动手前做两次廉价查证，各几分钟：
  ① **grep 本仓**确证那条东西**在本仓以那个名字/那条判据存在**（不存在就不是"清理"，是"新增"，得重新算成本收益）；
  ② 查 `待办` 的**封存节**（§10、§14 这类"已明确判过不管"的段落）——落点在封存区里的候选直接出局，不必再论证。
  本轮两条都是靠这两步当场否掉的；如果没做，代价是"改了个不存在的东西"整轮，还会把已封存的裁定再翻一次。
- **顺带记一条只有对账才能发现的错**：同一张许可表里，stb 那一格写"源码在**解码器仓库** `.3rd/stb-2.30/`"，
  而磁盘上 `解码器仓库.3rd` 不存在、`decoders/stb/build.rs` 取的是**项目根** `.3rd/`，
  且**同一个文件**第一节早就写着 windui 在"仓库根 `.3rd/`"。j 系门禁对的是代码、结构文档与数字，
  **不管散文与磁盘是否一致**——文档内部两处口径打架只有逐条对磁盘才照得出来。
- **教训**：**出处决定性质**。同一句话，写在"参考项目怎么做"的表里是资料，写进本仓的待办就成了缺陷；
  引用它之前必须先把它**落到本仓的文件名与行号**上，落不到就不是待办。
### K101 —— 缓存按"一次交接"设计，请求却按"同一张图来好几次"发生；离线探针重复解同一文件会测到缓存

- **现象**（m77）：给现代格式补首开读数，`bench_decode`（1 次预热 + 5 轮计时）报 AVIF
  **984 / 1240 / 638 MPix/s**——比 JPEG 的 127 还快一个数量级。这不是解码速度：**预热那一趟已经把结果
  放进解码器的线程本地缓存，5 轮全在测命中**。同一把尺量 HEIF 却是 54 MPix/s，因为 `decode_cached` 开头写着
  `if kind == Kind::Heif { 每次真解 }`。把这枚"不对称"拿到端点上才看见它值多少钱：12 MP HEIC 适应窗口
  请求 273.9 ms 之后按 `1`，原图档请求又付 **262.8 ms**（8.3 MP JXL 是 **892.8 ms**），而有缓存的
  AVIF 同一步只要 **30.9 ms**。
- **根因**：① **缓存的寿命按"哪两次调用相邻"设计**（查询→渲染交接完就 `take()` 走人 / 只服务一次），
  没按**请求序列**设计——宿主对同一张图会按档位发多次请求（适应窗口、原图档、缩放换档），
  每一次都要的是同一份全尺寸像素（解码器不理 `target_w/target_h`）；② 探针侧的错是把"重复解同一个文件"
  当成免费计时器，**没先问被测对象有没有缓存**。
- **判据与修法**：① 吞吐判读只认**第一次**；重复调用同一文件的离线读数一律标"可能是命中"，
  端点 `[main-latency] cost=` 才是判据。**同一轮追记里这枚陷阱咬了第二次**：`bench_decode` 给三张真机
  RAW 报 **447–483 MPix/s**（比 JPEG 的 127 还快 3.5 倍），看着像"RAW 比 JPEG 还快"，实际全是
  raw 解码器 `develop_cached` 命中，冷解真值是 728 / 846 / **2525 ms**——**一个小时内用同一把错尺量了两次，
  是因为第一次的教训只写在结论里、没写进"下一次量之前先问有没有缓存"这个动作里**；② 缓存改成"内容键 + 跨请求保留"（av 删短路、jxl 新增
  `cached_entry` 借用不消费），用例**不靠计时**：先把键手填进缓存、再喂一段必然解不动的字节，
  命中就 Ok、退回旧写法就 Err（`heif_render_hits_the_shared_cache`）；③ 缓存一旦跨请求留着，
  **键必须盖住整份内容**——jxl 原来只扫前 4 KiB + 长度（一次性交接时够用，留着之后就成了
  同长度同前缀两张图串图的窗口），升到整遍 FNV-1a 并补前缀外的用例。
- ★ **顺带一条工具事实**：`build/stall_probe.ps1:94,96` 会**强制** `RUPIX_DECODERS_DIR=.build\decoders`
  并 `Remove-Item Env:RUPIX_DECODE_TRACE`。我原本打算数 `[decode-req]` 来统计"一次打开发了几趟请求"，
  env 被抹掉后一条不出——改用默认就写的 `[main-latency]` 才拿到数。**引用探针前先读探针脚本对环境做了什么**，
  别把"没输出"读成"没发生"。（想换解码器目录做 A/B 臂：只能改 `.build/decoders` 本身，探针不认外部目录。）
- **教训**：写缓存时先问"同一个输入会被请求几次"，而不是"哪两次调用是成对的"；
  测速时先问"被测这一层有没有缓存"，而不是"数字看着合理吗"。

### K102 —— 同一枚"提 `opt-level`"的候选在两个解码器上结论相反：尺子是热循环在不在我们自己这层

- **现象**（m77 → m78）：m77 把"给 `rupix-jxl` 提 `opt-level = 3`"判废（首解 400.1/443.5 → 406.3/409.4 ms，
  无可复现收益）；m78 对 `rupix-raw` 提**同一枚**例外，RAW 首开端点直接 **698.7 / 874.4 / 2493.6 → 529.7 / 640.7 / 1781.1 ms**
  （−24% / −27% / −29%），而输出**逐字节没变**。一条候选、两处相反的结论，不是运气。
- **根因**：workspace 的发布 profile 是 `opt-level = "z"`（为体积准备），"按速度"的例外**逐条按依赖库**补
  （`jxl-oxide` / `image` / `rawler` / `rupix-stb`…），**从没问过"解码器本体里有没有逐像素热循环"**。
  jxl 的本体是 20 行封装，热路在依赖库里（那层已经是 3）；raw 的本体里躺着几百行显影链，
  m78 按段量出来它占首开 **81–94%**（26.7 MP 那张：`develop` 2345 ms vs rawler 解 CFA 155 ms vs 宿主 `post` 19 ms）。
- **判据与修法**：
  ① 立项任何"提速候选"之前先**按段归因**，把成本钉到一层：本仓代码 / 第三方库 / 宿主 / 内存带宽下限。
     热循环在**本仓** ⇒ 提档位有可能值钱；在**依赖库** ⇒ 去看依赖库那一档提了没有；贴着**带宽** ⇒ 提档位无效。
  ② 等价改写也要**逐字节自证**再谈速度：本轮把 `inv3` 挪出每像素循环（26.7 MP 就是 2670 万次 3×3 求逆）、
     把去马赛克的"坐标→通道"先摊平成表，两者输出指纹与改前**逐张相同**（证明真等价），
     但 3 档下交替三臂时间一点没动（CR2 320→344、RAF 1368→1370）⇒ **撤回**，代码回原样。
     LLVM 在 3 档已经做了这些提升，人再手写一遍只是把 diff 变大。
  ③ 分段计时必须与**被测路径同源**：宿主的 `read_ms` 段是 mmap（实测 0.05 ms），探针里用 `fs::read` 量到 2–5 ms——
     那一栏不能进端点的账，否则"读文件 3 ms"会被当成一笔真成本重复计一次。
- ★ **工具出口**（免得下轮再撞 K101 那条 env）：`build/stall_probe.ps1` 现在带 **`-DecodeTrace`**，
  同一次 run 既出 `[main-latency] cost=` 又出 `[decode-trace]` 五段（read/probe/query/render/post）。
  默认臂照旧清掉那两个 env，所以"用户实际拿到的那一档"没被污染——**加了开关就是新臂，必须换 `-Tag`**。
- **教训**：`opt-level` 这类"全局档位"的例外不能按库名背，要按**热循环的归属**判；
  而"提了更快"与"改了等价"是两件事——前者要有端点读数，后者要有逐字节指纹，缺一样就别落地。

### K103 —— 把逐点幂运算换成查表时，等价性的判据是"桶"不是"分界线"；用例里要写覆盖率断言

- **现象**（m79）：`develop` 的 gamma 每像素调 3 次 `powf`（占显影链 50–56%）。第一版把"能不能查表"
  写成**一条暗调分界线**——`dark_limit` 以下精算、以上查表，理由是"sRGB 曲线在黑端陡，边界都在黑端"。
  用例跑出来 `dark_limit = 65245`：**几乎整个定义域都要精算**，这条改写一分钱省不下。
- **根因**：想错了边界的分布。量化到 8 位一共只有 256 级，**每一级的交界处都恰好压着几个"跨边界桶"**，
  所以不合格的点有 255 簇、**散在全定义域**；暗调里只是因为曲线陡、这些簇**密集成片**，才看着像"一条分界线"。
- **判据与修法**：
  ① 判据按**桶**写，不按区间写：一个桶可查表 ⟺ **桶内恒定**（`f(lo) == f(hi)`）**且左右邻桶也恒定且同值**
     （第二条是为了 `(x * 65535) as usize` 那次 f32 乘法把 x 舍进邻桶时取值不变）。不满足的**逐桶标记**回精算。
  ② 用例里**同时断言覆盖率**（"可查表的桶必须过半"）。这条才是把上面那个错设计当场顶回来的东西：
     只断言"逐个桶自证等价"的话，一个"全都回退精算"的实现也能绿——**等价但不干活**，正是 K72 那一族。
     实测最终 64771/65536 = **98.83%** 可查表。
  ③ 等价性除了穷举用例，还要**拿真实数据留一份逐字节指纹**（本轮：三张真机 RAW 的 fnv1a64 与 m78 记录逐张相同）。
     穷举证的是"这条判据成立"，指纹证的是"这台机器上这条路真的被走到了"。
  ④ 用例要**先破一次再立**：表值 +1 ⇒ 两条 FAILED；把逐桶标记撤成"全表都查" ⇒ 两条 FAILED
     （`桶 9 桶内不恒定`）。后者尤其重要——它证明**暗调回退是承重的**，不是一段可以顺手删掉的保守代码。
- ★ **顺带一条测量事实**：这一台机器的负载在**一小时内漂 5–13%**（同一枚 DLL，18:15 端点 529.7 ms、
  18:30 同一份读出 568.6 ms）。所以**绝对值不跨时段比**：解码器侧计时用两个二进制交替跑，端点用
  `.build/decoders` 里换 DLL 交替跑；比完再引用数字。
- **教训**：写"快路 + 回退"这类结构时，回退的判据必须与被绕过的**真实原因**同形（这里是"量化边界"，
  不是"亮度区间"）；并且用例要问两句——**它对不对**，以及**它有没有真的在干活**。

### K104 —— 破坏实验验的不是"用例会红"，而是"红的正是这一条判据"：一条在退化实现下照样绿的断言，测的是环境不是代码

- **现象**（2026-10-21 m81，键盘翻页节奏闸）：我给接线用例写了四段，其中 ④「故意慢按每一记都当场翻」。
  做破坏臂 MUT-2（把按住判据 `held` 强写成 `true`，也就是退化成"无脑限速"）之后：
  **单元用例红了，接线用例却照样绿**。
- **根因**：④ 恰好排在一次"兜底翻"之后，那一刻 `key_due` 已经落在**过去**——于是无论 `held` 怎么写，
  `now < key_due` 都不成立，闸都放行。也就是说 ④ 观察到的"翻成功了"来自**环境时序**，
  不是来自我要验的那条形。它不承重，却长得像一条承重断言。
- **修法**：把手按那一记显式摆到"闸还没到点"的状态里（`key_due = now + KEY_PACE` 且
  `key_last = now - 400 ms`），于是只有"按同方向间隔放行"这一种写法能过。重跑 MUT-2 ⇒
  **两条同时红**（canvas 那条报 `left: 3, right: 1`，正是"手按被吃掉"的形状）。
- **教训**：破坏实验不能只问"有没有用例红"，要逐条问"**把这一条形反过来，哪一行会红**"，
  并且真的跑一遍看红的行号与形状。接线用例尤其危险：它靠调用序列造出时序，
  而时序本身容易替断言"预先放行"——所以接线用例的每个分支都要**自己摆好时钟**，
  不要继承上一段留下的状态。

### K105 —— 「逐字节指纹相同」只证明**改动没动画面**，不证明**画面对**：一条错着的显影链被四轮等价改造一路保绿

- **现象**（2026-10-21 m82，开工"按视口档显影"）：为了判分箱那一档的画质，我先搭了三臂对照
  （A 现路全尺寸显影→面积平均、A2 换取样起点、B 分箱直显）。图一落盘，**现路自己就是错的**：
  Nikon NEF 平均 RGB `8/181/160`（整张青绿）、Canon CR2 `0.3/195/157`（红道恒 0）、
  一张本来就是黑的 RAF 渲染成 `250/104/250` 的品红块。而这条链刚被 m78（提 `opt-level`）、
  m79（gamma 桶表）、m80（缓存共用缓冲）连着改过三轮，**每轮都记着"三张真机像素指纹逐张相同"**。
- **根因**：那枚指纹是**等价性**证据（改动前后同一张图），不是**正确性**证据（这张图该长什么样）。
  基准是"上一版构建"，而上一版本身就是错的 ⇒ 越等价的改造越能把错误保护得严丝合缝。
  两个具体错处都在这条链的最前面：① 线性化里 `let c = if cpp == 1 { 0 } else { i % 3 };`
  然后 `* wb[c]`——`cpp == 1` 是一切 Bayer / X-Trans 的形状，于是**三道色一律乘红道增益＝没做白平衡**，
  而色彩矩阵的前提恰恰是输入已白平衡，红道被算成负数再钳到 0；② 一条"观测峰值距黑电平 < 声明白跨度
  5% ⇒ 按观测值重归一"的兜底，**按它自己的触发条件只可能在黑帧/平场上成立**，一成立就把传感器噪声
  抬成满量程——而它的注释里那句见证样本（"数据 max 仅 ~1400"）查下来正是这张黑帧的 1371。
- **修法**：白平衡折进色彩矩阵（`inv3(xyz_to_cam)·diag(wb)`，一次列缩放，逐样本零额外乘法；
  能折是因为去马赛克只平均同道样本，与按道乘常数可交换）；那条兜底**整段删掉**，判词
  「查看器不替照片做自动色阶」。两条新用例分别钉住，且各自证明**旧用例测不到它**：
  MUT-1（把增益退回一律乘 `wb[0]`）下新用例红、`develop_synthetic_rggb` **照旧绿**——它增益全 1。
- **教训**（三条，都要落到动作上）：
  1. 判**画面**对不对，裁判必须是**改动之外的独立参照**：本轮用的是同一张文件里
     **相机自己写下的 JPEG 预览**（抠 SOI…EOI 即可，`.temp/m82_preview.py`）。
     拿上一版当基准，只能证明"没改坏"，不能证明"没改错"。
  2. 写启发式兜底时先问"**它什么时候会响**"，不是"它想救哪种文件"。触发条件就是它的适用域；
     若适用域与它想救的对象不重合（这里：想救"白电平撒谎的文件"，实际只会命中"黑帧"），
     它每一次生效都是错的，**包括那些看起来变好了的**。
  3. 一条被反复"等价验证"保护的通路，值得偶尔**拿外部参照重判一次**——尤其是自写的
     数值管线（本项目里就是 RAW 显影：rawler 只交传感器原样，颜色全是我们算的）。

### K106 —— 「申报尺寸」是承重的契约而不是 informational：缓存只认内容就会跨档位串档，而 17 个单测全绿

- **现象**（2026-10-22 m83，把按视口档显影接上 ABI）：这轮最容易做错的地方不在分箱算得准不准，
  而在两处**一致性**。① 解码器的线程本地缓存原来只按**内容指纹**认人——一旦同一份文件能出两档像素
  （视口档 / 整图档 / 缩略档），"命中"就变成了**把 101.8 MB 的整图当 240×180 的缩略交上去**。
  ② 宿主在**渲染之前**就把查询阶段回来的 `actual_w/h` 摘走（`main/src/decoders/mod.rs:1131` 取出、
  `:1212` 全程用它解释缓冲区），所以查询与渲染两阶段各算一次档位而**算出不一样**，轻则画面被按错误
  步长解释（花屏/黑边），重则 `out_cap` 不足直接打不开。
- **抓到它靠的不是单测**：变异 MUT-1（把缓存命中判据里的档位键删掉）之后，**17 个用例全部照旧绿**——
  它们没有一个走过解码器入口。红的是本轮新写的解码器端探针 `check_raw_tier`（解码器仓 examples），
  它按**宿主真实的调用序列**走 `iv_render`（①-a 问原图 → ① 查询档位 → ② 渲染档位 → 升级 → 再来一次
  档位请求 → 缩略档），当场报「整图 渲染与查询的尺寸/字节不一致 left=(1952,1308) right=(3904,2616)」。
- **修法**：① 缓存键从「内容指纹」扩成**内容 + 请求档位**（`target_w/target_h` + 缩放意图）；
  ② 档位判据收进**一枚只吃元数据的函数**（`tier_plan` → `bin_plan`：尺寸 / cpp / 图案 / 原样 dtype），
  两阶段共用，并逐张真机样本对账 dummy 与真解算出的档一致（rawler 里带 `dummy` 分支的地方一共三处，
  arw / cr2 / mos 三个解码器各一处——**逐一读过才敢这么立**：dummy 只跳过填数据，不动元数据）；
  ③ 用例里把"点亮缩放意图才有档""两种朝向都不许比显示尺寸小""过半组合真的算出了档"各自钉死。
- **教训**（三条）：
  1. **缓存键必须覆盖"这次请求要什么"，不只是"输入是什么"**。凡一个输入能对应多种输出形态
     （档位/尺寸/帧/页/区域），键里缺那一维就是**串档**；而串档的表现形式是"尺寸对不上"，
     不是崩溃，所以只测单点的用例抓不到。
  2. **"多个入口必须算出同一个答案"这类契约，护栏必须是按调用序列走的端到端探针**——
     单测再全也只是把每个入口各自问了一遍。写这种轮次时先问：**拔掉哪一行，17 个单测还会全绿？**
     会全绿的那一行，就必须有一枚探针为它红。（与 K104 同形，这次红的是 example 而不是用例。）
  3. ★ **顺带更正 K 前一条记账**（m80：「解码器那次瞬时拷贝不在峰值的关键时刻上 ⇒ 想动 603 MB 得回宿主侧」）：
     那次实测没错，但结论说得太窄。真正决定峰值的是**"这一趟要不要产出那一份"**——
     m83 让首屏与连翻根本不生成整图，连翻期进程峰值就从 **639 MB 落到 132 MB**。
     ⇒ 省内存的正解通常是**少产一份**，不是**少搬一次**；"搬运省了但峰值没动"不等于"峰值动不了"。

### K107 —— 少算 3% 的像素却慢了两成：逐样本闭包里的**运行时偏移**让取模提不出循环，而分段计时插桩会把这个差异量没

- **现象**（m84，RAW 画幅裁切）：这轮只做一件事——把传感器四周的光学遮光区裁掉，交回画幅。
  裁掉的面积 1.7%~3.6%，先验就该是"省一点点或不变"。端点第一轮却在 1:1 那一腿量到
  **新臂慢 +21%~+29%（两样本两轮、区间不重叠）**。一个只减少工作量的改动变慢，说明**代价不在"少算的那部分"上，
  在为了少算而改写的循环形状上**。
- **离线 A/B 会骗人**：同一份新代码内部把「整块显影」和「画幅显影」两条腿交替量，两腿几乎相等
  （+2.7% / −2.2% / −4.9%）——看起来"没有代价"。但对照臂必须是**旧构建的同一处代码**，不是新构建的另一条腿。
  ★ 教训：**A/B 的"B"选错对象，结论就成了"没有回归"**。这轮的回归是"新构建 vs 旧构建"，只有端点换 DLL
  双臂能看见。
- **决定性探针是减法，不是加法**：把改动一件件加回去都量不出主因（平铺、单形化闭包、`#[inline(always)]`、
  `#[inline(never)]` 各自无可复现差异）。真正定位靠的是**只删一个因素**：把去马赛克闭包里的
  `+ex.y / +ex.x` 偏移删掉、其余一律不动，同一份二进制里 NEF 253.3 → 310.9、RAF 774.0 → 999.4、
  CR2 190.2 → 242.5 ms（**+22.7% ~ +29.1%**，台账 `.temp/m84_bench_phase.txt`，两臂**像素指纹逐张相同**）。
- **根因**：rawler 的 `color_at` 写成 `pattern[(row+48)%48][(col+48)%48]`。偏移是编译期常量时，编译器能把
  `(k+48)%48` 折进索引表；偏移变成**运行时值**之后，那两次取模**提不出逐像素循环**——去马赛克每像素要查
  5~9 次，于是每像素多十几次真除法。修法不是加注释让程序员"注意"，而是**把偏移折进一张 48×48 表**
  （每次显影建一次，2304 次查询），内层重新变成 `rot[y % 48][x % 48]`，与起点为零完全同形。
- ★ **分段计时插桩把要量的东西量没了**：加上按段计时之后，两臂读数变得一样（m83 与 m84 同值）。
  插桩改变了内联边界与代码布局，**被观测的行为因观测而消失**。⇒ 用插桩定位"哪一段慢"之前，
  先确认插桩本身不改变总时间；否则退回"只改一处"的减法探针。
- **判据要跟着实测改口径，并写下为什么**：原判据 3 要求"四周各扩 1 像素真实邻域"以保证逐字节相同。
  实做发现横向也裁会让展开矩形的行宽从传感器那个偶数变成奇数（NEF 3874）、线性化从一整遍平铺变成逐行搬运，
  省不到 3% 反而更慢 ⇒ 改成**上下各扩 1 行、横向铺满整行**：左右方向永远在原样真实邻域里，
  钳位口径与整块那条腿一致 ⇒ 逐字节相同照样成立，代价归零。**改的是实现口径，不是判据的强度**。
- **三条可复用的规矩**：
  1. 任何"少算一点"的改动如果在端点上变慢，**先怀疑循环形状**（运行时下标、运行时取模、逐行切碎），
     别先怀疑少算的那一点。
  2. 归因用**减法探针**：一次只删一个因素，其余不动；加法（一件件试优化）只能证明"这个优化没用"。
  3. `#[inline(always)]` / `#[inline(never)]` 这类标注**只按实测留下**：量不出可复现差异就删掉——
     留在源码里会让后人以为它有用（与 K102 同一把尺子）。
  4. **对照臂要选"旧产物 vs 新产物"**，不是"新产物这条腿 vs 那条腿"：本轮新构建内部两条腿几乎相等，
     看着"没有代价"，而真正的回归只有换 DLL 双臂才看得见。

### K108 —— 「重编一次 md5 就变了」不等于代码变了：逐段比对才是等价性证据；而读错一个 PE 偏移差点让我"更正"掉一条本来写对的记账

- **现象**（m84，2026-10-22）：同一份 `rupix-raw` 源码，本轮六次门禁发布得到六个不同 md5
  （大小一律 6,923,264）。而解码器的性能判词一直是靠**换 `.build/decoders` 里的 DLL** 跑双臂的——
  如果"重编就变"意味着代码在变，那这套测量方法从头就不成立。
- **查法与结论**：写一枚段级比对量具（`.temp/m84_difftext.py`），两枚产物**整文件只差 24 个字节**：
  `.text`（机器码）**逐字节相同**；`.data/.pdata/.fptable/.reloc` 全 0 差；差异全在
  ① PE 头 `TimeDateStamp`（`e_lfanew+8`，实测就是两次门禁的构建时刻，相差 541 秒），
  ② `.rdata` 里三处 CodeView 记录带的同一个时间戳，③ 一处 **16 字节 PDB GUID**（旁边就是 `raw.pdb` 字样）。
  ⇒ `strip = true` 去掉的是调试信息，**去不掉 CodeView 目录项**。**md5 认产物，不认代码**：
  跨产物的双臂比较是安全的，但出货前要把"测量那一枚"与"出货那一枚"用段级比对对一次。
- ★ **我自己在这条上错了一次，且错得有价值**：第一次读 `TimeDateStamp` 时把偏移算成
  `e_lfanew+4+18`（那是 `SizeOfOptionalHeader`），解出 1971-02-01，于是当场写下"是定值、不是时间戳
  ⇒ 是链接/布局漂移"，还顺手把 m83 记的"构建里有时间戳"当过时结论"更正"了。
  把差异字节逐处 dump 出来、看清它落在哪个段旁边是什么字符串之后，才知道 m83 那条本来就是对的。
- **教训**（三条）：
  1. **单个 struct 字段读数不足以定论**，尤其当结论要用来推翻已有记账时：要把差异本身摊开看。
  2. 推翻旧记录要走"证据升级"而不是"读数升级"——**"我这次读到的值不一样"不构成更正**（本轮的更正已在
     本仓历史记录 §五与本条里写回原结论）。
  3. "产物字节会变"这件事要在**第一次发生时就查清差异的性质**（哪一段、几个字节、是什么），
     否则它会一直腐蚀所有换 DLL 的测量——本仓从 m78 起就在用这套方法。
  4. ★ **这条不许反着用**（m85 就地撤回过一次）：不能拿"上一对产物 `.text` 逐字节相同"当这一对的免测理由——
     那是**那一对**的段级读数，本对没做过段级比对。同源码被两条流水线先后覆盖发布（`build.ps1` 与宿主仓
     `full.bat`）时，端点双臂必须用**出货那一枚**重跑；顺手补一条更严的：**单一样本两轮同向只是必要条件**，
     立案前先廉价地再配一对（本轮把跑测脚本的样本/轮数做成环境变量可覆盖，一分钟单独复跑那一张），
     第三对一反号，"同向"就让位于"同臂跨 pass 漂移大于两臂之差"。

### K109 —— 「这一步有没有生效」不能靠输出数值判：恒等兜底长得像正路；而一条写对的"诚实边界"替这个缺陷背了三小时的书

- **现象**：m85 要给 RAW 首帧换源（内嵌预览），三臂量具一搭起来，**相机自己写进文件的那张预览
  把我方渲染比得没法看**——云是品红的、整张蒙一层青（档位均值 NEF `89.6/133.5/147.8` vs 预览
  `123.2/141.0/152.5`；CR2 `100.0/122.6/140.3` vs `155.2/165.3/177.2`）。这不是风格差。
- **根因**：显影链读的是 `img.xyz_to_cam`，而该字段在 rawler 0.7.2 里**恒为全零**
  （`Camera::xyz_to_cam` 只在初始化那一行写零，之后再无人赋值；字段自己标着
  `TODO: deprecated, use color_matrix`）。零矩阵行列式为零 ⇒ `det < 1e-9 → 单位阵` 那道兜底
  **每次显影都触发** ⇒ 色彩矩阵从第一天起就没进过链路，整条链实际是"把相机三道当 XYZ 再乘
  D50→sRGB"。真数据在 `color_matrix` 里，三张文件各躺着 D65(9) 与 A(9) 两条**没人读**的标定。
- **为什么三轮门禁都没拦住**：兜底路径的产物**仍然像一张照片**（构图、层次、亮度全对），
  22 条用例全绿——包括那条专门测白平衡的用例。★ 它用的合成夹具把矩阵配成"恰好与 D50 那步抵消"，
  于是它测的是白平衡，不是矩阵有没有值进来。**恒等也保中性灰**，所以"中性灰必须还是中性灰"
  这一类不变量判据同样抓不到它。
- **有效的判据长什么样**：`render_depends_on_the_color_matrix`——同一份有彩度的像素，
  两份真机矩阵（D80 / 30D 实读值）加一份"无标定数据"，三次渲染必须**两两不同**。
  这一条把 M1（把来源改回那个恒零字段）当场钉红，且**只红它一条**：这就是"旧仓 22 条对本轮
  缺陷全部无感"的直接读数。夹具的 `xyz_to_cam` 一律留全零（真机就是这副样子），
  矩阵改由 `color_matrix` 供 ⇒ 谁退回旧来源，退化立刻显形。
- **三条可复用的规矩**：
  1. **读依赖的字段之前先 grep 谁给它赋值**。标了 `deprecated` 的字段是信号，不是风格问题；
     一条 `grep -n "xyz_to_cam\s*[:=]"` 就出结论，成本远低于三轮验收。
  2. **兜底要能被探针问到**。本轮把 `cam_to_srgb_wb` 设成 `pub` 只为让量具直接问"生产现在把
     `(1,1,1)` 映到哪儿"，并让探针把"旧链 / 新链"两列并排打出来——**看不见的兜底等于没有兜底**。
  3. **给残差找解释时，解释里每一条"我们没做 X"都要先确证 X 的数据在不在手边、X 的代价是不是真为零**。
     m82 当时写下"修后仍与预览有差（红道 90 vs 122）——本仓是通用显影，**没有机型色彩配置**、
     不做到影曲线、不做高光重建"，并自称"对得起这份元数据"。那句话里只有后半截成立：
     机型色彩配置**就在元数据里**、三步线性代数**全是上游的 `pub` 件**、接上之后逐像素还**少一次**
     3×3 乘。⇒ 那条"诚实边界"当时是缺陷的藏身处。现在真正剩下的边界只有两条，已各自登记：
     ㉗（不做到影曲线 ⇒ 整体比相机预览暗 15%~40%）、㉘（不做高光重建 ⇒ 过曝处按道钳位）。

### K110 —— 提速把"串行"改成"并发"之后，占用判据必须换成与采样时刻无关的量；并用空载臂分清"重叠"与"新增"

- **现象**：m86 在端点量到首帧 −244 ~ −297 ms（五臂、区间不重叠），但同一批台账里
  **首帧那一刻的工作集新臂反而高 6~16 MB**。两件事同时成立是不可能的，除非读数有问题。
- **第一层坑：采样点本身不可比。** "首帧那一刻"在两臂里是启动过程中**相差 ~300 ms 的两个瞬间**——
  快的那臂采得早，正撞上后台还在干的活。补一个固定偏移（spawn 后 2600 ms）再采，看着合理，
  **但量出来两臂都是 0.6 MB**：产品自己在启动 2 s / 10 s 各 `EmptyWorkingSet` 一刀
  （`main/src/runtime/mod.rs:328`），2600 ms 的"当前工作集"读的是**裁剪地板**，与本轮改动无关的
  一个常量。⇒ **判据失效的形态不是"读出错值"，而是"读出两个相等的数"，看上去像"无差异"。**
- **换量**：同一时刻改读 `PeakWorkingSet64`——峰值不被裁剪抹掉，且与"什么时候采"无关（只要晚于
  被测工作发生完）。读数立刻稳定且**五臂区间全部不重叠**（含 blank：48.3..49.1 vs 59.4..65.6）。
- **空载臂把归因钉死。** blank 臂一张图都不解码，峰值照样 **+12.1 MB** ⇒ 这笔不是解码的账；
  真正的机制是**串行改并发**：旧臂主线程先扫完系统字体才建窗口/D2D，峰值 = 两者之**大**；
  新臂主线程不等了，扫描与初始化重叠，峰值 = 两者之**和**。两条佐证都在数里：
  新臂峰值散布 3.7~16.8 MB、旧臂 0.2~2.6 MB（一笔固定新增给不出这种随线程时序摆动的宽度）；
  2 s 之后两臂同为 0.6 MB（**常驻没变，变的是那一秒的峰值**）。
- **可复用的三条规矩**：
  1. **改动把任何一步从主线程挪到后台线程（或反过来），时间与占用要各自独立读数**，不许用"时间快了、
     占用应该没变"顺推。本轮时间那条赢（每次开机 −0.3 s），占用那条**如实付了 +12~21 MB 峰值**。
  2. **先查被测进程自己有没有在动你要量的那个量**（这里是两刀工作集裁剪）。凡是"固定时刻读一次"的
     判据，都要问一句"这个时刻之后谁还改过它"；有裁剪/回收/GC 的，改用**峰值类**或**累计类**指标。
  3. **加一臂空载**（什么都不干的启动）做归因对照。它能一句话区分"改动多占了内存"与"并发把两笔
     开销叠在了一起"，成本只是一次运行。
- ★ **顺带一条工具事实（本轮两次栽在同一处）**：bash 里 `P=E:\tmp\…` 会**把反斜杠当转义吞掉**
  （`E:tmpAI.AgentRuPix…`），递给 `md5sum` 得空串、递给探针得 `NO_EXE`。更阴的是失败形态：
  驱动用 `| grep -o 'STARTUP.*'` 过滤输出，`NO_EXE` 整行被吞 ⇒ 台账只剩 `ARMS`/`DONE` 两行、
  退出码照常 0，**看起来像"跑完了但没数"**。⇒ 变量一律存 POSIX 路径，递 Windows 程序前用
  `cygpath -w` 现转；过滤输出时**必须同时打印没匹配上的原始行**（本轮补了 `|| echo … NO-LINE`
  这一支，但它只在管道末位不是 `grep` 时才生效——真正的防线是**核对台账行数与运行次数**）。

### K111 —— 删掉一条预热不是"纯删码"：常见路径的"无可测差异"只证明它不在关键路径上，代价只能在它保护的那条罕见路径上量

- **背景**：m86 之后 `main/src/main.rs` 那枚 `sv-fonts` 预热线程成了正常启动**唯一**的取字体库者——
  它替"一张可能永远打不开的带文字 SVG"在每次开机扫一遍全系统字体。m87 删掉它，按的是"低占用"：
  每一次启动（连空启动）都付峰值，只服务一条罕见路径。
- **坑的形态**：删掉之后，不带文字的路径（图标、托盘、照片、零文字 SVG）**全部量不出差异**——
  tiny 臂的 `frame` 两臂区间重叠，三个启动臂只有占用变了。如果只量到这里，结论会是"删了没影响"；
  而真实代价是 **+273 ms**（带文字 SVG 首开 `cost=` 30.5→303.8 ms，n=6、两臂区间不重叠），
  只是它藏在一条**本仓随包的三枚 SVG 都走不到**的路径上（全都零 `<text`）。
  ⇒ **预热线程的"存在"与"有用"之间，隔着用户真的打开一张带字 SVG。**
- **怎么量的**：复用产品自己的单实例交接——私有根空启动，等 3 s（旧臂的预热早已完成），
  再用**同一枚 exe** 把带两个 `<text>` 的 SVG 交给首实例，读首实例日志里那条 `[main-latency]` 的
  `cost=`。两臂都成功解出（日志都带文件名与耗时），差别只有取库时机。
- **可复用的三条规矩**：
  1. **删/改一条预热、缓存或常备资源之前，先写清它服务的具体路径**（谁能走到、多常走），
     再在那条路径上配一对读数。只量常见路径，等于没量代价。
  2. "罕见"是**取舍的理由，不是省掉读数的理由**。读数在案，将来被问"为什么第一次打开这张 SVG
     要等 0.3 秒"才有据可查；没有读数时，删掉的东西会变成下一个"从来没生效过"（K109）。
  3. 反过来同样成立：一条预热若**常见路径每次都要为它付账**（这里是每次启动的峰值 +12~21 MB），
     它就必须有一条能被量到的收益路径，不能只是"以防万一"。

- **K111 补条（2026-11-01，m183）：当年那个"+273 ms"低估了，而且漏了一整段更大的代价。**
  用户拿 `.temp/testdata/1M/图片1.svg`（3,500 B、24 个元素、**12 个 `<text>`**、
  `font-family="DengXian,…,sans-serif"`）来问"为什么打开要等一两秒，以前是秒开的"。生产日志三条
  `[main-latency]` 读数：**1963.9 / 963.8 / 2346.1 ms**，而同一进程内后续每次只要 **16–21 ms**。
  新量具 `examples/svg_font_cost_probe.rs` 三臂把它拆开：
  ① `warm` 臂显式叫 `windui::render::image::svg_warm_fonts()` = **265–273 ms** —— 这一段确实就是
  K111 记的那笔（m87 把预热删了 ⇒ 从启动挪到首用），量级一字不差；
  ② 但预热之后**首解仍然要 769–781 ms**；同进程内按族连续量：Arial 740 ms → 等线 768 ms →
  Arial 再解 **27 ms** ⇒ 还有**第二段一次性代价 = 每个字体族第一次被用到时装载面数据**，
  它**按族**计，不是全局一次，K111 当年的夹具（2 个 `<text>`、单一字体）根本没暴露它；
  ③ 零文字对照 ≈ 0 ms、整篇重复解 23–26 ms ⇒ **不是 resvg 光栅化慢**，别拿"矢量渲染本来就慢"当结论。
  ④ `thumb-first` 臂是关键的一格：先按 256 解一张缩略图 = **1083 ms**，随后主画面档只花 **23 ms**
  ⇒ 这笔钱是**谁先碰这份文档谁付**。日常浏览文件夹时缩略图先跑，所以点开是秒开；而用户这两天是
  **命令行/双击把这张图直接交给首实例**（日志里三处 `命令行打开 …图片1.svg`），缩略图还没跑，
  主画面就成了第一个碰字体的人 ⇒ 当着他的面付 1 秒。**"以前秒开"与"现在等一秒"差的不是代码，是路径。**
  ★ 另注：这张 SVG 的 mtime 与它第一次出现在日志里都是 2026-11-01 02:5x —— 本机上它没有"以前"。
  **规矩补一条**：量预热代价时，"扫库"与"按族装载面数据"是两笔，必须**分别**给读数；
  只报一个总数（当年的 +273 ms）会让下次同题被问的人重新拆一遍，而且会误判成回归。

### K112 —— `[profile.release.package.<名>]` 按 **package 名**匹配：`[lib] name` / 目录名写得再像也不会命中，且构建静默成功

- **背景**：TIFF 解码器从一开始就在根 `Cargo.toml` 里有一条 `[profile.release.package.tiff] opt-level = 3`，
  此后几轮都把它当作"TIFF 已经按速度编译"。m89 立项时实读才发现：那条命中的是**上游依赖库 `tiff`**；
  解码器本体的 `[package] name` 是 `rupix-tiff`（目录名 = 解码器 id = `[lib] name = "tiff"`，三者都不是 package 名），
  所以解码器自己的行寻址 / 面积平均热循环一直是 workspace 默认的 `z`。
- **坑的形态**：改对键之后的**同一份源码**只换编译档位，6055² 降采样 177→121 ms——收益一直躺在地上，
  而构建、测试、发布、像素指纹**全部照常通过**：Cargo 对没有命中的 package 覆盖不报错，
  两条腿又逐字节相同，等价用例不可能变红。这是一个"读起来像已生效"的设置，和 K109 的恒等兜底同族：
  **配置项的"存在"与"生效"之间隔着一次实测。**
- **怎么发现的**：先分段（`render_ms` 占端点的 85% ⇒ 热循环确实在我们这层，不是宿主），
  再读 `Cargo.toml` 的 `[package] name` 与依赖清单，而不是相信目录 / lib 名。
- **可复用的四条规矩**：
  1. profile 覆盖的键是**被编译 crate 的 `[package] name`**。依赖库与解码器本体是两个键；
     `[lib] name`、目录名、解码器 id 都不是 profile 键。
  2. 新增 / 修改一条 profile 覆盖后，要用"只差这一项"的对照臂 + 时间端点证明它**真的命中**；
     "编译通过""DLL 已发布"都不算证明（K104 / K109 同一个尺子）。
  3. 这类未命中**不会被等价性用例抓到**——输出完全相同；只有计时端点能看见它。给热路径加编译档位时，
     读数与像素指纹两样都要有。
  4. 出货件来自另一种构建拓扑时（workspace 全量 vs `-p` 单包），**测与哈希都以实际出货的那枚 DLL 为准**：
     m89 的 workspace 构建版 654,336 B / md5 `94c3…`，单包构建版 652,288 B / `277c…`，
     最终读数与指纹是在出货件上复测的。

### K113 —— 「16 ms 轮询」在 Windows 上是 31 ms 的摸彩：定时器有 15.6 ms 量化，常数写得比它还小也买不到那档粒度

- **背景**：m90 之前，小图 `[main-latency] cost=` 一直呈 3.4 / 14–15 / 26–31 ms 三簇，
  而 PNG 解码本身只要 0.2–2 ms。代码里写着 `POLL = 16 ms`，读起来像"最多等 16 ms"。
- **坑的形态**：Windows 用户态定时器默认量化是 **15.625 ms**——`SetTimer(16)` 的实际周期是
  **≈31.2 ms**（两格），`SetTimer(1)` 也只能到 **15.6 ms**（一格）。用 `Sleep(1)` × 30 次实测：
  min 9.46 / **median 15.24** / max 23.29 ms。日志里那两簇就是按键落在"两格之间"与"跨一格"的相位差：
  **同一个 16 ms 常数，用户看到的等待在 0–31 ms 之间摸彩。**
- **怎么发现的**：先在真机上量定时器粒度本身，而不是相信常数；再搭一条 `POLL=1 ms` 临时臂做上界——
  它的中位仍钉在 15.6 ms 格上（15.15/15.20 ms），证明"把常数改小"这条路根本到不了 1 ms。
  最后上唤醒臂：同会话 **8.05/8.65 ms**，比 1 ms 轮询再快约 7 ms，且空闲不加回调。
- **可复用的四条规矩**：
  1. 报"每 X ms 轮询"前先量**实际节拍**；`SetTimer` / `Sleep` / `WM_TIMER` 的粒度由系统量子决定，
     常数只是请求值。本机量子 15.6 ms，16 ms 的请求会稳定跑成两格。
  2. 端点上出现"两簇/三簇"而不是连续分布时，先怀疑**采样相位**（按键时刻与定时器相位的差），
     不要先怪解码；分簇的间距往往就是系统量子的整数倍。
  3. 结果已经算好却要等下一拍，正解是**让生产者叫醒消费者**（wake / 通道），不是把轮询周期改小：
     改小受量子下限约束，还会线性抬高空闲占用；唤醒只在有结果时多跑一帧。
  4. 临时测量臂要有明确的上界身份（`POLL=1 ms` 只证明"轮询这条路的天花板"），
     不能因为"它也比基线快"就当成产品形态——它每秒 1000 次定时回调，换来的仍是 15.6 ms 的格。

### K114 —— 失败分支不许顺手撤销成功状态：一次升级失败会把好图清成空白，还会把重试闩焊死

- **背景**：大图分两档上屏（先 viewport 档、再 `(0,0)` 原生档），动画图逐帧回包；两者共用 `Viewer::apply`。
  m91 逐文件通读到 `Err` 分支时发现它无条件 `loaded = None; error = Some(msg); bump_image_gen()`。
- **坑的形态**：这个清法对"首解失败"是对的（本来就没图可看），对"升级/动画帧失败"却把**屏上仍有效的像素**
  一起撤销——用户正看着的大图突然变空白 + 中央红字，只因为更清晰那一档没拿到。更隐蔽的是
  `native_requested` 只在成功路径松：失败一次后这张图永远停在低清档，用户再怎么缩放都不会重试。
  两条缺陷同源：**失败处理把"这次请求"和"手里已有的成果"当成一回事。**
- **修法**：失败分支先按 `done.path == loaded.path` 判断"失败的是不是已上屏这张图"。是 ⇒ 保留像素、
  停动画时间线、松闩、清同 seq 的预览元信息、记 warn、返回 `false`；否 ⇒ 首解失败，照旧清空 + 报错。
  路径判据不能换成"有没有 `loaded`"：翻页窗口期旧图还在 `loaded` 里，必须让新图失败清掉旧图。
- **可复用的四条规矩**：
  1. 写 `Err` 分支前先问"手里的状态是否仍然成立"，而不是默认"出错了就清掉重来"。
  2. 任何"防重复请求"的闩都必须有**失败即松**的路径；只在成功时松，等于一次失败永久降级。
  3. 这类修法要两条用例夹住：一条正向（失败保留好图），一条反向（新图失败不许旧图冒充）。
  4. 回归用例必须先在旧判据下看到红（m92 用 `keep = false` 变异，红在返回值断言），再还原复绿；
     两条都绿说明用例只是复述了新代码。

### K115 —— `cargo fmt --all` 会格式化 `.3rd` 里的路径依赖，把补丁归档与工作树顶出漂移

- **背景**：m92 收尾格式化时跑了 `cargo fmt --all`。本仓的 `wind-ui` 是 path 依赖，工作树在 `.3rd/`，
  权威补丁归档在 `main/patches/`；j13 逐字节对撞两边。
- **坑的形态**：`--all` 把 `.3rd/wind-ui-rust-0.23.0/src/render/image.rs` 里一行 `hay.windows(...).any(...)`
  折了行——语义不变、编译测试全绿，但 **j13 当场红**。格式化器不认识"归档权威"，它只看见 workspace
  里能摸到的所有包。若当时跳过 j13，发布出的将是与归档不符的工作树，下次重建 `.3rd` 又会悄悄变回去。
- **处理**：用 `patches/` 下的权威文件覆盖回工作树（不是反向改归档），j13 复绿。
- **可复用的四条规矩**：
  1. 本仓改完源码只跑 **`cargo fmt`**（当前包），不跑 `--all`；路径依赖不在本轮改动范围内。
  2. `.3rd/` 一律视为工作树，`patches/` 才是权威；任何工具改动工作树后用归档覆盖回去。
  3. 跑了格式化 / 生成器这类"零语义"操作，也要重跑 j13；红名单精确到文件即证明门禁真的比到了东西。
  4. "测试和编译都绿"不能证明仓库自洽——j13 这种逐字节门禁存在的意义，就是抓这种**语义等价但产物漂移**。
- ★ **2026-10-25 修正该条第 1 条（同一天的同一行第二次漂）**：m128 格式化时跑的是**不带 `--all`**
  的 `cargo fmt`（正是当年立的规矩），它**照样**把同一个文件同一行（`hay.windows(...).any(...)`）
  折了行、j13 同样红。所以"不带 `--all` 就不会碰路径依赖"这个前提**是错的**——cargo 把 path 依赖
  算进当前 crate 的格式化范围。规矩收紧为：本仓格式化一律显式指包名
  **`cargo fmt -p rupix`（检查：`cargo fmt -p rupix -- --check`）**，并且**格式化之后必跑 j13**；
  已经漂了就按第 2 条用归档覆盖回工作树（本次即如此处理，并把这条教训补在本条之下）。
  顺带，`-p rupix_lib` 是无效的：那只是 lib target 名，不是包的成员名。

### K116 —— 预览缓存别存没有读者的字段：一个"占位"写进长期缓存，就是一条假数据

- **背景**：查询阶段的 `Meta` 曾带四个字段（natural / orientation / frame_count / page_count），
  只有 natural 有读者。`install` 在渲染落地后要把权威尺寸写回 `meta_cache`，当时的写法是整条替换，
  顺手把另外三个字段填成占位值（orientation=1、两个计数=0）。
- **坑的形态**：同一路径翻走再翻回来时，`navigate` 会把这条缓存取回当预览。三个占位值没有读者，
  所以**今天没有任何用户可见症状**；但只要将来有人接上帧数/方向，读到的就是缓存里的 0/1，
  而不是解码器当初报的真值——一个没有症状、却已经写坏了的缓存。同族问题：为了更新一列而整条覆盖，
  其余列就成了"最后一次写入者随手填的值"。
- **处理**：m93 没有去写"保留其余字段"的合并逻辑，而是删掉没有读者的三列——`Meta` 只剩 natural，
  缓存条目整条就是权威值，假值的载体不存在。帧数的权威来源留在 `Decoded.anim.count`，
  方向在解码阶段就折进了 natural（`fit_oriented`）。
- **可复用的三条规矩**：
  1. 放进长期缓存的字段必须有读者；"先存着将来可能用"= 提前制造第二事实来源。
  2. 覆盖缓存条目时，要么整条替换成权威值，要么只更新变化的那一列；**不许用占位值补其余列**。
  3. 同一事实已有权威来源（帧数在 `Decoded.anim`、方向在 natural）时，预览层不要再复制一份；
     复制出来的那份迟早与权威值分叉。

### K117 —— 原图档升级不是"装新图"：同步派生藏在 `install` 里，升级落地那一帧会按住 UI

- **背景**：`install` 的契约是"装上新解码结果，立刻派生一档上屏"。首解视口档 561×561 时这一刀只要 0.3 ms，
  看起来毫无问题；但同一张图的**原图档升级**（6055×6055 落地、目标仍是 1001×1001）也走同一个 `install`，
  那一刀实测 **38.1 ms**，正压在"改窗口 / 放大一格"之后的那一帧上。
- **坑的形态**：`tick` 里的本地换档早在 m2 就交给了 `LevelThread`，所以性能审计时容易只盯缩放与旋转，
  以为"换档不在 UI 线程"；唯独升级回包的 `install → rebuild_image` 还留在原地。更隐蔽的是：
  这不是新图——旧的上屏位图、鸟瞰、朝向都仍然有效，却被当成"新图首帧"同步重算了一遍。
- **处理**（m94）：同一张图的更大源落地时，把旧 `displayed/image/nav_image/nav_key` 原样留在屏上，
  新源投给 `LevelThread` 采到目标档，仍由 `poll_levels` 唯一落地。判据=同路径 + 双侧整图 +
  **新源严格更大** + 屏上朝向==目标朝向 + 源/目标像素过 `ORIENT_SYNC_PIXELS`；投递失败退回同步。
  同尺寸重解（动画下一帧）必须当场换，不能排队。
- **读数**：升级 `install` 38.1 ms → **0.1 ms**；派生 37.3 ms 在派生线程；48 ms 后新档上屏
  （清晰档晚到约 10 ms，换来那 38 ms 里窗口可画）。
- **可复用的四条规矩**：
  1. 装载路径里任何"按源尺寸计价"的活，都要先问一句能不能交给派生线程；首解便宜不代表升级路径也便宜。
  2. "升级"与"换图 / 换帧"共用同一个入口时，判据要落在**源是否严格变大**，不能落在"路径是否相同"——
     否则动画帧会被误挂起。
  3. 延迟换清晰档必须有**旧档接力**（空位图禁令不破），且落地只能有一条路（`poll_levels`），
     否则挂起与落地各写一套状态，迟早对不上。
  4. 这类优化的回归用例先破后立：把 `install` 改回无条件同步派生，看到"屏上该还是旧档"红，再还原复绿。

### K118 —— 字段文档里写的"消费者"不等于读者：装档每帧 stat 一个没人读的字段

- **背景**（2026-10-23，m98）：m96 的 O3 原打算"**缓存** `Loaded::file_size`，免得每次装档都 stat"。
  动手前数了一遍读者——`grep -rn "file_size" src tests examples` 只有三处命中：字段声明、
  `install` 里的初始化、以及那次 `fs::metadata` 本身。**读者零**。属性窗那行"大小"是它自己按路径
  stat 出来的（`ui/settings/metadata.rs` 里 `let meta = std::fs::metadata(&p)`），从不碰这个字段。
- **字段自己的文档是两处假话**：它写着「状态栏与属性窗口展示用；解码完成时一次性 stat，不每帧读盘」。
  状态栏从不读它；"一次性"也不成立——`install` 不是"换图才走"，同一张图的原图档升级、SVG 切片重渲、
  **动画的每一帧**都进来一次，于是那是一次按帧计价的 UI 线程 IO。
- **读数**：私有根（12 枚解码器硬链接齐全）里放同一张 GIF 跑 5 秒，`[main-latency]` **127 行**
  = 127 次装档 = 旧代码在 UI 线程付 **127 次 `GetFileAttributesW`**（本地 µs 级、网络盘 ms 级）。
  m97 件与 m98 件两臂各跑一次，行数都是 **127** ⇒ 删字段与删调用都没改逐帧节奏。exe **0 字节变化**
  （少一处调用与 8 字节字段，落在段对齐里）。
- **处理**（m98）：**删，不缓存**。把一个零读者的数缓存起来就是养第二份真相，与 K116 同族。
- **可复用的三条规矩**：
  1. 决定"缓存还是删"之前先数**读者**（跨 `src` / `tests` / `examples`），不要读它的文档——
     文档只会把当初的意图说圆，而意图会过期。与 K79（"能力存在"≠"能力可用"）同一族：
     **字段被写着用 ≠ 字段被用**。
  2. "每次解码完成"不等于"每张图一次"。动画、档位升级、矢量切片重渲都共用同一个装载入口，
     按帧入口里的 IO 要按帧算账。
  3. 这类"少干了 N 次调用"的收益用**调用计数**报，不要拿端点毫秒硬套：127 次 µs 级调用摊在 5 秒里
     测不出毫秒差，硬报一个数就是编。

### K119 —— 用截断后的整数反推比例、再乘到另一根轴：鸟瞰边缘长出图里没有的暗带

- **背景**（2026-10-23，m103）：用户报"鸟瞰图边缘总是有问题，明明图片没有空白或黑暗，鸟瞰图里却会显示"。
  绘制层先在 `nav_geom` 里把整图等比 contain 进 220×160 的盒（浮点算完 `as i32` 截断成整数盒），
  然后在 paint 里用**这个已经截断的盒宽**反推比例 `s = thumb.w / dst.w`，再拿同一个 `s` 去乘高度
  `th = idst.h * s`。
- **错在哪**：`s` 本该是"浮点盒 / 显示尺寸"，现在成了"`floor(浮点盒)` / 显示尺寸" ⇒ 恒 ≤ 真比例；
  乘回**另一根轴**时这个误差按 `dst.h` 放大。600×4000 的竖条图：盒 22×152（真比例 0.038），
  反推出 s = 22/600 = 0.0367，画出来的高只剩 **147** ⇒ 下缘长出一条 **5 px** 的盒底暗带；
  1234×2977 那格差 1 px。两根轴各用各的比例（`inner.w/dst.w` 与 `inner.h/dst.h`）串扰就没了。
- **第二条同族的错**：`as i32` 是**向零截断**。同一条式子里"除一遍再乘回来"在 `idst == dst` 时
  数学上等于原值，可 f32 往返差半个 ULP 就落到截断的另一边 ⇒ 右缘、下缘各少 1 px。
  规矩：**原点 `floor`、远端 `ceil`、再夹回目标框**，并把"源是整图时画的面必须等于盒"写成判据。
- **读数（实拍，不是推理）**：判据样本 = 整幅中灰 140 + **紧贴图缘 14 px 红框** + 左上蓝块
  （`.temp/m103-edge/`）；量具 `.temp/m103_navshot.ps1` + `.temp/m103_measure.py`。
  判据是"从黑框往里数，图自有的边缘色（红）出现在第几格"，四条边必须同一个数：
  修前 1234×2977 = **[0,1,0,1]**（右/下各被暗带与白框吃掉一格）；600×4000 的列剖面 = 内容止于
  y=633、y=634..638 是 5 格暗盒底、y=639 才是白框。修后两格分别 **[1,1,1,1]** 与 内容止于 y=638
  （暗带 **0** 格）。用例：`nav_whole_picture_fills_the_box_exactly`（铺开扫两万组，M1 退回旧算法时
  第一格就报 1234×2977 少 1 px）+ `nav_slice_lands_inside_the_box_and_never_spills`。
- **顺带一条口径**：画布空场 `rgb(15,15,15)` 与盒底 `rgba(28,28,30,225)` 在像素判据里**同属"暗"**。
  量具第一版拿"纯白行/列"当锚，结果锁到了视口框；拿"长纯暗段"当锚，又锁到空场的边界行。
  能分开两者的判据是**"1 px 线 vs 大面域"**（两侧邻行都必须是短的）。
- **可复用的三条规矩**：
  1. **比例只能从浮点原值来，不许从已经取整的结果反推**——取整一次的误差会被另一根轴乘回来放大。
  2. 画进某个框的东西，判据写成"必须等于这个框"，不写"差不多"：差 1 px 在 212 px 宽的盒里看不见，
     在 22 px 宽的窄条里就是 5 px 的洞。
  3. 外观缺陷按呈现像素判（K65），但**检测器自己也要先过判据**——先证明它在一格读得出已知缺陷、
     在另一格不误报，再拿它跨臂比。

  一条对着"把生产判据拆了"毫无反应的绿，不是凭据，是装饰。
- **根因（在被测对象的设计里，不在用例的写法上）**：`pointer_left()` 末尾那条 `||` 链
  以 `self.minimal_mode.get() && visible_bits` 收尾——**返回值自己就带档位因子**。
  传统模式里"悬停态被清光"与"悬停态原样保留"都报 `false`，所以任何只读返回值的断言
  在这个档位下**结构上分不开**这两个世界；而 runtime 那次省略恰恰依赖"清没清"。
- **立法（改完再验，不靠推理放行）**：判据要看副作用，就**把副作用抄成快照再比**——
  `bits()` 一次取七位（标题栏/浮条/信息条/两侧边带 + 三枚可选高亮，`Option` 连值一起取，
  这样"悬停从 A 键挪到 B 键"也算变了），`tick_hide` 前后各取一次比相等；
  另补一条**样本自证**（`hover_toolbar` 必须先为真），否则快照比对会退化成比两个空值而全绿。
  重跑变异：M-minimal **红在状态那条断言上**（且先于返回值那条），出货代码绿。
- **可复用的两条**：
  1. 写"我省掉了一次调用/一格输入"这类凭据用例时，先问**被省的那格落在哪一侧**——
     落在返回值上就比返回值，落在状态上就比状态；**判据的观察者必须与被省之物同侧**。
  2. 变异不是收尾仪式，是**用例的成立条件**：新用例写完就对它做一次"摘生产判据"，
     红了才允许写进文档说"这条钉着"。本条与"回归用例对着还原后的旧码也绿就不算用例"（记忆
     `evidence-driven`）同一条毛病的新形状——那次是**还原旧码**，这次是**摘掉守卫**。

### K123 —— 本机进程 CPU 记账量子 ≈15.6 ms：亚毫秒的"少做几次调用"用空闲 CPU 腿永远量不出

- **现象**（2026-10-24，m107）：ABBA 四腿、每腿 3 × 10 s，逐窗读数**无一例外是 15.625 ms 的整数倍**
  （0 / 15.625 / 31.3 / 62.5 / 93.75 / 312.5 / 687.5 …）。先怀疑量具：第一把用的是 PowerShell 的
  `Process.CPU`——同样全是 15.6 的倍数；换成 P/Invoke `GetProcessTimes`（返回 100 ns 单位）**还是**
  15.6 的倍数。⇒ 不是 API 精度问题，是内核把进程 CPU **按时钟节拍记账**，本机节拍 64 Hz ≈ 15.625 ms。
- **为什么值得单独立一条**：m90 那条"空闲 CPU 双臂"的方法论一直是低占用腿的正本，而它**能看见的下限**
  从没写下来过。本轮的预测收益是每窗 0.033 ms（41 拍/s × 0.8 µs）、整腿 ≈0.1 ms，比一把**小两个数量级**——
  于是"跑一对空闲 CPU 双臂"这类候选从立项起就不可能出读数。再叠上共享桌面的噪声（同一支臂两腿
  1,093.75 ms 对 125.00 ms），这类腿在这一台机器上只配回答两件事：**有没有变贵**、**有没有炸**。
- **可复用的三条**：
  1. 动"每拍省一次小调用"这类候选**之前**先算一遍 `预测收益 ÷ 15.6 ms`：不足一格的，
     **判据只能是调用次数**（K118），别把配对 CPU 腿写进"怎么量"——那是给一轮活配一把看不见它的尺子。
  2. 跑了而落在量子/噪声里，就照直写**判不出**，并写清是**尺子**的问题还是**环境**的问题；
     不许拿"方向 2/2 一致"当收益——本轮那 2/2 的差值是预测效应的 640× 与 94×，归账就是假账。
  3. m90 记过的"基线中位 31.3 ms"现在有了新读法：它正是**两格**记账量子。凡引用该数字，
     记住它的分辨率是 15.6 ms，不是 0.1 ms。

### K124 —— 探针与文档里用**行号**当锚点＝自带过期日期：本轮我写完八处引用，同轮自己把它们全弄漂

- **现象**（2026-10-24，m108）：新写的 D3 探针臂处处标注"逐字照 `core/thumbs.rs:143-157`"
  "`ui/filmstrip.rs:195-201 + 259-268`""与 `core/thumbs.rs:34` 同值"——八处。然后本轮收尾时我给
  `Thumbs::put` 加了**六行注释**（把判词钉在代码里，防第三次重做），那八处引用**当场全部指错地方**，
  而且**没有一个门禁会红**：编译器、clippy、两道 scan、j1–j13 都不读注释里的行号。
- **更要紧的一层**：`filmstrip.rs:259-268` 我写的时候就已经是错的——真正的 `lru_prune` 在 232 行。
  行号引用不只是会漂，它**连"当场就对"都不保证**，因为没人复算过。

  不用行号。行号只在**本轮这一次叙述**里用（"改的是第 147 格那一句"），且落盘前后各复算一次。
  与 K71"数字必须有单一正本与复测命令"同一条：锚点也要有能复算的形式，`grep 函数名` 可复算，
  `:143-157` 不可复算。
- **顺手一条**：探针里那句老话"改了生产常量要同步这里，否则臂就不是那条路"（`frame_cost_probe.rs` 头）
  同样管着**引用形状的地方**——臂照抄的是生产的**形状**，形状一挪，臂就在量另一件东西。
