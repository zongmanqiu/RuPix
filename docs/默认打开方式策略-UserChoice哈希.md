# 默认打开方式策略（自算 UserChoice 哈希）

> **定位**：宿主侧「每个图片后缀名能否在本机**默认打开**（双击直接走本程序、不弹选择器）」的策略正本。
> **相关文档**：后缀能力清单（运行时动态并集）见 [`图片格式与后缀名.md`](图片格式与后缀名.md)；
> 机制总纲归 [`架构总览.md`](架构总览.md)。那份回答「图片是什么后缀、谁能解」，本文档回答
> 「知道后缀之后，怎么让双击直接打开它」。
> **实现位置**：`src/platform/association.rs`（宪章「注册表唯一例外 = 文件关联」的唯一落点）。
> 本文档只写结论、证据与判定，**不写体积数字**（体积唯一正本 = 宪章 §4.1）。

---

## 一、结论

每个后缀（含解码器后续新增的格式）都能按同一条链路设为默认打开：

1. **算法帧已确证**：本机盘上 6 组真实 UserChoice 值（5 个图片类后缀 + `.pdf`）被同一套公开算法
   逐字节复现（6/6）。含只由 Explorer 亲手写下的 `.pdf`——开源项目管理方
   （SumatraPDF）的策略是「删键让系统代写」，它自己不写哈希，因此这条样本是系统算法的金标准。
   采集与复现脚本在 `.ex/imgview/_动态证据/`（逆向取证目录，非交付物）。
2. **写入侧按同帧执行**：对每个后缀执行「先删旧 UserChoice 子键 → 新建 → 取**新建键**的
   LastWriteTime（clamp 到分钟）→ 以它为 regdate 算哈希 → 写 ProgId 与 Hash → 通知外壳」。
3. **新增格式的成本 = 零**：关联循环逐后缀处理，输入集合就是运行时「内置 ∪ 解码器自述」
   的动态并集；解码器装出一个新后缀，只是下一轮循环多一个元素，公式、存储结构、写入顺序全不变。

## 二、判定（验收准绳）

某个后缀在系统上就叫「默认打开」，当且仅当满足**全部**四条：

1. 双击该后缀的任意文件：**不弹「选择打开方式」、不弹 UAC、不报未知扩展名**，直接进 RuPix 主窗口；
2. 拉起的进程/窗口是我们；
3. 关联只写 HKCU（`Software\Classes` + `FileExts\...\UserChoice`），系统级或其他用户的默认不被触碰；
   写入自 m314 起**勾选持久**——勾中的后缀记进 ini `assoc_exts`，点「应用」按它写一次。
   **持续维护是另一颗开关**（m315：ini `assoc_heal`，默认关）：开着才有启动满 60 秒后与每
   60 分钟一次的核对，被别的软件或系统改掉就重写回来（机制见 §八）；
4. 失败时如实进结果窗的「手动」栏（同时挂 legacy「打开方式」候选），不谎报成功。

本机 Windows 11 24H2 build 26200 实测（2026-11-10）：算法帧 6/6；写入侧流程按 §四 落地后，
以 §二 第 1 条实机双击验证。

## 三、算法帧（实现依据）

盘上参数（每个后缀一组，filetime 是 UserChoice 子键的 LastWriteTime）：

```
data = (ext + SID + ProgID + regdate + experience + '\0').toLowerCase()
     ext         = '.' + ext（小写，带点，如 ".jpg"）
     SID         = 当前用户 SID（GetTokenInformation(TokenUser) → ConvertSidToStringSidW）
     ProgID      = 注册表里实际写的值（本宿主用 "RuPix.<ext>"；Explorer 经 UI 设成默认时用
                   "Applications\<exe 文件名>"——两种形态的盘上样本都已验过）
     regdate     = %016x of 分钟对齐的 FILETIME；对齐 = ft - ft % 600_000_000
     experience  = "user choice set via windows user experience
                    {d18b6dd5-6124-4341-9318-804003bafa0b}"

buffer = data 编码为 UTF-16LE（含结尾 NUL）
md5    = MD5(buffer)                                   → 16 字节
hash   = Base64( sub_1(buffer, md5) XOR sub_2(buffer, md5) )   → 8 字节 → 12 字符（带 = 填充）
```

`sub_1` / `sub_2` 是两段私有混合（按 32 位字、魔数乘加的 FNV 风格迭代，各输出 8 字节）。
实现要点（`src/platform/association.rs`）：

- 全部 32 位算术必须 `wrapping_*`（溢出即取模，与原机等价）；
- 字长按公式取：`(len>>2 - 1)`，若 `len%4 == 0` 则再减 1（即总是奇数长，尾单品字单独处理）；
- base64 用标准字母表（STANDARD engine），8 字节输出恰为 12 字符、末位一个 `=`；
- 常量与输出被盘上 6 组样本锁死（6/6 逐字节等值），含 `0x13DB0000 / 0x69FB0000 / 0xB1110000 /
  0x16F50000 / 0xF2310000` 等家族魔数——**不需要猜测私有口径，盘上样本就是答案**。

## 四、写入侧时序（现行写法）

```
Legacy 先稳住（顺序要紧：壳 → 候选 → 默认值）：
① write_progid：ProgId 的 shell\open\command + DefaultIcon + 友好名
② 自检：shell\open\command 必须读回非空；读不回 → 回滚 `.ext` 默认值、该后缀失败
   （**悬空默认值比不写更坏**，GIMP 案例 C6/C11 实测）
③ 写 `.ext\OpenWithProgids\<ProgId>` 候选
④ 写 `.ext\(default)` = ProgId（**最后写**，前面任何一步失败都不碰它）
⑤ 写 ApplicationAssociationToasts 抑制「选择默认应用」气泡（失败只记日志）

UserChoice 直写（仅未被 UCPD 保护的后缀）：
⑥ 若后缀在 UCPD 保护名单（.pdf / .htm/.html / .doc…）→ **跳过 ⑦–⑩**，只留候选
   （UCPD 拦删也拦写；删成功写失败会把用户既有默认弄丢且补不回）
⑦ 删旧 UserChoice 子键（RegDeleteKeyExW）
⑧ RegCreateKeyExW 重新创建 UserChoice 子键
⑨ RegQueryInfoKeyW 立即取新键的 LastWriteTime
⑩ 以 ⑨ 的值（clamp 到分钟）为 regdate 算哈希（需 当前用户 SID 与 ProgID），
   写 ProgId + Hash，**读回自检两者一致**；不符退候选（绝不假装成功）
⑪ SHChangeNotify(SHCNE_ASSOCCHANGED, SHCNF_IDLIST)
```

任一步失败：该后缀退回「手动」栏。② 失败时回滚 `.ext` 默认值；⑦ 失败时旧 UserChoice
原样未动（安全）；⑦ 成功而 ⑩ 失败属极端情形（写自己刚建的 HKCU 子键几乎不会失败），
此时只挂候选、让用户手动补一次——**不做「内存备份恢复旧 Hash」**，因为旧 Hash 与旧键的
时间戳绑死，删键后无法原样写回。

**为什么删建而不复用旧键**：旧键的 filetime 已被它自己的 Hash 锁死；用旧键的 filetime 复算
哈希必然对不上它自己的旧值，改任意一个值，Explorer 校验都会判非法并重置（对侧：本机
2026-11-07 的 PS-SFTA 探针负结论的根因在写入侧时序，而非算法无效）。新建键保证 ⑥ 写入时
哈希与键时同源；key filetime 和请求校验的键时的差若跨分钟，以分钟对齐的钳制抹平（60 秒窗口）。

## 五、与 m244 现行态的关系（翻案与不翻案）

- **翻案一条**：m244「带哈希的 UserChoice 一字不动」不再成立。hash 可算且可写；
  「没人打赢过」的旧共识源自本仓 2026-11-07 探针的负结论，其根因是写入时序（§四），
  不是算法无效（§三 已反证）。探针判负与本轮判胜同时记入
  [`HISTORY.md`](../HISTORY.md) 与 [`踩坑记录/`](踩坑记录/)——负结论也要留着。
- **翻案二条**（m314，m315 收窄）：下面「不翻案」里的**永不后台复查**也不再成立——用户 2026-11-11
  拍板改成**勾选持久 + opt-in 自愈**（§八）：核对与重写只在 ini `assoc_heal`（默认关）被用户
  主动勾上时才发生。覆盖式写入与「只写不撤」仍然成立；取消勾选 = 退订，不撤销。
- **不翻案（继续成立）**：
  1. 注册表只写 HKCU，永不碰 HKLM；写入的键与值全部只在上文两棵树里；
  2. 覆盖式写入、不提供摘除（覆盖语义系用户口径）；
  3. 带哈希但已经是 RuPix 的默认（`Applications\<exe>` 或 `RuPix.<ext>` 两形态之一）→ 不 churn、
     计「已默认」（**但 legacy 三件套会补齐**：自愈把 `.ext` 默认值 / command / 图标 / 候选
     任一项缺失都算破损，不补就是"判破 → 零写入 → 下一轮还破"）；

## 六、体感边界（如果后面真要打）

- 本轮落的是「文件关联窗点『应用』后**首轮胜利**」：哈希与键同一分钟写入，Explorer 校验通过，
  双击直接打开。
- Explorer 只在**用户使用**时才校验哈希（写盘当时不校验）；因此第 ①②③ 步之间跨分钟率极低，
  但校验在下次双击才发生——这正是两轮探针结论相反的阈值所在，也是本策略上探针的原因。

## 七、维护与核对

- 复算脚本：`.ex/imgview/_动态证据/fit_hash_frame2.py`（6/6 判据）；
  样本采集：同目录 `collect_userchoice_live.py`。
- 何时必须跑：Windows 大版本更新、用户 SID 形态变化（造样本常是内网机器的 sid 结构）、
  experience 字符串变化后——重新采集 3–6 个盘上样本，跑 fit，6/6 才重钉本文档。
- 写入侧改动验收：拿一个真实后缀跑 §二 第 1 条的端到端「双击」，不是只看注册表有值。
- 策略定稿时在 `HISTORY.md` 补「哈希战探针重开」条目回应旧探针负结论。

## 八、勾选持久 + opt-in 自愈（2026-11-11 m314 建、m315 收窄）

「点一次写一次」已被推翻：用户勾的选择会落盘。但**「记住我想要什么」与「允许程序反复动注册表」
是两件事**，后者必须由用户显式打开——`assoc_heal`（默认 **关**）。

**两张表，两个层，加一颗开关。** 「保持默认」这件事的**意图**住 ini（`assoc_exts`，分号分隔的
后缀表），系统当前的**事实**住注册表。分开存，所以"我勾了什么"重启后还在；反过来，系统里被改成
什么，不影响我勾了什么。第三样是**授权**（`assoc_heal`，默认关）：只有它开着，运行期才会去核对
与重写；关着就只在点「应用」时写一次。

★ 为什么必须 opt-in：自愈分不清「别的程序抢走了默认」与「用户在系统设置里主动改成了别的程序」
——两种都是系统 API 写的合法哈希。勾一个后缀只表达"我希望它是 RuPix"，不等于授权"以后每次被改
都抢回来"。用户 2026-11-11 拍板：这是用户的选择权，界面上一颗默认不勾的开关，不许默认替用户做主。

**执行范围 = 勾选表 ∩ 当前可用后缀。** `formats::declared_exts` 本来就过滤掉被关闭与已卸载的
解码器，所以解码器关掉后它的后缀自动不参与维护；但**勾选本身不删**——一开一关不能丢用户的勾选。

**时间门**：启动**不**立刻查（头十秒里字体扫描 ~0.9 s、DLL 首扫、首屏解码、两轮工作集裁剪都在
抢），启动满 **60 秒**首查，之后每 **60 分钟**一次。实现在 `runtime::assoc`，写入在后台线程
（`SHChangeNotify` 那一声会让资源管理器重读关联，落在 16 ms 的帧里就是可感知的卡顿）。
开关关着时**不**推进时间戳：用户中途勾上，下一帧就放行，不必再等一小时。

**核对五项**（只读；任一项不过才重写，正常态零写入）：

1. `.ext\(default)` == `RuPix.<ext>`；
2. ProgId 的 `shell\open\command` 指着**当前** exe（换目录 / 升级后路径会漂）；
3. ProgId 的 `DefaultIcon` 同上；
4. `.ext\OpenWithProgids` 里挂着我们；
5. UserChoice 若存在：ProgId 指我们，且 Hash 与「现键 LastWriteTime + 当前 SID」自洽
   ——哈希就是这个键自己的盐，算得回来说明没人动过它。

另外**单独核**能力登记（`RegisteredApplications` / `Capabilities\FileAssociations` /
`SupportedTypes`）：它不影响双击打开，只影响系统「设置 → 默认应用」里看不看得到我们，
但被清理工具抹掉后不会自己回来。

**两样刻意不算破损**（否则会退化成"每小时重写一遍关联"）：气泡抑制值（纯体验，缺了只多弹一次
提示）与能力登记（单独核、单独修）。

**取消勾选 = 退订，不撤销。** 撤销要知道还原成哪个程序，我们不知道；删掉只会把用户推到
"双击弹选择器"的更差状态。

**一个已知的不可分辨**：自愈分不出「别的程序抢了默认」与「用户在系统设置里主动改了默认」——
两者都是系统 API 写的合法哈希。所以它是一把双刃的刀，**只能由用户主动打开**（`assoc_heal`）；
打开后每次抢回写一行 `[assoc] 自愈：…` 日志，方便事后翻。

## 九、明确不做

- ~~不做后台扫描 / 开机轮询~~ —— **2026-11-11（m314）用户推翻**，改为勾选持久 + 定时自愈（见 §八）。
  仍然不做的：开机自启、常驻独立进程、**启动那一刻的前置检查**（代价是"启动后 60 秒内被改掉
  要等下一轮"）；
- **不做默认开启的自愈**（m315 用户拍板）：开关默认关，必须用户自己勾。勾了后缀不等于授权抢回。
- 不做「卸载条目删掉写回对应 ProgID」的完整撤销——覆盖语义就是用户口径；取消勾选只是退订（§八）；
- 不错的承诺：任何写入失败都兜底 legacy 候选 + 结果窗「手动」栏，绝不静默。
