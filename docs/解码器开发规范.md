# 宿主侧解码器 ABI 对接说明

> 本文只讲 **RuPix 宿主如何消费解码器 DLL**，不复制解码器的开发教程。
> 契约结构体与常量以宿主快照 `vendor/rupix-abi/src/lib.rs` 为准；宿主不链接解码器仓库的源码或文档。

## 1. 边界

- 位图解码 100% 在解码器 DLL 内；宿主不内置任何位图解码库。
- 唯一例外是 SVG/SVGZ：矢量需要按视口重渲染，走宿主内置 resvg。
- 解码器是独立编译的 `cdylib`，跨边界只允许 C ABI：扁平函数 + `#[repr(C)]` 结构体。
- 宿主不 import 解码器 crate；`core::decode::DecodeBackend` 是宿主侧接口，`decoders::Host` 实现它。

## 2. 版本

- 当前 ABI 主版本：`IV_ABI_VERSION = 6`，最低可接受：`MIN_ABI_VERSION = 5`。
- **v5 是签名冻结下界，v6 只做加法**（新增可选导出 `iv_render_region` + 新结构体 `IvRegionReq` + 能力位 `CAP_REGION`，v5 的签名与结构体布局逐字节未动）⇒ v5 老 DLL 不必重编，v6 宿主照常收载。下界不许抬。
- 装载时读 `iv_abi_version()`；低于下界或高于宿主版本一律拒载（兼容是单向的：老 DLL 上新宿主可以，新 DLL 上旧宿主不行）。
- ★ **兼容性立约（永久条款，2026-10-28 用户拍板）**：**ABI 永远兼容旧版本 DLL，新 ABI 不得影响旧 DLL 的运行** ⇒ 宿主升级后旧 DLL **不需要重编、不需要重传**。已发布导出签名 / `#[repr(C)]` 结构体字段 / `ERR_*`·`PF_*`·`CAP_*`·`REQ_*` 编号**只增不改号**；新能力只加可选导出 + 新结构体 + 新位值；`MIN_ABI_VERSION` 永不抬；**"改结构体再 bump"已禁止**（会作废全部旧 DLL）。机器守约见契约仓 `tools/check_abi_freeze.py`（冻结基线 `tools/abi_freeze.txt`）。
- 结构体布局由编译期 `size_of` 断言钉死：
  - `IvDecoderInfo` = 48 B
  - `IvRenderReq` = 24 B
  - `IvRenderOut` = 48 B
  - `IvMetadata` = 24 B；`IvMetadataField` = 16 B
  - `IvRegionReq` = 40 B（v6 新增）

## 3. 导出

必需：

| 导出 | 作用 |
|---|---|
| `iv_abi_version() -> u32` | 自报 ABI 主版本 |
| `iv_decoder_info() -> *const IvDecoderInfo` | 自述 id / 名称 / 说明 / 扩展名 / 是否矢量 |
| `iv_probe(path, ext) -> i32` | 按路径/内容判断是否认领 |
| `iv_render(...) -> i32` | 两阶段渲染：查询 + 写像素 |
| `iv_last_error(buf, cap) -> usize` | 线程局部最近错误 |

可选：

| 导出 | 作用 |
|---|---|
| `iv_render_raw(...)` | 裸像素（无头/无魔数）参数化解码 |
| `iv_caps() -> u32` | 能力位图；缺席时宿主按既有字段推定 |
| `iv_metadata()` | 可扩展元数据键值表 |
| `iv_export_svg(...)` | 导出内嵌/等价 SVG（矢量侧） |
| `iv_render_region(...)` | 按区域重渲染（v6 新增，配套 `CAP_REGION`） |

`iv_last_error` 是线程局部、只反映**当前解码线程最近一次调用**的错误；宿主拿到非零返回码后再取。

## 4. 内存所有权

- 查询阶段：宿主以 `out = NULL` 调 `iv_render`，解码器只填 `IvRenderOut`（真实尺寸、`bytes_needed`、`pixel_format`、`bit_depth`、`orientation`、动画/分页、`icc_len`）。
- 宿主一次性分配 `bytes_needed + icc_len`（无重试），再把缓冲交给解码器写。
- 解码器只写入，不得释放、不得替换、不得跨边界传 `String`/`Vec`/泛型/trait object。
- 这样彻底规避跨 DLL 分配器/CRT 的 `free` 崩溃。

## 5. 路由与能力

- 路由输入是 `(扩展名, 能力位图)`，不是解码器身份。
- 宿主先按扩展名找候选，再按内容魔数嗅探兜底；失败分三类：
  - `NotClaimed` / `Unsupported`：让位给下一个候选；
  - `Hard`：损坏/过大/panic，立即中止，不再下探。
- 能力位：
  - `CAP_FULL`：能出完整尺寸；
  - `CAP_SCALED`：支持原生降采样（**只能由解码器显式声明，宿主不从缺席推定**）；
  - `CAP_RAW_PARAM`：支持 `iv_render_raw` 的裸像素参数；
  - `CAP_VECTOR`：矢量解码（整幅按 target 重画）；
  - `CAP_REGION`（v6）：支持 `iv_render_region` 区域重渲染，缺席 = 宿主不发区域请求，**不是错误**。
- `REQ_ALLOW_SCALED` 是单次请求意图位：缩略图/首屏/预读可以点亮，原图档升级与同图重解显式关掉。
- 宿主不维护“哪个 DLL 支持什么格式”的静态清单；格式清单 = 内置登记表 ∪ 各启用 DLL 的 `iv_decoder_info().extensions` 动态并集。

## 6. 线程与失败

- 宿主只有一条解码线程，串行调用；解码器需可重入，但不必 MT-safe。
- 解码器不得自建线程池。
- 每次 FFI 调用都过宿主 SEH 闸；panic 由 `catch_unwind` 转成失败结果。
- 解码器 panic 三振出局进会话黑名单；`--safe-mode` 不加载任何解码器。
- 隔离栈只拦“崩”，不拦“卡”；输入字节必须“推进且线性”，递归/交叉引用要 visited 去重，轮数上界取自文件长度。

## 7. 文件与自述

- 产物命名：`<id>_<ver>.dll`；同 id 只留一份。
- 目录里只有 DLL，没有清单/指针文件；id、名称、说明、扩展名全在 DLL 的 `iv_decoder_info()` 内。
- 宿主不读独立 JSON 清单来认解码器；在线索引只用于下载/版本比较，装完仍以 DLL 自述为准。
