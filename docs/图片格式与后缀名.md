# 图片格式与后缀名（宿主路由规则）

> **定位**：宿主侧「后缀能不能开、怎么路由」的现行正本。
> **数据来源不是手工维护的清单**：运行时 = 宿主内置登记表 `core::formats::BUILTIN_DECODERS`
> ∪ 各解码器 `iv_decoder_info().extensions` 的动态并集。**解码器的清单、选型与速度账归独立仓库
> `RuPix-Decoder/workspace/decoders/README.md` + `decoders.json` + 各档 README/HISTORY；宿主只认 ABI 与请求类型，
> **不记录具体 DLL、也不维护第二份清单**。
> 解码路由与分层见 [`架构总览.md`](架构总览.md)；解码器契约与导出签名见
> [`解码器开发规范.md`](解码器开发规范.md)；坑的完整分册见 [`踩坑记录.md`](踩坑记录.md)。
> 历史选型底账（`HISTORY.md` 与 `docs/踩坑记录.md`）是决策记录，**不是本表的数据源**。
> WIC 曾判弃，m56/m57 以「只走点名」的内置库回归；**2026-10-25 用户裁决整层删除**——
> 便携看图器不调系统解码器。今天宿主内置只有矢量那一条路，位图一律交给解码器。

---

## 一、能力来源的全部分支（只有两类，没有第三条路由）

| 来源 | 认领的扩展名 | 解码实现 |
|---|---|---|
| **宿主内置** `core::formats::BUILTIN_DECODERS`（`auto_claim=true` 的那几行） | `svg` `svgz` | `ui::svg::decode`：windui 内置的 resvg（usvg + tiny-skia），`svgz` 由 usvg 透明解压 |
| **解码器 DLL**（`<exe 目录>/decoders/`，数量不固定） | 各 DLL `iv_decoder_info()` 自述（运行时动态并集） | 各解码器内的解码库，两阶段 ABI 由宿主编排 |

四条规则：

1. **目录清单 = 内置 ∪ 启用解码器自述的并集**（`gallery::is_image_ext_in` / `known_exts`，
   `to_lowercase` 后比对，大小写不敏感）。装了解码器该后缀才出现，卸掉/关掉就消失——
   **能力与清单物理上不可能脱节**，没有第二份需要人工维护的全局表。
2. **没有系统级自动兜底**：宿主内置只有矢量（resvg）一条路，**位图一律交给解码器**；
   上一版登记在册、只接受用户点名的 WIC 于 2026-10-25 整层下线。
   认不出 = 报错（`Fail` 三分类决定要不要花一次魔数嗅探兜底，见 §五）。
3. **矢量与位图的分工**：解码器只输出 RGBA8 位图 + `orientation` 元数据（EXIF 1..8）；
   旋转 / 镜像 / 缩放 / 平移全部由宿主统一处理。SVG 必须按**可视区域 1:1 光栅化**才有
   无损放大，所以它走宿主而不是位图解码器。
4. **无魔数格式靠扩展名参数**：`iv_probe(data, len, ext)` 拿到扩展名才认得出 TGA 这类格式；
   `ext == NULL` 时解码器只按魔数认领——显式打开一个改过名 / 没有扩展名的文件时靠这条兜底。

## 二、能力表不在宿主文档里

「哪种后缀由谁解码」= **运行时**各启用 DLL `iv_decoder_info().extensions` 的并集。
宿主**不维护、也不允许维护第二份清单**：新增 / 替换 / 合并解码器一律改独立仓库
`解码器仓库`（单库源码 `workspace/singles/<id>/`，发布档装配 `workspace/decoders/<tier>/`），
宿主一行不改、不重编。

要查当前清单，读这三处之一（都是同一份动态结果的视图，不是人工表）：

1. `rupix.exe` 设置 →「解码器」页 →「首选解码器」卡（按实扫 DLL 的结果生成）；
2. `RuPix-Decoder/workspace/decoders/README.md` 的八档表与各档 `README.md`；
3. `RuPix-Decoder/decoders.json`（发布清单；宿主随包复制成 `docs/decoders.json`，下载时按 id / 版本 /
   abi 认定——**清单不记哈希**，2026-11-02 用户口径：官方产物只认名称与版本号。
   装完宿主还要读自述核对 `iv_decoder_info().id`，对不上不落盘。）

宿主自己的两条**内置**路径（它们不是解码器，不入上面的动态并集）：

| 内置库 | 后缀 | 实现 | 路由 |
|---|---|---|---|
| resvg | `svg` `svgz` | windui 内置（usvg + tiny-skia） | `auto_claim=true`，默认认领；按可视区域 1:1 重渲 |

> 表里**只有一枚**是刻意的：位图解码库一条都不内置（2026-10-25 裁决，WIC 整层删除）。
> 理由与宪章 §5.1 同一条——调系统解码器会让同一张图在两台机器上解出不同结果。

### 2.1 `.raw` 双认领的仲裁（按请求类型，不按解码器名）

`.raw` 既可能是相机 RAW，也可能是裸像素 dump；光看后缀与内容都可能分不出来。
宿主**按请求类型**选解码器（`decoders::select_candidate` 的 `require_caps` 能力位图）：

| 路径 | 候选要求 | `.raw` 实际走向 |
|---|---|---|
| 常规打开（`try_decode`） | 任意认领者，按 DLL 路径字典序取第一个 | 能按魔数认领相机 RAW 的实现 |
| 参数窗给了宽/高/布局（`try_decode_raw`） | **必须导出 `iv_render_raw`** | 声明 `CAP_RAW_PARAM` 的实现 |

判据是解码器自带的能力（有没有 `iv_render_raw` / 能力位），**不写 `ext → 解码器 id` 的优先级表**——
那会变成必须人工维护的第二份清单。

> **例外：用户显式首选**。设置窗「解码器」页的「首选解码器」卡（`rupix.ini` 键 `decoders_preferred`）允许按
> 后缀点名首选解码器，越过路径字典序——这是用户显式维护的**稀疏覆盖表**（只覆盖用户
> 点过的后缀），条目失效（解码器卸载/停用/不认领该后缀）静默回退上面的自动仲裁；
> 它不是那份被反对的全量人工清单。软失败后的嗅探让位链不受首选影响，仍作默认托底。

### 2.2 新增一种格式的落位

| 想做的事 | 需要动 | 不需要动 |
|---|---|---|
| 新增图片格式 | `RuPix-Decoder/workspace/singles/<id>/` + 接进 `workspace/decoders/<tier>/`，`build.ps1` 发布 | 宿主 exe |
| 替换某格式的解码库 | 对应单库 crate 内部 | 宿主、ABI |
| 优化解码性能 | 解码器内部（热循环 crate `opt-level = 3`，单库 workspace 默认是 `z`） | 宿主 |
| 宿主交互 / UI / 缓存 | `main/src` | 解码器 |
| 裸数据参数化解码 | ABI 可选导出 `iv_render_raw`（不 bump 版本，宿主 `GetProcAddress` 探测） | ABI 已冻结部分 |

按族合并解码器而不是每格式一个 DLL：空 cdylib 实测约 **101 KB** 固定开销，且依赖**不跨 DLL 共享**
（每个 DLL 各带一份 Rust 运行时），每格式一个 DLL × 20 就是约 2 MB 纯开销。

## 三、裸数据参数化（`iv_render_raw`）

无魔数的裸像素 / YUV 数据**必须给定宽高与布局才能解**，因此走一条参数化路径：

- **触发**：只有真正无头的裸像素后缀（`bgra/gray/gry/i420/nv12/rgb/rgba/uyvy/yuv/yuy2/yv12`）
  走这条路径；相机 RAW（CR2/CR3/NEF/3FR…）有完整头，仍走普通解码，不弹参数窗。
- **首开自动**：后缀决定布局（`.bgra`=BGRA8、`.gray`=GRAY8、`.yuv` 默认 I420），文件长度
  用常见宽度反推整数高度；推得出就直接打开，推不出才弹参数窗。用户不满意时从右键
  **「RAW 参数…」**重开参数窗修改；确认后 `Config.raw_last` 记住上次取值。
- **空格预览走同一条推断**：预览没有参数窗可弹，推不出宽高就静默不出窗（不打断用户）。
  准入（`core::formats::is_previewable`）**不按裸像素后缀预判**——它只回答"有没有解码器认领
  这个后缀"，"这个文件解不解得出"由上面那次推断现场判。拿后缀当代理的代价是
  "双击开得开、按空格没反应"（`.raf` / `.uyvy` 两轮实测，见 K184）。
- **常驻但按格式置灰**：右键「RAW 参数…」始终在「打开…」下面；只有上述无头后缀可点，相机 RAW 与普通图片置灰（避免误触，也保证入口永远找得到）。
- **布局**：复用 ABI 的 `PF_*` 枚举作输入布局，含 `PF_BGRA8` 与 YUV
  （YUY2 / UYVY = packed 4:2:2；I420 / YV12 / NV12 = planar 4:2:0，BT.601 limited range）；
  **输出恒为 `PF_RGBA8`**。非偶尺寸或字节数与声明不符 → `ERR_CORRUPT`。
- **改参数即重开**：同一路径的参数可变，而会话内的邻图预读只按**路径**记账，所以参数窗确认后
  走一次完整的 `open()`——旧预读连这批一起作废（见 `core::viewer::open`），不给"上一个参数
  解出来的位图"命中的机会；裸数据解码本身微秒级，重来一次不心疼。
- **支持清单也是动态的**：某扩展名没有解码器给它实现 `iv_render_raw`，它就不进参数窗路由。

### 3.1 无法生成 / 不公开样本的格式

测试语料生成器对以下格式保留**解码支持**，但不生成公开样本：

| 后缀 | 说明 | 语料策略 |
|---|---|---|
| `.crm` | Canon Cinema RAW Light，本质是 RAW 视频容器，不是静态图片 | 仅 local-only；公开 corpus 不含 |
| `.qtk` | Apple QuickTake 100/150 的静态 RAW；无 CC0 样本 | 仅 local-only；公开 corpus 不含 |

不得用 0 字节文件、改名 DNG 或其它假容器占位。以后新增任何无法生成或无法公开再分发的格式，必须在
`RuPix-Decoder/testdata/GENERATION_EXCEPTIONS.md` 和
`RuPix-Decoder/testdata/corpus/registry.py::GENERATION_EXCEPTIONS` 同时登记；
`RuPix-Decoder/testdata/tests` 会检查两边一致。

## 四、不支持 = 动态并集之外

判定只有一条：**运行时没有启用解码器认领这个扩展名**（内置只有 `svg` `svgz` 那两枚矢量后缀）。
宿主不保存静态的"支持/不支持"清单，原因与 §二 相同：解码器是独立仓库里可替换的商品，
合并、换库、追加格式都会让静态表当天过期。

想确认某个后缀能不能开：看设置 →「解码器」页的「首选解码器」卡；想知道**为什么某个格式还没做**，去
`RuPix-Decoder/workspace/decoders/README.md` / `decoders.json` / 各档 README/HISTORY；要不要做新格式的决定进
`docs/待办.md`，不写进本表。

## 五、实测坑摘要（与现行行为相关，完整条目见 [`踩坑记录.md`](踩坑记录.md)）

| # | 坑 | 现象 / 根因 | 对策 |
|---|---|---|---|
| 1 | 查询阶段必须回报**真实**尺寸 | ABI 是"查询→宿主一次性分配→渲染"两阶段，**没有重试**；解码器在查询阶段谎报尺寸（HEIF/AVIF 容器的 `ispe` 会撒谎，且报的是旋转前尺寸）→ 渲染阶段越界或尺寸错 | 解码器查询阶段回报转正后的实际宽高与 `bytes_needed`；宿主按 `budget_bytes`（= `MAX_PIXELS`×4 字节）与 `MAX_PIXELS`（41MP）在查询与渲染两侧校验；SVG 另有 `MAX_EDGE`（16384）边长上限 |
| 2 | 相机 RAW 元数据会撒谎 | compressed RAF 声明的白电平远高于实际峰值 → 按元数据归一后全黑 | raw 解码器按**观测峰值**兜底重归一 |
| 3 | `jxr` 必须锁 `=0.2.1` | 不带上界的写法会解析到要求 rustc 1.99.0 的版本（本机 1.97.0）→ 编译期直接拒绝 | `jxr = "=0.2.1"`；引库别用裸 `"*"` 或不带上界的 caret |
| 4 | crate 名撞车 | `xpm`（包管理器）、`ani`（动漫命令行工具）、`dpx`（Dropbox 客户端）、`ras`（AirPlay 服务）——名字对上不等于库对上 | 判定"能不能解这个格式"必须看 `description` 与 README |
| 5 | 库"已选定"不等于"已验证" | 解码正确性 / 速度 / 覆盖率必须逐库实测；有些库没有编码器（无样本就构造不了往返测试） | 引库前先拿真实样本跑通 `decoder_smoke`，再更新本表 |

## 六、核对与维护

```bash
# 端到端冒烟：宿主从 .build/decoders 加载真 DLL → probe → 两阶段渲染 → 像素校验
cargo run --release --example decoder_smoke -- ..\..\.build\decoders\*.dll
cargo run --release --example core_smoke

# 单文件直连同一条解码链路（成功打印 OK，失败退出码 2）
rupix.exe --probe-decode <文件>          # 装不上解码器时先试 --safe-mode

# 解码器工程一键：编译 + 测试 + 发布到 .build/decoders（测试失败不发布）
powershell -NoProfile -ExecutionPolicy Bypass -File .\build.ps1   # 在 解码器仓库 下执行
```

- **新增 / 改动解码器自述**：改 `解码器仓库`，跑那边的 `build.ps1`（含认领门禁 `check_claims.py`）；本表**不再**逐解码器登记。
- **接入新解码库**：把坑记进 [`踩坑记录.md`](踩坑记录.md)，选型理由记进 `HISTORY.md` 与解码器仓库自己的选型记录；横向评测工具在宿主 `examples/` 与解码器仓库内部。
- **格式支持范围的取舍**（要不要做某格式）：进 `docs/待办.md`，不写进本表。
