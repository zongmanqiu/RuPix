### K125 —— "这行写在每帧的路径里"不等于"这笔钱每帧都在付"：连着三条候选都栽在同一句前提上

- **现象**（2026-10-23→24，m107 / m108 / m109 三连）：m96 那份源码优化清单里"每拍 / 每帧做 X"这一类条目，
  三条被实测推翻了三条前提——
  ① **O13③**：写"每拍一次 `format!`"，真 shape 是 `Hub` 会话级单例、只在**首次开设置窗**时建，
  所以是"开过设置窗之后每拍、且关窗照跑"，不是从启动每拍；
  ② **O14①**：写"（LRU 淘汰）在每帧插入里"，真 shape 是 m100 起命中走 `get_mut`，**命中根本不碰淘汰**，
  插入只在新图进表那两刻走；
  ③ **O15**：写"每帧克隆 `Option<String>`"，听起来像每帧一次分配——**`None` 的克隆不碰堆**，
  常态那一档实测 1 ns 量级（一次判别式拷贝 + 一次跨模块调用），只有画面中央真摆着错误句那一档才有一次
  45–59 ns 的分配。
- **共同形态**：三条都是从**代码位置**推**成本存在**。位置只对"这行会不会被执行"说话，不对
  "这行走下来花不花钱"说话——中间隔着状态、前置闸、以及"这个类型的克隆到底做不做事"。
- **立新规矩：这类条目在算单价之前先答三问**，答不上就先量、不许先记账：
  ① 它在**什么状态**下才 fire（有没有"开过某窗 / 有没有某种数据"这种开关）；
  ② 那一帧/那一拍**真走到这行吗**（前面有没有闸：`window_open`、`contains_key`、`is_none` 早退）；
  ③ 这行在**常见输入**下到底产不产生分配/系统调用（`Option::clone`／`Arc::clone`／整数包装的
  "克隆"字样常常是零成本的，名字里有 `clone` 不等于有钱要付）。
- **入账的两条常数**（本轮 `examples/frame_cost_probe.rs` 的 D4 量出来的，跨模块 `#[inline(never)]` 口径）：
  `Option<String>::clone()` 于 `None` ≈ **1 ns、不分配**；于 `Some(42–111 B)` ≈ **45–59 ns**（一次
  malloc + memcpy + free）；`as_deref()` 两种状态都是 **0.5–0.7 ns**。
  ★ 一句提醒：拿"每帧"当收益口径时，先把它服务的那件事的工作量当**分母**——同一臂集合里
  `draw_text` 那句错误文案是 0.105–0.222 ms，50 ns 占它 0.025%~0.039%，这才是"值不值"的读法。
- **同类**：K118（计数账不许折算成毫秒）、K123（收益 ÷ 尺子量子先算一次除法）、
  K81（两臂对照里"快了"可能只是少做了一步）。
- **补充（m110 · O16）：三问答完"真在付"之后，还有第四问——省的那一档与付出去的那一档各是多少。**
  O16 是 K125 三问第一次答出"真在付"的一条（装档每帧一次 `PathBuf` 克隆 + 一次哈希插入，29–116 B 键长实测
  236–464 ns），于是顺手加了"值没变不写"的门闸去量它——结果两档分开读出来是：
  **同值重复那一档省 +77 ~ +100 ns**（动画 21.7 帧/s 摊＝+1.7~2.2 µs/s），
  而**键不存在／值真变那一档多付 +144 ~ +429 ns**（正落在翻页与首开那一路）。
  ⇒ 只报第一档就是做偏账：**"能省"不等于"该改"**，一条改动的净效果要看两档各占多少次，
  而占比没数过 ⇒ 本轮判废（"判据不足以支持改"比"收益太小"更硬）。
  ★ 两条从读数里读得出的形状：多付那一档**随键长上升**（29 B +144 → 116 B +429 ns，与"多一次整键哈希"同向，
  但没单独拆量，不许当结论引用）；省那一档**不随键长走**（三档都 ~80–100 ns，省的主要是分配器与写表，
  不是 memcpy）。





### K126 —— 探针复刻了生产的私有函数，就欠它一枚"拿真产物比语义"的钉子（而且钉子的活性要证一次）

- **现象**（2026-10-24，m111）：`core::gallery::natural_key` 与 `sort_natural` 都是**私有**的，
  `examples/` 够不到，于是仓里同时躺着**三份复刻**（`bench_gallery_sort`、`bench_dir_listing`、
  本轮新增的 `frame_cost_probe` D6 两臂）。两份复刻头顶写着"改了生产必须同步，否则基准测的是错的键"——
  这句话是**纪律**，不是**检查**：没人拦得住漏改的那一次，而漏改的后果是"读数很漂亮，量的却是另一条路"。
- **这一轮真的差点走进去**：D6 第一版的臂排序自己补了一层 `then(原名)` tie-break，看着比生产更"稳"，
  **但生产用的是稳定 `sort_by` 只比键**。合成册里键相同的两项（第 4 形只有 16 个不同名字、重复近 200 遍）
  在这两种比较器下顺序可以不同 ⇒ 臂与生产**不同形**，而两臂之间照样"完全一致"，读数一点都看不出来。
- **立法（落地形态，不是口号）**：复刻型量具必须配一枚**对生产钉子**——用**真产物**（公开 API）
  把语义比回来：本轮＝系统临时目录**真造 12 个刁钻文件**（大小写同段 / 前导零 / 无数字段 /
  超 20 位 parse 兜底 / 中文段 / 纯数字名），调**生产** `Gallery::from_file` 读回顺序，与臂的顺序**逐项 assert**。
  三条附属判据一条都不能省：
  1. **钉子必须先证明它会红**：故意把生产的零填充拆掉（`{num:020}` → `{num}`）重跑，
     当场红并报出 `img10` 排在 `IMG2` 前那条例子；还原后绿。
     **没做过这一步的"钉子"只是一个永远为真的 assert**（与 K122 同一族：测的和跑的必须能分开）。
  2. **夹具依赖的外部条件没挂上必须炸，不许空跑**：`.png` 由**解码器**认领（wic 是 `auto_claim=false`，
     进不了清单），钉子前不 `install_format_source()` 就得到一张**空册**——空册里"逐项相同"自动成立，
     量具绿得毫无内容。现在它是 `panic!("生产清单读不出（解码器目录没挂上？）")`。
  3. **臂的循环与比较器逐字照生产**，改一处就同步一处；复刻份数在文档里点名（本轮三份全同步），
     并把"不跟着改会怎样"写清（键相同、**分配次数不同** ⇒ 基准量的还是落地前的成本形状）。
- **端点口径顺带一条**：µs 级的改动在 GUI 上读不出，但**真目录基准能读**——`bench_dir_listing` 的
  **A 臂直接调生产** `Gallery::from_file`（真 3401 项，枚举 + 过滤 + 排序整段），本轮改前 min 4.2/4.0
  → 改后 3.4/3.5 ms，两对四个口径全正。⇒ "换过产物就要端点重测"这条在纯 CPU 项上同样适用，
  优先找**能直调生产公开 API 的既有量具**，别只用复刻臂。

### K127 —— µs/ms 级候选的裁决必须写成"单价 × 命中率"：只报单价会把"4% 路径上的 1 ms"说成"每次开图的 1 ms"

- **现象**（2026-10-24，m111 收口 → m112 更正）：给 O10（ICC 变换句柄缓存）写判词时我落的是
  "上限 ≈ 1 ms/张 ⇒ 摊在 100 ms 量级的开图上是 1%"——**单价有实测**（`icc_transform_cost`：1×1 固定开销
  **1.07 ms**、512² 整趟 **2.34 ms**），但那个 1 ms 只发生在**带嵌入 ICC 的图**上，而这个比例我当时没数。
  下一轮补量具（`.temp/m112_icc_scan.py`，只读头部）：**外部真图 3792 枚里 153 枚带档 = 4.0%**
  （jpeg 57/383＝14.9%、png 129/3115＝4.1%、bmp/gif **0 枚**；我自己造的 ICC 夹具那一目录 93.5%，**单独剔除**）
  ⇒ 摊到每次开图是 **0.04 ms**，不是我写的 1%。**同一天里在同一张表上更正自己那句**，并在 本仓历史记录
  的结案处写明"★ 就地更正"。
- **算术形式**（这条区别于"先测命中率再提新闸"的地方）：裁决值 ＝ **单价 × 命中率**，两个因子都要有读数，
  缺一个就只能写"未测"、不能写百分比。单价容易有（探针量一次就在手），命中率容易缺（它要一个**语料扫描**，
  不是计时循环），所以这一族错误反复出现。写判词时的自查句式：
  **"这个 ms 是每张都有，还是每 100 张有一张有？"**
- **顺带两条边界诚实**：① 判"嵌入档＝sRGB"我用的是色度参数字节全同（wtpt/rXYZ/gXYZ/bXYZ + 三条 TRC），
  这是**下界**——Adobe 常写 parametric TRC，数学相同而字节不同；② `desc` 标签我只解了 `desc`/`mluc` 两种形态，
  188/196 读成空串 ⇒ 只当旁证、不进判据。两处都不影响裁决（放宽到极限＝"全部带档都算 sRGB"，仍是 0.10 ms），
  但**必须写在读数和之间**，否则下一个人会把 6.1% 当成精确值引用。
- **判废的写法**：结案处要留下"重开的先决条件"且写成**可证伪的一条**（这里＝真实用户语料带档率 ≥ 30%），
  而不是"以后再说"。

### K128 —— 断言"哪一层贵"之前先按层夹表：O21 的直觉与实测方向相反

- **现象**（2026-10-24，m113）：D 档 O21（"整窗标脏、没有脏区"）挂着"要先有每帧图元数/合成面积的读数"，
  而它的前提——"脏区省下的是**重画大图**的钱"——从 m96 起就是**直觉**：图是画面里最大的一块，所以它最贵。
  三行分层夹表（`ui::canvas::ImageCanvas::paint` 的既有分层注释处插桩，A＝底+图+鸟瞰 / B＝悬浮+胶片条，
  每 0.5 s 一行 `[paint]`）出来是反的：**800×600 每帧 A 段 0.50–1.25 ms，B 段 1.9–2.8 ms，
  其中悬浮层单独就 0.94–2.05 ms**。A 段里"图与上一帧一模一样"的部分（脏区唯一能省的）上限只有
  **3.3 ms/秒＝单核 0.33%**，而改法要动 `.3rd` 的软/硬两后端 ⇒ **判废**。
- **根因（判断的顺序错了）**：我按"面积最大＝成本最大"排序候选，而画布的成本还跟**图元种类**
  （`draw_image` 比 `fill_rect` 贵约 88×，见 A5/追加那组读数）与**每帧做的事数**（悬浮层每次要排文案、
  描双层框、画箭头）有关。面积只是其中一个因子。
- **可复用的一句**：给"某一层贵"下结论之前，先**在既有分层边界上插一道秒表**，读出
  **每层 ms × 该层真的变了的比例**（后者是 K127 的命中率那一列）；两个数都拿到才谈改法。
  自查句式：**"这块钱在哪一层？"**——不是"这块钱大不大"。
- **配套一条卫生**：插桩用完必须**拆干净并证明拆干净**。本轮按 `canvas.rs` 回到快照态（`diff -q` 对
  历史快照）＋重链后与出货那枚 **`.text` 差异 0 字节**（K108 的段级尺子）两道一起收，
  不靠"测试还是绿的"。台账放 `thread_local`、不新增结构体字段（K116）。

### K129 —— 单价要拆成"固定项 + 面积项"再外推：一次 26×26 的贴图花 0.2 ms，按面积系数算只该值 0.005 ms

- **现象**（2026-10-24，m114）：拆悬浮层的构成时，标题栏里那颗**置顶按钮**——一个**已经预渲染成位图**、
  目标框只有 **26×26** 的 `draw_image`——每帧读 **0.172–0.254 ms**。
  而 m113 同一台机器上的另一组读数给出面积系数：512² blit ≈ 1.8–2.2 ms ⇒ **~8 ns/像素**。
  照这条外推，676 个像素只该值 **~0.005 ms**。**差 40 倍。**
- **说明什么**：一次绘制的成本不是"面积 × 单价"一条直线，至少是**固定项 + 面积项**两段；
  固定项在图元小的时候**就是全部**。用大面积那一档拟合出来的系数去解释小图元，必然把结论算错。
- **本轮没做的事如实写出**：固定项来自哪里（怀疑是 alpha/mask 那条路，`Fit::Contain` 也可能参与）
  **没有拆到那一层** ⇒ 这条读数只登记为"有 ~0.2 ms 的每次固定开销"，**不许当机制结论引用**；
  把它量实是下一枪（O26：尺寸阶梯 1×1/26×26/128×128/512²/1920×1080，**alpha 与不透明两形各跑**，
  n≥200、成对反序，一条直线解出两个系数）。
- **可复用的两句**：① 拿"每像素单价"外推之前，先跑**最小尺寸那一档**——它读出来的就是固定项，
  如果它和目标值同量级，说明这件事的瓶颈根本不在像素上；
  ② 一条成本曲线**至少要两个尺寸**才谈"系数"，一个尺寸只能谈"这一次多少钱"。
- **同族**：K118（计数不换算成毫秒）、K127（裁决值＝单价 × 命中率）、K128（先按层夹表再谈哪层贵）。

### K130 —— 离屏探针只许定"哪一形贵"，裁决价一律以生产插桩的 ms 为凭：同一形两边差过 2–4×，两个方向都出现过

- **现象**（2026-10-24，m115）：跑 O26 的尺寸阶梯时，把探针读数与 m113/m114 的**生产插桩**读数并排一放，
  两边**互差不合比例、且方向相反**：
  - 置顶那颗（1:1 半透明 26×26）：探针 **54 µs** ｜ 生产 **172–254 µs** ⇒ **探针低估 ~3–4×**；
  - 胶片条那一格（缩放 90×68）：探针 **205 µs/格** ⇒ 18 格推 **3.70 ms/帧**，而 m113 在 1920×1200 实测
    **整段 B（悬浮层＋胶片条）才 1.96–3.10 ms** ⇒ **探针高估 ~2×**（连 7 格那一档推 1.44 ms，也把生产整段
    0.77–1.69 ms 顶到上沿）。
- **说明什么**：离屏 `Pixmap` 探针没有生产的裁剪栈、DPI 换算、真实缓冲与同一帧里的其它图元，
  它给的是**这一形的相对价**，不是"生产里这一次要几毫秒"。
  ⇒ **拆系数、定"哪一形贵"用探针**（207× 那种量级差是可信的）；
  **"能省几 ms/秒、值不值"只用生产读数**——否则等于把自己造的量具当成被测物，O25 就会被算成"3.7 ms/帧的大口子"。
- **K129 那条待办本轮答了，而且答反了**：m114 写的嫌疑项是 **alpha/mask**，实机读数是
  **同为目标 16,384 px：缩放 422 µs ｜ 1:1 不透明 2.04 µs（207×），而缩放形里不透明 205.6 µs ≈ 半透明 202.7 µs**
  ⇒ 门槛是 windui 补丁 015 的**"物理 1:1"**，与混合无关。教训的同一半句：**量具缺一形，结论就会指向错的那一形**——
  本轮原来的阶梯全是 1:1，因为写代码前没核生产几何；核了 `filmstrip::layout`（96×68）与 `THUMB_W/H`（240×180）
  才发现**生产的两处 blit 全是缩放形**，于是补了缩放档。**先核被测对象的真实几何，再搭阶梯。**
- **可复用的三句**：① 报"某一层能省几 ms"之前，问一句这个数是探针给的还是生产插桩给的，后者才算数；
  ② 拆成本形之前，先把生产调用点的**几何**（源尺寸、目标框、fit）抄下来，按它搭臂；
  ③ 两列（最小/中位）**同号才立案**，反号就打"读不出来"（本轮窗口项就靠这条没把 +7 µs 的噪声说成"占 10%"）。
- **同族**：K128（先按层夹表）、K129（单价＝固定项＋面积项）、K126（复刻必须配会红的钉子）、K119（检测器先过自己的判据）。

### K131 —— 注释与 rustdoc 里的符号锚点一样会漂，而且没有门禁读它：`pub` 项的"零读者普查"要每轮跑，检测器要拿删除前的快照自证会红

- **现象**（2026-10-24，m116 收 O19）：`core::gallery::is_image_ext` 有 **六处注释/rustdoc 引用**
  （`formats.rs` 三处、`decoders/mod.rs` 两处、`docs/图片格式与后缀名.md` 与 `docs/架构总览.md` 各一处），
  看起来"到处都在用"；实际**代码里零调用者**——目录浏览走的是 `is_image_ext_in`（一次取好清单再逐个判），
  它只活在文字里。`#[deny(dead_code)]` 不报它，**因为它 `pub`**。
- **顺着这条普查，又抓到两处更坏的幽灵**（都是"文字指向一个不存在的符号"）：
  ① `decoders/mod.rs` 的 rustdoc 链 `[`crate::core::gallery::IMAGE_EXTS`]` —— 仓里**从来没有**这个符号
  （内置清单在 m56 就收成了 `formats::BUILTIN_DECODERS`）；
  ② **现行正本** `docs/图片格式与后缀名.md` 开头"数据来源"与能力表第一行都写着宿主常量
  `core::gallery::BUILTIN_EXTS` —— 那个常量同样早在 m56 没了；连带 `docs/踩坑记录.md` 的 K39 那条
  结尾还留着一句"**改内置认领时两边一起动**"，今天照着做的人会去改一个不存在的第二份。
  ⇒ 注释指错只是难看，**能力正本指错会把读文档的人送到假真源那儿去**，这一条比 O19 本体更值钱。
- **可复用的一条硬办法（已落工具）**：本仓审计工具 —— 数 `pub` 项的读者时
  **先剥掉注释**（`///`、`//!`、`//`、`/* */`），只数代码；`tests/ examples/ 解码器仓库src/` 都算读者。

### K133 补条二（2026-10-28，宿主那道闸抬到 64 MP ⇒ 上面那句"数值刻意不相等"已成过去式）

- **发生了什么**：用户拍板把宿主 `MAX_PIXELS` 从 41 MP 抬到 **64 MP**，与解码器侧那道
  分配闸**同值**。K133 里"解码器那枚是分配闸 64 MP、这道是看图硬顶 40 MP、数值刻意不相等"
  那句因此**不再成立**——不是被推翻，是那道闸自己长到了同一个数。
- **为什么当时是 41 而不是 64**：41 MP 那道闸比解码器那道**更紧** ⇒ 41–64 MP 那一档位图
  被**宿主先拒**，而解码器本来解得动（真机实测：9000×5000 = 45 MP 的位图在旧宿主上是
  "图片太大，超出宿主给的内存预算"，而 45 MP 的相机 RAW 在真语料里根本不存在——语料最大
  那个只有 40.01 MP，正好卡在旧闸下面）。这正是"同名两值"里**更紧的那一道**在替另一道
  做决定。
- **写破的口径随之改**：宿主 `MAX_PIXELS` 的 rustdoc 现在明说"两道闸管两件不同的事
  （分配闸防畸形头、看图闸防内存与停顿），但**上限取同一个数**；宿主再往上调就调不动了
  ——解码器那道先拒，与宿主给的 `budget_bytes` 无关"。
- **连带必须同步的两处**（不然门禁立刻红）：解码器仓 `testdata/make_samples.py` 的镜像值
  （`tools/check_caps.py` 核对它与宿主 `pixels.rs` 等值）+ `tools/check_caps.py` 的文档串。
  这是**镜像与门禁的两仓同步**，**不重编任何 DLL、不动 ABI、不改解码器行为**。
- **★ 更要紧的一层**：闸放开之后，"总量在限内、**单边**超限"的图出现了（30000×2000 的
  全景图 = 60 MP）。D3D11 建不出 16384 以上的单边 ⇒ 纹理创建失败 ⇒ 宿主当时的处理是
  "本轮留白"⇒ 用户看到的是**一片空白加一行日志**，比"打不开并说清楚"更难排查。
  ⇒ 由此多了一道**显示侧**的闸 `MAX_TEXTURE_SIDE`（单边 16384），上屏位图**主动等比降边**，
  宁可 1:1 时略糊，也不要白屏。**这三条闸各管一件事，别再混成一条**：
  `MAX_PIXELS`（总量 / 内存与解码工作量）、`MAX_TEXTURE_SIDE`（单边 / 能不能画出来）、
  解码器那道（分配闸 / 防畸形头）。
- **可复用**：**同名两值里更紧的那一道会替另一道做决定**——发现某道闸"比另一道紧"时，
  要问的是"这中间那一档本该谁做决定"，而不是"哪个数对"。放宽时也是：先看哪一道是瓶颈。

### K135 —— `SYMBOL_INFO` 少四个字段＝所有函数名静默变空，被误读成"debug 档位不够"；而报告里只写 `<unknown>` 的栈等于没写

- **现象**（m129）：`temp\crash-*.log` 里自己的帧全是 `<unknown>`；`dump_sym.py` 拿**指纹完全对得上**的 pdb
  去解，行号出得来、函数名恒为空。2026-10-21 那次（K56 段）据此写下"`debug = 1` 只发行表，公开符号要
  `debug = 2`"——**这条结论是错的**，一直在 Cargo.toml 里躺着，还差点让人为了"要名字"把 pdb 从 21.9 MB 撑到 74.2 MB。
- **根因**：`SYMBOL_INFO` 的真实布局里有 `Address(56) / Register(64) / Scope(68) / Tag(72)` 四个字段，
  老结构体把它们跳过、于是 `MaxNameLen` 落在 `Tag` 的槽位。dbghelp **不报错**：`SymFromAddr` 返回 TRUE、
  `Name` 空、`Size` 一坨垃圾。补齐这 16 字节后，`debug = 1` 的 pdb 立刻给出 `mainCRTStartup`；
  `debug = 2`（74.2 MB）与它**结果一样**。判据是同一 exe 两档 pdb 各解一次，不是读文档。
- **第二处更致命**：`std::backtrace::Backtrace` 的 `Display` 在没有本地 PDB 时只剩 `<unknown>`——
  名字没了，**地址也不留**，事后一个字节都解不出来。而"用户机器上没有 pdb"正是取证存在的理由。
  改成自己抓：`RtlCaptureStackBackTrace` + `RtlPcToFileHeader` + `GetModuleFileNameW`，每帧写
  `模块名+0x偏移`（偏移与 ASLR 无关，换台机器照样对得上），异常地址另排 `#00`。
  pecia 走的是另一条等价路（`/DYNAMICBASE:NO` 固定基址 + 每版归档 `.map`）；保留 ASLR 就必须记偏移。
- **第三处**：解析器**不许按文件名猜配对**。错版本的 pdb 能被 dbghelp 载入（它只按 CodeView GUID 校验），
  然后给出**错函数**——比解不出坏得多。改成"试解：至少解出一行才算配上"，并用负向验证钉住：
  只给 `…-5132288-…pdb` 去解 `5127168` 的现场 ⇒ `-> no line` + 退出码 2，绝不硬编名字。
- **验证**（三处抽行，逐行比对源码，全部命中）：`rupix::main main/src/main.rs:67` = `rupix_lib::run(initial);`、
  `rupix_lib::run main/src/lib.rs:85` = `runtime::run(initial);`、`runtime::run main/src/runtime/mod.rs:788` = `.run();`。
  整条链现在是：崩溃 → 报告自带 `模块+偏移` + 转储 → `python main\build\dump_sym.py <报告>` → 逐帧 `函数 + 文件:行`。
- **顺带**：不再链接 `std::backtrace` 的符号化代码，exe −5,120 B。
- **可复用**：① "API 返回成功但输出是空串"先怀疑**结构体布局**，别急着换更高的调试档位；
  ② 写进注释的历史结论要带**怎么量的**，否则它会变成一个没人复查的假设（K131 同族）；
  ③ 配对判据必须是"能解出行号"，不是"文件名看着像"（K133：一条判据只许一处定义）。

### K136 —— "试解命中了"不等于"是这一枚 pdb 解出来的"：dbghelp 拒载错 GUID 的 pdb 时，功劳会被记在别人头上

- **现象**（m129 收尾复核）：拿 `examples/panic_probe` 的 panic 报告跑 `dump_sym.py`，输出是

  ```
  pdb       : panic_probe-342528-20261025020432.pdb      <- 报告期望的那一枚（没人给它归档）
  try rupix-5128704-20261025020358.pdb (newest-first scan) -> line hit
  paired    : rupix-5128704-20261025020358.pdb            <- 342 KB 的示例"配"了 5 MB 产品的 pdb
  ```

  帧解得对（`panic_guard.rs:142` 等），**但配对那一行是假的**——看起来正是 K135 发誓不做的
  "拿错版本的 pdb 硬解"。
- **根因**：`pick_pdb` 只把归档里的候选摆进 scratch 试解，而搜索路径里**还带着 exe 所在目录**
  （那里躺着 GUID 天然对得上的 `panic_probe.pdb`——`debug = 1` 让每个 example 都自带 pdb）。
  dbghelp 按 CodeView GUID 校验，GUID 不符的归档 pdb 被**拒载**、真正在干活的是旁边那枚，
  于是"解出一行"这个判据把功劳记给了被拒载的那枚。判据没错，是**归属**错了。
- **解法**：`pick_pdb` 改成**先看 exe 自己旁边**（`resolve_hits(exe, rva, [])`：搜索路径只有 exe 目录）。
  命中 ⇒ 直接返回 `(旁边那枚, scratch=None)`，打印 `(alongside the exe)`；
  没命中才轮到归档——那时"解得出"必然是归档的功劳（exe 目录自己解不出，已证伪）。
  另：每次试解都新建/销毁 `Symbolizer`（dbghelp 的符号句柄是**进程级单例**，
  复用实例会把上一次载入的模块带进下一次，试解就成了上一次的结论）。
- **验证（三臂）**：① panic 报告 ⇒ `try panic_probe.pdb (alongside exe) -> line hit`、
  `paired: panic_probe.pdb (alongside the exe)`，`resolved 9 / 11`；
  ② 产品报告（`.build\rupix.exe` 旁无 pdb）⇒ 仍走指纹精确名 `…-20261025014544.pdb`、配对正常；
  ③ 负向（`--symbols=` 只放时间戳不同的 pdb）⇒ `-> no line` + 退出码 2，没有因为这次改动放宽。
- **可复用**：① 凡"试一试看行不行"的配对/降级逻辑，都要问一句**"成了的话，功劳是谁的"**——
  多个候选同在搜索路径时，"成功"是**整个路径**的属性，不是某一枚文件的属性；
  ② 归因要靠**差分**（去掉它就不行，才算它干的），不能靠"这次我把它放进去了"；
  ③ 单例/进程级状态的库（dbghelp、GDI、COM）在"试多次"的场景里必须每次重开，
  否则测的是上一次的残留（同族：K135 结构体错位那种"看着成功其实不对"）。

### K137 —— 解码器 DLL 的 pdb 有两个名字：发布名带 ABI 段，CodeView 名是编译时的 crate 名；而发布档默认**没有行表**

- **现象**（m130）：宿主那一侧崩溃已经能解到 `函数 + 文件:行`，解码器那一侧永远停在
  `crashplug.dll+0x1221`。给 `dump_sym.py` 摆了一堆 `jpeg-abi4_0.1.0.pdb` 也没用。
- **两个真因（各自独立，缺一不可）**：
  ① **发布档默认没有行表**：`[profile.release]` 不写 `debug` 时，rustc 的 pdb 里只有
  **公开符号**——实测 `iv_probe` 名字解得出来、`SymGetLineFromAddr64` **一行都给不出**。
  与宿主 2026-10-21 那次完全同源（宿主加上 `debug = 1` 才有行表，结论在那边的 `Cargo.toml`）。
  加上之后 pdb 从"只有名字"变成"有行表"，**dll 体积不变**（`strip = true`，行表只进 pdb）。
  ② **发布名 ≠ CodeView 名**：DLL 发出去叫 `jpeg-abi4_0.1.0.dll`，内部的 CodeView 记录写的
  却是**编译时的 crate 名** `jpeg.pdb`，而 dbghelp **只按后者查找**。归档必须存 `<id>.pdb`，
  解析时把 `-abi<N>_<ver>` 段剥掉反推回 id（形态 B 的 CMake 产物可能跟着发布名走，
  所以两种名字都摆上——但**这条没实测样本**，当前 12 枚全是 Rust cdylib）。
- **配对仍然不靠文件名**：解码器没有"字节数 + 构建时间"可写进报告，所以让 dbghelp 的
  **CodeView GUID 校验**当裁判——GUID 不符它就拒绝给行，绝不拿错版本编一个错函数名。
  "没解出来"要分两种说：`(no pdb archived for this decoder)`（该去归档）与
  `(archived pdb is another build)`（GUID 不符，不给行是对的）。
- **验证（三臂）**：① 真机 `crash_probe.ps1` ⇒ `#02 crashplug.dll+0x1221` 落到
  `crashplug::probe_filter …/crashplug/src/lib.rs:79`（= `f(info)`，逐行核对）；
  ② 真实解码器（合成报告，RVA 取自 `GetProcAddress("iv_probe")`）⇒
  `jpeg::iv_probe 解码器仓库decoders/jpeg/src/lib.rs:65`；③ 负向（拿 `jpeg.pdb` 冒充
  `crashplug.pdb`）⇒ `another build`，不编名字。
- **同族**：K135（同一次调试档位的错结论）、K136（功劳归属）、K112（profile 按 `[package] name`
  匹配，写错静默不生效）。
- **同症状的第二个成因（m131 补）**：`SymFromAddr` 给得出名字**不代表 pdb 配上了**——
  dbghelp 没 pdb 时也能从 **PE 导出表**给出导出符号（`iv_probe` 正是 `#[no_mangle]` 导出），
  于是"有名字、没行号"有两种截然不同的成因：① 发布档没开 `debug`（有行表需求的都在这里）、
  ② pdb 根本不是这一版（GUID 不符）。**判配对只能看行号**，而且报告里要把原因写出来，
  否则读者会以为"配上了，只是这行没行表"（实测：`iv_probe [jpeg-abi4_0.0.9.dll]
  (archived pdb is another build)`）。
- **可复用**：① "名字解得出来、行号没有"是**行表缺失**的特征信号，别去查路径/权限；
  ② 凡是"文件被改名发布"的工件（dll/exe/so），符号查找用的是**编译期那个名字**，
  归档与查找两侧必须各自做一次换算；③ 夹具自己也要带行表——否则它验不了"解码器那一侧"。

### K138 —— PS 5.1 的 `Get-Content -Raw` 把**无 BOM 的 UTF-8** 当 ANSI 读：中文 JSON 被拆坏，`ConvertFrom-Json` 报的是**解码后**的位置、还把整份文件当错误消息吐出来

- **现象**（m134）：`make_index.ps1` 要"读回上一版清单、保住手填字段"，结果每次都走 `catch`，
  而那条"警告"里**整份 16 KB 的 JSON 都印出来了**，末尾接一句 `notes/extra fields start empty`。
  看起来像"清单文件坏了"——但 `python -c "json.load(...)"` 读同一份文件毫无问题。
  报错原文：`传入的对象无效，应为":"或"}"。 (2548): { "schema": 1, …`。
- **根因**：文件是用 `UTF8Encoding($false)` 写出的**无 BOM** UTF-8（为让 gitee raw / 任何 HTTP
  消费方直接当 UTF-8 读），而 PS 5.1 的 `Get-Content` 默认按**系统 ANSI 代码页**解码无 BOM 文件。
  中文 `desc` 的多字节序列被拆成乱码，其中某些字节落成引号/控制字符 ⇒ JSON 结构被破坏 ⇒
  解析器在**字符位置 2548** 处失败。这个位置是**解码后**的计数，拿它去原文找字符只会更迷惑
  （实测原文该偏移处是一段毫不相干的 URL）。
- **修法**：`Get-Content -Raw -Path $p -Encoding UTF8`（或 `[IO.File]::ReadAllText($p)`，它自己认
  UTF-8）。**不要**为绕开它给文件加 BOM——HTTP 消费方会多出 BOM 字节。
- **可复用**：① "解析器说文件语法坏了，换个工具读就正常" ⇒ 先怀疑**读取端编码**，不是文件；
  ② 解析器给的位置是**它看到的文本**的坐标，不是磁盘字节的坐标；
  ③ 自己生成、给别的语言/工具消费的文本文件，**读写两侧编码都写死**（写端无 BOM UTF-8
  + 读端显式 `-Encoding UTF8`）——默认值不算约定。

### K139 —— PS 里 `-f` 不能放在**续行的行首**：报"缺少右 )"，错误位置还落在后面那条无辜语句上

- **现象**（m134）：写成
  `<字符串>"` 换行 `-f $a, $b, $c)` 的形式（即把 `-f` 写在续行开头），解析期就炸
  `表达式中缺少右")"`，而光标位置报在**下一处** `if (...)` 和更下面的 `foreach`，
  一路"语句块缺少右 }"滚下去，看着像整段括号不配对（实际一个不少）。
- **根因**：括号内允许换行，但**运算符不能做续行的第一个 token**。行首的 `-f` 会被当作
  "参数式的减号 + 标识符"，与上一行那个已完整的表达式脱钩 ⇒ 上一行的 `(` 收不了尾。
- **修法**：运算符留在上一行行尾；或抽个变量一次写完：`$msg = "{0}: {1} -> {2}" -f $id, $old, $new`。
- **同族 / 关联**：K138（同一次改动里两个 PS 陷阱一起撞上）、K27（`.ps1` 编码）。
  **可复用**：`-f` / `-join` / `+` 这类运算符一律不写在行首；跨行格式化就"结尾留运算符"。

### K140 —— 脚本的 shebang 会改变 Windows `py` 启动器挑哪个解释器：`#!/usr/bin/env python3` 挑中了**没装依赖**的那个，现象是"明明装过却说缺库"

- **现象**（m135）：`py testdata/make_samples.py` 报 `Pillow is required`，
  可同一台机器 `py -c "import PIL; print(PIL.__version__)"` 打出 `11.1.0`。

- **根因**：`py`（`C:\Windows\py.exe`）会读脚本第一行 shebang 并据此选解释器。

  （WorkBuddy 自带、没有 Pillow），不是默认的 3.11。于是"依赖装在 A、脚本跑在 B"。
- **修法**：这类"本机专用、Windows 优先"的脚本**不要写 shebang**；跑法在文档里写死用哪个启动器

- **可复用**：① "装了却缺依赖 / 版本对不上" ⇒ 先确认**实际在跑哪个解释器**
  （`sys.executable` 打出来，而不是猜）；② 任何"某行内容会影响行为"的文件（shebang、`#!`、

  K27（`.ps1` 无 BOM 被按 ANSI 读）。

### K141 —— `visible_when(false)` 只把节点从**测量**里摘掉，**不把它的 `bounds` 归零**：判"折叠生效"要量卡片，不能量被藏起来的正文

- **现象**（m143）：快捷键页改用折叠卡后写回归用例，断言「收起后正文 `bounds.h == 0`」，
  实测仍是 1168（= 29 行 × 40 + 卡头↔正文那格 GAP），红得莫名——**同一个断言**在解码器页
  那张默认收起的「可下载」卡上是**过的**。
- **根因**：windui 的 `Tree::arrange` 对 `effective_visible() == false` 的节点先写
  `n.bounds = bounds`（父给的那个框）再 `return`，子树不再排版；而 `measure_linear` /
  `measure_scroll` 走的是 `visible_children`——**父**（卡片）的高度因此真的缩到只剩标题条，
  但**被藏起来的正文节点自己**还挂着上一帧量到的高度。「可下载」那张卡之所以是 0，
  是因为它自始至终没展开过、一次都没被安排过——不是它更正确，是它更"干净"。
- **修法**：折叠类断言一律量**卡片自己**（收起 ⇒ 卡高 == `CARD_HEADER_H`；再展开 ⇒ 回到原高），
  或量页面 `content_h` 的下降；**不要**断言隐藏节点的 `bounds` 为 0。
- **可复用**：① "隐藏"在测量层生效、在安排层不清理，是**两趟布局**的通病——凡写"折叠 / 显隐"
  回归，先想清楚该量谁；② 顺带一条：正文用 `.fill()`（宽高都 Match）在滚动容器里**量得出**高度，
  别因为「主轴 Match 会被降级成 Wrap」那条（搜索框那次）就以为它也会塌成 0。
- **同族 / 关联**：K84（读数/判据的"身份"——本条是它的布局版：同一份代码里
  「从没显示过」与「显示过又藏起来」是两个不同的初始状态，判据不能照抄）。

### K142 —— 按「标记串取区间」拆文件时，**区间没覆盖全文**会静默丢代码：编译器只会报"找不到名字"，不会告诉你少了一整段

- **现象**（m143 拆 `decoders/mod.rs` 2294 行）：脚本按 7 个分节标记切出 8 个文件，`cargo check`
  报 `cannot find type Loaded in this scope`。回头核对：`Loaded` 结构体 + 它的 `impl Drop`
  正好落在**两个区间之间**——`[B, D)` 交给自述模块、`[E, G)` 交给仲裁模块，
  而 `[D, E)`（`// ── 宿主 ──` 那一节）**没有任何文件接**，20 行凭空消失。
- **根因**：切片脚本只写了"每段去哪"，没写"这些段合起来是否等于全文"。分节标记是**人写的注释**，
  相邻两个标记之间那段到底归谁，脚本无从判断；漏掉一段时不会有任何报错——新文件里少个类型，
  看起来像是"可见性没提"，很容易被误诊成另一类问题（我当时先加了 `pub(super)` 才发现的）。
- **修法**：切片产出一律配**行覆盖校验**——把所有新文件的行收成一个 `Counter`，与原始文件逐行比，
  `差值 = 0` 才算拆完（可见性前缀按 `pub(super) ` 归一化后比，否则提升可见性的行会被算成"丢失"）。
  本轮实测：规范化后丢失 8 行 → 补回 `impl Default for Host` 与 `try_decode` 头顶的文档注释 → 0 行。
- **可复用**：① 任何"按标记切段、逐段落盘"的脚本（拆文件、拆文档、批量迁移）都必须自带
  **覆盖性**校验，而不是只校验"每段都写成功了"——写成功 ≠ 没漏；② 覆盖校验要**按行比对**，
  不能只比"总行数"（一段丢、另一段因加了头注释变长，总数照样对得上）；③ 同族：K141
  （两趟布局里"测量"与"安排"各认一套事实）、K84（读数身份）——都是"两处定义、只查了一处"。

### K143 —— 桌面被别的窗口压着时，**截图拿到的不一定是被测窗口**：置顶/抢焦点都不可靠，用 `PrintWindow(PW_RENDERFULLCONTENT)` 直取窗口内容

- **现象**（m143，ui 层改动后的 GUI 冒烟）：拉起 `.build/rupix.exe` 打开一张真图，
  全屏截图再看——画面里是一整屏**直播画面**，RuPix 只剩右边缘一条和底部状态栏。
  先补 `SetWindowPos(HWND_TOPMOST)` 再拍、`SetForegroundWindow` 也试过，**还是同一张**。
- **根因**：被测窗是**分层窗**（`WS_EX_LAYERED` + `UpdateLayeredWindow`），而桌面那扇
  直播窗本身也在最前；对已经 topmost 的窗口再 `HWND_TOPMOST` 不会把它压下去，
  `SetForegroundWindow` 在没有输入焦点的会话里也常被系统忽略。全屏 `BitBlt` 抓到的是

  （这次它的画面里有图片、有颜色，纯看像素统计甚至能"通过"）。

- **可复用**：① 判据的对象**先验身份**再验内容——先确认拿到的是哪个窗口，再谈像素；
  ② "置顶 / 抢焦点"在多程序抢 z 序的机器上不是可靠手段，凡是"窗口内容"的判据优先窗口级抓取
  （`PrintWindow`），屏幕级抓取只适合"用户眼下能看到什么"这类真·屏幕问题；
  ③ 同族：K84（读数身份包含它跑在哪份配置上）、K141（两趟布局各认一套事实）——都是
  "你以为在量 A，其实量到了 B"。

### K144 —— 写进文档的「违禁示例」会被自己的门禁抓住：判据要留**实体长度**，示例只写形状

- **现象**（2026-10-26，两仓同时立「无密钥 / 无隐私」铁律）：规则表格里写了两行"样子"——
  「访问令牌：`glpat-` / `ghp_` / `AKIA…`」和「URL 内嵌凭据：地址里写成『账号:口令@主机』」。
  刚写完，`hygiene_scan.py` 报 `secret: main/AGENTS.md:126 credentials inside a url`、
  解码器仓报 `AGENTS.md:73 / :80`。**规则正文自己成了违规样本。**
- **根因**：判据写成"只要前缀就命中"（`\b(?:ghp_|glpat-|sk-)`）与"只要形状对就命中"
  （协议名 + `://` + 账号:口令 + `@`）。这在真实令牌上是好事（早拦），但把**举例**与**真凭据**混为一谈：
  文档要说明"这类东西不许写"，就得把形状写出来。
- **修法**（两边同源）：
  1. 判据要求**实体长度**：`glpat-[A-Za-z0-9_-]{16,}`、`ghp_[A-Za-z0-9]{20,}`——
     真实令牌都远长于此，而"只提前缀"的文档不再命中；
  2. 文档只写**形状**不写完整串：「地址里写成『账号:口令@主机』的那种」而不是整条 URL；
  3. 自检里两条都钉：`glpat-` 开头后接 18 位的一串必须命中，`文档里只说 glpat- 这个前缀` 必须不命中。
- **复验**：收紧后重新注入一个真令牌形状的串（`glpat-` + 20 位）⇒ 两仓仍各自报红；还原 ⇒ 0。
- **可复用**：① 「禁止 X」的文档天然携带 X 的样本，任何扫字符串的门禁都会咬到自己的说明书
  ——立规则时先跑一遍门禁，别等 CI；② 判据用**最小实体**（长度/校验位）区分"举例"与"真货"，
  比给规则文件加白名单稳（白名单会让"真把密钥贴进规则文件"也放过）；③ 同族：K142（切片漏段
  不报错）、K143（判据对象身份没先验）——都是"判据看起来在管，其实管错了东西"。

### K145 —— PowerShell 5.1 里 `@(ConvertFrom-Json …)` 会把顶层 JSON 数组**再套一层**：计数变 1、字段变数组，而且不报错

- **现象**（m145，`RuPix-Decoder/build.ps1` 的清单新鲜度检查）：`decoders.json` 刚从
  `{decoders:[…]}` 改成"顶层就是数组"之后，检查逻辑改成
  `$cat = @(Get-Content -Raw … | ConvertFrom-Json)`，随后逐项拼文件名——
  输出是 `1` 和 `System.Object[]_System.Object[].dll`：计数是 1、`$e.id` 是一个数组。
- **根因**：PS 5.1 的 `ConvertFrom-Json` 把**顶层数组**作为一个**不枚举**的对象输出到管道；
  `@(pipeline)` 收集的是"管道输出了几条对象"，于是把那个数组当成**一个**元素包进新数组。
  净效果是 `$cat` = 长度为 1 的数组，唯一元素是整个 Array。这不是 JSON 写错，也不是
  ConvertFrom-Json 的 bug——它只是"顶层数组"这个形状的特殊处理。
- **修法**：**别用 `@()` 包管道**，直接赋值（`$cat = … | ConvertFrom-Json`，实测 `.Count = 4`），
  再用 `if ($cat -isnot [System.Array]) { $cat = @($cat) }` 兜住"清单里只剩一项"时
  PowerShell 可能把数组退化成单对象的情况。改完实测 `count=4 gaps=0 drift=0`。
- **可复用**：① 换数据形状时，**判据要跟着形状换**（这次是"逐项取值"的写法换了，读法却没换）；
  ② PowerShell 的"单元素自动降级"是一整族坑——`@()` 通常救场，但对**不枚举输出**的 cmdlet
  恰恰相反；凡是"从 cmdlet 拿一个集合"，先打出 `count` 与第一个元素的 `GetType()` 再往下写；
  ③ 同族：K138（读写自造 JSON 必须写死编码）、K27（`.ps1` 被按 ANSI 读）——都是
  "PowerShell 的默认行为不是你以为了那个"。

### K148 —— 想看"某一扇窗自己的像素"就用 `PrintWindow`；而 windows-rs 0.62 把它绑在 `Storage::Xps` 里

- **现象**（m147，核「可下载」行版式）：探针要取设置窗的图，而 `setprobe` 的 `shot` 是**全屏**
  BitBlt——本机前台压着一扇 1920×1080 的直播窗（K143 同一类敌人），截出来的像素说不清属于谁。
  改用 `PrintWindow` 后一次就对。**第一个坑还不是这个**——先撞的是编译：
  `no PrintWindow in Win32::Graphics::Gdi`，换到 `Win32::UI::WindowsAndMessaging` 仍然没有。
- **根因**：`windows` 0.62 按 win32metadata 的分区落符号，`PrintWindow` 既不跟 GDI 也不跟
  WindowMessaging，而在 **`Win32::Storage::Xps`**，且要单独开 feature `Win32_Storage_Xps`；
  第三个参数是 newtype `PRINT_WINDOW_FLAGS`（`2` = `PW_RENDERFULLCONTENT`；少了它，分层窗
  与自绘窗常只回来一片黑）。
- **修法**：`Cargo.toml` 加 `"Win32_Storage_Xps"`；调用
  `windows::Win32::Storage::Xps::PrintWindow(hwnd, hdc_mem, PRINT_WINDOW_FLAGS(2))`，

  与"图上坐标"共用一个原点，点按钮时不必再减边框。
- **同轮第二条**（同一个脚本里一起踩的）：`setprobe enum` 打印的是 `HWND HWND(0x…)`——
  `{:?}` 打在 `HWND` newtype 上会多带一层类型名，按 `^HWND (0x…)` 写正则**一行都匹配不上**，
  症状是"新窗口一个都没找到"，而窗口明明开着。另外 hwnd 印的是十六进制，`rect` / `click` /
  `fg` 收的是十进制，PowerShell 侧要 `[Convert]::ToInt64($hex, 16)` 转一层。
- **可复用**：① 找 API 落在 windows-rs 哪个模块**别猜**，
  `grep -rn "pub unsafe fn <Name>" <cargo registry>/windows-*/src/Windows/Win32/` 一秒钟出结果
  （顺带能看到它要哪个 feature、参数是不是 newtype）；② 探针**解析自家输出**前先 `head` 一次
  实际形状——"我以为它印的是地址"这类错，与"按钮坏了"一样难分；③ 同族：K143（抢不过 z 序
  就 PrintWindow）、K147（坐标要从截图量）、K84（你以为在量 A，其实量到了 B）。

### K150 —— 进页同步打网络 + **失败不进缓存**：没网时每次切页都卡满超时

- **现象**（m148，用户口径「每次切换到解码器都会严重卡顿」）：设置窗其它页都正常，
  只有「解码器」页一进去就冻住几秒；有网时只卡第一次，没网/GitHub 被墙时**每次都卡**。
- **根因**：导航回调 `enter_decoders` 直接调同步的 `remote_refresh` → `platform::http::get`
  在 **UI 线程**上跑（WinHTTP 四阶段各 3 s 超时）；而缓存只在**成功**时写入，失败下一次
  仍会重打网络。于是"没有缓存"和"每次都失败"叠在一起，每次切页都完整付一遍超时。
- **修法**：① 进页只读本地 `docs/decoders.json`（`remote::load_local`，零网络）；② 只有用户点
  「刷新」才起后台线程（`remote::start_refresh` + `poll_refresh`），成功解析后才原子覆盖本地
  文件，失败保留旧清单；③ 切来源只换地址列、不联网。
- **可复用**：① **任何可能在 UI 线程上阻塞的动作都必须先问"这一步能不能本地完成"**——
  "进页要显示的数据"优先随包/缓存，联网只留给显式刷新；② 缓存**失败也要记**（短 TTL 的
  负缓存），否则"失败 → 无缓存 → 重试"会在用户每次操作时重复收费；③ 后台化的判据不是
  "请求小"（2 KB 也可能卡 3 s），而是"它是否在 UI 线程上等"。

### K153 —— 3 秒 WinHTTP 超时是"进页同步"时代的遗留：切 Gitee 刷新报 0x80072EE2

- **现象**（m148，用户实测）：GitHub 刷新/下载正常；切到 Gitee 点「刷新」报
  `读取清单失败：发送请求失败（0x80072EE2）`。`0x80072EE2` = `ERROR_WINHTTP_TIMEOUT`。
- **根因**：`platform::http::DEFAULT_TIMEOUT_MS` 还是 **3 秒**，那是"进入解码器页就同步
  拉清单"时代定的（为了不把 UI 冻成死机）。现在刷新已在后台线程，3 秒对 DNS / 系统代理
  探测 / 首次 TLS 握手太短，弱网下 `WinHttpSendRequest` 先超时，用户看到的是一句英文码。
- **修法**：① 四阶段超时统一放到 **30 秒**（用户拍板；后台任务等得起，UI 仍有「正在更新…」）；
  ② **不自动重试**——30 秒已经是一次完整尝试，再重试会让用户等 60 秒；
  ③ `catalog_error_text` / `download_error_text` 把错误翻译成人话（连接超时 / 连接失败 /
  更新失败），`0x...` 与裸 HTTP 码**只进日志**；④ Gitee 清单源用 CDN 直链
  `raw.giteeusercontent.com`（`gitee.com/.../raw/...` 会 302 到它，多一跳）。
- **可复用**：超时值要跟着**调用方式**走——UI 线程同步时短、后台任务可以长；
  `0x80072EE2` 不是"地址坏了"，是"这次没等到"；**错误码是给日志的，界面只给人话**。

### K154 —— 矢量解码器回填的 `actual_*` 是"这一次画出来的画布"，不是"文档有多大"：拿它当 `natural` 会让放大后显示的是文档的别处

- **现象**（2026-10-28 用户真机）：打开 WMF（文档 3102×3124）放大后，画布只显示文档的**一角**，
  且与右下角鸟瞰缩略图里标出的视口位置对不上——看着像"显示不全"。
- **根因**：`Decoded::natural` 的契约是"原图尺寸"，而宿主把它当**文档自然像素**用：
  画布几何（`eff_dims` → `dst_rect`）与 **ABI v6 的区域请求坐标系**（契约明写：区域的
  x/y/w/h 单位 = 文档自然像素）都吃这个值。位图那条路上 `natural` 确实是原图尺寸；
  **矢量那条路上不是**——解码器按 `target` 把**文档重画**成目标尺寸，回填的 `actual_*`
  是"这一次的画布尺寸"。于是宿主拿视口档的渲染尺寸（557×561）当文档尺寸，区域请求要的是
  557×561 坐标系里的那一小块，而解码器按 3102×3124 的真文档去裁 ⇒ **位置与比例全错**，
  放大后看到的是文档的**别处**（本次真机：宿主认知的比例是 5.569 = 3102/557）。
- **为什么它躲过了那么多闸**：区域渲染本身是对的（`region_align_probe` 量到 0.56% 差异 =
  对齐正确）、判据链也是对的（`is_region_renderable("wmf")=true`）、画布尺寸也是对的
  （`region_target` 的"4000% 仍是一屏大小"用例通过）。错的是**喂给区域请求的那个数**——
  每一环单看都对，接起来错。
- **修法（只在宿主侧，不动解码器）**：矢量路线补一次**零目标查询**——ABI 契约里
  `target_w/target_h = 0` 就是"要原始尺寸"，那是**问事实**的正规入口；拿它当 `natural`。
  只对"解码器自渲染 **且** 能按可视区域重渲"的后缀补（判据与 viewer 分流同源）；
  没有区域通道的矢量保持旧口径（那里 `natural` 只喂"是否已是整图"的闸，改了会让大文档
  突然去整幅渲原始尺寸，直接打不开）。
- **可复用的三条**：
  1. **同一个字段在两条路线上语义不同 ⇒ 不能共用**。位图的"原图尺寸"与矢量的"文档尺寸"
     在 `natural` 这一个字段上撞车，而宿主这一侧只看见一个字段。
  2. 契约里凡是写着"0 = 原始尺寸"的参数，都是**问事实**的正规入口：想知道原尺寸就该发一次
     零目标查询，而不是从渲染结果反推（反推也不成立：等比缩放后**绝对尺寸不可反推**）。
  3. 探针要能**同时量出"宿主认知的坐标系"与"解码器的真实坐标系"并算比值**：比值 = 1 才是对的。
     这一条比逐像素比对更能一句话说清根因，且**负向验证**很便宜（把修复临时关掉，探针必须转红）。

### K156 —— 水平轴上的 `fill()` 会超出前面定宽的兄弟：`Match` 拿的是**整条主轴**宽，不是剩余宽

- **现象**（2026-10-28，设置页「更新地址」卡首次做长输入框）：一行 `[标签(width 208), 输入框容器]`
  放在 640 宽的页里，容器右缘量到 **832**（= 640 + 208 − 16），整行溢出到页外。
  同一行改 `weight(1.0)` 后右缘 624 = 640 − 16，正对；但容器后面若还挂一颗
  `flex_spacer`（`option_row` 自带），两颗权重各 1.0 平分剩余宽 → 输入框只剩 200px。
- **根因**：windui 的 `measure_linear` 里，`Fill` / `Match` 子节点拿到的是容器**主轴可用宽**
  （不减已排前驱），只有权重子节点才按"剩余宽 × 权重占比"分。所以"前面有定宽兄弟"时
  `fill()` 一定多算那一格；而"后面还有占位兄弟"时 `weight(1.0)` 又会与它平分。
- **修法**：这一行**自己排**（不复用 `option_row`）：`[标签 width(COL1_W), 控件 weight(1.0)]`，
  行内没有第二颗权重子，控件独占剩余宽。回归用例断言 `cb.x == 16 + COL1_W` **且**
  `cb.right() == 640 - 16` **且** `cb.w > 160`——三条同时钉住"起点对、终点对、真的撑开了"。
- **可复用**：① 想"吃满余量"先数这一行有几颗权重子，多于一颗就不是它独占；
  ② 断言要**两端都断**，只断右缘会漏掉"起点错但宽度凑巧对上"；
  ③ 无头布局用例的根必须是**定宽**容器（`col().width(640)`），否则 `width_match`
  在无界宽下量出的是自然宽，用例永不失败（也会掩盖真 bug）。
