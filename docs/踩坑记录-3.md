### K71 —— 体积硬指标写在文档里却没人复测：涨破 4MB 时那一行还写着「3.89MB，达标」

- **现象**（2026-10-19）：用户问「exe 从 3MB 胀到 4.78MB，能分解体积来源吗」。第一次逐 crate
  结算才看见：`docs/产品定位与边界.md` §四 的体积行停在 `exe ≈ 3.89MB，达标`，而实测
  **5,016,064 B（4.78 MiB，事故当日读数；现行值只认宪章 §4.1）**——`lto = false` 那一档
  （K53，明写了 4.35 → 4.92 MB 的代价）
  就越过了 ≤4MB，宪章却没人回头改。README 首页同样挂着「≈3.8MB」。
- **根因**：这类数字**不是任何一次改动的产物，是几十次改动之和**。所以 `开发指南.md` §二
  那张「改 X 同步 Y」对照表永远不会提醒它——对照表按"改动"触发，而体积没有触发它的人。
  这是"列而不行"的第三例（第二例是 clippy，见 K69）：指标有正本、有数字，**没有复测动作**。
- **解法**：把复测做成一条命令（`python build/size_map.py`，工具进 `build/`），宪章那一行
  改成"本日期实测 + 命令"，并在 `开发指南.md` §二 加一行"动体积档位/加删依赖 → 跑它并同步"。
  **暂不进门禁**：目标值本身还待用户裁定，先立一个自己会误伤的阈值正是 K69 反对的假门禁。
- **做分解时一定会踩的三条方法学坑**：
  1. `set RUSTFLAGS=...` 是**整条覆盖** `.cargo/config.toml` 里 `target.<triple>.rustflags`，
     不是追加。只写 `-C link-arg=/MAP` 会把 `+crt-static` 丢掉，于是量成动态 CRT 的另一种链接形态。
     要加开关就得把 `+crt-static` 一起写上。
  2. **MSVC 的 `.map` 不给符号长度**，只给地址：每条符号的字节数只能取"同段内下一条地址 − 本条"，
     段末那条记 0，同址别名（`f`/`o`/`__imp_` 几条）只算第一条，对齐填充算进前一条。
     所以**必须逐段打"归账 vs PE 段实测"的闭合差**来证明没解析错——本次 `.text` 差 32 B、
     `.rdata` 差 656 B，才算这本账可用；差几 KB 就是解析错了，不能拿它说话。
  3. map 的段编号 `0001:` / `0002:` / `0003:` **不等于 PE 段名**：`0002` 的第一行是
     `.idata$5`，照编号取名字会把 1.09 MB 的 `.rdata` 全记成 0（第一版就栽在这里）。
     正确做法是拿符号的 `Rva+Base` 减 image base，看它落在哪个段的虚拟地址区间里。
- **顺带量到、值得记一笔的三条**：
  - **`debug = 1` 对 exe 体积是免费的**（配对：关掉后 5,016,064 → 5,018,112 B，多出的 2 KB 是
     段对齐噪声；PDB 21.6 → 7.9 MB）。行表只进 PDB，`strip = true` 早把调试段剥掉了——
     所以**别拿"要控制体积"当理由关掉崩溃取证用的行表**（K56 那套 `.dmp` 解到源码行靠它）。
  - `.rdata` 里 328 KB 的 `$ip2state$` 单步状态表**不来自 debug 档位**（关掉一分不省），
     它与 `.pdata` 187 KB、`$cppxdata$` + `$stateUnwindMap$` 139 KB 同源：都是 Win64 展开/清理
     元数据，随**函数条数**增长。`panic = "unwind"` 是功能红线（后台解码线程靠 `catch_unwind`
     把解码器 panic 收成"这张图失败"，见 `Cargo.toml` 与 `crash_evidence.rs` 头注），
     所以这笔账**没做**省它的测算——要动它得先动"打不开图不许闪退"这条行为。
- **★ m104 量到的一条（分组读数会说谎，实测到）**：注释定稿后重新编译，**只重编了 `rupix` 一枚
  crate、exe 文件字节一字未动（5,105,152）**，`size_map.py groups` 的分组却整片挪位：
  本项目组 893.0 → **897.4 KB**，同时 SVG 栈 −2.5、图像/压缩 −0.9、windows 绑定 −0.9、日志 −0.2，
  而**符号行条数（38,638）与归账总字节（4,892,108）两次完全相同**。 ⇒ 动的不是体积，是"按地址区间
  归账"的边界（**为什么挪：机制未定性**，坑 2 那条"段末记 0、对齐算进前一条"是候选）。所以宪章 §4.1
  那句 **"跨轮增量只认文件字节数、别拿单 crate 的跨轮读数当增量"**不是套话：一次连代码都没变的编译就能
  让某一组涨 4.4 KB。
- **★ m105 勘误（我把"分组读数会挪"归因过宽）**：m104 写过"分组读数挪动是因为注释重编译动了代码布局"——
  注释不改代码布局，这条因果**没验证过**。本轮用 m84 那把现成的尺子量了一遍（`.temp/m84_difftext.py`
  比 `.build/rupix.exe` 与 clean 重链的 `.temp/target/release/rupix.exe`）：**`.text` 差异 0 字节**、
  `.rdata` 差 25、全文件差 28 字节，判定"机器码逐字节相同 ⇒ 同一份代码，差异只是构建印记"。
  ⇒ **归账分组读数会挪这件事仍然成立**（两次都是实读），但**机制未定性**：连机器码都没变，
  说明挪动出在"按地址区间归账"的口径本身，而不是代码。结论不变：**跨轮增量只认文件字节数**。
- **定式**：**凡文档里以数字形式写死的硬指标，同一行必须给出"怎么复测这条数字"的可执行命令**；
  给不出命令的，就把它写成方向而不是数字。

### K72 —— 批量改文案时 `\r` 被吃掉：一次改了十个文件，编译错误在四轮之后才炸

- **现象**（2026-10-19，日志落点搬家）：用 Python 脚本批量把文档与注释里的
  `rupix.log` 改成 `temp\rupix-<今天>.log`。串里写的是 `'temp\rupix'`，**跑完 `cargo fmt` 才报**
  `unknown start of token`——某行注释变成 `` /// 直接往 `temp`` 后接一枚**真换行**再接 `upix-…`，
  第二行的 `///` 前缀没了，成了代码。在此之前 `cargo test` 一路绿了四轮：
  注释里混进裸 CR（0x0D）rustc 不当错（注释什么都能装），**`fmt` 才会把它当成行边界重写出来**。
- **根因**：同一批文本里我写了两种转义，命运不同——`\c`（`temp\crash`）不是合法转义，
  Python 原样保留反斜杠 ✓；`\r` 是合法转义，被解析成回车 ✗。再叠一层：
  `Path.write_text(..., newline=None)` 在 Windows 上还会把 `\n` 译成 `\r\n`，于是有的地方留下
  裸 CR、有的地方留下真换行。**两种坏法形状不同，`grep -c` 一种也数不清**。
- **解法**：改完立刻按**字节**复核，而不是等编译器：
  ```
  python -c "import pathlib; b=pathlib.Path('src/x.rs').read_bytes(); \
             print(b.count(b'\r') - b.count(b'\r\n'))"      # 必须是 0
  ```
  残留裸 CR → 换成反斜杠+r；被劈成两行的 → 接回去并删掉那枚空行（`//!` 块、段落、
  Markdown 表格都会被一枚空行拦腰截断）。规矩：**批量替换文本之后，`fmt` 与 clippy 要在
  跑测试之前跑**，且这类"改的是注释/文档"的批次必须做一次字节级自查。
- **连带的两个真缺陷**（都不是搬家本身，是搬家暴露的）：
  1. **读侧没跟着搬**：`examples/crash_probe.rs` 里那句"已有报告：false"读的是根目录
     `crash.log`。落点一改，它就永远报 false——**探针的判据指向旧路径 = 假装通过**，
     比没有探针更糟。同类的还有 `recovery_hint` 的提示文案与 `待办.md` §8 的复现判据。
     规矩：改落点时把"**谁在读**"一起列进改动面（`grep -rn` 旧文件名，一个不许漏）。
  2. **崩溃报告粘行**：会话头没采到时那句"（未采集…）"没有换行收尾，下一节
     `--- 现场 ---` 被接到同一行。只在真机产物里看得见，单测没覆盖。已补断言
     `report.contains("\n--- 现场 ---")`，并把 `env` 那一节统一"保证以一个换行收尾"。
- **同类**：K69 / K71（同一族：机器没看着的约定必漂）、K52（拿旧结论当证据）。
- **定式**：**凡"名字里带日期"的清理判据，认不出日期就一个不删**——这一条本轮写成了单测
  （`rupix.run`、`notes.txt`、旧式紧凑名 `crash-20260101000000.dmp` 三种都必须活过清理）。
- **自查范围补一条（同日）**：上面那条"按字节复核"当时只对**本轮动过的文件**跑，全仓扫下来
  仍有一枚裸 CR 留在**本文件 K72 正文自己**那行 `temp\rupix-<今天>.log` 里（反面样本没被自己修掉）。
  规矩：字节自查**全仓扫**，不只本轮文件。修它时又在 heredoc 里写了一次字面反斜杠——
  `b'temp\\rupix'` 被吃成 `CR`，**同一个坑同一个会话复发**。定式：**heredoc / 脚本里别写字面
  反斜杠，用 `bytes([0x5C])` 构造**；要落"反斜杠 + 文字"就拼 `BS + b'rupix'`。

### K73 —— `||` 短路链里做 `Cell::replace`：第一位变了，后面几位根本不覆写

- **现象**（2026-10-19，用户报障原话）：「极简模式下，鼠标悬停标题栏或者按钮工具栏，对应栏会
  浮现。但是不够流畅。而且鼠标光标移开后，有时候没能及时隐藏。」两个症状，两处病灶，都在
  `ui/chrome.rs` 与 `ui/canvas.rs` 的悬停链路上。
- **根因 ①（浮现慢半拍）**：`Chrome::activity()` 每枚 Move 都重算 `hover_title/toolbar/info`
  这三位，而 `paint` 就是按这三位决定那两条栏画不画——**可它的返回值当年没人接**，
  Enter/Move 分支只按"按钮级高亮变没变"标脏。于是显隐位翻了却没人发起重绘，浮条只能等
  **别的**标脏源（跨过某颗按钮、2 秒定时器、解出一帧图）。模块头那句"隐藏时立即显示"
  写在文档里，机器上没人执行 ⇒ 正是 K69/K71 那一族：列而不行的约定必漂。
- **根因 ②（移开有时收不走）**：三处写成一条链的
  `hover_btn.replace(None).is_some() || hover_toolbar.replace(false) || …`——`||` **短路**，
  只要第一位变了，后面几位**根本不会被覆写**。`Leave` 分支那条有七位，所以恰好**压在按钮或
  翻页箭头上把指针移出窗口**时，`hover_toolbar` 还挂在 `true`；而 `tick_hide` 读的是滞留的
  `last_pos`（还在那条栏里）⇒ 判成贴边豁免 ⇒ 连 2 秒那道兜底都不发生，那条栏就永远亮着。
  用户那句"**有时候**"正是短路条件的形状：取决于离开时第一位变没变。
- **解法**：① `activity` / 新增的 `pointer_left` 都返回"画面要不要变"，并挂
  `#[must_use = …]`——吞掉返回值直接编译警告，与 K57 把 `unwrap` 红线交给 `hygiene_scan`
  是同一个思路：**约定挂在机器上才算存在**；② canvas 四个调用点（Enter/Move 与三处 Down）
  全部接住并 `mark_dirty`；③ 链式改写**逐位赋值后再合并**，一行都不许塞进 `||`。
- **定式**：**凡是"一条 `||` / `&&` 链里做副作用"（`replace` / `set` / 写文件 / 自增）就是可疑写法**，
  一律先求值到具名变量再合并。要判"多位里有没有一位变了"，必须每一位都被真正写过。
- **测试有效性（本轮最值钱的一步）**：两条新用例写完都绿，但绿不证明它们测到了东西——
  把两处修复**临时还原**（先 `cp` 两个文件到 `.temp/m42_backup`，改完 `cp` 回来并核对
  哈希）再跑，两条都**红**，且 panic 文案正好是用户那两句症状
  （"移进顶条这一枚就该重绘——浮现慢半拍就是这里漏的" / "Leave 之后仍有悬停位没被清掉"）。
  定式：**回归用例要对着旧代码跑一遍**；旧代码也过的用例等于没测，与"未测 ≠ PASS"是同一枚币的两面。
- **没修的（诚实记账，见 `待办.md`）**：windui 的离开通知是一次性旗——`mouse_tracked`
  只在 `WM_MOUSELEAVE` 里复位（`.3rd/…/platform/win32/mod.rs:2476`），`start_window_drag`
  与 `WM_ENTERSIZEMOVE` 都不清它。一枚 leave 被模态拖动循环吞掉之后，`track_mouse_leave`
  从此早退，**该会话再没有 `WM_MOUSELEAVE`**。本项目已被 ①② 兜住大半（显隐位由每枚 Move
  现算，指针回到窗口内一动就纠正），残余窗口是"光标停在浮条上直接出窗且此后不再进来"。
  彻底解法要么给 windui 打第 14 枚补丁（拖动结束清旗），要么在 `platform` 加一枚
  `GetCursorPos` 预言机让 `tick_hide` 不再信任滞留位置——两条都判给下一轮。
- **同类**：K57（红线要机器执行）、K69 / K71（列而不行）、K65（取证要先固定环境再读代码）。

### K74 —— UI 线程的 `Drop` 里 `join()` 后台线程：整进程退不掉，而单测两头都绿

- **现象**（2026-10-19 用户报，`docs/待办.md` §8 就此结案）：「rupix 目前并没有系统托盘，
  但是我在任务管理器里面看到了进程。这属于 BUG。」——具体形状是关窗之后窗口没了、进程不退、
  此后再点按任何键都没反应，而 `close_to_tray=0` 时也没有托盘图标可以把人唤回来。
- **根因**：`DirWatcher` 装在 16 ms 轮询闭包里，而那个闭包属于框架的宿主状态——
  **windui 是在 `WM_DESTROY` 里、也就是 UI 线程上析构它的**。旧 `Drop` 最后一句是 `t.join()`，
  于是"等后台线程醒来"这件事发生在 UI 线程上；而"关掉目录句柄就能叫醒阻塞中的
  `ReadDirectoryChangesW`"这条**并不被保证**（微软给的正规打断方式是 `CancelIoEx`）。
  叫不醒 ⇒ UI 线程停在 `DestroyWindow` 里面 ⇒ `PostQuitMessage` 已入队却没人读 ⇒
  `App::run()` 永不返回 ⇒ 退出收尾整段不执行（`close_session()` 没跑，所以会话戳
  `temp\rupix.run` 还挂在原地——这正是"每次启动都提示上次未正常结束"的上游，也是
  `deploy.py` 删不掉 `.exe.old` 的上游）。
- **三臂实测**（同一枚探针 `.temp/m43_stuck_probe.py`，只换 `Drop` 写法，`.build` 真机）：

  | 臂 | `Drop` 写法 | 结果 |
  |---|---|---|
  | 红 | 只 `CloseHandle` + `join` | WM_CLOSE 后 **8 s 不退**，会话戳还在 ⇒ `close_session()` 没跑 |
  | C | `CancelIoEx` + `CloseHandle` + `join` | **0.0 s 退出，code=0** |
  | 绿（最终） | `CancelIoEx` + 关句柄 + **不 join**（放手） | 0.1 s 退出，code=0，会话戳被删 |

  ⇒ **承重的是 `CancelIoEx`**；`join` 本身不是病灶，它是把"叫不醒"放大成"整个进程退不掉"的**放大器**。
  两条都改：取消让线程真的走掉（换目录不漏线程），不 join 让 UI 线程永不因它而停。
- **解法**：`DirWatcher::drop` = 置 `stop` → `CancelIoEx(handle, None)` → `CloseHandle` →
  `let _ = self.thread.take();`（drop 掉 `JoinHandle` 即 detach）。放手是安全的，判据写死在注释里：
  **线程只持自己拥有的东西**（句柄数值的 `usize` 副本、move 进来的 `Sender`、`Arc<AtomicBool>`），
  不借结构体任何字段。
- **定式三条**：
  1. **退出路径上的线程（UI 线程尤其）不许在 `Drop` 里 `join`**。要收尾后台线程就用"取消 + 放手"，
     要确定性等待就交给一条不会挡住退出的路径。
  2. **阻塞式内核调用必须可被外面打断**：`ReadDirectoryChangesW` 认 `CancelIoEx(h, NULL)`
     （取消该句柄上所有线程的挂起 I/O），别赌 `CloseHandle` 的副作用。
  3. ★ **这类缺陷单测测不到**：join / 不 join 两版写法在裸测试里**两头都绿**（本机 `drop` 只等了几毫秒）。
     新加的两条只能当**哨兵**——钉"Drop 不许无限等"与"线程确实自己走掉"（出口判据用
     `rx.try_recv() == Disconnected`：线程持有唯一那份 `Sender`，它退出通道即断；不数线程、不 sleep 赌）。
     **能定案的只有真机配对复现**；写文档时不许把哨兵用例写成"证明了修复"。
- **同一轮复发的老账（别再猜二进制布局）**：
  ① 探针里我按记忆写 `THREADENTRY32` 的字段，`Thread32First` 恒失败 ⇒ 报"0 条线程"，读起来像"线程没了"——
  换预言机而不是继续猜：改用 `Get-Process .Threads` 的 `ThreadState/WaitReason`。
  ② 旧 dump 脚本把 flags 的位值记错了（注释写"0x20 = 线程 info"）：`MiniDumpWithThreadInfo` 是
  **0x1000**，0x20 是 `WithUnloadedModules`、0x10 才是 `ScanMemory` ⇒ 拍出来的挂起 dump 里根本没有线程信息流，
  `build/dump_sym.py` 解不出帧不是工具的错，是**现场缺料**。本轮起 `.temp/m43_hang_dump.ps1` 用
  `0x1000 | 0x100 | 0x10 | 0x4 | 0x40 | 0x1`。
- **同类**：K73（同一族"看着做了，其实没做"）、K57 / K69 / K71（约定要挂在机器上）、K63（deploy 文件锁的下游）。

### K75 —— 共享桌面上合成的 `WM_MOUSEMOVE` 会被一枚真的 `WM_MOUSELEAVE` 追掉：悬停浮现不能单次采样

- **现象**（2026-10-19，m44 取证连做九轮）：同一枚 `PostMessage(WM_MOUSEMOVE)` 打到左/右边带，
  第一轮拍到"箭头浮现"、第二第三轮**九枚消息一枚都不动**——连 20 ms 的连拍都抓不到，
  读数自相矛盾，一度像"右带判据写错了"。代码没错，错在取证办法。
- **根因**：`TrackMouseEvent` 的申请是**按真实光标**判离开的（K73 已记下它是一次性旗）。
  合成的 Move 只把坐标写进 `lParam`，物理光标仍在桌面别处；于是每枚 Move 都顺手武装一次
  离开通知，而别家代理一动光标，系统立刻补一枚 `WM_MOUSELEAVE` → windui `clear_hover()`
  派发落在一切之外的 Move → 我们的 `pointer_left()` 把悬停位清空。**浮现态只活到下一次真实
  光标移动为止**，捕获时机落在哪一侧纯看运气——这就是"第一轮成功、后面全灭"的形状。
- **定式 ①（判行为）**：这类"会被人抢的输入通路"**不许单次采样**，改成**连发连拍数命中率**
  （本轮 60 帧里右带命中 1 帧，裁出来那颗 › 圆盘位置字形都对），并把读数写成 `1/60` 而不是
  "看到了"。同一轮配一条**控制臂**（点画面正中）：它不该翻页，实测只动了底部浮条那一格
  （17892 px，bbox 448×39）——没有控制臂，"整幅变了"这句话没有意义。
- **定式 ②（判外观）**：要看"画出来长什么样"就别跟竞争抢时序，**换一档**：把
  `minimal_mode=0`（箭头常驻）拍一帧，圆盘的字形、边距、配色全都拿得到，一行代码都不用改。
- **定式 ③（代理量两条禁令）**：
  ① 用"某区域均值"当状态代理，**不许跨图比较**——翻页之后底图换了，均值差跟箭头没关系
  （本轮 `v4_1click-prev` 左盘 51.7 其实是被 a.jpg 的底图换出来的，我一度把它标成"箭头在"）；
  ② **起手第一帧常常是还没解出图的黑帧**，均值比圆盘还低，会被数成一次命中
  （`v7_min_L` 那 1 次命中就是这么来的，剔除黑帧后左带 59 帧 0 命中）。
- **为什么不能靠"把窗口挪到光标底下"**：那确实能让浮现态稳住，但会把别家代理正在点的坐标
  盖住——共享桌面的规矩是**不动别人的输入**，宁可把命中率测低。
- **同类**：K65③（PrintWindow 会被别家 overlay 污染，判行为要换预言机）、K73（同一枚一次性旗）、
  K74（能定案的只有真机配对）。

### K76 —— 异步注册的夹具只造一次事件：20 轮假红 10 轮，而生产侧漏了无害

- **现象**（2026-10-19，m44 重跑门禁时）：m43 新加的
  `rearming_the_same_folder_still_delivers_changes` 在 20 轮连打里 **红 10 轮**，
  panic 在"换目录之后连造一次文件，5 秒内没收到变化事件"。
- **根因**：`DirWatcher::new` 只 `spawn` 线程，**通知是在后台线程跑到 `ReadDirectoryChangesW`
  那一刻才开始登记的**。测试主线程 spawn 完立刻写文件，那次创建整个落进"读还没开始"的窗口 ⇒
  事件永远不来（没有第二次变化去撞它）。所以红不是产品缺陷，是**夹具把自己的一次性事件
  发在了注册完成之前**。
- **解法**：每 50 ms **造一个新文件**，直到事件出现（5 秒兜底）。20 轮 20 绿。
- **定式 ①**：被测方是"异步登记的监听器"时，夹具要**反复造事件直到出现**，不能只造一次；
  只造一次的版本测的是"我发消息的时机刚好比它注册晚"，那是运气不是行为。
- **定式 ②（顺手记产品侧的账）**：生产侧同理会漏一枚事件，但**漏了无害**——换目录时上层本来
  就要重扫清单。这条要写进注释，否则下一轮会被当成缺陷再修一次。
- **定式 ③（读自己的输出）**：第一次跑全量时我用
  `grep -E "^test result|FAILED"` 之类只看汇总的过滤，**失败用例名被切掉**，只看到"1 failed"，
  差点按"偶发超时"放过。判红必须先拿到**用例名 + panic 文案**再谈归因（`grep -B1` 或干脆
  留全量输出）。与 K65"先固定环境再读代码"同一族：**先确认自己读到了什么**。
- **同类**：K66（夹具必须落在判据真的管着的那个分支里）、K75（取证环境的噪声要显式记账）。

### K77 —— 整数比例的夹具让"块划分相位"隐形：一条假绿差点把 m49 的第一版送上线

- **现象**（2026-10-19，m49）：想把宿主的 EXIF 转正从"整张 48 MB"挪到缩放之后（省 m48 量到的
  +95 ms）。第一版实现被配套用例在方向 6/7/8 判红，我按"两条路逐字节相同"的直觉改判：
  **只把缩放框的宽高互换、不动块划分**。探针跑 `4000×3000 → 1280×800` 打出
  `orient=5/6/7/8 差异像素=0` —— 看着像成立了。换 `1280×720`、`748×561` 再跑，6/7/8
  **每一个输出像素都不同**（平均差 3.5/255、最大 49；方向 5 才是真的 0）。
- **根因**：`4000×3000 → 800×600` 两根轴**恰好都是 5:1**。面积平均的格边界是
  `floor(i·n/t)`，`n/t` 为整数时 `floor ≡ ceil` ⇒ "从近端锚定"与"从远端锚定"是同一套格，
  相位问题在这组数字上**数学上不存在**。夹具退化成了恒等式，把判据照成假绿——与 K66 同族，
  但更阴：不是"夹具没进那个分支"，而是"**进了分支却恰好落在分支的退化点上**"。
- **解法**：把被方向反着取样那根轴的划分显式改成远端锚定（`band(i, n, t, ceil)` 用
  `(i·n).div_ceil(t)`），转正只作用在降采样后的小图上 ⇒ 与"整张转完再缩"**逐字节相同**
  （`fit_oriented_matches_orient_then_fit`：8 组尺寸 × 8 个方向，另在真照片 45 MB 上复验）。
  12 MP 竖拍首屏实测省 61–99 ms，且不改画面。
- **定式 ①**：凡判据是"**两套整数划分是否等价**"，夹具必须**除不尽**（专门挑 `n/t` 非整数的
  尺寸），并配一条**反向用例**证明夹具是活的——本项目是
  [`naive_orient_after_fit_is_not_equivalent`](../src/core/geometry.rs)：断言"朴素先缩后转只在
  方向 5 相同"，哪天夹具退化成整数比，它先响。
- **定式 ②**：**"换个顺序不改结果"必须按集合论证，直觉在这里不可信**。"缩放与镜像可交换"
  在整数下取整面前是错的：镜像把取样相位挪到块的另一头，`floor` 与 `ceil` 罩住的源像素
  不是同一批。同理，`4000×3000` 这种"好看的圆数"正是最容易骗过判据的那一组。
- **同类**：K66（夹具要落在判据真的管着的分支里）、K76③（先确认自己读到了什么）。

### K78 —— Windows PowerShell 5.1 把无 BOM 的 `.ps1` 按 ANSI 解：脚本里的中文会把解析器带沟里

- **现象**（2026-10-19，m50 真机自测）：取图脚本里写了一句中文注释和一个中文文件名的
  `Launch "$d\说明.txt"`，`powershell -File` 直接报 `UnexpectedToken: }`，指向的是**函数末尾**
  那个本来完全合法的 `}`；同一份脚本把所有中文删掉就一次跑通。
- **根因**：Windows PowerShell 5.1 对没有 BOM 的 `.ps1` 按系统 ANSI 代码页解码。UTF-8 的中文
  字节序列被拆成若干奇怪的单字节字符，其中只要有一个落成引号/反引号，**字符串或注释的边界
  就没了**，词法错误报到几行之后的闭合括号上——报的行号与真凶无关。
- **解法**：给自动取图/探针脚本规定两条就够：① 文件名与命令行参数一律 ASCII（夹具改名
  `readme.txt`，中文只许出现在**被测内容**里）；② 源码里不留非 ASCII（注释也删/改英文），
  或者存成带 BOM 的 UTF-8。用 `Write` 工具新建 `.ps1` 默认无 BOM ⇒ 直接按 ① 办。
- **定式**：脚本报的 `UnexpectedToken` 行号**不是**出错行；先怀疑"文件解码边界被吃掉"，
  而不是去数那个括号。判据：同一份脚本删掉全部非 ASCII 后能否跑通。

### K79 —— 无边框窗"四条边都能拖"是两件事：命中码对，和光标会变，各有一半在别人手里

- **现象**（2026-10-20，m54）：无边框主窗左/右/下三条边能拖动改大小，**顶边拖不动**，
  而且四条边悬停时全是箭头光标，看不出哪里能拖。
- **根因 ①（顶边）**：windui 补丁 05 在 `handle_nchittest` 里给顶边留了一个
  "画布可交互就先让给客户区"的例外。主窗画布是 `focusable()`，`interactive_at` 在顶边
  恒为真 ⇒ 顶边永远返回 `HTCLIENT`。DPI 感知探针实测（旧 exe）：左 10 / 右 11 / 下 15 /
  顶 **1**；中心 1 是对的，顶 1 是缺陷。修法＝缩放边带**无条件优先**，删掉那条例外
  （补丁 014）。新 exe 同一探针：顶 12、四角 13/14/16/17、中心 1。
- **根因 ②（光标）**：windui 的 `WM_SETCURSOR` 过去只处理 `HTCLIENT`，非客户区交给
  `DefWindowProc`；本窗口这条默认路径实测不会按命中码换成缩放光标。修法＝补一张
  `HTLEFT|HTRIGHT→IDC_SIZEWE`、`HTTOP|HTBOTTOM→IDC_SIZENS`、两组对角→
  `IDC_SIZENWSE`/`IDC_SIZENESW` 的映射并返回 TRUE。
- **取证坑**：给 `WM_SETCURSOR` 发消息时，**命中码在 `lParam` 的低 16 位**
  （高 16 位是鼠标消息）。第一版探针按 `WM_NCHITTEST` 的习惯打成 `hit << 16`，
  九种命中全返回 0，看起来像"处理器根本没跑"；纠正后九种全返回 1。
  另外 `GetCursorInfo` 在别的进程里读到的句柄不随这次 `SetCursor` 分门别类
  （九次读数同一个值）⇒ **只能证明"处理了"，证不了"换对了"**，后者必须人眼看。
- **定式**：① "能拖"和"看得出能拖"是两条独立验收项，别拿其中一条当另一条的证据；
  ② 自定义 `WM_SETCURSOR` 时，把命中码映射写成纯函数并让未知码回落到
  `DefWindowProc`，不要在一个大 `match` 里顺手处理；③ 同一族消息的参数打包方式
  不通用，发消息前先查头文件。

### K80 —— 一次性通知旗被模态循环吞掉后整会话失聪：判据要用**增量**去兜，而不是去补那枚旗

- **现象**（2026-10-20，m55）：极简模式下光标停在浮条上 → 拖一下标题栏 → 光标移出窗口不再回来
  ⇒ 那条栏**永远亮着**。同一件事在没拖动过的时候完全正常。
- **根因**：框架用 `TrackMouseEvent` 申请"指针离开"通知，申请是**一次性**的，而它拿一枚
  线程内布尔旗去重（只在收到 `WM_MOUSELEAVE` 时复位）。交互式拖动/缩放走的是
  DefWindowProc 的**模态消息循环**（我们顶条拖动就是 `WM_NCLBUTTONDOWN(HTCAPTION)`），
  那一趟里该发的 leave 被吞掉 ⇒ 旗不复位 ⇒ **此后整个会话再也收不到任何离开通知**。
  于是"我以为光标还在浮条里"那份滞留位置，被 `tick_hide` 当成贴边豁免的依据，连兜底定时器都触发不了。
- **解法**：不去补那枚旗（要动第三方），而是给"位置记录"配一条**独立的事实来源**——
  记下位置的那一刻同时记下 `GetCursorPos` 的屏幕坐标（锚点），定时器里比对**增量**，
  差出阈值（8 物理 px）就判记录过期、整串清悬停位。
- **★ 关键手法：比对"增量"就不需要把两套坐标系对上**。绝对坐标比对要窗口左上角 + DPI 刻度，
  而框架既不公开 HWND、`WindowState` 也不含矩形——为了一条判据去加一枚补丁不值。
  同一份屏幕读数在自己两次调用之间比较，单位天然一致（都是物理像素），零换算、零新依赖。
- **定式 ①**：凡是"**申请一次、靠回执复位**"的通知机制（`TrackMouseEvent`、`RegisterHotKey` 配对、
  一次性定时器、IOCP 的投递/完成），都要问一句"**回执丢了会怎样**"。丢回执 = 永久失聪，
  而失聪的表现通常是"某个状态卡在 true"，比崩更难复现。防护要么把旗在**别的**事件上也复位，
  要么像本轮一样换一条不依赖回执的判据。
- **定式 ②**：**"读不到"与"读到了但不同"必须分档**。锚点或当前读数缺失时**不下判**——
  把 `None` 当成 (0,0) 就是"每次取不到都把浮条闪没一次"。
- **定式 ③**：判据的输入**作参数注入**（本轮是 `tick_hide(viewport, cursor)`），
  与 `core::config` 的防抖时钟同一定式；否则单测只能测真桌面，而真桌面的悬停态在这台机器上
  根本造不出来（K75）。
- **实测**：`GetCursorPos` 单次 779.3 / 806.6 ns（两臂各 200 万次，`-O`）⇒ 每 16 ms 一次
  ≈0.005% 单核，代价可以忽略；但**这条必须量了才写**，"API 很便宜"不是证据。
- **同类**：K73（`||` 短路链里做 `Cell::replace` ⇒ 后面几位根本不覆写）、K75（合成 Move 追不上真
  `WM_MOUSELEAVE`，这条通路只能真机签收）、K74（退出路径上的隐式等待）。

### K81 —— 两臂对照里"快了 19%"可能只是**少做了一步**：速度账必须先证明功能等价

- **现象**（2026-10-20，m57）：带 ICC profile 的 4000×3000 JPEG 上，内置 WIC 路对解码器路是
  **0.81×**（141.9 ms vs 175.5 ms），看着像"WIC 解 JPEG 明显更快"。
- **拆账**：同一尺寸的**无 profile** 对照是 **0.98×**（143.4 vs 146.9）。差的 29 ms 全在解码器臂的

  png/tif 差 0.000）。所以那 19% 不是解码快，是**少干活**。若只报第一张表，就等于给一条
  会偏色的路记了性能功劳。
- **★ 定式**：配对计时**必须与逐像素差同表出**（本轮探针 `examples/wic_vs_decoder` 两列一起打）。
  比值单独看只能证明"谁更快"，不能证明"谁在干同一件活"。同一轮里方向那一判也靠这条：
  `natural`/尺寸一致 + TIFF 逐字节相同，才敢说"WIC 没自己转正、宿主补转不会重复转"。
- **附带坑（判废的证据要从 API 手里拿，不能靠猜）**：想给 WIC 路补 ICC，得先拿到那份档。
  `IWICBitmapFrameDecode::GetColorContexts` 以 `(0, NULL, &n)` 问数报 **n=1**，以 `(1, buf, &actual)`
  索取一律 **`E_INVALIDARG`**（jpg/tif 报 actual=1 却不给对象，png 改报 0），解码器层级
  **`0x88982F81`**；无档文件问数 0、索取 **S_OK** ⇒ 错误与"文件带档"严格相关，不是调用姿势。
  另注：windows-rs 的强类型包装在 count=0 时给的是**悬空非空**指针，要真 NULL 只能走裸 vtable——
  但裸调用与包装读数**一致**，所以这条不构成翻案理由。"能力存在"≠"能力可用"，与 K79 同一族。
- **同类**：K77（4000×3000→1280×800 恰好 5:1 造成的假绿）、K71（体积账要逐段闭合才算账）、
  K79（跨进程读数不分类，只能证"处理了"）。

### K82 —— `format_timestamp_millis()` 在 `default-features = false` 下**静默失效**：一个字节都不输出

- **现象**（2026-10-20，m59）：日志里从来没有时刻。`grep -c "^\[20"` 打在当天那枚 681 行的

### K83 —— 日志的"开头"比"最近"金贵：覆盖写会吃掉会话头，而默认档一提级就露出顺序坑

- **现象一**（判废的账）：旧闸门是"单文件写到 `RUN_LOG_MAX_BYTES` 就 `File::create` 截断重写"。
  截掉的是**当天开头**那几行——会话头（版本 + exe 字节数/构建时间 + 路径 + 系统 + DPI + 命令行）
  与解码器清单。丢了它们，后面写得再全是废的：报告里的崩溃对不上哪一枚 PDB，也判不出环境。
  参照项目走"无上限"，但那对便携目录（U 盘）是不可接受的赌注。
- **解法**：上限提到 2 MiB，**写满即停**——落一条标记（恰好一条）后本进程不再追加，stderr 那一路
  照旧。一次正常会话实测只有 **3.5–5.5 KB**（含会话头 + 12 行解码器 + 翻页叙事），日常根本碰不到
  闸门；真能写满的是反复调试的一整天，那种日子保住开头更值钱。用例
  `run_log_stops_at_the_cap_instead_of_eating_the_head` 钉死这三件事（把 `write()` 改回截断重写，
  第一条断言当场红）。
- **现象二**（提级才现形的顺序坑）：默认档从 `warn` 提到 `info` 之后，抓下来的日志变成
  **第一行是正文**（`[ INFO] rupix: 命令行打开：…`），**会话头在它下面**。因为那句 info 过去被
  过滤器挡在门外，从没落过盘；而写会话头的 `append_run_log` 在 `rupix_lib::run()` 里，比它晚。
- **解法**：那句"命令行打开"挪进 `run()`，紧跟前言之后（`lib.rs`）。绕开过滤器的直接写入
  （前言）与第一条经过过滤器的日志之间**有先后关系**，这条关系以前没人看过。
- **★ 定式**：改变日志**级别档**不是零风险动作——它会唤醒一批从没执行过的代码路径（顺序、
  格式、体积都要重看一遍）。提级之后必须**抓一次真产物**逐行读，而不是只读代码。
- **同类**：K72（批量改文案把路径写成裸 CR，四轮 cargo test 全绿才被 `cargo fmt` 炸出）、
  K63（部署只搬不建，收尾必查 exe 时间戳）。

### K84 —— 真机读数的臂身份**包含配置**：`.build` 的 ini 与当天日志是别人的可变态

- **现场**（2026-10-20，m60 去复现 m59 §17 那条"8 次按压只数到 6 次上屏"）：第一臂跑完就 8/8 对齐，

  当天那枚共享日志从 66 KB 变成 **7.8 KB / 只剩 2 段会话**。
- **直接后果**：同一台机器、同一个 exe、同一条命令，三件事自己变了——① 关窗判词从
  `action=Exit` 变成 `action=Hide`（于是"探针关完窗进程还在"）；② 命中率构成变了（`prefetch=0`
  时每臂都是现解）；③ 我抓的"本轮追加的字节"落在一枚**被别人清过**的文件上。
- **解法**：`build/flip_probe.ps1 -Private` ⇒ 臂自己带环境：`.temp\probe-<tag>\` 里放一枚

  **钉死的 `rupix.ini`** + **自己的 `temp\` 日志根**；解码器仍走 `RUPIX_DECODERS_DIR` 指回
  `.build\decoders`。另加 `-Prefetch 0|1`（要造"每次翻页都现解"的现场）与 `-CloseWhileBusy`
  （不等队列排空就关窗）。
- **★ 定式**：`.build\` 下的 `rupix.ini` 与 `temp\rupix-<日期>.log` 是**运行期可变态**，不是夹具。
  读数只在这些状态属于本臂时才可比；共享目录里读到的东西只能当"现场发生过什么"，
  不能当对照，更不能拿来判"缺陷存在/已修"。判一条真机观察之前**第一步是固定环境**，
  不是加臂次数——**加臂只是在同一个坏环境里多采几次**（本轮三臂齐平才是结论，一臂不齐不是）。
  与 K65（共享桌面上 `.temp` 被别家写入导致位置号漂移）、K36/K78（探针只读自己那一段）同族，
  这次的污染面从"文件位置"扩到了"被测程序自己的配置"。
- **同类**：K65、K75（合成输入只能报命中率，手感必须用户签收）、K72。

### K85 —— 写在交付表里而没有任何一步执行的门禁，等于没有门禁（extension 全仓 clippy 从没通过过）

- **现象**：`RuPix-Decoder/AGENTS.md` §七 的核查表里列着"格式化 exit 0"，`build.ps1` 却在 2026-10-17 才
  补上 fmt 那一步；clippy、`check_docs.py`、`check_deps.py` 三行**始终只在表里**。m61 第一次真跑
  `cargo clippy --all-targets --workspace --release`，结果是 **17 条 deny-by-default 的
  `not_unsafe_ptr_arg_deref` error**（12 枚解码器 × `iv_probe`/`iv_render` + 宏生成的 `iv_last_error`），
  编译直接中断——也就是说这个仓**从来没有通过 clippy**，而 `待办 §15` 当时只量到 `abi` 的 3 条红。
  同一天 `check_docs.py` 被接进门禁后立刻报出文档锚点的空行/越界，逗号清单里漂了好几行的
  `docs/core.md` 才第一次被机器看见。
- **根因**：门禁的"存在"被当成了"生效"。列表里有一行 = 心理上已经交付了；但**没人执行的那一步
  永远不会失败**，于是它保护的东西可以一路坏到底，且坏得没有声音。第二层根因是判据太弱：
  旧 `check_docs.py` 的正则只认整段恰为 `:N` 或 `:N-M` 的锚点（实测 373 段里只解析 261 段），
  所有锚点一律按 `src/lib.rs` 解析，于是"根 `Cargo.toml:…`"这类天然量不准，作者干脆当它不存在。
- **解法**：`build.ps1` 加 `0c`（两条 python 门禁，秒级，放在任何编译之前）与 `0d`
  （`cargo clippy ... -- -D warnings`）；`check_docs.py` 扩锚点正则 + 按"反引号自带 → 行内最近的
  文件名 → 本解码器 lib.rs"三级判定目标文件，本地找不到的记 `skipped` 而不是假报越界。
- **★ 定式**：**新增/修改任何门禁，先让它失败一次给我看**（本轮＝改前 `CLIPPY=101`、改后 `STRICT=0`；
  `build.ps1` 日志的头两行就是 `0c` 的输出，用它证明顺序）。另一条同族纪律：**clippy 不带
  `-D warnings` 就不是门禁**（它打完警告照样 exit 0，见 K69）；warm cache 下 clippy 0.34 s 完成
  ≠ 它没工作，指纹没变就不复检——**证据是改动后手跑一遍为 0、改动前为 101**，不是"跑得快"。
- **同类**：K69（`-D warnings`）、K72（批量改文案把 CR 写成裸 CR，连绿四轮才被 fmt 炸出）、
  K63（收摊必查产物时间戳）。

### K86 —— `grep` 把含 NUL 的源文件判成 binary 就**静默跳过**，批量改动必须让编译器复核

- **现象**：m61 把 kit 的 `write_last_error` 改成 `unsafe fn` 后，按 `grep -rn "write_last_error"`
  列出的清单改了 14 处调用点，`cargo clippy` 仍报 **2 条 `E0133`**——`decoders/jpeg/src/lib.rs` 的
  两处压根没出现在清单里，因为 grep 把那个文件当二进制（"Binary file ... matches"，只打一行提示，
  不吐内容）。
- **根因**：搜索工具的"命中"不等于"全集"。同一个坑在 K78（PS1 无 BOM 被按 ANSI 解）与
  编码/换行差异上是同族：**工具的解析方式决定它看得见什么**，而它报错的方式往往只是一句提示。
- **解法**：跨仓/跨文件批量改名，**以编译器为第二 oracle**：`grep` 清单改完必须跑一次
  `cargo build`/`clippy`（本轮正是它抓回那两处）；检索侧用 `grep -a` 强制按文本处理。
- **★ 定式**：任何"我按清单改完了"的断言，要么给出清单来源，要么给出**能数出全集的另一台机器**
  （编译器、`--list`、sha256 对账）。清单来源单一（一次 grep）时，默认它漏了。
- **追补（m62，根因已查到并清掉）**：那个文件里躺的是**真裸 NUL 字节**——`decoders/jpeg/src/lib.rs`
  把 `"ICC_PROFILE"` 写成含 `\0` 的字节数组字面量，`docs/jpeg.md` 里把 `Exif\0\0` 直接抄成了可见文本
  之外的原始字节。两处都不是谁故意塞的，是把"字符串常量里的终止符"当文案写进了源文件。
  现在改成 `c"ICC_PROFILE".to_bytes_with_nul()` 与"`Exif` 后接两个 0 字节"，两文件 NUL 计数归 0。
  **并把它升成硬门禁**：`解码器仓库工具check_docs.py` 的 `invisible_bytes()` 扫 `abi/`、`decoders/`、
  `docs/`、`scripts/` 与根 `*.md`，出现裸 NUL 直接失败。按 K35/K85 先让它红一次再还原
  （往 `docs/qoi.md` 植一枚 → `MISS docs\qoi.md: 1 raw NUL byte(s)`、`exit=1`；还原后 sha256 逐字节相同）。
  ★ 由此得出的一条通用判据：**"看不见"的字节必须在门禁里显形**，否则它每次都以"某工具静默跳过一段"
  的形式回到你面前，而那份清单看起来是完整的。
- **同类**：K78、K72、K35（判据要能自己红一次）。

### K87 —— 「预渲染一张位图再 blit」在软光栅里**不是 memcpy**：实测比它要替换掉的笨循环慢 9–11 倍

- **现象**：m63 给 `待办 §13` 的 A5（棋盘格每帧 4K 满窗 57,600 次 `fill_rect`）做修法评估。
  当年清单写的候选是"预渲染一张位图、pan 时挪位，只在尺寸变化时重建"。照这个形状加一臂实测：
  4K 满窗 **逐格 4.78 ms → 预渲染 blit 52.99 ms**，800×600 **0.267 → 2.55 ms**，**慢 9–11 倍**。
  直觉里"一次贴图当然比五万次画格子快"，量出来是反的。
- **根因**：`draw_image` 的成本跟**目标框面积**走，而 1:1 吸附（补丁 13）只消掉"双线性重采样"这一项，
  **没有把它变成整数搬运**。同一探针分账：目标框缩到 1/32 面积 ⇒ 快 22–24×；
  框不变、把窗口从 4K 缩到 800×600 ⇒ 只省 0.5–0.9 ms（每帧造一块**整窗** Mask 那一项）。
  每目标像素：blit **5.5–9.0 ns**，同面积纯色 `fill_rect` **0.09–0.25 ns** ⇒ 差 **60–100 倍**（三跑 61/82/101×）。
- **顺带查出的另一件**：那笔整窗 Mask 在"满幅大图"上只占 1–2%，但在**小图大窗**（512² 图放在 4K 窗里）
  占那一臂的 **~36%**（0.85 / 2.37 ms）。所以框架注释里自己点名的"真要根治得复用一块按帧复位的 mask"
  不是洁癖，是一条有百分比的账——只是它救不了满幅那一档。
- **解法**：A5 **登记数字、代码不动**（开关默认关，净代价 4K +2.46 ms/帧、小窗 +0.22 ms/帧；
  "合并同行同色"在 4K 也在噪声带内不省）。候选④（框架级真 blit）的价钱与收益由这条钉住，
  走不走等用户点头。
- **★ 定式**：**"缓存成位图再贴"≠"便宜地贴"**。软光栅里绘制位图本身有每像素成本，它可能比它要替换掉的
  那个"笨循环"更贵。凡是以"改成 blit / 贴图 / 一次画完"为卖点的方案，先和**同面积纯色铺底**比一次——
  那才是这件事的物理下限；下限都打不过，方案就直接判废。
- **同类**：K52（成本随目标像素数走）、K53（读数必须带上发布配置，跨档比较等于换探针）、
  K35（判据要能自己红一次）、K68（只算时间账会漏掉形态账）。

### K88 —— python 的 `read_text()` + `write_text()` 会把整份源码的换行符换成 CRLF，"原样还原"必须拿哈希证

- **现象**：m64 给滚轮节奏闸做先破后立，用 heredoc python 往 `ui/chrome.rs` 植一处破坏、跑完测试
  再替换回去，然后 `sha256sum -c` **FAILED**。查下去发现 `chrome.rs` 与 `canvas.rs` 从纯 LF
  变成整文件 CRLF（1937 / 2278 行全中），等于把两份文件整体改了一遍。
- **根因**：Windows 上 `Path.write_text(s)` 默认 `newline=None`，写入时把 `\n` 翻译成
  `os.linesep`（`\r\n`）；而 `read_text()` 已经先把盘上的 CRLF 读成 `\n`。⇒ **一次读 + 一次写
  就是一次全文件换行符转换**，跟你改没改内容无关。`canvas.rs` 是被同一趟"验证 round-trip 是否无损"
  的试验打回 CRLF 才暴露的（结论：LF 文件 round-trip **不等价**，CRLF 文件等价）。
- **解法 / 规矩**：改源码文件**一律用编辑工具**（实测保留各文件自己的行尾：LF 的改完仍 LF，
  CRLF 的改完仍 CRLF）。非要写 python 脚本动源码，就用二进制口径
  （`read_bytes()` / `write_bytes()`，或 `write_text(..., newline="")`），并且**改完立刻 `sha256sum -c`**。
- **★ 定式**：任何"我用脚本原样还原了"的断言，判据是**哈希**，不是"我把那段替换回去了"。
  本仓文件行尾本来就不统一（`config.rs` / `runtime/mod.rs` 是 CRLF，`canvas.rs` / `chrome.rs` 是 LF），
  "看起来一样"在这种仓库里根本靠不住——整文件换行符改动在没 git 的仓里连 diff 都看不见。
- **★ 补一条（同日收尾差点被自己的探针骗）**：数行尾**别用 `grep -c $'\r'`**。git-bash 里那个模式
  退化成"匹配每一行"，`canvas.rs` 报 2278 而它盘上 `\r` 字节数是 **0**，当场像是"K88 又犯了一遍"。
  判行尾只有**字节口径**：`open(p,'rb').read().count(b'\r\n')` 与裸 `\n` 分开数，再与上一轮快照比。
  与 K86 同形：**探针本身会谎报，而它谎报的方向刚好让你确认你怕的那件事**。
- **★ 再补一条（m66 同日，K88 的镜像方向）**：这次不是 LF→CRLF，而是 **CRLF→LF**。
  用"安全"的二进制口径重写文件：`read_bytes() → .decode('utf-8') → 拼新代码 → .encode('utf-8') → write_bytes()`，
  看着全程没碰文本模式，**但新拼进去的那段是 LF 字面量**，于是文件变成"CRLF 主体 + LF 新增段"的**混色文件**；
  紧跟其后的 `cargo fmt --all` 遇到混色就把**整份文件按它自己的判断归一成了 LF**（390 行全中）。
  两道手续各自都"没错"，合起来还是一次整文件换行符改动——**"我用二进制读写"不等于"我没动行尾"**。
  规矩加一条：**新写代码段要沿用目标文件自己的行尾**（本仓 CRLF 与 LF 文件并存，动手前先数一次），
  并且 `cargo fmt` 之后**再数一次**，与快照对齐。发现方式＝改完立刻与上一轮快照比 CRLF 计数（这次没等哈希报错）。
- **同类**：K72（批量改文案写出裸 CR）、K78（PS1 无 BOM 被按 ANSI 解）、K86（grep 把含 NUL 的文件
  判成 binary 静默跳过）——三件加这一件是同一族：**工具的解析与写出方式决定它动了什么，
  而它通常不报告自己动了什么**。
- **★ 2026-10-24（m113）补这一族的第二个失效形态：锚点没命中时，python 的"按索引拼接"会把整段内容吞掉。**
  我给 `docs/待办.md` 追加一条流水，写的是
  `j = s.find(第二个锚); lines/s = s[:i] + 新块 + s[j+1:]`——**两个锚都没 assert**。第一个锚命中了，
  第二个锚那份文本在文档里**不存在** ⇒ `find` 返回 `-1` ⇒ `s[j+1:]` 变成 `s[0:]`，
  等价于"删掉 i 之后所有内容再补一份全文"：实际结果是 **156,793 B → 44,154 B，§6–§18 与"已完成"存档整段不见了**。
  发现方式不是我检查了文档，而是**改完与本轮 `历史快照` 快照 `wc -c`/`diff` 对了一眼**——快照habit救的。
  ⇒ 三条硬规矩：① **脚本改文件，每个锚点都要 `assert s.count(a)==1`**（找不到就当场炸，不许静默 -1）；
  ② **只在"追加/替换一小段"时用 Edit 工具**，它按字面匹配、失配就报错，不做索引数学；
  ③ **任何脚本化改写之后立刻 `diff` 上一轮快照并看"删掉的行数"**——`^<` 只该出现被我明确替换的那几行。
  （这条与 K105 的"字节级读写 + sha256 对账"是同族：**改文档的风险和改源码的风险同一量级，因为正本只在文档里**。）

### K89 —— 单条腿的孤立提速必须在"用户等的那一段"复测，否则 10–26% 在端到端噪声里不存在

- **现象**：m65 查首屏 `post` 那条腿（宿主 `fit_to` 面积平均）。单测很干净——把宿主 crate
  从 `opt-level="z"` 提到 3，`fit_to` 从 119 → 108 ms（6055²）、111 → 82 ms（5120×3840），**10–26%**。
  照这个数，"提编译档位"像是一行就赚的事。
- **复测**：同一台机器、同一批样本、z 与 opt3 两套产物**交替四趟**跑生产入口 `bench_first_paint`：
  PNG 56.3 / 61.6 对 56.2 / 62.7，JPEG 458 / 473 对 474 / 532，TIFF 260 / 265 对 273 / 286
  ⇒ **两臂互相咬进 ±10% 的噪声带**，TIFF 那臂甚至反过来像变慢。那条腿在首屏里只占 10–26%
  （其余是解码本体的 150–900 ms），所以单函数的收益一相乘就掉进噪声以下了。
- **裁决**：**不做**（代价是整箱代码生成换档 + 体积要涨 + 每次比较都要重出基线）。
  对照 K53 那一次能成立，是因为它量的是**每帧**的绘制成本（`lto` 关掉，整窗铺底 0.130 → 0.048 ms、
  生产@200% 一帧 9.7 → 7.1 ms，幅度 27%，而那一臂本身就是终点）——**同一条"提优化档位"的手术，
  量对了终点才有结论，量错了终点只剩噪声**。
- **★ 定式**：任何"某函数快了 X%"的读数，写进裁决之前必须回答**"用户等的那一段"快了多少**
  （本项目三条计时终点：首屏空白期 `bench_first_paint`、每帧 `paint_cost_probe`、按键到上屏
  `[main-latency]`）。孤立增益 × 占比 落在噪声带里，就写"量不出来"，不许写"快了 10–26%"。
  配套两则：①两套产物要**交替**跑（同一臂连跑四轮只证明它自洽）；②`opt-level` / `lto` 一换，
  历史读数全部作废为"另一档配置的数字"（K53 的"跨档比较等于换了一支探针"）。
- **同轮另一条（下限探针自己也要验）**：第一版 `post_leg_probe` 的"摸一遍内存"下限写成
  **逐字节**求和，量出 152 MB 要 46 ms＝只有 3.3 GB/s，据此算出"`fit_to` 比下限慢 3 倍"，
  于是把"还有向量化头寸"判小了；改成**按字宽**求和（`chunks_exact(8)` + `from_ne_bytes`）
  后同一份只要 9.5–11 ms（≈14 GB/s），差距真实是 **11–12 倍**。
  规则：**"下限臂"必须自己先跑到该机的带宽量级**（读一遍大缓冲应在 10 GB/s 以上），
  否则它不是下限，是另一段没优化的代码——用错下限会把"有肉"判成"没肉"，也会反过来把噪声判成收益。

### K90 —— "免一次 syscall"的等价改写不等价：缓存属性判的是链接本身，而夹具会绿得毫无意义

- **现象**：m66 量 B1（大目录枚举）。拆段很清楚——3000 项里 `read_dir` 本身 1.4–1.5 ms，
  而逐项 `Path::is_file()` 要 46–54 ms（占 87%），每次都是一个 `GetFileAttributesW`。
  于是"显然的修法"浮出来：`DirEntry::file_type()` 读的是 `FindNextFile` 已经递到手的
  `WIN32_FIND_DATAW.dwFileAttributes`，**不用额外 syscall**。照它写出来的 B 臂确实到地板（3.5 ms，
  13–17×），探针里三档目录的清单也**逐项等于生产**。
- **翻车点**：那个"逐项等于"是在**纯普通文件**的夹具上得到的。专门造一组链接形态夹具（真文件 /
  硬链接 / 链到真文件的符号链接 / 断链 / 顶着图片后缀的目录 / junction）之后，B 臂**少一项**：
  `file_type().is_file()` 对符号链接报的是**链接本身**（`is_symlink`），跟不到目标，于是
  "链到别处的那张 `.jpg`"被判成不是文件、**从清单里消失**。这不是性能差异，是用户翻不到那张图。
- **修法（落地的形态）**：只在**缓存属性已经说是文件**的那一支免 stat，其余（目录 / 符号链接 /
  `Unknown` / 读不到属性）一律照旧 `Path::is_file()` —— 这样**不可能比生产少一项**（最坏是退回旧成本），
  而快路覆盖率就是收益：3000 项 54–66 → 3.6–4.0 ms。`Unknown` 那支不是假想：
  `DirEntry::file_type()` 在非 Windows（NFS 等）上可能给不出类型，而本项目的可移植性是要讲的
  （弃 WIC 的理由就是它），`core` 层不能留"换个平台整目录看不见"的洞。
- **★ 定式一（优化换了判据的**来源**，就要把新旧判据的分歧形态造进夹具）**：判据从"问文件系统"
  换成"问枚举缓存"，等价性就不该按"看着一样"来判——两者只在**没有链接的目录**里相等。
  分歧形态要逐个造出来比清单，且**先比清单再谈加速**（本轮同一条规矩救了这次：B 臂的 17× 当场作废）。
- **★ 定式二（夹具活性自检，本轮栽了两次）**：
  ① 第一版链接夹具把 `../.temp/.../real.jpg` 当符号链接目标传给 `CreateSymbolicLinkW`——相对目标是
  **相对链接所在目录**解析的，于是三条链接全成断链，A 与 B"都挡掉"、等价性"通过"，绿得毫无意义。
  改成绝对路径后 `sym` 才真的进 A 的清单。② 同一轮把这条判据搬进 lib 单测时用 `.jpg` 造夹具，
  而单测进程没装解码器、`declared_exts()` 只剩内置登记表（自动认领的只有 `resvg` 的 `svg/svgz`）⇒
  清单直接空、`from_file` 报 `NoImages`，用例红在**前提**而不是**判据**。两条合起来是一条：
  **夹具必须落在被判据管的那条分支里，并自证它活着**（探针里现在打一行"夹具活性：在/不在"，
  不在就整组不判）。这与"escape-hatch fixtures keep suites green over dead code"是同一个病。
- **★ 定式三（反序复跑不是仪式）**：②段手势第一遍读"换档 4 次"，同参数复跑读"10 次"——
  共享桌面上派生线程被抢带宽时结果会整段消失。本轮只把**两遍都成立**的东西写进结论
  （解码回包 0 包、放大段像素单调递增），量与量之间的比值一律不当数。

### K91 —— 判据要落在用户看得见的量上；竞争型夹具要靠"堵路"变成确定性的

- **现象一（m66 埋雷、m67 撤回）**：m66 量缩放跟手性时，我拿"上屏清晰比 0.83–0.94"当作
  "画面在追"的证据，据此写下一个预测：派生压到 20–40 ms 就追得上滚轮。m67 把派生真的压到
  42–46 ms，同一个探针复跑，手势期间的糊面占比仍是 **91.7 / 48.0 / 96.6%**，与改前几乎逐位相同——
  预测不成立。原因不在数字，在**判据选错了量**：清晰比是"某一时刻像素够不够"的**比值**，而用户
  感受的是"这段手势里有多长时间是糊的"；压住后者的是 **120 ms 的换档节拍**（每格来一次、派生
  再快也只在节拍点上换），不是单次派生的耗时。派生变快只缩短了"停手到清晰"这一段（137–254 →
  58–198 ms），这一段是真实收益，但它不是原来那条预测说的东西。
- **★ 定式一（比值降 ≠ 用户那件事变好）**：一个比值可以变好而用户毫无感觉，也可以原地不动
  而用户明显受益。下预测前先问：**这个量在用户那里对应哪一段可感知的时间/动作？** 对不上就
  换量（本轮正解是"糊面时长占比"与"停手到清晰"两条分开报），而不是拿比值硬解释。撤不回的数
  不如不报；已被实测推翻的预测**就地写"不成立"**，不改口径去圆它。
- **现象二（m67 抓到一个既有用例的假绿）**：`level_thread_collapses_to_the_newest_job` 原来连投
  四档、断言"只回一包"，平时一直绿。给合流加计数时它偶发回两包——因为派生线程若在第一次投递
  之后才醒来，`try_recv` 只能吞到当时已到的那些，**这是夹具与线程的赛跑，不是合流的漏洞**。
- **★ 定式二（竞争型夹具要"先堵路再开门"）**：把它改成**先投一个能算很久的大活**（2400×1600），
  确定线程已经在算，再连投四档小活；然后用**最终一致性**等 `collapsed + computed == posted`
  再断言（附 5 秒死线，超时把计数打出来）。这样"合并成几包"不再取决于调度时机。同时变异验证：
  把合流计数摘掉，用例立刻红在 `collapsed: 0`。**竞争型断言只测它想测的那件事，别顺手把
  调度顺序也钉成契约。**

### K92 —— 为了"让它崩"去保护目标代码页，会把异常分发自己打死：无报告、无 dump、UEF 一次没进

- **现象**（m68 造发布版崩溃夹具）：为了让异常地址落在宿主 `wndproc` 上，把 `wndproc` 所在页
  `VirtualProtect(PAGE_NOACCESS)`，再 `PostMessage` 叫宿主走进去。结果 VEH 先报一次 AV
  （地址确为 wndproc），**紧接着同一个系统地址 `0x7FFC3A883793` 刷屏**，最后异常码
  `0xC00000FD`（栈溢出）；生产 UEF 过滤器**一次没被调用**，`temp\` 里无报告、无 dump。
- **根因**：异常分发与栈展开（`KiUserExceptionDispatcher` → handler 查找 → unwind）
  **自己就要读/执行被保护的那一页**。页不可访问 ⇒ 分发过程中再次 AV ⇒ 递归 ⇒ 栈溢出；
  到了栈溢出那一刻，同一线程已经没有余量去写 dump。
- **解法**：**别保护一个"即将在其中执行"的页**。要造真实的 `0xC0000005` 且故障地址在宿主页上，
  应当改**代码**而不是改**权限**：在目标函数入口写入 `48 A1 FF FF FF FF FF FF FF FF`
  （`mov rax, moffs64`，读 `0xFFFFFFFFFFFFFFFF`），`FlushInstructionCache` 后叫宿主进入——
  页仍可执行，故障发生在指令内部，异常码是干净的 AV。附：`int3`（`0xCC`）不行，
  user32 会把窗口过程里未处理的异常转成 `0xC000041D`，且故障地址漂到别处。

### K93 —— 读 dump 的脚本跑了几个 build 也可能全错：必须拿**真产物**喂一次

- **现象**（m68）：`build/dump_sym.py` 此前一直对着 `examples/crash_probe` 的 dump 用。第一次
  拿发布版 `rupix.exe` 的 dump 喂它，暴露两处：
  1. 打印线程名时抛 `UnicodeEncodeError: 'gbk' codec`——**整条符号化在最后一步（输出）挂掉**，
     前面解出的地址全白算；
  2. 线程名从第二项起变成模块路径——`MINIDUMP_THREAD_NAME` 的步长猜错（8 字节、16 字节
     两种都试过，都不对）。
- **根因**：① 本机控制台是 GBK，脚本头注释承诺"输出保持 ASCII"但代码没做到；② 该结构是
  **紧凑 12 字节**：`ThreadId` u32 @+0、`ThreadNameRva` RVA64 @+4。
- **判据**：**流长度自己会说话**——`ThreadNames` 流长 `52 = 4 + 4×12`（4 字节条数 + n 条 ×12）。
  修法：`sys.stdout.reconfigure(errors="backslashreplace")`；步长按长度反推，不再按"对齐直觉"猜。
- **教训**：对"返回成功但内容是垃圾"的工具，要加**结构自洽校验**（长度、范围、条数），
  并拿已知地面真值（自家线程名 `main / sv-decode / …`）对账；工具的验收产物必须是
  **用户实际会拿到的那一份**，不是最方便造的那一份。

### K94 —— 臂名写着"生产@200%"，几何却是 26% 降采样；变异"存活"不等于实现等价

- **现象**（m70）：
  1. `paint_cost_probe` 里一条臂标着"主图 pixelated 6055² → 1600×1200（生产@200%）"，
     实际 1600/6055 ≈ 26%，是**降采样**——pixelated 与 Nearest 从头就没进过那条路。
     m69 据此把"生产最近邻 15.3 ns/px"报了出去，直到 m70 补真几何（6055² → 12110² 框）
     才发现真正的数在 6.3 ns/px 这个量级。
  2. 最近邻快路的映射写成 `(p - t)/s` 后跑测：**全部用例绿**。差别只在整数边界的 1 ulp，
     既有几何（整数倍率、落点 0）两条写法恒等——变异根本没被夹具覆盖。
- **根因**：① 臂名是**人写的注释**，与 `Rect` 里的几何没有机器对账；对像素敏感的结论
  必须从几何本身推（`dw/iw`），不能信标签。② "等价改写"只在两种来源**会分歧的形态**上
  才可证；随手挑的样本恰好落在分歧之外时，green 是假证据。
- **判据与修法**：① 探针臂名写清倍率来源，m70 把降采样臂改名并另立真 @200% 臂与
  "强制通用路"对臂（`opacity = 0.999_999`）；② 用 numpy 搜 f32 分歧点，找到
  6×6→13×13、`dx=6`（inv+乘加 = 2.9999998，除法 = 3.0），把它作为边界用例塞进
  逐字节测试，变异随即变红；③ 映射顺序（先乘后加、`trunc`、夹取）写进补丁台账，
  标为与上游对齐的契约，不是实现细节。
- **教训**：变异存活先怀疑夹具，再怀疑实现；"我换了个写法"要证明的正是
  **两种写法会给出不同结果的输入**，而那种输入往往不在自然样本里。

### K95 —— 时间的函数不会自己上屏：日志对了，画面还是旧的

- **现象**（m71）：解码卡住的可观测提示第一版只改了 `status()` 文案与 `tick()` 里的 warn。
  挂死夹具复跑：日志在 **10.0 s 准时**写出 `WARN [stall]`，但同一时刻截图上的状态栏
  仍是 `1/3 · 载入中…`——既没有秒数，也没有「可能卡住」。
- **根因**：本项目"没人标脏就不合成"。`status()` 只在**发生一帧绘制**时被读一次，
  而"已等 N 秒"是**时间的函数**：第 3 秒、第 4 秒都没有任何事件去标脏。
  改前那张图同样停在旧句，正好说明 `PrintWindow` 也不会替你重算——它截的是最后一帧。
- **判据与修法**：凡是显示内容里含"现在几点 / 等了多久 / 倒计时"，就必须有一个
  **按整秒变化主动返 `true`** 的标脏源（`wait_shown_secs`）。存整数秒而不是
  "每帧都脏"：卡住时每秒一帧，符合省电设计；也保证文案的每一档变化都有一次绘制。
- **教训**：`status()` 的单测只能证明"这时候该写什么"，证明不了"这句话会出现在屏幕上"。
  时间型状态要在**真探针的截图上**验收；日志与画面是两条独立通路，一边对了不代表另一边也对。

### K96 —— match 里的裸标识符是绑定不是常量；"快了 N 倍"与"不卡了"是两笔账

- **现象**（m72）：
  1. `transformed` 的 8 朝向改成 u32 分块后，rot=3 的输出与 rot=1 相同。
     原因是臂写成 `(1, flip)`：`flip` 在模式位置是**绑定**，匹配任何 bool，
     于是 `(3, ...)` 永远先命中它；编译器不报错，用例只在 8 朝向全比时才抓住。
  2. 搬运本身已从 592 ms 降到 199.8 ms（100 MP rot90），看着像"性能已解决"；
     但同一张图按 `R`，UI 线程一次往返仍是 112–233 ms——搬运提速没有改变
     "主线程停下来算"这件事。
- **根因**：① 模式匹配的常量与绑定在语法上只差一个 `_`/字面量，且覆盖顺序决定结果；
  ② 性能账有两条独立通路：**算法耗时**（基准）与**用户等待**（UI 线程是否停下）。
  前者变快不会自动兑现后者，尤其当耗时仍高于一帧预算时。
- **判据与修法**：① 多臂常量匹配写 `(1, fl)` / `(3, fl)` 这类显式绑定并每条臂都用上，
  或写 `(1, true)`；修好后补 65×67 非整块 + 非对齐回退的逐字节用例。
  ② 大图朝向改走派生线程，判据用"源像素 + 目标像素"上限（2.7 M ≈ 8 ms）分流；
  端点只认 `SendMessageTimeout(WM_NULL)` 的 UI 往返，并另记 `transformed` 基准。
- **教训**：会静默出错的匹配臂要用**对照用例**钉住；性能改动必须同时报
  "算法 ms"与"用户等 ms"，只报前者等于没验。

### K97 —— `Arc<[u8]>` 从 `Vec` 建出来一定整图搬一次；判据要写在便宜的那一侧

- **现象**（m73）：36.7 MP 的图按 `1`（原尺寸），UI 线程连停两段 64 + 52 ms。挂临时秒表拆开：
  1. `install` 里 `let base: Arc<[u8]> = Arc::from(d.bitmap.rgba)` ⇒ **146.7 MB / 32.9 ms**。
     这一句上一轮的文档写的是"移动，不拷贝"——**写错了**：std 只能为 `Arc<[u8]>` 另开一块
     带 Arc 头的分配再把字节搬过去，`Vec` 的分配前面塞不进那个头。
  2. 鸟瞰留用判据写成 `let fresh = nav_thumb_of(&base, w, h);` **再**比较 `fresh` 与旧档尺寸——
     采样本身已经发生了，判据等于没写（`nav ms=52.2` 里扣掉拷贝还剩 26 ms 就是那一刀）。
- **根因**：① 把"类型带 Arc"当成"零拷贝"，没查这条转换在 std 里到底做什么；
  ② 判据的**成本顺序**没审：先做贵的一步再判断要不要做，逻辑上对、时间上白花。
- **判据与修法**：① 像素缓冲统一改 `Arc<Vec<u8>>`（`Arc::new(vec)` 真的只是装箱，一个字节不动；
  用它的地方仍按 `&[u8]` 走 deref 链），M1 的"显示档与 base 同一块内存"照旧由 `Arc::ptr_eq` 用例钉；
  ② 判据先算便宜的一半：`fit_dims` 只出尺寸，比完再决定要不要 `nav_thumb_of`；
  ③ 留用的门槛写成"旧档 ≥ 新档的 3/4"而不是 `>=`：视口档采出来是 **511**、原图档是 **512**，
  严格比大小会让每次升级都重读整图，而鸟瞰只画 ≤512 px，那 1 px 看不见。
- **顺带记一条工具的限度**：`examples/mem_chain_probe.rs` 只读**常驻**字节。给 `install` 加一个
  `.clone()`（瞬时多 140 MB）再跑，它"install 又自己留下多少"那行读数一字未动、峰值也不动——
  **瞬时峰值它看不见**。所以本轮只报时间收益，不报内存收益。
- **教训**：一句"不拷贝"必须有**实测的毫秒**背书；判据要按"便宜的先算、贵的后决定"排；
  工具读不到的量，就不许写成收益。
