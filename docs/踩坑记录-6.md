## 七、门禁自己的坑

### K157 —— 文档点名门禁长期绿，却漏登记了 21 个文件（整层没人读）

- **现象**（2026-10-29，宿主查缺补漏轮）：`docs_consistency.rs` 的 j2「结构文档覆盖 `src/` 全部 `.rs`」
  一直是绿的。把判据改成**按小节拼出完整相对路径**再与磁盘比，当场翻出 **21 个从未登记的的文件**——
  其中包括**整个 `extensions/` 层**（5 个文件在 §一 分层表与 §三 文件清单里一个字都没有），
  以及 `core/ext.rs`、`core/derive.rs`、`platform/logging.rs`、`platform/shared_mem.rs`、
  `ui/tokens.rs`、`ui/text_window.rs` 等。§三 是"哪个文件管什么"的唯一人读入口，它缺了一层。

- **根因**（判据读错了对象）：旧判据是 `doc.contains(文件名 basename)`。而同一份文档的**第五节符号索引
  是机器生成的**，每行都写着 `core/ext.rs`、`extensions/run.rs` 这类完整路径 ⇒ 任何一个 basename
  都能在生成段里被子串命中。**被检查的那张表根本没被读，读的是它的副产品**。
  第二条同因：§一 表格与 §四「计数相等」那行**确实**把 extensions 的 5 个文件计进了 101，
  所以"总数对得上"这件事从头到尾没有断过——总数对得上恰恰不能证明逐文件登记过。

- **解法**（就地修判据，不另立第二道门禁）：
  1. j2 改为**按 §三 的小节标题拼路径**：`### 3.4 \`extensions/\`` 之下的 `| \`mod.rs\` |`
     拼成 `extensions/mod.rs`；根文件节不加前缀。散文与符号索引段不参与判定。
  2. 配一枚用例钉住这条判据本身的形状（`j2_same_basename_does_not_cover_another_path`）：
     core 与 ui 两节各有一行 `mod.rs` 时，必须分别覆盖 `core/mod.rs` 与 `ui/mod.rs`，
     而**没开小节的层不许被别处的同名行顶上**。
  3. `structure_gen.py` 的 §一 表格更新正则里原本漏了 `extensions` 一档（LAYERS 有它、正则没有），
     补上后生成器才真能刷这一行的数字——**生成器与门禁读同一张表时，两边的名单必须同源**。

- **可复用的判据**（比这条坑本身更有用）：
  **「多处描述同一事实」先问哪两两之间有机器读过**。这里同时有三处写着"有哪些源文件"
  （§一 计数 / §三 清单 / §五 索引），机器只把它们当**总数**核对，**逐文件那一维没人读**——
  于是登记缺口可以无限期存在。要么给那一维上判据，要么删掉其中一处的独立性，别再复制第三份。

### K158 —— 宿主用例把"某个后缀有人认领"当常量，解码器换档当天就红

- **现象**（2026-10-29）：`tests/config_pipeline_e2e.rs::decoders_disabled_key_gates_decode_end_to_end`
  红了，报「发布目录里应有认领 .ppm 的解码器」。宿主代码一字未动。
- **根因**（把外部集合的快照当常量）：这条用例的意图是「ini 键 `decoders_disabled` → 停用唯一认领者
  → 解码失败」，它**已经**做到不硬编解码器 id（从运行时自述里找），但**仍钉死了后缀 `.ppm`**。
  同日另一路把发布档换到 common 0.2.4 / modern 0.3.2 / pro 0.4.1，common 自述的后缀
  从 31 缩到 24，`ppm` 不在里面 ⇒ 夹具的门票没了。而按魔数嗅探仍能解 `.ppm`
  （所以另外三条 ppm 用例照绿）——**红的那条不是解码坏了，是"谁认领这个后缀"变了**。
- **解法**：夹具格式也按运行时自述挑（`claimant_fixture`：在"我们能自己造字节的格式"里
  找今天真有人认领的那一种），后缀与 id 都不写进代码。判据一句话：
  **凡是向外部集合（解码器自述 / 远程清单 / 系统字体）取的常量，都要在运行时问，不许抄快照**。
- **顺带**：换档后随包的 `docs/decoders.json` 与目录里的 DLL 版本不再对应，设置页「可下载」卡
  如实显示「清单异常，请「刷新」」——那是清单该重出（解码器仓的事），不是宿主缺陷。


### K159 —— 「不卸库」这种判据，缓存桩在结构上就读不到；可删性才是物证

- **现象**（2026-10-29，m157）：待办 §21.3「真实 DLL 被加载锁住时的热更新」在 m156 被当成
  "已有两条用例钉住"。真去量才发现那三条 audit 用例全都用 `Loaded { _lib: None, .. }` 手工塞表——
  **桩里没有 `Library`**，于是"淘汰只置停用、不在会话中途 `FreeLibrary`"这句话
  桩在结构上就不可能读到：把 `self.loaded.remove(path)` 写进生产代码，桩用例照样全绿。
- **根因**（判据的主语搞错了）：这条判据的主语是**操作系统持有的镜像映射**，不是宿主的表项。
  拿"表里还有没有这一条"的桩去钉"句柄还在不在"，钉的是两个东西。
- **解法**（真机配对，跑 0.04 s）：把发布档里的真 DLL 拷进仓内 `.temp` 夹具，
  **用可删性当探针**——`remove_file` 失败（这台机器 `code=5` ERROR_ACCESS_DENIED）= 映射还在，
  能删 = 已卸库。再配一枚对照：同目录里一枚从没加载成功的坏档**必须删得掉**，
  否则"删不掉"可能只是介质只读。两条变异各验一头：改成摘条目**只红被淘汰那一格**；
  改成 `_lib: None` 三条**全红且红在首次解码**（`解码器「common」探测时出错，已隔离`）
  ⇒ 句柄不只是一把文件锁，它撑着函数指针。
- **顺带量到一条反直觉**：**改名（挪位）对正被加载的 DLL 是成功的**，改完名仍删不掉
  ——映射跟文件对象走，不跟名字。所以 `install.rs` 那句「旧 DLL 挪不开（多半正被加载，重启后再装）」
  的因果要反过来读：升级撞上"这张图正在用这一格式"时**挪位能成**，真后果是旧档变成
  删不掉的 `.old` 留在目录里，而这条链以前全程无声。
  判据：**Windows 上"占用"挡的是删除，不是改名**；凡按"删不掉"设计回滚的代码，都要量一次改名。
- **可复用的判据**：**判据主语在 OS 手里时，桩只能钉宿主表项，钉不了句柄**——
  这种格子要么写真机量具（可删性 / 文件锁 / 进程句柄这类外部探针，并配一枚"应当成功"的对照），
  要么在台账里明写"未测"。**不许用桩的条数冒充覆盖。**

### K160 —— `canonicalize()` 会加 `\?\` 前缀，而 Win32 的一批路径接口不认它

- **现象**（2026-10-29，m159 收测试落点）：把 37 处测试夹具的落点从系统 TEMP 收回仓内
  `.temp/rupix-test/`，助手函数顺手写了一版 `raw.canonicalize().unwrap_or(raw)`（本意是消掉路径里
  的 `..`，好让 `p.parent() == Some(dir)` 那类比较拿到同一个形态）。改完
  `platform::recycle::moves_file_into_recycle_bin` **当场红**：「移进回收站失败：文件仍在原地」，
  而这条用例在此之前一直绿。
- **根因**：Windows 上 `Path::canonicalize()` 返回的是 **verbatim 路径** `\?\E:\…`。
  `std::fs` 认它，`SHFileOperationW`（回收站走的那条）**不认**——它不解析这个前缀，也不做规范化，
  拿到就直接失败。同类接口还有一串（凡是老式 `*W` 路径入口都该怀疑），所以这不是回收站一条用例的毛病。
- **为什么以前没撞到**：`std::env::temp_dir()` 从来不返回 verbatim 路径。缺陷藏在**新写的助手**里，
  不在被改的用例里——用例只是把"藏在落点里的那一步"暴露出来了。
- **解法**：改用**词法**绝对化 `std::path::absolute()`（同样消掉 `..`，但**不加前缀**）。
  判据落在函数注释里：**跨 API 的路径要按最窄的那个接口写，别按 Rust `Path` 的手感写。**
- **可复用的两条**：
  ① **机械换落点时先做最小版本**（纯换根路径，不加规范化、不顺手清理），跑一遍门禁再谈改进——
  这次红的那条与被移动的语义无关，是"顺手加的那步"带进来的。
  ② **用例先问"是产品坏了还是量具坏了"**：同一轮里两条外部读数（新条目确实落在了 `.temp/rupix-test/`、
  系统 TEMP 按 36 条前缀命中 0）已经证明落点改动是对的，所以红点该往量具自己身上找——
  顺着这条路三分钟就定位到 `canonicalize`，否则很容易被读成"回收站功能坏了"。

### K161 —— `grep -c $"\r"` 数的是本地化翻译引号，不是回车：我用它报了一出不存在的 CRLF 缺陷

- **现象**（2026-11-01，m180）：审计两仓时我报"219 / 30 个文本文件虽然 `.gitattributes` 写了
  `eol=lf`、实际存的是 CRLF"，还给了修复方案（`git add --renormalize` + 两仓各提交一次）。
  用户批准"那就修复并提交"。复测之后才发现**缺陷根本不存在**：解码器仓 348 个跟踪文件里文本 blob
  含 `0x0D` 的是 **0**（含 CR 的 20 枚全是 `testdata/golden/*` 二进制夹具，CR 是图片数据本身）、
  插件仓 46 个文件也是 **0**；`git status` 两边都干净，`git add --renormalize` 是 no-op，
  那两次提交会是**空提交**。
- **根因**：Git-Bash 里 `$"…"` 是**本地化翻译引号**（Windows gettext 的语法），不是 ANSI-C 转义——
  要写回车得用 `$'\r'`（单引号）。于是 `grep -c $"\r"` 拿到的是字面量，数出来的是"匹配某串的行数"：
  同一份 `README.md` 报 32，而它真实 CR 数是 0。**假计数被我用 `sort | uniq -c` 汇总成"219/30"，
  看起来就像一次严谨的普查。**
- **解法**：数行尾只按字节读——工作副本用 `tr -cd '\r' | wc -c` 或 Python `b.count(b"\r")`；
  要看**仓库里存的是什么**就 `git cat-file blob HEAD:<file>` 再数（这才能把"工作副本 CRLF"与
  "blob CRLF"分开，两者是两回事：`text eol=lf` 下磁盘可以是 CRLF，blob 与 index 仍是 LF，
  归一化发生在 `add`，不产生 diff）。
- **可复用的三条**：
  ① **缺陷规模这类数字，写进结论之前要换一把独立的量具复测同一格**。同一条 shell 管道里的两个计数
  不能互相证明——这次的 219 和 30 出自同一把坏尺子，所以它们"互相印证"是幻觉。
  ② **用户批准的是"修那个缺陷"；缺陷不存在时，正确动作是当场撤回并给数**，不是"总归没坏处就跑一遍
  renormalize"——那会留下空提交和"已经修过"的假记录，比没做更坏。
  ③ 顺着这条又抓到一处**同族的真限度**：两仓清单的 `size` / `sha256` 描述的不是同一层字节
  （解码器 = 包内 DLL，宿主 `decoders::install` 解压后比；插件 = 整枚 ZIP，宿主
  `extensions::verify_package` 对下载到的 zip 比）。判"改了一层材料要不要 bump / 重传 / 重算数字"
  先问**清单的 sha 算的是哪一层**，别把另一仓的习惯照抄过来；判据表在解码器仓
  `docs/releasing.md`「改了哪一层材料」，宿主侧的分流在 `decoders/install.rs` 与
  `extensions/mod.rs` 两处校验点的注释里各写了一句。

### K162 —— 矢量「原图尺寸」其实是首屏渲染画布：夹在它上面放大，就只有位图插值

- **现象**（2026-11-01，m189）：用户在 `.build\矢量图` 逐份检查后报「示例.pdf 放大后就模糊
  不清，但我用 PDF 阅读器打开能完美放大」。同一批里绝大多数 doc 族格式（PS/WMF/EMF/DXF/HPGL…）
  放大也都只能是位图糊面——只有 svg/svgz 是真的曲线。
- **根因**：这些解码器没有 ABI v6 的 `iv_render_region`（报告 `region=false`），而且只回
  `actual_w/actual_h`（这一次渲染的画布），**不回页面点数**。于是宿主手里的 `natural` 就是
  "按视口框渲出来的第一张画布"；`desired_pixels` 又按位图口径把目标夹在 `natural` 以内 ⇒
  缩放永远只在首屏画布上做本地重采样。**图本身是矢量、解码器也肯按 target 重画**（实测
  target=2000 时 PDF 出 1413×1999、DXF 出 2000×1238），是宿主从来没再问过更大的那一档。
- **解法（只在宿主侧，不动解码器）**：新增 `core::formats::needs_zoom_rerender(ext)`
  = 解码器自渲染 **且** 不能区域重渲；Viewer 在"缩放变化 + 当前位图盖不住"时按
  `natural × 倍率 × DPI`（总量夹 64 MP）**再要一整幅**，落地后 `natural` 冻结在首屏画布
  （`prefetch::install` 同路径沿用），并按（路径 + 上次目标）记账 `vector_zoom_req`，
  防"解码器不理 target"时每轮重发。单测 `viewer::tests::target_vector_*` 三条，红证 = 关掉
  这条支路即红。
- **可复用的两条**：
  ① **"报告尺寸"不等于"文档尺寸"**：凡是渲染方按 target 画、只回画布尺寸的契约，宿主就必须
     区分"这一次画多大"与"文档多大"；拿前者当后者，几何、区域坐标、升级闸会一起错。
  ② 判"放大糊"先问**解码器肯不肯重画**，再问**宿主有没有再问**。这次两个前提都成立（探针
     直接调 DLL 按 target 2000 出图正常），坏的只是调度那一步——不去查调度，很容易误判成
     "解码器只支持位图"。

### K163 —— 解码器声明 `vector_exts` 不等于这份格式有矢量内容：取样必须逐份看像素

- **现象**（2026-11-01，m189）：m188 按 `vector_exts` 并集建样本集，用户逐份检查后发现两张
  "假的"：`示例.djvu` 是扫描件（本来就该在像素格式里，不是矢量），`zebra.zbr` 放大是
  100×100 的马赛克。排查后确认：doc-legacy 把 `zbr` 写进了 `"vector_exts"`，而实现只解出文件
  内嵌的 100×100 4 位预览 DIB（`zbr_preview` + 最近邻放大），没有任何矢量指令；ZMF 的四份
  libzmf 测试样本则是 draw2/draw3 直接 `ERR_CORRUPT`、draw4/draw5 只出全透明空画布。
- **根因**：`vector_exts` 是**归属声明**（"这个后缀由我这枚矢量解码器接"），不是**能力证明**
  （"这份文件里真有路径"）。两者在 ABI 上分得很清楚，但建样本时按声明取并集会默认二者一致。
- **解法**：样本集只收**逐份渲染出来看过**的文件；`.build\矢量图` 的 README 里把 ZMF/ZBR
  为什么不在、XPS/OXPS 为什么是白纸、DXF 为什么内容只占 1/3 全部写明（据实说明，不假装）。
- **可复用的两条**：
  ① **清单来自"声明"，证据只能来自"像素"**：给用户看的素材，每一份都要有一张渲染图对过眼，
     否则"覆盖了 N 个后缀"里会混进"其实什么都没画"的那几份。
  ② 遇到"声明是矢量、实际是位图"的成员，正确动作是**不放进矢量样本集并在说明里点名**，
     而不是为了凑齐后缀数把它塞进去——后者正是 m188 被用户点破的那件事。

### K164 —— DXF 的颜色在组码 430（`color_name`），组码 62 只是个 ACI 索引

- **现象**（2026-11-01，m190）：`.build\矢量图\DXF.dxf` 放大后"颜色都不对，只有线条"——
  图纸内容全黑，而样本里每条线各有自己的颜色。
- **根因**：`dxf` crate 把组码 62 解成 `EntityCommon.color`（一个 ACI 索引），组码 430 解成
  `EntityCommon.color_name`（字符串）。`dxf_to_svg` 只读 **`color_name`**：只写 `color` 时
  它看不见，一律按默认前景色画。ACI 还有 BYLAYER（256）这一档要回到图层表里取色。
- **解法**：`doc-cad` 在交给 `dxf_to_svg` 之前先过一遍 `paint_colors`——`color.index()` 命中就
  换算成 CSS，否则回落到 `layer.color`，写进该实体的 `color_name`；换算表覆盖 ACI 1–9 与
  250–255 灰度，其余按索引取色相（0.70 饱和 / 0.38 亮度）。用例
  `entity_color_index_becomes_a_real_css_color`（组码 62=1 的 RED_LINE 必须出现 `#e02020`）。
- **可复用的一条**：第三方"格式 → SVG"库读的是它自己挑的字段，**字段名对不上时不会报错，
  只是静默用默认值**。改颜色/线宽这类属性时，先用一条带已知取值的夹具把"库到底读哪个字段"
  钉死，再写换算。

### K165 —— 库"能打开"不等于"画了东西"：justpdf-formats 的 XPS `render_page` 是白页桩

- **现象**（2026-11-01，m190）：`XPS.xps` / `OXPS.oxps` 打开纯白，`--probe-decode` 也报成功。
- **根因**：`justpdf-formats` 的 XPS 实现只解析到页面外壳，`render_page` 返回一张空白画布
  （源码里明写是未实现）。宿主侧一切正常：探测认领、渲染成功、像素全白——**没有一处错**，
  错的是"库能开"被当成了"库会画"。
- **解法**：`doc-xps` 丢掉该库，自己走 OPC 链（`_rels/.rels` → `fdseq` → `fdoc` → `fpage`）
  再把 FixedPage 映射成 SVG（Path / Canvas / Glyphs、SolidColor / Linear / Radial 画刷、
  Transform、ClipPath），交给 resvg 光栅化；每个部件有 16 MiB 读取上限、嵌套深度 64 上限。
  未实现的按限制如实写进 README：`Image` 与 `ImageBrush` 不渲染，`Glyphs` 用系统字体近似。
- **可复用的两条**：① 换库前先渲一张**有内容**的夹具并断言像素，不要只看返回码；
  ② 用户报"纯白"时先分两种——"解不了"会报错，"解了没画"才是这类静默失败。

### K166 —— "先按 72 dpi 整幅光栅、再最近邻放大"是放大必糊的写法

- **现象**（2026-11-01，m190）：PS / PRN / EPS / AI 放大后满屏像素块（PDF 用户报"放大很多倍
  才这样"，PS 类是全程糊）。
- **根因**：`doc-print` 当初为省内存，把整篇按固定 72 dpi 渲成位图（`render_to_display_list`
  返回的页面尺寸 = 点 × dpi / 72），显示时用 `FilterType::Nearest` 缩放到目标尺寸。放大时
  每个源像素被复制成方块——**源头分辨率是常数，倍率再高也不会多出细节**。
- **解法**：只解析一次（`DisplayListPage` + `prepare_display_list` 缓存在线程局部），
  **按目标画布直接光栅化**：整幅档与区域档走同一个 `render_region_prepared`，区别只是视口
  （整幅 = 0,0,page_w,page_h；区域 = 请求那一块）与像素尺寸。密度 = `dpi × scale`。
  用例 `region_is_rasterized_at_density`（40,0 起的 20×20 区域 request 成 80×80，竖线边缘落在 x=40）。
- **可复用的一条**：凡"先渲成固定尺寸位图再缩放"的实现，放大档必然是插值；正确形状是
  **把目标尺寸一路传到光栅化调用**里。中间层只要能"重放"（display list / 场景树），
  就不要让它先落地成像素。

### K167 —— 能力位是 DLL 级单值，合并档成员能力不齐时会发错请求（`region_exts`）

- **现象**（2026-11-01，m190，潜在）：`doc` 档里 EMF/EMZ 走 `emfsdk`，它的光栅器只有
  "整幅画布多大"（`RenderOptions{target_width_px, target_height_px}`），**没有视口参数**。
  若它们跟着 `CAP_REGION` 一起进区域通道，放大时会把**整页**缩进那一小块——内容错误，
  比糊更难解释。
- **根因**：`iv_render_region` 与 `CAP_REGION` 都是**整枚 DLL** 的事实，而"哪些成员真的能按
  区域密度重光栅化"是**成员级**的事实，ABI 里原先没有表达它的地方。
- **解法**：加法式元数据键 **`region_exts`**（分号分隔小写后缀，`iv_metadata` 里追加一行）；
  宿主 `decoders::registry::declared_cached` 读它收窄区域集——键缺席 ⇒ 该 DLL 的
  `vector_exts` 全部，空串 ⇒ 明确一个都不进。用例
  `region_exts_narrows_the_vector_list_per_member`（缺席 / 声明 / 空列表三种形状）。
  协议条文进了解码器仓《解码器开发规范.md》§十六 末节。
- **可复用的两条**：① 把"能力"从 DLL 级下沉到成员级时，**加法式元数据键**比新增导出更省事
  （v5 老 DLL 不认这个键 ⇒ 走缺省读法，行为不变）；② 收窄的判据必须是"它真的按区域密度
  重画了吗"，不是"它是不是矢量"。

### K168 —— 没有视口 API 的光栅器，区域渲染只能"整幅超采样再裁剪"，代价按倍率平方涨

- **现象**（2026-11-01，m190）：`EMF.emf` 放到 8 档时，宿主按 m189 的整幅路线请解码器重画，
  实测 `bitmap=4674x3344 cost=2233.3ms`，再放大到 `9684x6929 cost=7908.0ms`。
- **根因**：`emfsdk` 只能指定"输出画布多大"，想让某一块更清楚，就只能把**整幅**渲到
  `自然尺寸 × 倍率`（像素数按倍率平方增长）。这不是宿主选错了路线，是库的能力边界。
- **解法**：EMF/EMZ **不进区域通道**（见 K167 的 `region_exts`），保留 m189 的整幅重渲路线：
  放大仍然清晰（按倍率重画，不是插值），只是倍率越高越贵；代价在 README/HISTORY 里如实写明。
  **不为"覆盖全部后缀"硬塞区域通道**——那是拿内容错误换一个漂亮的覆盖率数字。
- **可复用的判据**：评估"要不要给某个成员补区域通道"时，先看**它下面的光栅器收不收视口参数**；
  不收的话，区域通道只能变成"超采样 + 裁剪"，收益是"能封顶内存"，不是"更快"。

### K169 —— DXF 的 `TEXT`：字高是组码 40，编码看版本；`dxf_to_svg` 两样都不管

- **现象**（2026-11-01，m191）：`DXF.dxf` 放大后"文字笔画缺了很多"——其实样本里根本没有
  `TEXT`，标签是字形轮廓折线描边，放大就是双线/断线的空心字。
- **根因**：`dxf_to_svg` 支持 `EntityType::Text`，但它排出的 `<text x y fill>` **没有
  `font-size`**（落到 SVG 默认 16 用户单位）也不写字体栈；而且它把 viewBox 的 padding
  写死成 1.0（每边各留 100%），图纸只占中间九分之一。编码上，`dxf` crate 只认
  `$ACADVER`：R2007+ 整份按 UTF-8 读、**不**解 `\U+XXXX`；更早的版本才按
  `$DWGCODEPAGE` 解码并处理 `\U+XXXX`。样本若声明 AC1027 却写转义，会原样显示成
  `\U+4E2D…`。
- **解法**：`TEXT` 不再交给 `dxf_to_svg`——doc-cad 自己排字（`font-size = 组码 40 ÷ 0.72`，
  字体栈带系统中文，两种编码写法都认），再把 `dxf_to_svg` 那份无 `font-size`
  的 `<text>` 剥掉；viewBox 收回到内容框 + 4%。`.dxf` 输入同时改成**直接**交给 `dxf`
  crate（原先也走 `acadrust → DxfWriter → dxf`，DXF 二次转换只会丢字段）。
- **判据**：`text_entities_carry_height_and_a_cjk_font_stack`（字高/中文/颜色三样都在，
  且 `<text>` 只出现一次）、`viewbox_is_tightened_to_the_content_box`。

### K170 —— `nom-hpgl` 遇到不认识的命令就**停**：`PC` 一出现，后面的几何全丢

- **现象**（2026-11-01，m191）：HP-GL 全家族只有黑白，用户报"颜色有问题"。
- **根因**：HP-GL 的笔色是 `PC`（HP-GL/2 `PC r,g,b;`、HP-GL `PC pen,r,g,b;`），`nom-hpgl`
  不解析它；而它的顶层是 `separated_list_complete`，**遇到解析不了的命令就返回前缀**，
  我们这边又把"有剩余字节"当成功 ⇒ 带 `PC` 的真实文件从第一个 `PC` 起整段丢失。
  另一个坑：把 `PC…` 改成空串会留下 `;;`，空命令同样让解析停下。
- **解法**：先按 `;` 切一遍命令流，把 `SP`/`PC` 摘成"笔号 → 颜色"表，**连分隔符一起**
  从流里删掉（用保留项 `join(";")` 重建），几何再交给 `nom-hpgl`；场景按笔色分组输出
  `<path>`（颜色是呈现属性，不能挂在子路径上）。没有 `PC` 的文件按默认黑笔，不臆造色。
- **判据**：`pen_colors_survive_without_truncating_geometry`（两支笔两种色 + 两段线都在）、
  `four_argument_pen_color_targets_a_named_pen`、`files_without_pen_colors_stay_black`。

### K171 —— `emfsdk` 的栅格器没有抗锯齿、没有视口、字体缓存只有一支无衬线

- **现象**（2026-11-01，m191）：`EMF.emf` / `EMZ.emz` 的文字"坑坑洼洼"，中文还是空心描边。
- **根因**：`emfsdk` 的 `set_pixel` / 扫描线填充都写硬像素（无 AA），`RenderOptions` 只有
  目标宽高（没有视口），`RenderFontCache::load()` 只按 `Family::SansSerif` 取**一支**字体
  ⇒ 汉字 `glyph_index()` 返回 `None`，文字直接不画。所以"把中文交给它排"这条路根本不存在。
- **解法**：① **超采样**——预算内（2× 画布 ≤ 12 MP）按 2× 请求、拿到结果盒式降采样回目标
  尺寸，4 个样本一平均就是抗锯齿；位图成员只回自然尺寸，不能降采样。② **中文填充多边形**——
  样本侧把字形轮廓发成 `EMR_POLYGON`，按绕向区分外轮廓/挖空：先填外轮廓（前景色）、再把
  挖空轮廓填回底色（`emfsdk` 只认单条轮廓的 even-odd，没有子路径概念；用"点在别的轮廓内"
  判挖空会把中文字里互相重叠的笔画误判成挖空，填回去就是白斑）。
- **可复用**：拿"整幅超采样 + 降采样"给不支持 AA 的第三方栅格器**当面糊补**，前提是它
  认目标尺寸；代价是 4 倍像素，必须封顶（这里 12 MP）。

### K172 —— `usvg::Options::default()` 的字体库是**空的**：场景里有 `<text>`，屏上一个字都没有

- **现象**（2026-11-01，m192）：HP-GL 的 `LB` 标签解析对了、导出的 SVG 里明明白白写着
  `<text x=… font-size=…>PLT</text>`，真机与离屏渲染却一个字形都不出现（连英文也没有）。
- **根因**：`doc-hpgl` 建树用的是 `resvg::usvg::Tree::from_data(svg, &Options::default())`。
  `Options::default()` 里装的是**空的** `fontdb::Database`——解析期查不到字体就把文字节点
  丢掉，而且不报错。同档其它成员（CAD / WMF / XPS / doc-legacy）都装了系统字体库，只有这条漏了。
- **解法**：装一份进程内只扫一次的系统字体库（`OnceLock<Arc<Database>>` + `load_system_fonts()`），
  每次解析只克隆 `Arc`；判据必须**落在像素上**（`label_text_reaches_the_pixels`：画布上
  那个区域必须出现深色像素），只断 SVG 字符串的用例在老代码上也是绿的。
- **红证**：把那一行换回 `Options::default()` 重跑，用例当场红（"一个深色像素都没有"）。
  真机取证同一现象：0.2.1 的 `PLT.plt` 截图里只有几何、没有标签。

### K173 —— 第三方库"在库里排字"且没有字体回调时：只能打补丁，`forbid(unsafe_code)` 要放宽成 `deny`

- **现象**（2026-11-01，m192）：`EMF.emf` 里的中文渲染成品是 5×7 点阵方块。
- **根因**：`emfsdk` 0.2.0 的 `RenderFontCache::load()` 只按 `Family::SansSerif` 取**一支**
  字体，并且完全忽略 `EMR_EXTCREATEFONTINDIRECTW` 里的 `LOGFONTW::lfFaceName`
  （它读了字体记录，只留 `lfHeight`，名字丢掉）。汉字 `glyph_index()` 返回 `None` ⇒
  `render_text` 返回 `None` ⇒ 整段（连同 ASCII）退回 `draw_glyph_5x7`。库内绘制、没有回调，
  外部改不了；宿主侧又必须不动。
- **解法**：按仓库规则在 `/.3rd/emfsdk-0.2.0` 留一份带补丁（E01）的副本，`doc-emf` 走 path 依赖：
  ① 字体栈 + `OnceLock` 进程内只索引一次（原本每次渲染都重扫系统字体，本机 400 面 260–950 ms）；
  ② 字库数据用 `fontdb::make_shared_face_data` 走 **mmap 共享**，不复制进堆（单个中日韩字库
  10–20 MB）；③ `LOGFONT` 点名的字族排最前，其余按兜底栈**逐字**找字形，全都没有才退回点阵。
- **踩点**：`make_shared_face_data` 是 `unsafe`，而 crate 顶部是 `#![forbid(unsafe_code)]`
  ——`forbid` 不能被就地 `allow` 推翻，只能降成 `deny(unsafe_code)` 再给那一个函数
  `#[allow(unsafe_code)]`（补丁登记在副本的 `SOURCE.md`，别处照抄不了）。
- **补丁要能被别人重建**（2026-11-01 补）：`.3rd` 不入库，只把改动留在副本里等于发布物不可重建。
  补丁现有**公开登记**在解码器仓 `RuPix-Decoder/patches/emfsdk-0.2.0/`（README + manifest + patch），
  判据是"上游 0.2.0 原文 + 该补丁 = 构建用的副本"；`manifest.json` 记上游核对日期，
  超 90 天 `check_patches.py` 判红（2026-11-02 起该门禁不记也不核哈希，只核补丁触及路径与登记一致）。
  重放一律 `git -c core.autocrlf=false apply`（CRLF 会让副本行尾偏离上游）。
- **判据**：`cjk_glyphs_come_from_a_real_font`——"两个不同的汉字必须画出不同的字形"。
  5×7 点阵对**所有**非 ASCII 字符画同一个方框，所以这条老代码上必红（实测：上游两字逐字节相同）。

### K174 —— `LB` 以 `<ETX>` 收尾：拼回流时再补 `;` 会造出空命令，后面的几何全丢；GBK 夹具必须是真 GBK 字节

- **现象**（2026-11-01，m192）：`LB` 正文里带 `;` 的用例里，标签出来了，**标签之后那条线没了**。
- **根因**：`nom-hpgl` 的 `Label` 用 `take_until("\x03")` 吃掉了 `<ETX>`，顶层分隔符是
  `one_of!(";\x03")`；把命令 `join(";")` 拼回去时给已带 `<ETX>` 的 `LB` 又补了一个 `;`，
  下一次解析就撞上空命令、`separated_list_complete` 在那里停下。**只删命令不删分隔符**
  （K170 的同一类）与**多补分隔符**是同一个坑的两面。
- **解法**：逐条拼回流，只有"不以 `<ETX>` 结尾"的命令才补 `;`。
- **另一半**：`gbk_labels_are_decoded` 原先写的是 `"中文".as_bytes()`——那是 UTF-8，整份文件
  合法 UTF-8，第一跳就成功，**GBK 分支根本没被走到**（假绿）。改成真 GBK 字节
  （`D6 D0 CE C4`）并先断"这四字节不是合法 UTF-8"，夹具才真的站在判据管的那条分支上。
- **附带**：`std::str::from_utf8(&[0xd6, 0xd0, 0xce, 0xc4])` 会触发 `invalid_from_utf8`
  lint（clippy `-D warnings` 红灯），把常量先塞进 `Vec<u8>` 再传引用即可。

### K175 —— 解码器版本号写在两处：`Cargo.toml` 与 `export_metadata!` 字面量

- **现象**（2026-11-01，m192 收尾审计）：`doc` 升到 0.2.2、`decoders.json` 也对，可 DLL 里
  自述的 `version` 还是 `0.2.1`——用户界面上看到的版本与更新比对用的版本对不上。
- **根因**：版本号有两份真源。`Cargo.toml` 的 `[package] version` 被 `decoders.json`/更新比对
  使用；`src/lib.rs` 的 `rupix_abi::export_metadata! { "version" => "x.y.z", … }` 是宿主实际
  读到的那个（`decoders::host` 用它给"同 id 多份 DLL 谁胜出"排序，设置页也显示它）。
  只 bump 一处，另一处静默留在旧值上——编译不报、门禁不红。
- **解法**：升级时两处一起改；`tools/check_history.py` 增设一致性检查（读 `src/lib.rs` 的
  metadata `version` 与 `Cargo.toml` 比对）。发布前另补一道字节级核对：DLL 里应有
  `version\0x.y.z\0`，且与清单一致。
- **红证**：这次不是造出来的——门禁加上去当场就红了（`doc: metadata version 0.2.1 !=
  Cargo.toml 0.2.2`），改完字面量才转绿，说明它抓的是真实缺陷。
- **同类提示**：凡是"同一事实写两处"的字段（版本、ABI 号、后缀清单），要么合并成一处派生，
  要么必须有一道门禁同时读两边。

### K176 —— 图标字体码位是赌局：先查 `.ttf` 的 cmap 再写

- **现象**（2026-11-02，m193 翻页按钮）：浮条上新增的"上一页 / 下一页"两颗渲染成
  **两个空方框**（豆腐块）。代码编译通过、单元测试全绿、`Btn::name()` 也有中文标签，
  只有真机截图看得出来。
- **根因**：`\u{E89C}` 在 `segmdl2.ttf` 里是真字形，但它是**信封**（发信/分享），
  不是"翻页"；`\u{E89D}` 在整个字体里**没有字形**——PUA 区里既缺字又有"看着像但不
  是那个意思"的位，凭印象写码位等于赌。
- **解法**：先用字体 cmap 实查再写码位。本机一条命令：

  ```py
  from fontTools.ttLib import TTFont
  cmap = TTFont(r"C:\Windows\Fonts\segmdl2.ttf").getBestCmap()
  print([hex(c) for c in (0xE76B, 0xE76C) if c in cmap])
  ```

  cmap 只证明"有字形"，不证明"长什么样"，所以第二步是把候选码位渲染成一张对照图
  （`PIL.ImageFont.truetype(segmdl2.ttf, 44)` 画一排 + 码位标签）用眼睛挑。
  翻页最终用 `E76B`/`E76C`（ChevronLeft/Right）：清晰、方向直白，
  且与逐帧的 `E892`/`E893`（竖线 + 三角）一眼可分。
- **配套**：`chrome.rs` 加 `page_glyphs_are_their_own_pair`，钉住"翻页两颗彼此不同、
  且都与逐帧不同"——这挡得住"复制粘贴时改成同一颗"，挡不住"码位在字体里不存在"，
  后者只能靠上面那条实查流程。
- **同类提示**：`Btn::Info` 退回普通文本 `!` 是同一个理由的旧例——PUA 码位拿不准时，
  宁可画一个 ASCII 字符，也不要赌一个可能不存在的位。

### K177 —— `RUSTFLAGS` 一旦定义就**整条覆盖** `.cargo/config.toml` 的 `rustflags`：`+crt-static` 会静默消失

- **现象**：为了把本机绝对路径从产物里去掉，在构建入口设了
  `RUSTFLAGS="--remap-path-prefix=…"`。编出来的 exe 体积正常、跑起来也没事。
- **根因**：cargo 的口径是「`RUSTFLAGS` 环境变量存在 ⇒ **完全替代** target 级 `rustflags`」，
  不是追加。三个仓的 `+crt-static` 都写在 `.cargo/config.toml` 里（宿主一处；解码器
  `workspace` 与每个 crate 各一处），于是它被一起顶掉，CRT 从静态变动态——用户机器上
  缺 `vcruntime140.dll` 就是"打不开"。
- **判据**：改 `RUSTFLAGS` 之后必须把原来那条**整条抄进去**：
  `-C target-feature=+crt-static --remap-path-prefix=<repo>=. --remap-path-prefix=<home>=~`。
  `build/size_map.py` 的注释早就写过这一条（它要加 `/MAP` 时踩过），这次是同一个坑第二次。
- **例外**：插件仓没有任何 `.cargo/config.toml`、本来就没开 `+crt-static`，那里只能加
  remap 一条——顺手把链接方式改掉是"借隐私修复改产品行为"，不是修 bug。
- **配套**：`build/deploy.py` 新增「本机路径门禁」兜住反方向（RUSTFLAGS 没生效、有人直接
  `cargo build` 就拒绝部署）；但门禁挡不住"crt-static 丢了"，那一项只能靠这条纪律。

### K178 —— 逐像素透明窗**每帧重绘都会补一条指针消息**：状态唤醒不能借 `hover_toolbar` 那一格

- **现象**：极简模式下播 AVIF 序列（100 ms/帧），底部按钮栏**一直闪**。
- **取证**：`build/pill_probe.ps1` 用 `PrintWindow` 逐帧采浮条上五个点。同一点在
  `FF101010`（无浮条）与 `FF1B1B1C`（胶囊底色）之间交替，且四个点**同步**翻转 ⇒ 是整条
  显隐在翻，不是宽度随文本抖动（后者只会让边缘点变、中心点恒定）。
- **根因**：`wake_on_status_change` 借 `hover_toolbar` 表达"状态刚变、浮条该亮"，而
  `UpdateLayeredWindow` 每次重绘都会让系统重新做命中测试、补一条指针消息；`activity`

- **解法**：状态唤醒走自己的到期时刻（`Chrome::status_until` / `status_alive()`），绘制取

- **同类**：`M8` 的平移限速、`A3` 的滚轮节奏闸都是"一条通道一个写入者"的既有先例。

### K179 —— 编 `doc-legacy` 必须让 `C:\msys64\ucrt64\bin` 在 PATH 上：缺它时 cc1plus **静默退 1**

- **现象**：全量 `RuPix-Decoder\build.ps1` 走到 `cargo clippy -p rupix-doc-legacy --target
  x86_64-pc-windows-gnu` 时报一句 `error occurred in cc-rs: command did not execute
  successfully (status code exit code: 1): "C:/msys64/ucrt64\bin/g++.exe" ...`，
  **g++ 一个字都不印**。第一反应像是上一轮的 `--remap-path-prefix` 把构建弄坏了。
- **定性**：设 `RUSTFLAGS`（带 remap）与不设（只 `+crt-static`）两臂各跑一次，**两臂同 rc=101**
  ⇒ 与 remap 无关。真因有**两层**：
  ① `singles/doc-legacy/build.rs` 用绝对路径点名 `g++.exe`，而 g++ 要拉起
  `lib\gcc\x86_64-w64-mingw32\16.1.0\cc1plus.exe`；`objdump -p` 显示后者依赖
  `ucrt64\bin` 下的 `libgcc_s_seh-1` / `libgmp-10` / `libisl-23` / `libmpc-3` / `libmpfr-6` /
  `libwinpthread-1` 六枚。Windows 找这些 DLL 从**被加载 exe 自己的目录**开始、再沿 PATH——
  调用方 PATH 里没有 `ucrt64\bin` 就起不来，且**不打印一个字、只给退码**。
  ② **PATH 里的位置也判生死**：同一台机器把 `ucrt64\bin` **追加**到末尾仍然 rc=1，
  **前置**才 rc=0。因为本机 PATH 靠前的 Git for Windows `mingw64\bin` 里带着**同名不同 build** 的
  `libgcc_s_seh-1.dll` / `libgmp-10.dll` / `libwinpthread-1.dll`，加载器取第一个命中，
  cc1plus 就绑到了 Git 那份上。
- **解法**：调用方把 `C:\msys64\ucrt64\bin` **前置**进 PATH。这里必须前置而不是追加——
  反过来的顾虑（"前置会把 git/python 换掉"）当场核过：那个目录只有 gcc 家族十四个 exe，
  没有 python / cmake / nasm / git，流水线别的工具一个都遮不住。
  **不动 `build.rs`**：那台机器的 msys 位置写进源码仓就是本机路径入库（AGENTS 无隐私条），
  而且解码器仓自 2026-11-01 起冻结只读。
- **判据**：凡是 build script 用**绝对路径点名**编译器的地方，都要问两句——"它拉起来的子进程
  能不能找到依赖 DLL"、"PATH 上**第一个**同名 DLL 是不是它自己那套"。
  这类失败的签名是**退出码非 0 + 零输出**：先查 DLL 解析（`objdump -p` 列依赖 + 逐段试 PATH），
  别顺着最近一次改动猜——本轮差一点把 `--remap-path-prefix` 判成凶手。

### K180 —— 「构建入口改了」≠「发到用户手里的字节改了」：隐私类修复的验收对象是**发布目录那一份**

- **现象**：2026-11-02 那轮报"8 档 DLL 全部 clean、实测为 0"。次日复核 `.build\decoders`：

### K181 —— `ZipFile(compresslevel=…)` 对我们**传进去的 ZipInfo 不管用**：构造档被静默绕开

- **现象**：想把发布包压小一点，给 `zipfile.ZipFile(..., ZIP_DEFLATED, compresslevel=9)`。
  打完十个包一对体积：**与默认档逐字节同长，省 0 B**。
- **根因**（读本机 `zipfile` 源码 + 三臂实测，不是猜的）：`writestr()` 只在它**自己新建** `ZipInfo`
  的那一支里回填 `zinfo._compresslevel = self.compresslevel`；调用方传进来的 `ZipInfo`
  原样使用，而 `ZipInfo("x")._compresslevel` 默认是 **`None`** ⇒ 下游按 `Z_DEFAULT_COMPRESSION`（6）压。
  两仓打包器为了钉条目名与 1980 时间戳**全都是自己造 `ZipInfo` 再 `writestr`**，所以正好整支被绕开。
  三臂（同一枚 851,456 B 的 DLL）：A 构造档 9 + `writestr(info, data)` = **387,412**、
  B 逐次传 `writestr(info, data, compresslevel=9)` = **386,288**、C 现状（都不传）= **387,412**。
  ⇒ 只有 B 生效，且只省 1,124 B（0.29%）。
- **判据**：旋钮要放在**真正被读的那一层**——这里有效形状是逐次传参，不是构造档。
  凡是"设了个参数、产物一字节没变"的修复，先用同一份载荷跑两臂（带 / 不带）再决定写不写进文档；
  要量压缩本身就直接问底层（`zlib.compressobj(level, DEFLATED, -15)`：26,720,256 B 的 doc DLL
  在 L6 / L9 = 13,444,313 / 13,409,290，也才 0.26%）。
  **级别这条路省不了体积，省体积的是压缩器族**（同一批载荷：deflate → LZMA 是 −26.5%，见 `.plan/m203`）。
- **同类**：K112（`[profile.release.package.*]` 的 profile 名写错时构建照样成功、只是静默不生效）。

### K182 —— `7za` 往 ZIP 里写的是**源文件 mtime**：发布流水线的工作副本是现解现拷的，于是包变成时间的函数

- **现象**：用 7za 重打同一份负载，条目时间戳读出来是 `(2026, 11, 3, 18, 12, 24)`，
  而两仓 Python 侧钉的是 `(1980, 1, 1, 0, 0, 0)`。也就是说换成 7za 之后，
  **m180 那条"包必须是内容的纯函数"当场不成立**。
- **根因**：7-Zip 对 zip 容器默认记录源文件的修改时间。这里的"源文件"是打包用的工作副本——
  Python 的 `extractall()` **不会**按 ZIP 条目回写 mtime（实测工作副本 mtime = 提取那一刻的 18:12:22），
  真实发布流程里 staging 也是现拷 DLL，mtime 就是"当时"。⇒ 同一份内容，换个时间打包就是另一串字节。
- **差点被骗的那一步**（值得单独记）：我第一版"确定性自测"是**在同一份工作副本上连打两次**比 sha
  ——两次当然相同（因为 mtime 没变）。判据必须按流水线真实形状设计：**跨一次重新提取**再比，
  原地重打不算测过。
- **解法**：加 **`-mtm=off`**。实测条目戳回到 `1980-01-01 00:00:00`，且**隔 4 秒两次 sha 相同**
  （`926db9fee7a0` == `926db9fee7a0`）。写进规矩时必须和命令一起写，不写就是埋雷。
- **判据**：换打包工具 = 换"包的字节由哪些输入决定"。除了内容，还要逐项问：时间戳、
  条目顺序、属性位、压缩器版本、绝对路径。我们现有的三条（内容纯函数 / 条目名相对 / 不带本机路径）
  里，7za 会破第一条，所以它只能带 `-mtm=off` 进流程。
- **同类**：m180（`ZIP_FIXED_DATE` + `add_entry()` 钉 Python 侧那一半）、
  K181（同一家族：旋钮放在不被读的那一层＝没旋钮）。

### K183 —— 投消息**驱动不了拖动**：真光标在窗口外，重绘注入的那枚 Leave 会把 drag 结束掉

- **现象**：m204/m205 用 `PostMessage` 投 `WM_LBUTTONDOWN` + 14 枚 `WM_MOUSEMOVE` + UP 去验
  "左键拖图片"，截图互相关只量出 **2~3 px** 位移，窗口矩形也不动——看起来像功能没开火。
- **取证**（临时在 `press_left` 与平移分支各加一行判词，跑完即撤）：
  `[drag-probe] mode=PanImage drag_image=true can_pan=true pos=(392,280) view=(0,0,784,561)`
  与 `[drag-probe] move changed=true pan=(5.0, 0.0)` ——**决策与状态机在真 app 里都对了**，
  第一枚移动也确实把 pan 推到了 5。但后面 13 枚移动与随后补投的 `VK_RIGHT` 一条都没进 WndProc，
  而 `WM_CLOSE` 照常处理。
- **根因**：这个窗口是逐像素透明窗，**每次重绘都会让系统按真实光标位置补一枚指针消息**
  （就是 K178 那条）。探针的鼠标是"投"进去的，真实光标根本不在窗口里 ⇒ 第一枚移动触发重绘后，
  系统注入的那枚 Leave 走进 `PointerKind::Leave` 分支，那里**照设计**清掉所有按下/拖动位
  （`end_drag()`、`lmb_pending`、`nav_drag`——不清就是"指针拖出窗口在外面松手，回来后不动按钮也继续拖"）。
  于是 drag 在第二帧就没了。这不是产品缺陷：人手拖时光标一直在窗口内，Leave 不会来。
- **判据**：`PostMessage` 能证"事件进得来、决策对、状态机动了"，**不能证"连续手势的呈现"**。
  要证后者只有两条路：真实光标（`SendInput`——共享桌面上会碰别人的窗口，不做），
  或者交给用户两秒钟手测。探针的结论必须按这一层写，不许把"没量到位移"写成"功能没生效"，
  也不许把"决策日志对了"写成"手势已验证"。
- **顺带抓到自己**：m204 那条"真机读数：画面平移 70px"是**误读**——那两张帧的差别来自
  预览档→原图档落地（噪声图换档＝每个像素都变），不是位移；而互相关在噪声图上根本没有尖峰，
  所以"最佳 dx"是噪声。测量要挑**低熵有特征**的夹具（本轮改用的 320×240 标记图，
  误差 0.58 时能干净地指出"就是没动"）。
- **同类**：K178（同一枚"重绘补指针消息"，那次是浮条闪，这次是探针被顶掉）、
  K84（臂身份包含环境：投消息的臂 ≠ 真人的臂）。

### K184 —— 空格预览的准入拿**后缀**当"解不解得开"的代理：`.raf` 按 `is_raw` 排一次、`.uyvy` 按 `is_headerless_ext` 再排一次

- **现象**（同一处，用户两轮实测）：`.raf` 与 `.uyvy` 都是**双击开得开、在资源管理器里按空格毫无反应**。
  主窗那边一切正常的对比极具迷惑性——不是解码失败，是取件环节就被筛掉了。
- **根因**：`formats::is_previewable` 想回答"这个文件空格能不能预览"，手上却只有一个**后缀**。
  于是两次都拿后缀当代理：
  ① 先按 `is_raw`（**DLL 级**判据："这枚解码器实现了 `iv_render_raw`"）排除——可 raw 档一枚 DLL
  同时提供相机 RAW（`cr2`/`nef`/`raf`，自带完整文件头）与裸像素（`rgb`/`yuv`），整档二十多个后缀
  一起被关在门外；
  ② 改成按 `is_headerless_ext` 排除那 11 个裸像素后缀——**它们其实能开**：首开参数由后缀定布局、
  由**文件长度**反推宽高（`infer_raw_params`），双击路径本来就是"推得出就直接开"。
  代理错在把**文件级**事实（这个文件的长度能不能整除出宽高）压成了**后缀级**判断。
- **解法**：把这一层判断从后缀表挪到文件上。
  - 准入（`is_previewable`）只回答"这个后缀有没有解码器认领"：内置 ∪ 解码器自述，**不减任何后缀**。
  - 能不能真出图，由解码前那次参数推断决定；推不出就静默不出窗（预览不该弹参数窗打断用户，
    与双击"推不出才弹窗"是同一条分岔）。
  - 两个配套点缺一不可：`decode::probe_decode` 的 `raw` 必须读**会话 store**（空格预览在独立线程
    直接调它、不经过 `Viewer`，恒 `None` 时裸像素必然解不出）；`spacehook` 要在解码前对无参数文件
    做一次推断并 `set_raw_params` 落 store。
- **判据**：探针里"取件用全放行、判据另测"的结构会把这类病全滤掉——`space_probe` 的 `step5b`
  必须点名验证「已装后缀 ⊆ 可预览集合」，且名单要含**裸像素**（不只相机 RAW）。`step7b` 用现造的
  640×480 RGB8 裸样本走一遍"推断 → 解码"，把"准入放开了但链路没接"也一起堵上。
- **同类**：K39（空格预览漏内置 SVG：判据只查解码器自述，内置格式永远不在表里）、
  凡是"用分类属性代替个体事实"的判据，都要问一句**这个属性真的能推出结论吗**。

### K185 —— 「多开」被做成多进程：任务管理器两个条目、通知区两个图标

- **现象**（2026-11-04，用户实测）：勾上「允许多开」后双击第二张图，任务管理器里出现
  **两个独立的 rupix.exe 条目**，系统托盘里也出现**两个图标**。用户口径："多开的意思，是
  窗口可以有多个，但系统托盘、以及系统进程都是同一个。"
- **根因（两层）**：
  1. **语义读错**：第一版把"多开"实现成"跳过单实例闸门、再起一个进程"，即把窗口数量问题
     当成了进程数量问题。用户要的是**一个进程里多扇窗**。
  2. **就算按多进程算，托盘互斥也是失效的**：判"命名互斥体是否已存在"看的是
     `CreateMutexA` 的返回句柄，而它对"新建"和"打开已存在的"**都返回非 NULL 句柄**——
     必判 `ERROR_ALREADY_EXISTS` 才算"别人已经建过"。所以第二个进程照样会建托盘图标。
     这类判据没测过负向臂（"第二个进程"那一路）时，看着有其实就是没有。
- **解法（正确形状）**：常驻宿主 + 全部窗口，没有任何"主窗"：
  - `App::resident(TITLE).tray(..).run_resident()`：不建主窗，托盘挂在应用级 message-only
    宿主上，窗口关掉即销毁、渲染资源随 `WindowState` 的 drop 归还。
  - 每个看图窗口 = `Window::new(..).frameless(true)`，自带 `on_interval` / `on_shortcut` /
    `on_close_request`；状态一窗一份（`runtime::WinRt`），跨窗唯一的只有配置与窗口注册表。
  - 单实例闸门**恒生效**；`allow_multiple` 只决定"首实例收到 argv 后开新窗还是就地换图"。
  - 两条框架缺口要各补一手：常驻模式下单实例的 `activate(0)` 自行跳过（会由应用回调开窗，
    不需要"激活主窗"）；**应用级退出没有入口**（`TrayCtx::quit` 只有托盘有，`EventCtx` 只有
    作用于本窗的 `request_close`）⇒ 补丁 025 加 `EventCtx::quit_app()`。
- **顺手撞出来的三个坑**：
  - `META_TX` / `DONE_WAKER` 是**进程级单槽**（单窗口时代的遗留）。每窗一条解码线程之后，
    第二个窗口的 Meta 全被灌进第一个窗口的队列、唤醒也只叫醒第一个 —— 症状是第二扇窗的
    info bar 与"按原始像素开窗"要等整图解完才动。改成随线程的 `DecodeSink`（thread-local），
    全局槽只留作直调路径（探针 / 示例）的兜底。
  - `App::channel` 的回调在常驻模式下拿到的 `EventCtx` **背后没有具体窗口**，`mark_dirty`
    无处可落 ⇒ 不能用它做"回包叫醒某一帧"（m90 的收益在常驻模式里拿不到）。回包退回各窗
    自己的 16ms 定时器（实拍 ≈31 ms 一拍）。要么接受，要么等框架提供"按窗口投一帧"。
  - 「托盘唤回窗口」不需要枚举 HWND：给每扇窗一个 `Window::single("viewer-<id>")`，
    再 `open_window` 一次 —— 平台走 `NewWindow::Focus` → `show_and_activate`，命中即前置。

### K186 —— "解码挂死"不是解码器的病，是宿主的病：一道锁把整条链焊死

- **现象**（2026-11-04 用户）："关闭多开、保持系统托盘，打开新图片又卡住了……这种看图卡住，
  已经不是一次两次了。我们最小化时，经常有其它操作，结果也频繁卡住。" 现场日志一天
  **301 条** `[decode-watchdog]`，跨 `图片2.emf` / `图片1.svg` / `noise.bmp` / `noise.cr2` /
  `noise.avifs` 等十来种格式，`age_ms` 一路涨到 20007、`pending` 一路涨到 7。
- **根因（两层，第二层才是致命的）**：
  1. 某个解码器在 `iv_render` 里不返回（死循环 / 等待内部锁 / mmap 打在坏盘上）。
     `catch_unwind` 与 SEH shim **只拦崩不拦卡**——这是本仓早就写在 `decode_watchdog`
     模块头里的边界。
  2. ★ `BACKEND: OnceLock<Mutex<Box<dyn DecodeBackend>>>` 的 guard 覆盖
     **probe + 查询 + 渲染整段 FFI**。僵尸线程把锁带到进程结束，于是"换一条解码线程"
     这种朴素救法根本走不通：新线程第一件事就是 `with_backend`，当场堵在锁上。
     这就是"打开一张图卡住，之后**所有**图都打不开"的机制（2026-10-28 的
     `.temp/p11-hang-watchdog.md` §2 已经把它列成表，当时只落了 C 期"检测+日志"）。
- **解法（B 降级版，2026-11-04 落地；A 独立解码进程仍留作后续）**：
  1. **后端工厂化**：`install_backend_factory(fn() -> Box<dyn DecodeBackend>)` +
     线程私有 `LOCAL_BACKEND`。每个 worker 自建一份 `Host`，挂死者只钉死它自己那份；
     直调路径（探针 / 示例）继续用进程级单例。
  2. **监督者 + 可丢弃 worker**：`decode_loop` 不再自己解码，它只出队、把 `Req` 交给
     worker、`recv_timeout` 等结果。超时就**不再等**（Rust 没有可靠的线程取消原语，
     `TerminateThread` 会漏锁），丢掉它的句柄（泄漏一条栈），起新 worker。
  3. **熔断按解码器 id**：`decoders::decode_with` 在调 FFI 前 `report_current_decoder(&id)`，
     超时后监督者读它 → 记进 `HUNG` → 该 id 本会话不再进（`is_hung_decoder` 挡在
     `decode_with` 之前，返回 `Unsupported` 让榜单继续试下一家）。UI 取走后补进
     `decoders_disabled` 落盘，**下次启动也不踩同一个坑**。
  4. **回给的错误必须可行动**：「解码超时（20 秒没有返回）：已停用解码器「modern」
     （设置 → 解码器 里可重新启用），其余图片不受影响」——静默变成"载入中…"等于没修。
- **两个实现坑**：
  - `take_hung_decoders()` 不能 `mem::take` 把熔断集取空：`is_hung_decoder` 是**本会话
    判据**，取空之后 UI 补 `add_disabled` 的那几微秒里会漏进一个新请求。另留一张
    `REPORTED` 做"已上报"去重，判据表全程有效。
  - 探针第一版用两笔 `Main` 验证超时，读到"第一笔 ms=0 空串 Err"——`Main` 会被后一笔的
    floor 判过期、**根本没进 worker**。要测超时得用 `Thumb`（不参与 floor），或者接受
    `Queue::pop` 的 Main 插队（那就不能假设哪一笔先挂）。判据要按"两笔各自的结果"统计，
    不能按发送顺序。
- **判据**（`cargo run --release --example hang_recover_probe`）：假后端第一次必挂 60 秒、
  超时设 2 秒、提交两笔。**PROBE PASS** 的读数是
  `timeouts=1 backend_hits=1 slowest_ms=2008`——一笔在 2 秒被放弃、另一笔在新 worker 上
  立刻解完；不是 60000 ms。
- **遗留代价（如实记）**：每次挂死泄漏一条线程 + 它那份后端 + 一份 mmap，直到进程退出。
  退出时 `ExitProcess` 先杀线程再跑 DETACH，只有僵尸恰好卡在 loader 锁里才可能拖慢退出
  ——这个风险在引入本机制之前就已经存在。
- **同类**：K182（检测不等于恢复）、`decode_watchdog` 模块头那段"这是检测，不是防护"。

### K187 —— 看门狗测的是「排队」不是「解码」：301 条报警里绝大多数是错觉

- **现象**（2026-11-04，用户不满足于 m212 的超时）：「我需要的不是让卡死现象暂时消失或绕过它
  的临时方案，而是从根源上彻底定位并修复。」于是先回头审那条判据本身。
- **判据错在哪**：`note_sent` 在**发出**时登记、`note_done` 在**回包**时销账，`age_ms` 记的是
  两者之差——它同时包含"排队等前一张"和"在解码器里待着"。两者在日志里长得一模一样。
- **实测反证**：真机上用方向键连按 260 次（每 90 ms 一次）翻遍 `.build/1M`：
  `pending` 顶到上限 64、`age_ms` 一路 10s/20s/30s/40s、七个格式"同时报卡"——**而那条解码
  线程一秒都没停过**，`[main-latency]` 一直在出（每次 15–390 ms），停手后队列自行排空。
  也就是说：**报警量 ≠ 挂死数**，之前的 301 条绝大多数是"用户手比解码快"。
- **另外一个反证**：108 个样本文件逐个走真 DLL（`examples/decode_repro`）全部 ≤1 s 解完
  （EMF ~0.6–0.8 s，其余 <0.4 s）；320 笔请求逐个 seq 对账（`examples/done_audit`）
  **0 丢失、0 重复**。所以既没有"毒文件"，也没有"宿主丢回包"。
- **但真挂死确实存在**：另一段现场（00:11 那次）是 `pending=1`——只有一笔在途，UI 每 10 s
  照常巡检（证明窗口 tick 活着、`drain_decode` 在跑），而那一笔 **20 分钟没回包**。
  `pending=1` 把范围锁死：UI 活着、请求已发出、解码线程没产出 ⇒ 它卡在外来代码里。
- **所以"根治"的边界在哪（这条最重要）**：ABI 明写解码器「可重入但不必 MT-safe」，宿主承诺
  **串行调用**。一次调用挂死不返回 ⇒ 那条线程还留在 DLL 里 ⇒ 本进程里再进去一次就是并发违约，
  既不能重试、也不能"再开一条线程并行解别的图"。m212 的熔断因此**不是可选项，而是 ABI 要求**；
  真正能根治的只有一条：**把外来代码搬进可被杀死、可随时重启的独立进程**。进程一杀，
  僵尸没了、锁没了、DLL 状态没了，重试才重新合法。
- **本轮顺手修掉的两处**：
  1. **两段计时**：`Pending.begin`（出队时刻）由 `note_picked` 写入，报告同时给
     `age_ms`（用户等多久）与 `run_ms`（其中真在解多久，`-1` = 还在排队），并带
     `phase=`（11 段：open/read/probe/natural/doc-natural/query/render/post/region/svg）与
     `codec=`。判据从此一眼可读：`run_ms=-1` 是队列问题，`run_ms` 大且 `phase=render` 是外来代码。
  2. **熔断不再落盘**：m212 把挂死 id 写进 `decoders_disabled`，一次偶发就把那个格式变成
     "永远打不开"。这是**错误推广**——脏的是本次进程（僵尸还在 DLL 里），不是这个解码器。
     改成只在本会话停用，重启自动恢复（提示也照实说"重启后自动恢复"）。
- **教训**：`age_ms` 这种"端到端差值"看起来最直观，但**它答不出是谁慢**。凡是拿来定责的
  指标，必须能切到"责任段"上——切不开就只能得到"七个格式同时挂死"这种结论。
- **★ 最终定位（同日晚些时候，靠上面那个 `phase` 字段）**：加了阶段打点后第一次真机复现，
  **468 条报警全是 `phase=query codec=modern`**——一句话把范围缩到"AVIF 家族的查询阶段"。
  顺着这条线用真 DLL 反复解 `noise.avif`（`examples/decode_repro`），抓到：
  ```
  thread 'rav1d-worker-2' panicked at rav1d-safe-0.5.7/.../dav1d/picture（第 641 行）:
      overlapping DisjointMut: current: &mut _[40448..40512] ... existing &mut _[40500..40504]
  ```
  `rav1d-safe 0.5.7` 的多线程路径有**真实的别名竞争**（两个 `&mut` 区间重叠），
  `rav1d-disjoint-mut` 的校验器在 **worker 线程**上 panic。而阻塞中的解码调用者只是在等
  那个 worker 的结果——**本线程既没有异常也没有返回值**，于是 `iv_render` 永不返回。
  这解释了全部"玄学"：同一文件换一次运行又能打开（race 决定成败）、挂住后整条串行链全堵、
  日志里"随机"文件在报（谁排在它后面谁报）。`catch_unwind` 与 SEH 在这条路上**一个字节都
  帮不上**——它们只拦本线程的崩溃。
- **修法**：解码器仓 `modern` 0.3.3 → **0.3.4**，AVIF/AVIFS 一律**单线程**解码
  （`zenavif::DecoderConfig::new().threads(1)` + `decode_with` / `decode_animation_with`）。
  worker 线程整条路去掉，竞争与"等死掉的 worker"一起消失。取证：修前 3 轮×15 笔出现 1 次
  panic + 挂死；修后 **148 笔 0 panic 0 超时**（真 DLL 3×24 + 单文件 60 + 部署 exe 的
  43 次 GUI 打开 0 watchdog）。代价是 AVIF 慢一些（1 MP 量级仍几十毫秒），按宪章 §5.1
  「跨机行为一致 > 快」取这个方向。
- **教训二**：`phase` 这种**责任段标签**比任何"耗时"都值钱——耗时告诉你"慢"，标签告诉你"谁"。
  加它花了不到 60 行，定位花了一次复现。
- **同类**：K182（检测不等于恢复）、K186。三条连着读：先"能看见"，再"看得准"，最后才谈"救得回"。

### K189 —— 关到托盘再打开，旧图又回来了：一个活到进程结束的局部变量

- **现象**（2026-11-04 用户）："我们关闭窗口到最小化，结果已经打开的图片没有清除。"开着
  「关闭到托盘」，关掉窗口（进程留托盘），再从托盘唤回——出来的窗口**还是刚才那张图**，
  连缩略图条的页码（51/103）和缩放档（109%）都一模一样。
- **第一层判据先要对**：窗口到底是被销毁了还是被藏起来了？真机枚举该 pid 的全部顶层窗口
  （不只看可见性）：关窗后 `WindUiWindowClass` **确实消失**（句柄从 `0x350AE8` 变成
  `0x360AE8`，内存 12.9MB→7.1MB），所以"隐藏窗口又露出来"这条不成立——是**新的窗口在
  显示旧的状态**。
- **根因**：`runtime::run()` 里

  ```rust
  let first = WinRt::create(shared.clone(), initial.clone());
  app = app.start_window(first.request());
  ```

  那个 `first` 是 `Rc<WinRt>`，命名局部变量**活到 `run()` 栈帧结束**，也就是
  `run_resident()` 返回、进程退出为止。于是第一扇窗的运行期状态（`Viewer` / 图片像素 /
  缩略图条 / `Gallery` 目录表 / 解码线程）**永不释放**。窗口关闭只是把 OS 窗口与框架那侧
  的回调（另外 4 个强引用）拆了，注册表里那枚 `Weak` 仍能升级成功 ⇒
  `Shared::newest()` 找到"已经关掉的那一扇" ⇒ 托盘「显示窗口」把它的 `request()` 再喂给
  平台一次 ⇒ 新的 HWND + 旧的状态。
- **怎么定位的**（值得记，因为走了两条弯）：先做**最小复现**（`examples/window_rc_probe`：
  常驻单窗 + 一枚带 `Drop` 日志的 `Rc`），结论是**框架不扣引用**——关窗即释放，这排除了
  windui 的嫌疑；再在 RuPix 里给五个回调各挂一枚"哨兵"（带 `Drop` 日志的零尺寸结构），
  关窗时五枚全打印 ⇒ 回调也都放掉了；可 `prune` 仍读到 `strong=1`。三者一对，
  剩下的只可能是"我们自己留了一个没带哨兵的 `Rc`"——回去看 `run()`，一眼就找到了。
  ★ 顺带踩到一个**测量坑**：`log!("{:?}", w.upgrade().map(..), w.strong_count())` 里
  `upgrade()` 的临时 `Rc` 会被算进同一条语句的 `strong_count()`（临时值活到语句结束），
  读数恒 ≥1，差点得出"框架扣了一份"的反结论。先取计数、再升级。
- **修法**：把启动窗口的创建收进 `fn start_window_request(shared, initial) -> WindowRequest`，
  `Rc` 的作用域被关在函数体内，返回时即释放；`run()` 里不再有任何 `WinRt` 绑定。
  写成函数而不内联，就是为了让"顺手留一份"这件事**写不出来**。
- **同时确认的两件好事**：状态真的死在关窗那一刻——真机连开关 8 轮，线程数
  `5（关）→ 8（开）` 不累积、工作集 `~12.8MB / ~29.8MB` 不抬头、每轮 HWND 都是新的；
  多开（`allow_multiple=1`）关掉两扇里的一扇，另一扇的图还在、进程不退，关掉最后一扇
  之后唤回是空窗。
- **判据**（`build/probe_tray_clear.ps1`，本次新增）：空窗截图 < 60KB、有图的窗口 > 800KB
  ——同一条判据在修前读到 `908872`（旧图）、修后读到 `7808`（空窗），**正负两臂都跑过**。
- **同类**：K185（多开的多进程误做）。两条都指向同一件事：**窗口的"活着"只能由它的
  创建-持有-销毁链回答**，任何跨窗口/跨轮次的缓存都得先问"这扇窗还在吗"。

### K192 —— 探针里 `[int][char]'.'` 是 ASCII 不是 VK：46 是 VK_DELETE

- **背景**：m216 写按键探针验证 §22 双派发，第一版用 `[int][char]$Key` 算 VK：
  `'.'` 的 ASCII 是 46，而 `VK_OEM_PERIOD` = 190——46 恰好是 `VK_DELETE`。
  探针"发一个点"实际发的是 Delete 键，读数自然不对（还凑巧只翻 0 帧，像"没生效"）。
- **修法**：字母/数字 ASCII==VK 可以直用；**符号键一律 `VkKeyScanW`**（返回 VK + Shift 态）。
  同理 `WM_CHAR` 的 wparam 是 **UTF-16 码元**（`.` = 46），不是 VK——第一版 B 臂把 190
  塞给 WM_CHAR，windui 把它当 `¾` 处理，零动作。
- **教训**：探针读数异常时先验**自己发出去的是什么**——把 wparam 打进日志对一遍，
  再怀疑被测程序。`rotate_probe.ps1` 的 `$vk = [int][char]$Key` 只对字母/数字成立，
  拿它发符号键会静默发错键。

### K193 —— windui 的右键菜单是自绘浮层，不是原生 HMENU：探针别按菜单枚举设计

- **背景**：m217 要给取色器做真机端到端探针，第一版设想"弹菜单 → 枚举 `#32768` 窗口 →
  `GetMenuStringW` 找「工具」→ 点「取色器」"。查了 `windui` 才发现 `EventCtx::show_context_menu`
  走的是 `MenuRequest` + 自绘 `ContextMenu`，**没有 HMENU 可枚举**（托盘菜单才是原生
  `TrackPopupMenu` + `AppendMenuW`，两条路不同）。
- **修法**：给低频工具补一个默认键 `K`（菜单项显示它，浮条仍不加按钮），探针发真键盘路径
  的 KEYDOWN/KEYUP → `TranslateMessage` 生成 WM_CHAR → 进模式；判据用**系统剪贴板文本**
  （纯红夹具 → `#FF0000`），零 OCR、零像素猜测。
- **教训**：要给"点了菜单里的某一项"写自动化，先确认菜单是**原生还是自绘**；自绘浮层只能
  靠坐标或另开一条快捷键通道。后者顺带给了用户一个更快入口，比脆弱的坐标点击划算。

### K194 —— fit 档的上屏位图是插值像素，取色器报的不是文件字节

- **背景**：`pick_at` 第一条单测拿 4×4 彩色网格在 100×100 视口里取第 (1,1) 格，期望
  `[60,60,100]`，实得 `[90,90,100]`——正是 1.5 格处的双线性插值结果。
- **原因**：fit 档 `rebuild_image()` 会把 4×4 本地重采样成视口档（100×100），`Loaded::image`
  里已经是放大后的像素。取色器读的是**屏上所见**，不是磁盘上的原始字节。
- **口径**：这是唯一诚实的取样口径（SVG 区域渲染时宿主手里只有切片，没有整图字节），
已在 `core::pixels::Pick` 文档写明；单测改钉在 1:1 档（`zoom_at_center(1.0)` +
`rebuild_image()`，位图 == 原图）验坐标映射，不被插值噪声糊住。

### K195 —— 借日志路径函数给图片命名：后缀错了，用户看到的是文本编辑器

- **现象**：直方图插件真机跑通（PNG 签名与 CRC 都验过，922,098 字节的合法图），用户反馈
  「根本打不开，反而呈现的是文本」。现场 `.build/temp/crash-barcode-1793782074815.png.log`
  正是那张图；本机 `.log` 的用户级关联 = Pecia（文本编辑器），`.png` = rupix.exe。
- **根因**：`platform::shell::save_temp_image` 借 `core::paths::crash_log_path(...)` 拼落点，
  而该函数按崩溃报告的命名规则加 `crash-` 前缀、`.log` 后缀 ⇒ 真实落名
  `crash-barcode-<毫秒>.png.log`。`ShellExecuteW` 只看最终后缀，于是把 PNG 交给了文本编辑器。
  与插件无关：走同一条 `open_image` 通道的 scan 插件也受影响。
- **修法**：落点直接由 `diagnostics_dir().join(format!("barcode-{stamp}.{ext}"))` 给出，
  `ext` 只由 `image_ext_of` 的文件头判定，插件声明的后缀完全不参与命名。新增单测
  `temp_image_lands_with_a_real_image_suffix` 钉住「后缀 == magic / 无 `crash-` / 无 `.log`」。
- **教训**：**交给系统默认程序的文件，后缀是行为的一部分，不是标签。** 复用别的路径函数前
  先看它会不会改写名字；探针判据不能只验「文件生成了、字节合法」，还要验**系统拿它当什么
  打开**（本机关联表 + 宿主 `plugin-open` 成功日志 + 没有文本编辑器进程被拉起）。
- **遗留**：`temp\` 里的临时图片仍不自动清理，与崩溃日志同属既有口径，本轮未动。
