## 七、门禁自己的坑

### K157 —— 文档点名门禁长期绿，却漏登记了 21 个文件（整层没人读）

- **现象**（2026-10-29，宿主查缺补漏轮）：`docs_consistency.rs` 的 j2「结构文档覆盖 `src/` 全部 `.rs`」
  一直是绿的。把判据改成**按小节拼出完整相对路径**再与磁盘比，当场翻出 **21 个从未登记的的文件**——
  其中包括**整个 `extensions/` 层**（5 个文件在 §一 分层表与 §三 文件清单里一个字都没有），
  以及 `core/ext.rs`、`core/derive.rs`、`platform/logging.rs`、`platform/shared_mem.rs`、
  `ui/tokens.rs`、`ui/text_window.rs` 等。§三 是"哪个文件管什么"的唯一人读入口，它缺了一层。

- **根因**（判据读错了对象）：旧判据是 `doc.contains(文件名 basename)`。而同一份文档的**第五节符号索引
  是机器生成的**，每行都写着 `core/ext.rs`、`extensions/run.rs` 这类完整路径 ⇒ 任何一个 basename
  都能在生成段里被子串命中。**被检查的那张表根本没被读，读的是它的副产品**。
  第二条同因：§一 表格与 §四「计数相等」那行**确实**把 extensions 的 5 个文件计进了 101，
  所以"总数对得上"这件事从头到尾没有断过——总数对得上恰恰不能证明逐文件登记过。

- **解法**（就地修判据，不另立第二道门禁）：
  1. j2 改为**按 §三 的小节标题拼路径**：`### 3.4 \`extensions/\`` 之下的 `| \`mod.rs\` |`
     拼成 `extensions/mod.rs`；根文件节不加前缀。散文与符号索引段不参与判定。
  2. 配一枚用例钉住这条判据本身的形状（`j2_same_basename_does_not_cover_another_path`）：
     core 与 ui 两节各有一行 `mod.rs` 时，必须分别覆盖 `core/mod.rs` 与 `ui/mod.rs`，
     而**没开小节的层不许被别处的同名行顶上**。
  3. `structure_gen.py` 的 §一 表格更新正则里原本漏了 `extensions` 一档（LAYERS 有它、正则没有），
     补上后生成器才真能刷这一行的数字——**生成器与门禁读同一张表时，两边的名单必须同源**。

- **可复用的判据**（比这条坑本身更有用）：
  **「多处描述同一事实」先问哪两两之间有机器读过**。这里同时有三处写着"有哪些源文件"
  （§一 计数 / §三 清单 / §五 索引），机器只把它们当**总数**核对，**逐文件那一维没人读**——
  于是登记缺口可以无限期存在。要么给那一维上判据，要么删掉其中一处的独立性，别再复制第三份。

### K158 —— 宿主用例把"某个后缀有人认领"当常量，解码器换档当天就红

- **现象**（2026-10-29）：`tests/config_pipeline_e2e.rs::decoders_disabled_key_gates_decode_end_to_end`
  红了，报「发布目录里应有认领 .ppm 的解码器」。宿主代码一字未动。
- **根因**（把外部集合的快照当常量）：这条用例的意图是「ini 键 `decoders_disabled` → 停用唯一认领者
  → 解码失败」，它**已经**做到不硬编解码器 id（从运行时自述里找），但**仍钉死了后缀 `.ppm`**。
  同日另一路把发布档换到 common 0.2.4 / modern 0.3.2 / pro 0.4.1，common 自述的后缀
  从 31 缩到 24，`ppm` 不在里面 ⇒ 夹具的门票没了。而按魔数嗅探仍能解 `.ppm`
  （所以另外三条 ppm 用例照绿）——**红的那条不是解码坏了，是"谁认领这个后缀"变了**。
- **解法**：夹具格式也按运行时自述挑（`claimant_fixture`：在"我们能自己造字节的格式"里
  找今天真有人认领的那一种），后缀与 id 都不写进代码。判据一句话：
  **凡是向外部集合（解码器自述 / 远程清单 / 系统字体）取的常量，都要在运行时问，不许抄快照**。
- **顺带**：换档后随包的 `docs/decoders.json` 与目录里的 DLL 版本不再对应，设置页「可下载」卡
  如实显示「清单异常，请「刷新」」——那是清单该重出（解码器仓的事），不是宿主缺陷。


### K159 —— 「不卸库」这种判据，缓存桩在结构上就读不到；可删性才是物证

- **现象**（2026-10-29，m157）：待办 §21.3「真实 DLL 被加载锁住时的热更新」在 m156 被当成
  "已有两条用例钉住"。真去量才发现那三条 audit 用例全都用 `Loaded { _lib: None, .. }` 手工塞表——
  **桩里没有 `Library`**，于是"淘汰只置停用、不在会话中途 `FreeLibrary`"这句话
  桩在结构上就不可能读到：把 `self.loaded.remove(path)` 写进生产代码，桩用例照样全绿。
- **根因**（判据的主语搞错了）：这条判据的主语是**操作系统持有的镜像映射**，不是宿主的表项。
  拿"表里还有没有这一条"的桩去钉"句柄还在不在"，钉的是两个东西。
- **解法**（真机配对，跑 0.04 s）：把发布档里的真 DLL 拷进仓内 `.temp` 夹具，
  **用可删性当探针**——`remove_file` 失败（这台机器 `code=5` ERROR_ACCESS_DENIED）= 映射还在，
  能删 = 已卸库。再配一枚对照：同目录里一枚从没加载成功的坏档**必须删得掉**，
  否则"删不掉"可能只是介质只读。两条变异各验一头：改成摘条目**只红被淘汰那一格**；
  改成 `_lib: None` 三条**全红且红在首次解码**（`解码器「common」探测时出错，已隔离`）
  ⇒ 句柄不只是一把文件锁，它撑着函数指针。
- **顺带量到一条反直觉**：**改名（挪位）对正被加载的 DLL 是成功的**，改完名仍删不掉
  ——映射跟文件对象走，不跟名字。所以 `install.rs` 那句「旧 DLL 挪不开（多半正被加载，重启后再装）」
  的因果要反过来读：升级撞上"这张图正在用这一格式"时**挪位能成**，真后果是旧档变成
  删不掉的 `.old` 留在目录里，而这条链以前全程无声。
  判据：**Windows 上"占用"挡的是删除，不是改名**；凡按"删不掉"设计回滚的代码，都要量一次改名。
- **可复用的判据**：**判据主语在 OS 手里时，桩只能钉宿主表项，钉不了句柄**——
  这种格子要么写真机量具（可删性 / 文件锁 / 进程句柄这类外部探针，并配一枚"应当成功"的对照），
  要么在台账里明写"未测"。**不许用桩的条数冒充覆盖。**

### K160 —— `canonicalize()` 会加 `\?\` 前缀，而 Win32 的一批路径接口不认它

- **现象**（2026-10-29，m159 收测试落点）：把 37 处测试夹具的落点从系统 TEMP 收回仓内
  `.temp/rupix-test/`，助手函数顺手写了一版 `raw.canonicalize().unwrap_or(raw)`（本意是消掉路径里
  的 `..`，好让 `p.parent() == Some(dir)` 那类比较拿到同一个形态）。改完
  `platform::recycle::moves_file_into_recycle_bin` **当场红**：「移进回收站失败：文件仍在原地」，
  而这条用例在此之前一直绿。
- **根因**：Windows 上 `Path::canonicalize()` 返回的是 **verbatim 路径** `\?\E:\…`。
  `std::fs` 认它，`SHFileOperationW`（回收站走的那条）**不认**——它不解析这个前缀，也不做规范化，
  拿到就直接失败。同类接口还有一串（凡是老式 `*W` 路径入口都该怀疑），所以这不是回收站一条用例的毛病。
- **为什么以前没撞到**：`std::env::temp_dir()` 从来不返回 verbatim 路径。缺陷藏在**新写的助手**里，
  不在被改的用例里——用例只是把"藏在落点里的那一步"暴露出来了。
- **解法**：改用**词法**绝对化 `std::path::absolute()`（同样消掉 `..`，但**不加前缀**）。
  判据落在函数注释里：**跨 API 的路径要按最窄的那个接口写，别按 Rust `Path` 的手感写。**
- **可复用的两条**：
  ① **机械换落点时先做最小版本**（纯换根路径，不加规范化、不顺手清理），跑一遍门禁再谈改进——
  这次红的那条与被移动的语义无关，是"顺手加的那步"带进来的。
  ② **用例先问"是产品坏了还是量具坏了"**：同一轮里两条外部读数（新条目确实落在了 `.temp/rupix-test/`、
  系统 TEMP 按 36 条前缀命中 0）已经证明落点改动是对的，所以红点该往量具自己身上找——
  顺着这条路三分钟就定位到 `canonicalize`，否则很容易被读成"回收站功能坏了"。

### K161 —— `grep -c $"\r"` 数的是本地化翻译引号，不是回车：我用它报了一出不存在的 CRLF 缺陷

- **现象**（2026-11-01，m180）：审计两仓时我报"219 / 30 个文本文件虽然 `.gitattributes` 写了
  `eol=lf`、实际存的是 CRLF"，还给了修复方案（`git add --renormalize` + 两仓各提交一次）。
  用户批准"那就修复并提交"。复测之后才发现**缺陷根本不存在**：解码器仓 348 个跟踪文件里文本 blob
  含 `0x0D` 的是 **0**（含 CR 的 20 枚全是 `testdata/golden/*` 二进制夹具，CR 是图片数据本身）、
  插件仓 46 个文件也是 **0**；`git status` 两边都干净，`git add --renormalize` 是 no-op，
  那两次提交会是**空提交**。
- **根因**：Git-Bash 里 `$"…"` 是**本地化翻译引号**（Windows gettext 的语法），不是 ANSI-C 转义——
  要写回车得用 `$'\r'`（单引号）。于是 `grep -c $"\r"` 拿到的是字面量，数出来的是"匹配某串的行数"：
  同一份 `README.md` 报 32，而它真实 CR 数是 0。**假计数被我用 `sort | uniq -c` 汇总成"219/30"，
  看起来就像一次严谨的普查。**
- **解法**：数行尾只按字节读——工作副本用 `tr -cd '\r' | wc -c` 或 Python `b.count(b"\r")`；
  要看**仓库里存的是什么**就 `git cat-file blob HEAD:<file>` 再数（这才能把"工作副本 CRLF"与
  "blob CRLF"分开，两者是两回事：`text eol=lf` 下磁盘可以是 CRLF，blob 与 index 仍是 LF，
  归一化发生在 `add`，不产生 diff）。
- **可复用的三条**：
  ① **缺陷规模这类数字，写进结论之前要换一把独立的量具复测同一格**。同一条 shell 管道里的两个计数
  不能互相证明——这次的 219 和 30 出自同一把坏尺子，所以它们"互相印证"是幻觉。
  ② **用户批准的是"修那个缺陷"；缺陷不存在时，正确动作是当场撤回并给数**，不是"总归没坏处就跑一遍
  renormalize"——那会留下空提交和"已经修过"的假记录，比没做更坏。
  ③ 顺着这条又抓到一处**同族的真限度**：两仓清单的 `size` / `sha256` 描述的不是同一层字节
  （解码器 = 包内 DLL，宿主 `decoders::install` 解压后比；插件 = 整枚 ZIP，宿主
  `extensions::verify_package` 对下载到的 zip 比）。判"改了一层材料要不要 bump / 重传 / 重算数字"
  先问**清单的 sha 算的是哪一层**，别把另一仓的习惯照抄过来；判据表在解码器仓
  `docs/releasing.md`「改了哪一层材料」，宿主侧的分流在 `decoders/install.rs` 与
  `extensions/mod.rs` 两处校验点的注释里各写了一句。

### K162 —— 矢量「原图尺寸」其实是首屏渲染画布：夹在它上面放大，就只有位图插值

- **现象**（2026-11-01，m189）：用户在 `.build\矢量图` 逐份检查后报「示例.pdf 放大后就模糊
  不清，但我用 PDF 阅读器打开能完美放大」。同一批里绝大多数 doc 族格式（PS/WMF/EMF/DXF/HPGL…）
  放大也都只能是位图糊面——只有 svg/svgz 是真的曲线。
- **根因**：这些解码器没有 ABI v6 的 `iv_render_region`（报告 `region=false`），而且只回
  `actual_w/actual_h`（这一次渲染的画布），**不回页面点数**。于是宿主手里的 `natural` 就是
  "按视口框渲出来的第一张画布"；`desired_pixels` 又按位图口径把目标夹在 `natural` 以内 ⇒
  缩放永远只在首屏画布上做本地重采样。**图本身是矢量、解码器也肯按 target 重画**（实测
  target=2000 时 PDF 出 1413×1999、DXF 出 2000×1238），是宿主从来没再问过更大的那一档。
- **解法（只在宿主侧，不动解码器）**：新增 `core::formats::needs_zoom_rerender(ext)`
  = 解码器自渲染 **且** 不能区域重渲；Viewer 在"缩放变化 + 当前位图盖不住"时按
  `natural × 倍率 × DPI`（总量夹 64 MP）**再要一整幅**，落地后 `natural` 冻结在首屏画布
  （`prefetch::install` 同路径沿用），并按（路径 + 上次目标）记账 `vector_zoom_req`，
  防"解码器不理 target"时每轮重发。单测 `viewer::tests::target_vector_*` 三条，红证 = 关掉
  这条支路即红。
- **可复用的两条**：
  ① **"报告尺寸"不等于"文档尺寸"**：凡是渲染方按 target 画、只回画布尺寸的契约，宿主就必须
     区分"这一次画多大"与"文档多大"；拿前者当后者，几何、区域坐标、升级闸会一起错。
  ② 判"放大糊"先问**解码器肯不肯重画**，再问**宿主有没有再问**。这次两个前提都成立（探针
     直接调 DLL 按 target 2000 出图正常），坏的只是调度那一步——不去查调度，很容易误判成
     "解码器只支持位图"。

### K163 —— 解码器声明 `vector_exts` 不等于这份格式有矢量内容：取样必须逐份看像素

- **现象**（2026-11-01，m189）：m188 按 `vector_exts` 并集建样本集，用户逐份检查后发现两张
  "假的"：`示例.djvu` 是扫描件（本来就该在像素格式里，不是矢量），`zebra.zbr` 放大是
  100×100 的马赛克。排查后确认：doc-legacy 把 `zbr` 写进了 `"vector_exts"`，而实现只解出文件
  内嵌的 100×100 4 位预览 DIB（`zbr_preview` + 最近邻放大），没有任何矢量指令；ZMF 的四份
  libzmf 测试样本则是 draw2/draw3 直接 `ERR_CORRUPT`、draw4/draw5 只出全透明空画布。
- **根因**：`vector_exts` 是**归属声明**（"这个后缀由我这枚矢量解码器接"），不是**能力证明**
  （"这份文件里真有路径"）。两者在 ABI 上分得很清楚，但建样本时按声明取并集会默认二者一致。
- **解法**：样本集只收**逐份渲染出来看过**的文件；`.build\矢量图` 的 README 里把 ZMF/ZBR
  为什么不在、XPS/OXPS 为什么是白纸、DXF 为什么内容只占 1/3 全部写明（据实说明，不假装）。
- **可复用的两条**：
  ① **清单来自"声明"，证据只能来自"像素"**：给用户看的素材，每一份都要有一张渲染图对过眼，
     否则"覆盖了 N 个后缀"里会混进"其实什么都没画"的那几份。
  ② 遇到"声明是矢量、实际是位图"的成员，正确动作是**不放进矢量样本集并在说明里点名**，
     而不是为了凑齐后缀数把它塞进去——后者正是 m188 被用户点破的那件事。

### K164 —— DXF 的颜色在组码 430（`color_name`），组码 62 只是个 ACI 索引

- **现象**（2026-11-01，m190）：`.build\矢量图\DXF.dxf` 放大后"颜色都不对，只有线条"——
  图纸内容全黑，而样本里每条线各有自己的颜色。
- **根因**：`dxf` crate 把组码 62 解成 `EntityCommon.color`（一个 ACI 索引），组码 430 解成
  `EntityCommon.color_name`（字符串）。`dxf_to_svg` 只读 **`color_name`**：只写 `color` 时
  它看不见，一律按默认前景色画。ACI 还有 BYLAYER（256）这一档要回到图层表里取色。
- **解法**：`doc-cad` 在交给 `dxf_to_svg` 之前先过一遍 `paint_colors`——`color.index()` 命中就
  换算成 CSS，否则回落到 `layer.color`，写进该实体的 `color_name`；换算表覆盖 ACI 1–9 与
  250–255 灰度，其余按索引取色相（0.70 饱和 / 0.38 亮度）。用例
  `entity_color_index_becomes_a_real_css_color`（组码 62=1 的 RED_LINE 必须出现 `#e02020`）。
- **可复用的一条**：第三方"格式 → SVG"库读的是它自己挑的字段，**字段名对不上时不会报错，
  只是静默用默认值**。改颜色/线宽这类属性时，先用一条带已知取值的夹具把"库到底读哪个字段"
  钉死，再写换算。

### K165 —— 库"能打开"不等于"画了东西"：justpdf-formats 的 XPS `render_page` 是白页桩

- **现象**（2026-11-01，m190）：`XPS.xps` / `OXPS.oxps` 打开纯白，`--probe-decode` 也报成功。
- **根因**：`justpdf-formats` 的 XPS 实现只解析到页面外壳，`render_page` 返回一张空白画布
  （源码里明写是未实现）。宿主侧一切正常：探测认领、渲染成功、像素全白——**没有一处错**，
  错的是"库能开"被当成了"库会画"。
- **解法**：`doc-xps` 丢掉该库，自己走 OPC 链（`_rels/.rels` → `fdseq` → `fdoc` → `fpage`）
  再把 FixedPage 映射成 SVG（Path / Canvas / Glyphs、SolidColor / Linear / Radial 画刷、
  Transform、ClipPath），交给 resvg 光栅化；每个部件有 16 MiB 读取上限、嵌套深度 64 上限。
  未实现的按限制如实写进 README：`Image` 与 `ImageBrush` 不渲染，`Glyphs` 用系统字体近似。
- **可复用的两条**：① 换库前先渲一张**有内容**的夹具并断言像素，不要只看返回码；
  ② 用户报"纯白"时先分两种——"解不了"会报错，"解了没画"才是这类静默失败。

### K166 —— "先按 72 dpi 整幅光栅、再最近邻放大"是放大必糊的写法

- **现象**（2026-11-01，m190）：PS / PRN / EPS / AI 放大后满屏像素块（PDF 用户报"放大很多倍
  才这样"，PS 类是全程糊）。
- **根因**：`doc-print` 当初为省内存，把整篇按固定 72 dpi 渲成位图（`render_to_display_list`
  返回的页面尺寸 = 点 × dpi / 72），显示时用 `FilterType::Nearest` 缩放到目标尺寸。放大时
  每个源像素被复制成方块——**源头分辨率是常数，倍率再高也不会多出细节**。
- **解法**：只解析一次（`DisplayListPage` + `prepare_display_list` 缓存在线程局部），
  **按目标画布直接光栅化**：整幅档与区域档走同一个 `render_region_prepared`，区别只是视口
  （整幅 = 0,0,page_w,page_h；区域 = 请求那一块）与像素尺寸。密度 = `dpi × scale`。
  用例 `region_is_rasterized_at_density`（40,0 起的 20×20 区域 request 成 80×80，竖线边缘落在 x=40）。
- **可复用的一条**：凡"先渲成固定尺寸位图再缩放"的实现，放大档必然是插值；正确形状是
  **把目标尺寸一路传到光栅化调用**里。中间层只要能"重放"（display list / 场景树），
  就不要让它先落地成像素。

### K167 —— 能力位是 DLL 级单值，合并档成员能力不齐时会发错请求（`region_exts`）

- **现象**（2026-11-01，m190，潜在）：`doc` 档里 EMF/EMZ 走 `emfsdk`，它的光栅器只有
  "整幅画布多大"（`RenderOptions{target_width_px, target_height_px}`），**没有视口参数**。
  若它们跟着 `CAP_REGION` 一起进区域通道，放大时会把**整页**缩进那一小块——内容错误，
  比糊更难解释。
- **根因**：`iv_render_region` 与 `CAP_REGION` 都是**整枚 DLL** 的事实，而"哪些成员真的能按
  区域密度重光栅化"是**成员级**的事实，ABI 里原先没有表达它的地方。
- **解法**：加法式元数据键 **`region_exts`**（分号分隔小写后缀，`iv_metadata` 里追加一行）；
  宿主 `decoders::registry::declared_cached` 读它收窄区域集——键缺席 ⇒ 该 DLL 的
  `vector_exts` 全部，空串 ⇒ 明确一个都不进。用例
  `region_exts_narrows_the_vector_list_per_member`（缺席 / 声明 / 空列表三种形状）。
  协议条文进了解码器仓《解码器开发规范.md》§十六 末节。
- **可复用的两条**：① 把"能力"从 DLL 级下沉到成员级时，**加法式元数据键**比新增导出更省事
  （v5 老 DLL 不认这个键 ⇒ 走缺省读法，行为不变）；② 收窄的判据必须是"它真的按区域密度
  重画了吗"，不是"它是不是矢量"。

### K168 —— 没有视口 API 的光栅器，区域渲染只能"整幅超采样再裁剪"，代价按倍率平方涨

- **现象**（2026-11-01，m190）：`EMF.emf` 放到 8 档时，宿主按 m189 的整幅路线请解码器重画，
  实测 `bitmap=4674x3344 cost=2233.3ms`，再放大到 `9684x6929 cost=7908.0ms`。
- **根因**：`emfsdk` 只能指定"输出画布多大"，想让某一块更清楚，就只能把**整幅**渲到
  `自然尺寸 × 倍率`（像素数按倍率平方增长）。这不是宿主选错了路线，是库的能力边界。
- **解法**：EMF/EMZ **不进区域通道**（见 K167 的 `region_exts`），保留 m189 的整幅重渲路线：
  放大仍然清晰（按倍率重画，不是插值），只是倍率越高越贵；代价在 README/HISTORY 里如实写明。
  **不为"覆盖全部后缀"硬塞区域通道**——那是拿内容错误换一个漂亮的覆盖率数字。
- **可复用的判据**：评估"要不要给某个成员补区域通道"时，先看**它下面的光栅器收不收视口参数**；
  不收的话，区域通道只能变成"超采样 + 裁剪"，收益是"能封顶内存"，不是"更快"。

### K169 —— DXF 的 `TEXT`：字高是组码 40，编码看版本；`dxf_to_svg` 两样都不管

- **现象**（2026-11-01，m191）：`DXF.dxf` 放大后"文字笔画缺了很多"——其实样本里根本没有
  `TEXT`，标签是字形轮廓折线描边，放大就是双线/断线的空心字。
- **根因**：`dxf_to_svg` 支持 `EntityType::Text`，但它排出的 `<text x y fill>` **没有
  `font-size`**（落到 SVG 默认 16 用户单位）也不写字体栈；而且它把 viewBox 的 padding
  写死成 1.0（每边各留 100%），图纸只占中间九分之一。编码上，`dxf` crate 只认
  `$ACADVER`：R2007+ 整份按 UTF-8 读、**不**解 `\U+XXXX`；更早的版本才按
  `$DWGCODEPAGE` 解码并处理 `\U+XXXX`。样本若声明 AC1027 却写转义，会原样显示成
  `\U+4E2D…`。
- **解法**：`TEXT` 不再交给 `dxf_to_svg`——doc-cad 自己排字（`font-size = 组码 40 ÷ 0.72`，
  字体栈带系统中文，两种编码写法都认），再把 `dxf_to_svg` 那份无 `font-size`
  的 `<text>` 剥掉；viewBox 收回到内容框 + 4%。`.dxf` 输入同时改成**直接**交给 `dxf`
  crate（原先也走 `acadrust → DxfWriter → dxf`，DXF 二次转换只会丢字段）。
- **判据**：`text_entities_carry_height_and_a_cjk_font_stack`（字高/中文/颜色三样都在，
  且 `<text>` 只出现一次）、`viewbox_is_tightened_to_the_content_box`。

### K170 —— `nom-hpgl` 遇到不认识的命令就**停**：`PC` 一出现，后面的几何全丢

- **现象**（2026-11-01，m191）：HP-GL 全家族只有黑白，用户报"颜色有问题"。
- **根因**：HP-GL 的笔色是 `PC`（HP-GL/2 `PC r,g,b;`、HP-GL `PC pen,r,g,b;`），`nom-hpgl`
  不解析它；而它的顶层是 `separated_list_complete`，**遇到解析不了的命令就返回前缀**，
  我们这边又把"有剩余字节"当成功 ⇒ 带 `PC` 的真实文件从第一个 `PC` 起整段丢失。
  另一个坑：把 `PC…` 改成空串会留下 `;;`，空命令同样让解析停下。
- **解法**：先按 `;` 切一遍命令流，把 `SP`/`PC` 摘成"笔号 → 颜色"表，**连分隔符一起**
  从流里删掉（用保留项 `join(";")` 重建），几何再交给 `nom-hpgl`；场景按笔色分组输出
  `<path>`（颜色是呈现属性，不能挂在子路径上）。没有 `PC` 的文件按默认黑笔，不臆造色。
- **判据**：`pen_colors_survive_without_truncating_geometry`（两支笔两种色 + 两段线都在）、
  `four_argument_pen_color_targets_a_named_pen`、`files_without_pen_colors_stay_black`。

### K171 —— `emfsdk` 的栅格器没有抗锯齿、没有视口、字体缓存只有一支无衬线

- **现象**（2026-11-01，m191）：`EMF.emf` / `EMZ.emz` 的文字"坑坑洼洼"，中文还是空心描边。
- **根因**：`emfsdk` 的 `set_pixel` / 扫描线填充都写硬像素（无 AA），`RenderOptions` 只有
  目标宽高（没有视口），`RenderFontCache::load()` 只按 `Family::SansSerif` 取**一支**字体
  ⇒ 汉字 `glyph_index()` 返回 `None`，文字直接不画。所以"把中文交给它排"这条路根本不存在。
- **解法**：① **超采样**——预算内（2× 画布 ≤ 12 MP）按 2× 请求、拿到结果盒式降采样回目标
  尺寸，4 个样本一平均就是抗锯齿；位图成员只回自然尺寸，不能降采样。② **中文填充多边形**——
  样本侧把字形轮廓发成 `EMR_POLYGON`，按绕向区分外轮廓/挖空：先填外轮廓（前景色）、再把
  挖空轮廓填回底色（`emfsdk` 只认单条轮廓的 even-odd，没有子路径概念；用"点在别的轮廓内"
  判挖空会把中文字里互相重叠的笔画误判成挖空，填回去就是白斑）。
- **可复用**：拿"整幅超采样 + 降采样"给不支持 AA 的第三方栅格器**当面糊补**，前提是它
  认目标尺寸；代价是 4 倍像素，必须封顶（这里 12 MP）。

### K172 —— `usvg::Options::default()` 的字体库是**空的**：场景里有 `<text>`，屏上一个字都没有

- **现象**（2026-11-01，m192）：HP-GL 的 `LB` 标签解析对了、导出的 SVG 里明明白白写着
  `<text x=… font-size=…>PLT</text>`，真机与离屏渲染却一个字形都不出现（连英文也没有）。
- **根因**：`doc-hpgl` 建树用的是 `resvg::usvg::Tree::from_data(svg, &Options::default())`。
  `Options::default()` 里装的是**空的** `fontdb::Database`——解析期查不到字体就把文字节点
  丢掉，而且不报错。同档其它成员（CAD / WMF / XPS / doc-legacy）都装了系统字体库，只有这条漏了。
- **解法**：装一份进程内只扫一次的系统字体库（`OnceLock<Arc<Database>>` + `load_system_fonts()`），
  每次解析只克隆 `Arc`；判据必须**落在像素上**（`label_text_reaches_the_pixels`：画布上
  那个区域必须出现深色像素），只断 SVG 字符串的用例在老代码上也是绿的。
- **红证**：把那一行换回 `Options::default()` 重跑，用例当场红（"一个深色像素都没有"）。
  真机取证同一现象：0.2.1 的 `PLT.plt` 截图里只有几何、没有标签。

### K173 —— 第三方库"在库里排字"且没有字体回调时：只能打补丁，`forbid(unsafe_code)` 要放宽成 `deny`

- **现象**（2026-11-01，m192）：`EMF.emf` 里的中文渲染成品是 5×7 点阵方块。
- **根因**：`emfsdk` 0.2.0 的 `RenderFontCache::load()` 只按 `Family::SansSerif` 取**一支**
  字体，并且完全忽略 `EMR_EXTCREATEFONTINDIRECTW` 里的 `LOGFONTW::lfFaceName`
  （它读了字体记录，只留 `lfHeight`，名字丢掉）。汉字 `glyph_index()` 返回 `None` ⇒
  `render_text` 返回 `None` ⇒ 整段（连同 ASCII）退回 `draw_glyph_5x7`。库内绘制、没有回调，
  外部改不了；宿主侧又必须不动。
- **解法**：按仓库规则在 `/.3rd/emfsdk-0.2.0` 留一份带补丁（E01）的副本，`doc-emf` 走 path 依赖：
  ① 字体栈 + `OnceLock` 进程内只索引一次（原本每次渲染都重扫系统字体，本机 400 面 260–950 ms）；
  ② 字库数据用 `fontdb::make_shared_face_data` 走 **mmap 共享**，不复制进堆（单个中日韩字库
  10–20 MB）；③ `LOGFONT` 点名的字族排最前，其余按兜底栈**逐字**找字形，全都没有才退回点阵。
- **踩点**：`make_shared_face_data` 是 `unsafe`，而 crate 顶部是 `#![forbid(unsafe_code)]`
  ——`forbid` 不能被就地 `allow` 推翻，只能降成 `deny(unsafe_code)` 再给那一个函数
  `#[allow(unsafe_code)]`（补丁登记在副本的 `SOURCE.md`，别处照抄不了）。
- **补丁要能被别人重建**（2026-11-01 补）：`.3rd` 不入库，只把改动留在副本里等于发布物不可重建。
  补丁现有**公开登记**在解码器仓 `RuPix-Decoder/patches/emfsdk-0.2.0/`（README + manifest + patch），
  判据是"上游 0.2.0 原文 + 该补丁 = 构建用的副本"；`manifest.json` 记上游核对日期，
  超 90 天 `check_patches.py` 判红（2026-11-02 起该门禁不记也不核哈希，只核补丁触及路径与登记一致）。
  重放一律 `git -c core.autocrlf=false apply`（CRLF 会让副本行尾偏离上游）。
- **判据**：`cjk_glyphs_come_from_a_real_font`——"两个不同的汉字必须画出不同的字形"。
  5×7 点阵对**所有**非 ASCII 字符画同一个方框，所以这条老代码上必红（实测：上游两字逐字节相同）。

### K174 —— `LB` 以 `<ETX>` 收尾：拼回流时再补 `;` 会造出空命令，后面的几何全丢；GBK 夹具必须是真 GBK 字节

- **现象**（2026-11-01，m192）：`LB` 正文里带 `;` 的用例里，标签出来了，**标签之后那条线没了**。
- **根因**：`nom-hpgl` 的 `Label` 用 `take_until("\x03")` 吃掉了 `<ETX>`，顶层分隔符是
  `one_of!(";\x03")`；把命令 `join(";")` 拼回去时给已带 `<ETX>` 的 `LB` 又补了一个 `;`，
  下一次解析就撞上空命令、`separated_list_complete` 在那里停下。**只删命令不删分隔符**
  （K170 的同一类）与**多补分隔符**是同一个坑的两面。
- **解法**：逐条拼回流，只有"不以 `<ETX>` 结尾"的命令才补 `;`。
- **另一半**：`gbk_labels_are_decoded` 原先写的是 `"中文".as_bytes()`——那是 UTF-8，整份文件
  合法 UTF-8，第一跳就成功，**GBK 分支根本没被走到**（假绿）。改成真 GBK 字节
  （`D6 D0 CE C4`）并先断"这四字节不是合法 UTF-8"，夹具才真的站在判据管的那条分支上。
- **附带**：`std::str::from_utf8(&[0xd6, 0xd0, 0xce, 0xc4])` 会触发 `invalid_from_utf8`
  lint（clippy `-D warnings` 红灯），把常量先塞进 `Vec<u8>` 再传引用即可。

### K175 —— 解码器版本号写在两处：`Cargo.toml` 与 `export_metadata!` 字面量

- **现象**（2026-11-01，m192 收尾审计）：`doc` 升到 0.2.2、`decoders.json` 也对，可 DLL 里
  自述的 `version` 还是 `0.2.1`——用户界面上看到的版本与更新比对用的版本对不上。
- **根因**：版本号有两份真源。`Cargo.toml` 的 `[package] version` 被 `decoders.json`/更新比对
  使用；`src/lib.rs` 的 `rupix_abi::export_metadata! { "version" => "x.y.z", … }` 是宿主实际
  读到的那个（`decoders::host` 用它给"同 id 多份 DLL 谁胜出"排序，设置页也显示它）。
  只 bump 一处，另一处静默留在旧值上——编译不报、门禁不红。
- **解法**：升级时两处一起改；`tools/check_history.py` 增设一致性检查（读 `src/lib.rs` 的
  metadata `version` 与 `Cargo.toml` 比对）。发布前另补一道字节级核对：DLL 里应有
  `version\0x.y.z\0`，且与清单一致。
- **红证**：这次不是造出来的——门禁加上去当场就红了（`doc: metadata version 0.2.1 !=
  Cargo.toml 0.2.2`），改完字面量才转绿，说明它抓的是真实缺陷。
- **同类提示**：凡是"同一事实写两处"的字段（版本、ABI 号、后缀清单），要么合并成一处派生，
  要么必须有一道门禁同时读两边。

### K176 —— 图标字体码位是赌局：先查 `.ttf` 的 cmap 再写

- **现象**（2026-11-02，m193 翻页按钮）：浮条上新增的"上一页 / 下一页"两颗渲染成
  **两个空方框**（豆腐块）。代码编译通过、单元测试全绿、`Btn::name()` 也有中文标签，
  只有真机截图看得出来。
- **根因**：`\u{E89C}` 在 `segmdl2.ttf` 里是真字形，但它是**信封**（发信/分享），
  不是"翻页"；`\u{E89D}` 在整个字体里**没有字形**——PUA 区里既缺字又有"看着像但不
  是那个意思"的位，凭印象写码位等于赌。
- **解法**：先用字体 cmap 实查再写码位。本机一条命令：

  ```py
  from fontTools.ttLib import TTFont
  cmap = TTFont(r"C:\Windows\Fonts\segmdl2.ttf").getBestCmap()
  print([hex(c) for c in (0xE76B, 0xE76C) if c in cmap])
  ```

  cmap 只证明"有字形"，不证明"长什么样"，所以第二步是把候选码位渲染成一张对照图
  （`PIL.ImageFont.truetype(segmdl2.ttf, 44)` 画一排 + 码位标签）用眼睛挑。
  翻页最终用 `E76B`/`E76C`（ChevronLeft/Right）：清晰、方向直白，
  且与逐帧的 `E892`/`E893`（竖线 + 三角）一眼可分。
- **配套**：`chrome.rs` 加 `page_glyphs_are_their_own_pair`，钉住"翻页两颗彼此不同、
  且都与逐帧不同"——这挡得住"复制粘贴时改成同一颗"，挡不住"码位在字体里不存在"，
  后者只能靠上面那条实查流程。
- **同类提示**：`Btn::Info` 退回普通文本 `!` 是同一个理由的旧例——PUA 码位拿不准时，
  宁可画一个 ASCII 字符，也不要赌一个可能不存在的位。
