## 一、一句话架构

**宿主 exe 只做"看图"（窗口、交互、几何变换、缓存），位图解码全部外置为解码器 DLL；
矢量格式也由解码器渲染（按目标像素尺寸自渲染），只有原生 SVG 走宿主内置的 resvg。**

```text
┌──────────────────────── rupix.exe ────────────────────────┐
│  core(0)      状态机 / 解码调度 / 目录清单 / 缓存 / 几何        │
│  platform(1)  Win32 薄封装：SEH 闸 / DLL 硬化 / 剪贴板 / 崩溃钩子 │
│  decoders(2)   解码器宿主：DLL 生命周期 + 目录 + FFI 编排        │
│  extensions(2) 非解码器扩展：manifest 发现 + 进程外编排（P0）    │
│  ui(3)        无边框窗口 / 画布 / 悬浮层 / 设置 / 托盘        │
│  runtime(4)   装配：run() + 16ms 轮询 + 解码栈接线          │
└───────────────────────┬──────────────────────────────────┘
                        │ ABI v6（加法式：v5 的 6 个 C 导出与结构体逐字节未动；可选 iv_render_raw / iv_caps / iv_metadata / iv_export_svg / iv_render_region）
                        ▼
  decoders\*.dll  —— 运行时扫描；格式清单 = 各 DLL `iv_decoder_info()` 的动态并集
      │             能力路由 = `iv_caps()`（FULL / SCALED / RAW_PARAM / …）
      │             具体有哪些档与库 → 独立仓库 `解码器仓库`（宿主文档不维护第二份清单）
      ▼
  SVG / SVGZ → 宿主内置 resvg（原生 SVG，不进解码器体系；**位图一律交给解码器**，宿主不再内置任何位图解码库）
  其余矢量 → 一枚矢量解码器 DLL，按目标像素尺寸自渲染（无中间格式；契约见 .plan/m153）
```

**便携**：全部持久化写在 exe 同级目录之内——用户会看的 `rupix.ini` 与 `decoders/` 在根，
只用来取证的（`temp\rupix-<日期>.log`、`temp\crash-<日期>.log` 与 `temp\crash-<日期>-<时分秒>.dmp`、
`temp\rupix.run`）收在 `temp\` 里、按天命名，启动清掉文件名日期早于 7 天前的；
纯提速件（SVG 字体索引缓存 `cache\svg-fonts.bin`，丢了只损失速度）收在 `cache\` 里、
不参与按天清理（2026-11-01 用户裁定不得混进 temp）；
不碰注册表与用户配置目录，删掉目录即干净卸载
（唯一落点由 `core::paths` 的 `OnceLock` 给出；写失败 = 只读介质 → 静默降级为纯内存会话）。
`rupix.ini` 的写盘是 `.tmp` → `sync_all` → `rename` 三步：改名原子，但**内容不在文件系统
日志里**，少一步 fsync 就可能留下"名字是新的、内容是空的"配置（见 `core::config::save_to`）。
**解码结果一律只在内存**，磁盘解码缓存 2026-10-19 撤除（见 §六 能力表与 K68）。

## 二、分层架构（五层，扩展与解码器平级）

```text
core(0) → platform(1) → {decoders(2), extensions(2)} → ui(3) → runtime(4)
```

**方向规则**：高层可以 `use` 低层，低层**不得**知道高层。每层还有一条禁引外部 crate 的
可测性红线。**机器判定的唯一正源是 `main/build/layering_scan.py` 的 `LAYER_ORDER` / `BARRED` 表**
（本文、`目录结构说明.md` §一、`AGENTS.md` §三 都只是它的读者视图）。

| 层 | 序 | 一句话职责 | 禁引（BARRED） | 装配位置 |
|---|---|---|---|---|
| **core** | 0 | 纯逻辑：配置 / 路径 / 目录清单 / 解码调度 / 查看器状态机 / 像素与几何，**不引任何 UI 与平台 API**，单测可无头跑 | `windui` `windows` | `src/core/` |
| **platform** | 1 | Win32 薄封装：SEH 调用闸、DLL 搜索路径硬化、剪贴板、崩溃钩子、无边框外框反算、**HTTPS GET**（WinHTTP，只服务清单刷新与 DLL 下载，支持读块进度回调）、扩展 IPC 底座（命名管道 / 共享内存 / 进程） | `windui` | `src/platform/` |
| **decoders** | 2 | 解码器宿主：DLL 生命周期 + 解码器目录 + FFI 编排 + 候选仲裁 + **解码器清单**（本地 `<exe>/docs/decoders.json` 优先；用户点「刷新」才后台联网更新，地址存 ini `decoder_index_*` 可改）+ **下载安装**（后台线程 + 读块进度，Win32 一律经 platform） | `windui` `windows` | `src/decoders/` |
| **extensions** | 2 | 非解码器插件宿主：`plugins/*/manifest.json` 已安装发现、`docs/plugins.json` 本地清单 + Gitee/GitHub 远程刷新（地址存 ini `plugin_index_*` 可改）、release ZIP 后台下载 / 校验 / 更新安装；命令型与编辑型插件已接（管道 + 共享内存底座），面板型未接；插件可自报**动态热键**（manifest `hotkey`，宿主运行时收集，内置快捷键优先）。与 decoders 平级且双向禁互引 | `windui` `windows` | `src/extensions/` |
| **ui** | 3 | windui 控件与窗口内容（画布 / 悬浮层 / 设置 / 托盘 / SVG 渲染后端），不含装配 | `windows` | `src/ui/` |
| **runtime** | 4 | 唯一认识所有人的装配层：`run()` + 16ms 轮询 + 解码栈接线，允许引 windui | — | `src/runtime/` |

- 逐文件清单、源文件数量与行数见 [`../目录结构说明.md`](../目录结构说明.md) §一、§三，由结构生成器维护。
- `src/` 根下的 `lib.rs`（各层导出 + `install_decode_stack()` / `run()`）与 `main.rs`
  （命令行 + `--probe-decode`）不判层。
- **不设第 6 层**：`extensions` 与 `decoders` 同层平级，不是新的一层；托盘在 runtime 装配里建，
  没有独立的壳层职责；跨线程只有一条解码
  `Done/Req` 通道 + 三个进程级静态（裸数据参数、禁用集、重扫代次），出现第二条通道时
  再考虑独立事件层。

## 三、关键类型（跨层契约）

这些类型是分层能否站住的关键：**core 只认识它们，不认识 windui**。

### 3.1 `core::pixels::RgbaImage` —— 上屏位图 + `gen` 代号（判脏键）

```rust
pub struct RgbaImage { pub width: u32, pub height: u32, pub rgba: Vec<u8>, pub gen: u64 }
```

`gen` 是进程内单调递增的代号（每次构造 +1，永不复用）。core 用它替代 UI 框架的位图句柄：
**上屏层只在 `gen` 变化时重新上传纹理**，语义与 windui `Image::cache_id` 同构，但类型本身
不认识任何 UI 框架——这是 core 可纯化的关键。位图变化只发生在「解码结果落地 / 旋转 / 翻转 /
重新取样」这些本来就要重建图像的时刻。

### 3.2 `core::geometry::RectI` —— 框架无关的整数矩形

`{ x, y, w, h: i32 }`，`Copy` 的 POD。`ui::canvas` 在边界处做 1:1 转换
（`to_rect` / `from_rect`），core 内部一律用 `RectI`。

### 3.3 `core::decode::DecodeBackend` 与 `SvgDecodeFn` —— 依赖倒置的注入口

```rust
pub trait DecodeBackend: Send {
    fn decode(&mut self, path: &Path, ext: &str, max_w: u32, max_h: u32,
              frame_index: u32, raw: Option<RawParams>) -> Result<Decoded, String>;
}
pub type SvgDecodeFn = fn(&Path, Option<&RegionReq>, u32, u32) -> Result<Decoded, String>;
```

- **消费方定义接口、高层实现**：`core::decode` 声明 trait，`decoders::Host` 实现它。
- **SVG 走 fn 指针**（零虚表、单态化），实现在 `ui::svg::decode`（windui resvg）。
- 两者的装入点是**同一个** `rupix_lib::install_decode_stack()`：GUI 入口、命令行探针
  与示例统一调这一处；core 因此不 import 解码器与 windui。未装入时返回可诊断错误，不 panic。
- 过去这里有**第三个注入点** `set_decoder_stamp(u64)`：磁盘解码缓存需要知道"这一张是由谁
  解出来的"。那套缓存 2026-10-19 整体撤除（依据见 `HISTORY.md` 与 `docs/踩坑记录.md`），
  注入点与 `decoders::catalog` 里算指纹的那段随之退场；K59 那条坑仍留在踩坑记录里，
  它的教训（"换解码器后旧结果照样命中"）对任何将来重新引入缓存的设计依旧成立。

### 3.4 `ui::canvas::ImageCache` —— 代号驱动的纹理缓存

```rust
struct ImageCache { gen: u64, img: Option<Image> }
```

`obtain(&RgbaImage)` 只在 `gen != self.gen` 时做一次 `Image::from_rgba` 重传；
未命中的翻页与缩放路径仍是每帧 `Rc` 克隆 + `draw_image`。**上传失败不置错**：沿用旧纹理
并记 `log::error`（画面冻在上一帧好过弹错误）。主位图与鸟瞰缩略图各持一个实例。

### 3.5 `decoders::Fail` 三分类 —— 失败后还要不要换解码器再试

```rust
enum Fail { NotClaimed(String), Unsupported(String), Hard(String) }
```

| 变体 | 含义 | `worth_sniff()`（换解码器还有救吗） |
|---|---|---|
| `NotClaimed` | 解码器 probe 明确拒绝内容（魔数不认识） | ✅ 走嗅探兜底 |
| `Unsupported` | 内容认了但本解码器缺能力（`ERR_UNSUPPORTED`） | ✅ 走嗅探兜底 |
| `Hard` | 损坏 / 过大 / panic（已隔离） | ❌ 换个解码器再全解一遍只是重复失败 |

分类的目的只有一个：ext 命中的解码器解不动时，**要不要再花一次嗅探兜底**
（`.jxl` 改名 `.png` 的场景就靠这条救回来；坏掉的 50MP RAW 则不值得重试）。

### 3.6 其余契约类型

| 类型 | 位置 | 作用 |
|---|---|---|
| `Decoded` / `Bitmap` / `Anim` / `Region` | `core::pixels` | 解码产物的统一货币：静态图 / 动画（帧元数据）/ 区域（SVG 局部重渲） |
| `MAX_PIXELS`（64MP）`MAX_EDGE`（16384）`MAX_TEXTURE_SIDE`（16384） | `core::pixels` | 位图硬顶的**单一定义点**：`MAX_PIXELS` 作用于解码器两阶段（查询与渲染都按它校验，2026-10-28 起与解码器侧那道分配闸同值），`MAX_EDGE` 作用于 SVG 光栅化的边长上限，`MAX_TEXTURE_SIDE` 作用于**显示侧**单边封顶（GPU 纹理建不出来的尺寸 ⇒ 上屏位图等比降边，不撞白屏）。★ 这道总量闸判的是**文件头声明的原图尺寸**，两侧同口径（解码器侧 `check_dims` 注释明写"缩放腿不能拿小图绕过闸"）⇒ 超 64 MP 的位图**连视口档那一层都进不来**，让它进金字塔低层要先解冻解码器仓、把判据来源改成请求档位（账在 `待办.md` §20，2026-10-29 裁定：不抬这个数） |
| `to_rgba8` / `normalize_to_rgba` / `oriented` / `fit_to` / `fit_oriented` | `core::pixels` / `core::geometry` | 像素格式归一、EXIF 方向转正、按目标框取样——几何的**单一定义点**。`fit_oriented` 把"转正 + 缩到框"合做一步：反向轴按**远端锚定**分块降采样，再把小图转正 ⇒ 与 `fit_to(oriented(..))` **逐字节相同**而省掉整张那一趟搬运（m49 / K77） |
| `Done { seq, path, out }` | `core::decode` | 解码结果回包；`seq` 是世代令牌，过期一律丢弃 |
| `ReqKind { Main, Prefetch, Thumb }` | `core::decode` | 请求语义——`Main` 推 `main_floor` 且过期早退，`Prefetch` 允许被新主画面作废，`Thumb` 独立解码不被翻页取消 |
| `FormatSource`（`declared_exts` / `declared_raw_exts`） | `core::formats` | core 问"哪些后缀算图片 / 走裸数据窗"的接口，数据由 decoders 层 install 进来 |

## 四、层间数据流：打开一张图到上屏

```text
命令行 / 拖放 / 右键打开
   │
   ▼
① main.rs ── install_decode_stack() ──► 装入 DecodeBackend(decoders::Host) + SvgDecodeFn(ui::svg)
   │  panic_guard::install()（platform）
   ▼
② runtime::run() ── 通道 → 解码线程 → Viewer（顺序不可换）
   ▼
③ core::viewer::open(path)
      └► core::gallery::from_file  以该图为锚枚举整目录；传的是文件夹就取该目录
            锚点不在图片清单里 ⇒ 插进清单并定位为当前项（是图不是图由解码层判）
            清单 = 内置登记表（formats::BUILTIN_DECODERS 的 auto_claim 行）∪ 启用解码器自述并集
      └► request_decode()（视口尺寸未知时先 mark_need，拿到真实视口再补发）
   ▼
④ core::decode（单解码线程，串行）Req{seq, kind, ...}
      └► 过期早退：Main/Prefetch 若 seq < main_floor（新 Main 已入队），
         不发解码，直接以空串 Err 回包让 UI 清 prefetch_seq / 过期丢弃
      └► catch_unwind 包住整张解码（坏图不能打挂线程）
            svg/svgz ──► SvgDecodeFn（ui::svg，resvg 按目标尺寸光栅化）
            其余     ──► DecodeBackend = decoders::Host
                          选候选（扩展名 + 未禁用 + 未拉黑 + **能力位图覆盖请求所需位**）
                          → platform::seh::invoke 闸内 FFI：probe → 两阶段 render
                          → to_rgba8 → fit_oriented(EXIF 转正 + 收到目标框，一步)
   ▼
⑤ Done{seq, out} ── mpsc ──► runtime 的 16ms 轮询（App::on_interval）
   ▼
⑥ core::viewer::apply(done)
      seq ≠ want_seq → 丢弃（翻页后画面不会跳回去）
      seq 命中      → install()：装成 RgbaImage{gen+1}，同时排相邻图预读
   ▼
⑦ ui::canvas::paint
      ImageCache 按 gen 判脏 → 仅变化时 Image::from_rgba 重传 → draw_image
      几何 RectI → windui Rect（边界 1:1 转换）
   ▼
⑧ 旋转 / 镜像（R / M 键或菜单）
      core::geometry::transformed 就地重算像素 → 新 RgbaImage（新 gen）→ ⑦ 重传
      ※ 不走解码线程，像素层即时变换
```

**这条链上的四条不变量**：

1. **解码全在后台线程**，UI 线程只收结果，因此翻页不卡界面。
2. **过期结果必丢**：`seq` 不等于当前 `want_seq` 的回包一律不装（防止"翻页后画面跳回去"）。
3. **换图不清旧图**：旧图留在屏上直到新图解码完成由 `apply` 原子替换（否则解码期间只剩背景）。
4. **渐进预览占位**：大图先回一张低清占位顶屏（不排动画时刻表、不触发预读），全解回来再替换。

## 五、解码路由与清单规则

1. **默认路由只有两条**：内置登记表认领的后缀 → 该内置库的实现（今天 `svg`/`svgz` → `SvgDecodeFn`，
   即内置 resvg）；其余一切 → `DecodeBackend`（解码器宿主）。**没有第三条兜底路由**。
   内置认领哪些后缀由 `core::formats::BUILTIN_DECODERS` 一张表决定（m56），路由代码里不再硬编码后缀。
   ★ 表上的 `auto_claim=false` 是硬门：这样的内置库**不进默认路由**，只有被用户点名为某后缀的
   首选时才走。今天表里没有 `false` 的条目了——唯一一枚（m57 接入的 `wic`）已于 2026-10-25
   整层删除：便携看图器不调系统解码器（宪章 §5.1）。
2. **能力与清单不脱节**：目录里出现哪些扩展名 = 内置登记表派生的 `formats::builtin_exts()` ∪
   各启用 DLL 自述扩展名的动态并集（`gallery::is_image_ext_in` / `known_exts`）。
   内置那半**只有登记表一处**（m56 之前它是三份副本：路由硬编码 + `is_builtin_ext` 的
   `matches!` + `gallery::BUILTIN_EXTS` 常量，现已收成一个真源）。解码器没装 / 被关掉，该后缀就不出现在
   目录清单里——没有人工维护的全局表，`cargo test --lib ext` 锁住这条语义。
3. **两阶段 ABI**：解码器先在 `out = NULL` 的查询阶段回报真实尺寸与 `bytes_needed`，
   宿主一次性分配（**无重试**）后再渲染；位图解码器路径上 `budget_bytes`（= `MAX_PIXELS`×4
   字节）与 `MAX_PIXELS` 在查询与渲染两侧都校验，SVG 路径另有 `MAX_EDGE` 边长上限。
4. **几何分工**：解码器只输出 RGBA8 + `orientation`；旋转 / 镜像 / 缩放 / 平移全在宿主
   （`core::geometry` 是单一定义点）。
5. **★ 矢量格式的"渲染责任方"分两种**（2026-10-28 收口，宿主侧已落地）：
   - **内置渲染**（`HostBuiltin`）：原生 `svg` / `svgz` → 宿主内置 resvg
     （区域重渲 + 文档缓存，缩放零 IPC）。
   - **解码器自渲染**（`DllSelf`）：其余矢量后缀 → 一枚矢量解码器 DLL，
     **按目标像素尺寸直接光栅化**，**不经中间格式**（不转 SVG）——"无损放大"的技术内容全在这一句。
     宿主只负责说清"要多大"（target = 视口设备像素，或区域 + 密度），DLL 负责按那个尺寸渲染。
   - 判据集中在 `core::formats::vector_render_mode`（**一处**判，别散在各处 `if`）：
     ① 矢量后缀并集 = 内置登记表的 `is_vector` 位 ∪ 解码器自述的 `vector_exts`
     （**宿主不手写第二份清单**）；
     ② 解码器认领的矢量后缀**一律**是 `DllSelf`——**没有第三档**。
   - ★ **宿主侧只认两条路径**：矢量后缀要么走内置 resvg（仅 `svg` / `svgz`），
     要么走解码器自渲染；宿主**不持有矢量文档、不做二次渲染**
     （不探测 `iv_export_svg`，没有导出缓存与导出分支）。
     理由：让解码器交出文档、宿主再渲染 = **同一个格式挂着两条渲染路径**，
     换机器 / 换 DLL 版本 / 换字体栈时两边的像素可能不同——
     "同一文件跨机同结果"这条立宪理由会被自己破掉。
     宪章 §5.2 的口径因此是"矢量格式一律由解码器按目标尺寸自渲染；宿主内置 resvg 只服务 svg/svgz"。
   - ★ **同一格式只能有一条渲染路径**，否则"同一文件跨机同结果"这条立宪理由会被自己破掉。
   - ★ M2 模式下矢量格式**没有"整图档"**：loaded 图 = 当前视口那一档；"1:1 原始尺寸"档
     超出 `MAX_PIXELS` 就置灰并说明。完整契约见 `.plan/m153-矢量格式统一解码器契约.md`。
   - ★ **ABI v6 的区域渲染**（2026-10-28，`iv_render_region` + `IvRegionReq` + `CAP_REGION`）：
     "**能不能按区域重渲**"是与"谁渲染"**相互独立**的一维（`core::formats::is_region_renderable`）：
     ① 宿主渲的（内置 svg/svgz）；② 解码器自渲染**且**实现了 `iv_render_region` 的。
     **不在这一维里的矢量后缀，宿主绝不发区域请求**——没有区域接口的解码器只能把**整篇**
     缩进那一小块，那是**内容错误**不是"糊一点"。
     **v6 是加法式升级**：v5 的每个导出签名与结构体布局逐字节未动，宿主按区间 `5..=6` 收载
     ⇒ v5 老 DLL 不必重编、照常工作。契约与对接见 `.plan/m154-ABIv6-区域渲染契约与对接任务书.md`，
     规范全文真源在解码器仓《解码器开发规范.md》§十六。
   - ★ **能力位是 DLL 级、成员能力不齐时用 `region_exts` 收窄**（m190）：`CAP_REGION` 与
     `iv_render_region` 都是整枚 DLL 的单一事实，而合并档里各成员的能力可能不同——
     `doc` 的 EMF/EMZ 走 `emfsdk`，它只有"整幅画布多大"、**没有视口参数**，真把区域请求发过去
     只能把整篇缩进那一小块（内容错误）。所以解码器在 `iv_metadata` 里追加
     **`region_exts`**（分号分隔小写后缀）如实点名"哪些后缀吃区域请求"；宿主在
     `decoders::registry::declared_cached` 里按它收窄区域集（键缺席 ⇒ 该 DLL 的
     `vector_exts` 全部，空串 ⇒ 一个都不进）。判据只看"这个成员真的按区域密度重光栅化了吗"，
     不看"它是不是矢量"。
   - ★ **4000% 无损的机制**（宿主侧保证）：区域 = 视口在图像坐标里的那一小块（放大时越来越小），
     画布 = 区域 × 密度 ≈ **一屏大小** ⇒ 像素预算恒定、倍率无上限；
     而解码器是按那个密度**重新光栅化**的，不是位图插值放大。
   - ★ **矢量路线的 `natural` = 文档自然尺寸，不是"这一次渲染出来的画布"**（2026-10-28 真机报障修）：
     宿主把 `Decoded::natural` 当**文档自然像素**用——画布几何（`eff_dims` → `dst_rect`）与
     **区域请求的坐标系**（ABI v6 明写：区域的 x/y/w/h 单位 = 文档自然像素）都吃它。
     位图那条路上 `natural` 确实是原图尺寸；矢量那条路上不是——解码器按 `target` 把**文档重画**
     成目标尺寸，回填的 `actual_*` 是"这一次的画布尺寸"。拿视口档的渲染尺寸当文档尺寸 ⇒
     区域请求要的那块与真图那块不是同一块 ⇒ 放大后显示的是文档的**别处**。
     **解法（只在宿主侧，不动解码器）**：矢量路线补一次**零目标查询**（ABI 契约：
     `target_w/target_h = 0` = 要原始尺寸），拿它当 `natural`；只对"解码器自渲染 **且**
     能按可视区域重渲"的后缀补（判据与分流同源），没有区域通道的矢量保持旧口径
     （那里 `natural` 只喂"是否已是整图"的闸，改了会让大文档直接打不开）。
     机器闸见 `decoders::tests::doc_natural_query_only_for_self_rendered_region_vectors`，
     真机复核见 `examples/vector_zoom_probe.rs`。
   - ★ **没有区域通道的矢量：`natural` 冻结在首屏画布，放大时整幅重要一档**（m189）：
     这一档（`core::formats::needs_zoom_rerender`：解码器自渲染 **且** 不能区域重渲，m190 之后
     只剩 `doc` 的 `emf`/`emz`（`emfsdk` 没有视口 API）与 `doc-legacy` 的 `zbr`（预览位图）三个后缀）
     的 `natural` 只是"首次渲染出来的画布"，
     不等于文档页面尺寸（解码器只回 `actual_*`，没有"页面多少点"这条通道；为它补零目标查询
     等于开图就多付一次整解）。所以：① **同图重解沿用首次画布**（`prefetch::install` 只在
     路径相同、两边都不是切片时沿用），几何与倍率锚在它上面不漂；② 缩放自上次解码起**变化**
     且当前位图盖不住需求时，按 `natural × 倍率 × DPI`、总量夹 `MAX_PIXELS`（64 MP）**再要一档
     整幅**交给解码器重画（`viewer/schedule.rs` 的重渲支路 + `vector_target_pixels`）——
     不重要就只能在首屏画布上本地重采样，放大必然成马赛克（PDF 真机报障即此）；
     ③ `vector_zoom_req` 记账（路径 + 上次目标），解码器**不理 target** 时不会每轮重发；
     重置视图与解码失败都清账。单测见 `viewer::tests::target_vector_*`（含"解码器忽略 target
     不反复重发"），判据有红证（关掉支路即红）。
   - ★ **文字必然要渲染**（2026-10-28 用户拍板，写进契约）：解码器找不到原字体时用兜底字体，
     **绝不**丢字/空字/崩，并在 `iv_last_error` 记一句（宿主转达用户）。
     由此产生的**跨机像素差异是已登记且已接受的唯一例外**（`.plan/m153` §7.3 E2）。
6. **分派 = 置信度榜 + 让位链，失败三分类决定去留**：候选按 `sniff_ranked` 给分排序
   （后缀命中 / 魔数嗅探；冠军 100、`core` 兜底 50、平手按 DLL 路径字典序，确定且跨平台
   一致），`try_chain` 按榜逐个试解：`ERR_UNSUPPORTED` / `ERR_UNRECOGNIZED`
   （`Fail::NotClaimed` / `Unsupported`）**让位**换下一家；硬失败（`Fail::Hard`：损坏 /
   过大 / panic）立即中止，不再下探。宿主侧分类见 §3.5，解码器侧契约见 `解码器开发规范.md` §三「让位链」。
   解码器 panic 三振出局进会话黑名单，FFI 调用统一走 `platform::seh::invoke`
   （SEH 访问违规 + panic 双兜底），`--safe-mode` 可一键不加载任何解码器。
7. **`.raw` 双认领按请求类型仲裁**（常规打开 → 相机 RAW；参数窗给了宽高布局 → 只有实现了
   `iv_render_raw` 的解码器入围）：规则与完整表格见
   [`图片格式与后缀名.md`](图片格式与后缀名.md) §2.1、§三。
8. **按扩展名的用户首选覆盖**（设置窗「解码器」页的「首选解码器」卡）：`decoders_preferred` 稀疏表让用户为
   单个后缀点名首选解码器（第三方 DLL 争用同一后缀时的仲裁手段）。命中且仍可用（认领该
   后缀、未停用/拉黑、满足 `require_caps`）即定它；条目失效**静默回退自动**——是用户
   显式维护、跟解码器同生共死的稀疏覆盖，不是全量人工优先级清单（后者被
   `select_candidate` 的注释明确反对）。软失败后的嗅探让位链不受它影响，仍作默认托底。
9. ★ **宿主 ⇄ 解码器的接口边界是冻结的**（2026-10-28 用户口径「解码器不再改动」）：
   宿主对 ABI 的依赖面 = **9 个导出符号**（必备 5 + 可选 4，见 `core::abi` 的
   `ABI_REQUIRED_SYMBOLS` / `ABI_OPTIONAL_SYMBOLS`）。机器闸
   `host_abi_dependency_surface_is_frozen` 逐文件扫宿主源码：出现集合外的 `iv_*` 符号
   ⇒ 红灯 ⇒ 必须走「用户拍板 → 解码器仓改契约 → 加法式 bump ABI → 整份复制快照到
   `vendor/rupix-abi/`」；退役的矢量导出符号只许出现在测试代码里。
   ⇒ **宿主的新功能在宿主内部做，不靠"让解码器多一个导出"**——这条让两仓不再互相触发改动。
   ★ **兼容性立约（永久，2026-10-28 用户拍板）**：ABI 永远兼容旧版本 DLL，新 ABI 不影响
   旧 DLL 的运行 ⇒ 宿主升级后旧 DLL **不必重编、不必重传**；"改既有条目再 bump"已禁止。
   契约仓侧的机器守约 = `tools/check_abi_freeze.py` 比对冻结指纹 `tools/abi_freeze.txt`
   （导出签名 / 结构体字段 / 布局字节数 / 常量值 / ABI 版本单调，改既有条目即红灯）。

## 七、性能要点与改动红线

- **帧路径零新增分配与虚调用**：`ImageCache` 只在 `gen` 变化时转换；每帧仍是 `Rc` 克隆 +
  `draw_image`。SVG 注入是 fn 指针单态化，不是虚表。
- **热循环 crate 必须 `opt-level = 3`**（workspace 默认 `z`）：解码库与 resvg 相关 crate 在
  `Cargo.toml` 的 `[profile.release.package.*]` 单独提级。
- **任何性能改动前后必须跑同一基准并记录**（用户红线）。基线数字与复测判据见
  [`../HISTORY.md`](../HISTORY.md) 与本文 §七（判据：位图族 avg 不慢于基线 +5%；
  SVG 注入路径持平或更快）。基准工具：`cargo run --release --example bench_decode`。
- **五条改动红线**（功能不减 / 速度不降 / 每步可编译 / 快照先行 / 门禁先红后绿）与六步流程
  的正本在 [`../开发指南.md`](../开发指南.md) §一，改代码前照它走。

## 九、明确不做

- **PDF / 视频 / 音频**：另一套文档模型与播放管线，塞进看图器会让体积与复杂度失控。
- **系统级解码器兜底**：解码能力只来自内置登记表（今天只有 `resvg`，且只认领矢量）与解码器 DLL
  两类来源。**位图一条都不内置**。
  ★ 2026-10-20 曾拍板让 WIC 以"可被点名的内置库"回归（仍不做兜底），2026-10-25 用户裁决
  **整层删除** `platform::wic`：便携看图器不该调用系统解码器，同一张图在两台机器上必须解出
  同一个结果。这段历史的落点在宪章 §5.1，代码侧已无任何内置位图解码路。
- **独立 JSON 解码器清单文件**：解码器的 id、显示名、作用说明、认领扩展名全部内置在 DLL 里
  （`iv_decoder_info()`），传播时只拷一个 DLL。
- **大而全的错误框架 / 事件总线 / 空层**：手写最小错误体系（`core::error`），
  不引 `thiserror` / `anyhow`；跨线程流只有一条时不开独立事件模块；不设 app / scripting 层。
