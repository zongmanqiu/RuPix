> P0.1b 底座已落地——命名管道帧、共享内存 RGBA、进程启动/等待/终止、请求/响应 JSON；
> 设置页「插件」可列出已发现插件并启停（`extensions_disabled` 落 ini）；
> 右键「插件」子菜单已接命令型插件的后台调用与结果窗；图片体检插件 `checkup` 与条码识别
> 插件 `scan`、色阶分析插件 `levels` 均已跑通全链路——这三枚都是**真的吃下宿主下发的整图像素**的命令型插件，
> 所以 `image.read` 这个能力位对两种类别都名副其实了。
> 命令型调用可取消（运行中条目在菜单里就地变「取消」）；超时/取消都会终止进程并
> 打断阻塞中的 accept，不悬挂线程；`min_host` 不满足的插件入口整体关闭（菜单置灰标原因）。
> 编辑型（`kind=editor`）已落地：共享内存回写 + 宿主编辑态 +「另存为 PNG」/还原。
> **能力通道已对齐**（2026-10-28；2026-10-31 加 `open.url` / `open.file`）：宿主真正提供通道的能力共七项——`image.read`、
> `image.write`、`clipboard.write`、`settings.read`、`settings.write`、`open.url`、`open.file`；其余能力只是
> **告知**用户（见 §四），声明了不会有宿主通道。
> 插件的 stdout/stderr 抽进宿主日志；响应超时由 manifest 声明（`timeout_ms`，上限 30 分钟）。
> **动态热键已落地**（2026-10-28）：插件在 manifest 里报 `hotkey`，宿主运行时收集，按下就跑
> 这个插件（内置快捷键优先；见 §3.2）。
> **尚未落地**：`kind=panel`（宿主托管面板）、画布选区（`selection.read` 无宿主来源）。
> 插件源码在**独立仓库**（本仓之外，宿主文档不复制它的目录名与内部路径）；宿主只消费发布产物，不 import 插件源码。

## 一、边界：扩展不是解码器

| | 解码器（decoder） | 扩展（extension） |
|---|---|---|
| 形态 | 进程内 DLL，C-ABI | **独立进程**，命名管道 + 共享内存 |
| 职责 | 把文件字节解成 RGBA8 | 消费已上屏的图片 / 路径 / 选区，做识别、分析、编辑这类活儿 |
| 认领格式 | 是（`iv_decoder_info().extensions` / 魔数） | **否**，不参与解码路由，不声明图片后缀 |
| 契约 | `vendor/rupix-abi`（v5 起签名冻结，现行 v6 加法式） | `manifest.json` + 扩展协议 v1 |
| 失败影响 | 解码失败 / 崩溃由宿主隔离栈兜底 | 独立进程，崩了不拖宿主；宿主只收错误码 |

**扩展不共用解码器 ABI，也不允许在宿主进程内加载第三方 DLL。** 宿主只负责发现、启动、
传参、收结果；扩展自己管自己的依赖与界面。

## 二、目录约定

```text
<exe 目录>/
├─ rupix.exe
├─ plugins/                 # 已安装：右键「插件」菜单从这里取
│  └─ scan/
│     ├─ manifest.json
│     ├─ scan.exe
│     ├─ README.md / LICENSE      # 随包给人看，宿主不解析
│     └─ settings.json            # 宿主写的插件私有设置区
├─ docs/
│  ├─ decoders.json            # 解码器清单（已有）
│  ├─ plugins.json          # 插件可下载清单
│  └─ scan_0.1.0.zip
└─ rupix.ini
```

- 已安装根目录固定为 **exe 同级 `plugins/`**（`core::paths::plugin_dir()`），与 `decoders/` 一样用复数。
- 「可下载」不再是一个插件目录：清单是 **`docs/plugins.json`**，ZIP 包与它同目录——
  与解码器 `docs/decoders.json` + release ZIP 同一模型。**只有一个插件运行时目录。**
- 安装 = 远程 release ZIP 或本地 `docs/<file>.zip` 解压到 `plugins/<id>/`；进页只读本地，点「刷新」才联网。
- 每个插件一个子目录；**只有 DLL / 清单文件不算插件，必须有 `manifest.json`**。
- 入口必须是插件目录内的相对路径，禁止 `..`、根路径、盘符。

## 三、`manifest.json`

```json
{
  "schema": 1,
  "id": "example-ocr",
  "name": "文字识别（示例）",
  "version": "1.0.0",
  "protocol": 1,
  "min_host": "0.1.0",
  "kind": "command",
  "entry": "example-ocr.exe",
  "args": ["--pipe"],
  "capabilities": ["image.read", "clipboard.write"],
  "platforms": ["windows-x64"],
  "description": "离线文字识别",
  "author": "example",
  "hotkey": "Ctrl+Shift+O"
}
```

| 字段 | 必填 | 规则（当前实现） |
|---|---|---|
| `schema` | 是 | 只接受 `1`；结构变更时升版 |
| `id` | 是 | 3–64 字符，ASCII 字母/数字开头，只允许字母/数字/`.`/`_`/`-`；全局唯一 |
| `name` | 是 | 非空，显示用 |
| `version` | 是 | 数字点分（如 `1.0.0`） |
| `protocol` | 是 | 宿主支持**区间** `MIN..=MAX`（当前 `1..=1`，只增不改、下界永不抬）；超区间拒载 |
| `min_host` | 是 | 数字点分；宿主版本低于它时入口整体关闭（菜单置灰标原因，启动拒绝）。**进 `plugins.json`**，未安装时也看得见 |
| `kind` | 是 | `command` / `editor` / `panel` |
| `entry` | 是 | 扩展目录内相对路径；`command` / `editor` 必须 `.exe` |
| `args` | 否 | 字符串数组；宿主原样附加到命令行 |
| `capabilities` | 否 | 能力名数组；未知能力在解析期拒绝 |
| `platforms` | 是 | 必须包含 `windows-x64` |
| `timeout_ms` | 否 | 响应超时（毫秒）。缺省 30000；上限 1800000（30 分钟），超过即坏清单 |
| `hotkey` | 否 | 动态热键（键串），见 §3.2；写不成宿主认得的键串 = 坏清单 |
| `settings_ui` | 否 | 布尔，缺省 false；`true` = 插件自带设置窗口（卡片上的齿轮，见 §5.6）。**必须同时声明 `settings.write`**，否则改完存不下来 = 坏清单 |
| `description` / `author` | 否 | 字符串，展示用 |
| `license` / `released` | 否 | 字符串，进插件信息窗的两行「许可证」/「发行时间」（`or_unknown` 兜底，缺席显示「未知」而不是空白格） |
| `settings` | 否 | **声明式设置数组**（`bool` / `choice` / `int` / `text` / `hotkey`），由宿主按 schema 画窗口 ⇒ 见 §5.5。解析期三条互斥：必须同时有读写能力、与 `settings_ui` **二选一**、数组里的 `hotkey` 项与顶层 `hotkey` **二选一** |

**校验失败 = 跳过该扩展并记 `warn`**，不影响同目录其他扩展；`manifest.json` 缺失或 JSON
坏掉同样跳过。

### 3.1 `timeout_ms`：长任务插件自己声明要跑多久

OCR / 批处理这类插件天生比 30 秒慢。宿主不替插件猜——猜短了腰斩，猜长了用户干等——
所以**插件自己声明，宿主只负责封顶**：

- 缺省 30 s（`core::ext::DEFAULT_TIMEOUT_MS`）；
- manifest 里写 `timeout_ms` 放宽到它真正需要的时长；
- 超过 30 分钟（`MAX_TIMEOUT_MS`）= 坏清单，直接拒（桌面软件没有"等半小时"这种设计，
  插件也不能替宿主决定它等多久）；
- **编辑型不适用**：编辑是交互任务，用户画多久都行，由「取消」兜底，没有响应超时。

超时的提示语带秒数（"插件响应超时（120 秒）"），用户能一眼看出是自己声明的时长。

### 3.2 `hotkey`：插件自己声明的动态热键

内置快捷键（翻页、缩放、全屏……）是宿主写死的一套枚举，用户可在设置页改。**动态热键**
是另一回事：插件在 manifest 里报一把键，按下就跑这个插件。宿主运行时收集，不写死在代码里。

键串用**宿主那套规范写法**（与内置快捷键同一个解析器）：`Ctrl+Shift+O`、`F8`、`NumAdd`、
`Left`…（修饰键 `Ctrl` / `Alt` / `Shift` / `Win`，主键大小写不敏感）。写不成宿主认得的键串
= **坏清单**（不是"照办"）：一条永远按不出来的热键等于没写，还会让用户以为插件坏了。

**裁决口径（宿主定，插件无权）**：

| 情形 | 结果 |
|---|---|
| 与内置快捷键撞键 | **内置优先**，插件这条热键不生效（记一条 warn） |
| 两个插件抢同一把键 | 按插件 id 排序先来先得，后来者不生效（记 warn） |
| 插件被停用 / 三振隔离 / `min_host` 不满足 | 热键不生效 |
| `kind` 不是 `command`（编辑型 / 面板型） | 热键不生效（编辑要整图像素，面板没有入口） |

其它口径：

- 热键**不进 `rupix.ini`**——它由 manifest 决定，改热键 = 改 manifest；
- 插件菜单里那条目会把热键显示在尾随列，用户看得见自己按的是哪把键；
- 内置快捷键的键位改了，冲突裁决**立刻**跟着变（用户把 `Ctrl+Shift+O` 抢回来，插件那条就失效）；
- 宿主只在**命令型**插件上支持；一次按键只触发一次插件调用（不重复触发）。

## 四、能力声明

扩展在 manifest 里**声明**需要什么。声明分两类，**对用户的意义完全不同**：
一类是宿主真的会开通道，另一类是插件自己去做、宿主既不提供通道也不背书。
★ 2026-10-29 用户口径：**安装即视为同意**，不再弹首用同意页；
能力声明仍是给用户的知情权（写在 manifest 与插件文档里），宿主只按声明开通道。

### 4.1 宿主提供通道（声明 = 真的有）

| 能力 | 宿主给的东西 | 落地 |
|---|---|---|
| `image.read` | 当前图片的**路径** + **共享内存 RGBA**（编辑型与命令型同一份，m166 第一格起） | 未声明 → 菜单不发路径、编排层 `pixels_to_send` 再拦一道（也不为它建映射） |
| `image.write` | 回写编辑结果 → 宿主编辑态（另存 / 还原） | 未声明 → 宿主拒收回写 |
| `clipboard.write` | 命令型结果**自动写入系统剪贴板** | 开结果窗时 toast「已复制到剪贴板」（无痕副作用必须留提示） |
| `settings.read` | 插件**自己的**设置区（见 §5.4 存储 / §5.5 声明式 schema） | 未声明 → 宿主不发 settings |
| `settings.write` | 插件回传设置 → 宿主落盘（合并写） | 未声明 → 宿主不落盘 |
| `open.url` | 响应里的 `open_url` → 宿主验 **http/https** 后交系统默认浏览器（`platform::shell::open_target`） | 未声明 → **根本不读这个字段**；打开失败只 toast，不撤结果 |
| `open.file` | 响应里的 `open_image{ext,base64}` → 宿主按**文件头**复核（插件自报的后缀不作数）→ 落 `<exe>/temp/` → **开一扇新看图窗**（m219：不交系统关联，否则会把用户正看的那张顶掉） | 未声明 → 不看；解不出 base64 只记 warn |

### 4.2 仅告知（声明 ≠ 有通道）

| 能力 | 含义 | 宿主的态度 |
|---|---|---|
| `network` | 插件自己联网 | 宿主**不提供**通道；安装即视为同意，联网是插件自己的行为 |
| `process.spawn` | 插件自己起子进程 | 同上 |
| `ui.window` | 插件自建窗口（在图上画、裁剪这类） | 同上（进程外，本来就在插件自己的窗口里） |
| `file.read` / `file.write` | 插件自己读写文件 | 同上；宿主**没有**这条通道 |
| `selection.read` | 读取画布选区 | 宿主暂无选区概念 → **给了也没有** |
| `ui.panel` | 宿主托管面板 | 尚未支持（见 §十） |

未声明的能力，宿主不提供对应入口；扩展自行绕过（例如直接读任意文件）属于扩展自身行为，
宿主不为其背书。**"声明"是给用户的知情权，"宿主开通道"才是承诺**——判据在
`core::ext::Capability::host_provides()`。

## 五、传输层（已具备底座）

### 5.1 命名管道

- 名字前缀 `\\.\pipe\rupix-ext-`；宿主创建、扩展连接。
- 帧格式：`u32 LE 长度 + body`；单帧上限 16 MiB。
- 管道只传 JSON/文本；像素走共享内存。
- 当前实现是同步阻塞读写；命令型插件由 `extensions::run` 在后台线程加 10s 连接 / 30s 响应超时。
- 阻塞的 `ConnectNamedPipe` 没有超时参数：超时/取消用 `CancelSynchronousIo` 打断
  accept worker（`platform::pipe::cancel_synchronous_io`），句柄由其 `Drop` 关闭——
  每次失败不悬挂线程、不漏句柄。

### 5.2 共享内存

- 名字前缀 `Local\rupix-ext-`；宿主创建可读写映射，扩展只读打开。
- 布局：32 字节头（magic `RPXIMG01`、width、height、stride、len、保留 8 字节）+ RGBA8 像素。
- 扩展只能拿到请求里给的名字；名字必须带前缀，防止枚举/误开其他映射。
- **编辑型与命令型都能收到像素**（m166 第一格）。以前命令型只拿到路径，于是"任何解得开的图
  都能体检 / 都能扫码"根本不成立——插件自己解不了 HEIF / RAW / PSD，而"把解码结果写成临时
  文件再喂外部工具"被便携铁律禁掉（解码结果只在内存）。现在两型走**同一个 `publish_image`、
  同一根闸 `pixels_within_limit`、同一份屏上朝向像素**。
  拿不到整图（切片态 / 超上限）时**照旧只发路径**：老插件的行为是子集，不会突然变坏。
  这条口径的正本在插件侧的《插件开发规范》§6.2（那份文档不在本仓），本处只记宿主侧的实现落点，避免两处各写一份。
- ★ **交出去的像素是"屏上朝向"**（所见即所得，宽高可能随旋转与原图对调），回包同尺寸同朝向；
  宿主在落地前把它转回源朝向。实现三处：
  [`Viewer::whole_image_for_plugin`](../src/core/viewer/edited.rs) 转正**并冻结这一次朝向**、
  [`JobOutput::Edited`](../src/extensions/run.rs) 把冻结值一路带回、
  [`Viewer::install_edited_displayed`](../src/core/viewer/edited.rs) 用它的逆变换还原
  （逆元表与 `transformed` 同文件、互逆性由用例拿生产内核逐种验）。
  **为什么必须用冻结值而不是此刻朝向**：用户在插件窗口里待着的时候，主窗口可能被再转一次——
  那时读 `self.rot` 会带上一轮多余旋转，而像素数量对得上，任何尺寸校验都挡不住。
  这条判据钉在用例 `edited_return_is_restored_with_the_frozen_orientation`。

### 5.3 请求 / 响应

请求（宿主 → 扩展）：

```json
{
  "protocol": 1,
  "id": "example-ocr",
  "action": "run",
  "image_path": "C:\\a.png",
  "selection": {"x": 0, "y": 0, "w": 100, "h": 50},
  "args": ["--lang=chi_sim"],
  "settings": {"lang": "chi_sim"}
}
```

- `image_path` 与 `image` 至少给一个；`image` 是共享内存描述（`name/width/height/stride`）。
- `selection` 可选；`args` 是 manifest 的 `args` 原样附加。
- `settings` 可选：**只在插件声明 `settings.read` 时出现**，内容是它自己的设置区
  （见 §五.4）。老插件不认识这个字段——不认识就不理，协议向后兼容。

响应（扩展 → 宿主）：

```json
{"protocol": 1, "ok": true, "text": "识别结果"}
```

或编辑结果：

```json
{"protocol": 1, "ok": true, "image": {"name": "Local\\rupix-ext-...", "width": 800, "height": 600, "stride": 3200}}
```

或带回设置：

```json
{"protocol": 1, "ok": true, "text": "好了", "settings": {"lang": "en-US"}}
```

`ok=false` 必须带 `error`。协议版本不在宿主支持区间、缺字段、超限帧一律拒绝。
`--rupix-protocol` 回**插件声明的版本**（不硬塞宿主最新版），旧插件继续按自己的版本说话。

### 5.4 插件私有设置区

插件要记事（上次用的语言、选好的模型、要不要自动复制），宿主替它存一小块：

- **位置**：`<exe>/plugins/<id>/settings.json`（便携铁律：只在 exe 同级，不碰 `%APPDATA%`）。
- **形状**：扁平的字符串键值对。宿主是 **dumb store**——只存只取，不解释结构；
  插件要复杂结构，自己编码成一个 JSON 字符串塞进来。值只接受标量
  （字符串/数字/布尔，数字与布尔按字面量转成字符串），嵌套对象一律拒绝。
- **门禁**：只有声明 `settings.read` 的插件才会在请求里收到设置；只有声明
  `settings.write` 的插件回传 settings 才会被落盘。**没声明 = 没有通道。**
- **合并写**：插件回传的是"它改的那几个键"，宿主**合并**进现有设置（同名覆盖、新键追加），
  不会把插件没提到的键清掉。
- **原子写**：先写 `settings.json.tmp` 再改名覆盖——断电时留下的要么是旧文件、
  要么是新文件，不会是半截 JSON（半截 JSON = 插件下次读到就当设置没了）。
- **读不到 = 空设置**（首次运行/文件坏了都一样）：设置区是锦上添花，
  不该让插件跑不起来。写失败只降级为 warn。
- **升级保留**：插件升级是"整目录换掉"（旧目录挪走 → 新目录换入 → 旧的删掉），
  所以升级时宿主会把旧版的 `settings.json` **搬进新版目录**（新包自带设置则不动）。
  不搬的话，用户升一次插件偏好就全丢——升级是常规操作，不是事故。

### 5.5 声明式设置（`settings` schema，2026-10-31）

manifest 可选 `settings` 数组，每格一项：`key` / `label` / `type`（`bool` / `choice` / `int` /
`text` / `hotkey`）/ `default` / `choices` + `labels`（仅 choice）。

- **宿主渲染**：声明了它，齿轮打开的是**宿主的**设置窗（`ui/plugin_settings.rs`），不再是
  `action=settings` 拉起插件；与 `settings_ui` 二选一（解析期互斥）。
- **版式**：行版式直接复用设置页那份两列（`ui/settings/rows.rs::option_row`——标签列
  `COL1_W`、控件列 `CONTROL_GROUP_W`，下拉 / 输入框 / 快捷键框同宽），窗宽按这两列算。
  2026-11-01 用户口径：插件设置也跟随宿主的列宽，全部 UI 统一。
- **落盘**：值写进 `plugins/<id>/settings.json`（与老路同一个文件、同一套原子写），
  每次 `run` 随请求的 `settings` 字段下发。
- **热键**：`type=hotkey` 的那一项就是该插件的动态热键，值存在设置区（不是清单——
  清单是发布物，用户改不了）。`extensions::effective_hotkey` 优先读它，没有 schema 的
  老插件退回 `manifest.hotkey`；热键表在设置保存后重算（`invalidate_installed_cache`）。
- **为什么由宿主画**：命令型插件没有窗口，让每枚插件各画一遍对话框等于把校验 / 落盘 /
  快捷键捕获各写五遍。插件只声明 schema 与读值。

### 5.6 插件设置窗口（`settings_ui`）

设置区（§5.4）解决"存在哪"，这一节解决"**用户从哪改**"。

- **manifest**：可选 `settings_ui: true`（缺省 false）。**必须同时声明 `settings.write`**——
  只有读权限的插件给了齿轮，用户改完落不了盘，那比没有入口更糟，所以 `core::ext::Manifest::parse`
  与插件侧的 manifest 校验工具（不在本仓）都在解析期拒。
- **入口**：「已安装」卡该行「!」**左侧**一颗齿轮（`\u{E713}`，Segoe MDL2 Assets），**只有声明者才显示**；
  ★ 2026-10-29 用户口径：齿轮放「!」左侧，两卡的「!」才能落在同一条竖线上；
  停用 / 已隔离 / `min_host` 不满足时置灰。2026-10-29 起没有首用授权门禁，
  装上就能直接开。
- **协议**：新增 `action="settings"`，**只发给 `settings_ui` 的插件** ⇒ 旧插件永远收不到
  未知 action，`protocol` 不必 bump（与 ABI 的加法规则同构）。插件不认识某个 action
  必须回 `ok=false`。
- **形态**：交互任务——**不设响应超时**（和编辑型一样由「取消」兜底），10 s 连接超时、
  Job Object 隔离、管道 DACL、PID 校验、三振全复用 `extensions::run` 同一条路径。
- **落盘**：响应的 `settings` 照旧走 §5.4 的合并写；插件关窗即结束，回传了什么就存什么。
- **结果**：`JobOutput::Settings` —— 不进结果窗、不弹提示（窗口开与关用户自己看得见）。
- **第一方用户**：**现在没有**——官方三枚都走 §5.5 的声明式设置（宿主画窗口），比让每枚插件
  各画一遍对话框省事。这一条通道为**第三方**保留（协议已发布、下界永不抬，撤它就是毁约），
  宿主侧的 `action=settings` 分支与齿轮都照旧接通，只是没有第一方样本可点。

### 5.7 插件的输出与诊断

插件是**别人的进程**：它崩了、它卡了、它打了诊断信息，宿主这头不能装没看见。

- 插件的 **stdout / stderr 逐行抽进宿主日志**（stdout → info，stderr → warn，
  行首带 `[插件 <id>]` 前缀）；抽取线程随子进程退出自行结束，不留悬挂线程。
  （此前这两路输出直接接 `Stdio::null()` 丢弃，插件现场只剩"没回应"四个字。）
- 插件的 stdout/stderr **不进结果窗**：那是给用户看结果的地方，不是日志。
- **结果窗是纯文本窗**（2026-10-29，参考 CurSeen 的信息档）：系统标题栏 + 无框线、白底的
  多行文本区，**没有按钮**；高度按内容行数自适应（160–520 px），长文本在窗内滚动；
  可以直接点进去改（改动只留在窗内的本地草稿），选中后 Ctrl+C / Ctrl+A 复制。
  插件自动复制（`clipboard.write`）只用开窗时的一条 toast 报"已复制到剪贴板"。
- 诊断信息（宿主自己的崩溃报告、运行日志）见本仓 `docs/踩坑记录.md` 与
  `temp\rupix-<日期>.log`。

## 六、发现与启停

- `extensions::discover(disabled, isolated)` 扫描 `<exe>/plugins/*/manifest.json`（已安装）；
  两个集合都是**闸**：`extensions_disabled`（用户停用）与 `extensions_isolated`（三振出局后被
  隔离的插件，`runtime` 在计数到位时写入并落 ini —— 与解码器那侧"熔断只本会话、不落盘"
  **刻意不同**：插件反复崩是它自己的包坏了，重启继续踩更糟）。命中任一就不进候选。
- `extensions::remote::load_local(installed)` 读 `<exe>/docs/plugins.json`（进页零网络）；点「刷新」走后台 `remote::start_refresh_for(&config)`，按 `download_source`（选项页「下载源」）选 ini 里 `plugin_index_gitee` / `plugin_index_github` 那一条去拉，并原子覆盖本地清单。
  ★ **地址在配置里、用户可改**（2026-10-28）：`SourceId::plugin_index_url` 只是内置默认值。
  ★ 2026-10-29 用户口径：这两条键**不进界面**，只给高级用户手改 ini；插件页原先那张「更新地址」卡已撤。
- 清单里的 `gitee` / `github` 是两列 release ZIP 地址，切来源只换列、不重新下载清单；下载走 `extensions::install::start`（后台线程 + 250 ms 进度轮询）。
- 本地 `docs/<file>.zip` 仍保留为离线回退：远程取不到时用同版本 ZIP 安装；`install_local(entry)` 可直接从本地包装。
- 解压到 `plugins/<id>/` 的隐藏 staging，校验 manifest / 入口后整目录 rename；更新时旧目录先挪 `.old`，失败原样放回。

- 坏包只 `log::warn!("跳过扩展 …")`，不 panic、不阻塞其他扩展。
- `min_host` 门禁：宿主版本低于 `manifest.min_host` 的插件照常列出，但入口整体关闭——
  右键菜单置灰并标注「需宿主 x.y.z+」，编排层启动时再拦一道（比较用
  `extensions::remote::version_cmp`，宿主版本常量 `core::ext::HOST_VERSION`）。
- 结果按 `id` 排序，保证设置页稳定。
- `disabled` 来自 `Config.extensions_disabled`（`discover_configured`）；设置页勾选框写这个键，勾掉 = 写 id，勾上 = 移除。
- 设置页「插件」页分「已安装 / 可下载」两卡，带搜索/计数/刷新（**来源不在这张卡上**：
  2026-10-30 起统一到「选项」页的「下载源」，两张卡共用一份配置）；已安装可启停，行内「!」打开详情并可卸载（移回收站），声明了 `settings_ui` 的插件在「!」左侧多一颗齿轮（§5.5）；可下载带「下载 / 升级」按钮，下载中按钮显示百分比。
- 安装前**不校验清单指纹**（2026-11-02 用户口径：官方产物只认名称与版本号，`size` / `sha256`
  两栏连同宿主校验一起删了）。包身份由 ZIP 结构兜住：必须有 `manifest.json`，读出来核 `id`，
  目录名与 `id` 对不上整包拒绝。安装/更新成功后自动从停用表移除并刷新列表。
- 右键「插件」子菜单只取**已安装且启用**的插件；命令型条目点击后后台启动，结果由 16ms 轮询取回，文本进结果窗。
- 清单缺失 / 已安装目录不存在 = 零插件，不报错。

## 七、分层与依赖

```text
core(0) → platform(1) → { decoders(2), extensions(2) } → ui(3) → runtime(4)
```

- `extensions` 与 `decoders` **平级但双向禁互引**：解码器不认扩展，扩展不调解码器。
- `core::ext` 只放 manifest / 能力 / 类型，不碰文件系统、Win32、UI；单测无头跑。
- `extensions` 层禁引 `windui` / `windows`（Win32 一律经 `platform`）。
- 机器判定在 `build/layering_scan.py` 的 `LAYER_ORDER` / `BARRED` / `FORBIDDEN_PEERS`。

## 八、安全底线

1. **默认不自动运行**：发现扩展只代表“目录里有它”，启动必须由用户动作触发（菜单 / 设置页）。
2. **进程外**：第三方扩展不进宿主地址空间；宿主不 `LoadLibrary` 扩展 DLL。
3. **路径围栏**：`entry` 只能是扩展目录内相对路径；宿主解析后必须仍落在该目录内。
4. **能力最小化**：manifest 未声明 `network` / `file.write` / `process.spawn` 时，宿主不提供对应通道。
5. **退出可控**：扩展进程由宿主启动的，宿主关闭时先请求退出，超时再终止；不得把 UI 线程卡在等待上。

## 九、冒烟

插件源码在独立仓库（本仓之外）。★ 宿主只关心两件与它有关的事实：**清单地址按 `main` 分支写**
（`core::config::plugin_index_url` 的默认值；插件仓的默认分支是 `main`，与解码器仓的 `master` 不同，
而 Gitee raw 只服务默认分支——写错分支就是 404），以及**发布产物落在 `<exe>/docs/` 与 `<exe>/plugins/`**：
构建产出 `.build/docs/<id>_<ver>.zip` + `.build/docs/plugins.json`，设置页点「下载」后解压到
`.build/plugins/<id>/`。release tag = `<id>_<version>`，ZIP 作为该 release 的附件上传。
ZIP 里除 `manifest.json` + 入口外，还带上插件的 `README.md` / `LICENSE`（存在才带）——**供人阅读，宿主不解析不渲染**。
三枚官方插件都要**真实像素**，所以冒烟要带一张图，并让解码器目录可寻址——探针的第二腿
会用宿主自己的解码栈真解那张图，再经共享内存送进插件：

```powershell
cd main
set RUPIX_DECODERS_DIR=<工作区>\.build\decoders
cargo run --release --example plugin_smoke -- ..\.temp\plugin-dist\checkup <一张真实图片>
cargo run --release --example plugin_smoke -- ..\.temp\plugin-dist\scan <一张带码的图片>
```

预期先输出 `started: 图片体检` / `started: 条码识别`，随后是插件返回的整份报告（打到 stdout）。
宿主 UI 中命令型插件的结果会打开一个可滚动、可复制的「结果」窗，不再塞进短 toast。

## 十、未接入（后续批次）

- **面板型**：`kind=panel` 的宿主托管面板——需要第一个真实面板插件才有接口可验，
  契约（枚举/详情/门禁）已备。
- **画布选区**：`selection.read` 暂无宿主来源（看图窗口目前没有框选），所以这项能力
  只能是"告知类"；要做就得先给宿主加选区（那是看图器功能，不是插件体系的事）。
- **动态扩展热键**：已落地（见 §3.2）——插件在 manifest 里报 `hotkey`，宿主运行时收集，按下就跑；内置快捷键优先。仍缺：用户可自定义插件热键（改热键 = 改 manifest）与面板型/编辑型的热键。
- **崩溃重启策略**：三振隔离已落地，自动重启不做（崩溃插件重跑大概率再崩，交给用户）。
- **签名 / 发布者信任**：两样都没有——2026-11-02 起清单连哈希也不记了（`size`/`sha256` 校验删除），
  安装即视为同意（2026-10-29 撤掉首用同意窗）。**别把"能读清单里的 id"当成任何形式的认证**：
  插件体系的信任模型是"A 级本地内容"（见 §1），不是签名。
- **管道 DACL**：已落地——命名管道现在用受保护 DACL（只放当前用户 + SYSTEM），造不出来时退回默认 DACL
  并只记 warn（见 `platform::pipe_dacl`）。
- 契约源码在插件侧仓库（本仓之外）；改动协议时两边文档必须同轮更新。
