## 0. 一句话定位

**RuPix 是一个轻量看图器。** 宿主 exe 只做"看图"这件事——窗口、交互、几何变换、解码调度、缓存、路由；**所有位图解码 100% 外置为可替换的解码器 DLL**。

唯一例外：SVG / SVGZ 走宿主内置的 resvg（矢量需按视口 1:1 重渲，位图解码器语义表达不了）。

## 1. 核心原则（题眼，一切规则的源头）

> **宿主框架是唯一需要长期优化的资产；解码器是可随时替换的商品，无论它用什么语言写、多快，都只是一个满足 ABI 契约的 DLL。**

这一条由三条落地推论支撑：

1. **解码器 = 商品**：JPEG 今天用 `zune-jpeg` 编的 DLL，明天 `libjpeg-turbo` DLL 更好就换上——框架只认 `vendor/rupix-abi` 那个 C-ABI 契约，不在乎 DLL 里面是 Rust 还是 C。换解码库不动框架一行代码。
2. **新格式 = 丢一个 DLL**：解码器自己在 `iv_decoder_info()` 里声明支持的扩展名与版本，框架按路由接上，**框架代码零改动**。
3. **团队精力全投框架**：框架才是竞争壁垒，解码器是别人（或未来）随时能换的零件。框架该优化的清单见 §3。

**对历史纠结的终局**：
- "Rust 是不是选错了" → 不再是问题。框架语言无关（经稳定 C-ABI），宿主用 Rust 写、舒服又安全；解码器是任何语言的 DLL。"纯 Rust 解码最优"不是目标（§6 定义边界）。
- "WIC 快为什么不接" → **2026-10-20 用户拍板：接，作为内置解码库，但只走「首选解码库」点名这一条路**（实测侧：WIC 解 JPEG/GIF/PNG 并不慢，见 `HISTORY.md`）。旧文"WIC 是 Windows 独占的隐藏解码器，违背自包含 / 跨机行为一致"这句**没有被推翻**——被推翻的是"因此不接"，接法因此被限制成：不进默认路由、不做兜底、不认领 WIC 扩展格式。若哪天要做默认快路径，那是一次新的修宪，得再拍板。★ 2026-10-25 用户裁决已整层删除，现行条文见 §5.1——本条仅留史。
- "几百种格式怎么办" → 热门格式用各自 best-of-breed DLL 精控，长尾交给一个元解码器 DLL（FreeImage 类）兜底；框架只管"路由 + 加载"。

## 2. 宿主的职责边界（只做这些）

宿主（main crate）负责"看图"所需的一切**框架能力**，做到下表程度即止。任何具体格式的解码算法都**不在宿主内**。

| 宿主负责 | 做到什么程度 | 判据 / 落点 |
|---|---|---|
| 窗口与无边框交互 | 模仿菠萝看图范式：无边框深色窗、画布铺满、悬浮控件、边缘缩放、置顶/锁住/透明度 | `ui/` + `platform/` |
| 几何变换 | 旋转 / 镜像 / 缩放 / 平移，是宿主的**单一定义点**（`core::geometry`），解码器只输出 RGBA8 + orientation | `core::geometry` |
| 解码调度 | 后台线程解码、16ms 轮询收结果、过期结果丢弃（`seq` 令牌）、相邻图预取、首屏可降档 | `core::decode` + `runtime` |
| 格式 → 解码器路由 | 两条路由：svg/svgz → 内置 resvg；其余 → `DecodeBackend`（解码器宿主）。无第三条兜底。扩展名不可信时按魔数嗅探选 DLL | `core::decode` + `core::formats` |
| 解码器生命周期 | DLL 发现 / 加载 / 版本区间判定（`MIN_ABI ≤ 解码器 ≤ IV_ABI`）/ 同 id 去重 / 失败静默降级 / 三振出局黑名单 | `decoders/`（`Host`） |
| ABI 契约 | `vendor/rupix-abi` 是宿主侧 C-ABI 快照；自 v5 起签名冻结，现行 v6（加法式升级，下界锁 5）；改契约必须新增可选导出 / 新结构体并兼容旧解码器（否则静默降级） | `vendor/rupix-abi` |
| 缓存 | **只在内存**：邻图预读（视口档，份数闸 + 256 MiB 字节闸）+ 缩略图条 + 换档本地派生。磁盘解码缓存 2026-10-19 撤除（未压缩整图一张 140–160 MB，写盘 +214 ms 落在用户等待里；参照各家落盘的都只是压缩受限档），老 ini 键 `cache_age`/`cache_limit` 按未知键静默忽略 | `core::viewer` + `core::thumbs` |
| 首屏降档 | 换图首解点 `REQ_ALLOW_SCALED`（还要候选声明 `CAP_SCALED` 才真降），先出一框"够用的首屏"；`Decoded::natural` 记原图尺寸 ⇒ 升级闸响、随后补一次 `(0,0)` 原图档替换。**没有**逐块 / 逐行上屏那种部分解码呈现 | `core::viewer/schedule` + `decoders::decode_with` |
| 跨解码器资源共享 | 按族合并 DLL、共享 zlib/libjpeg 内核、按格式族合并省体积（"多库合并减体积"是框架的活，不是解码器的活） | 构建脚本 + 解码器划分 |
| 自包含分发 | 全部持久化写在 exe 同级之内：`rupix.ini` + `decoders/` + `plugins/` + 随包 `docs/decoders.json`/`docs/plugins.json` 在根，诊断物（日志/报告/转储/会话戳）收在 `temp\` 且按天命名、7 天自清，纯提速件（`cache\svg-fonts.bin`）收在 `cache\`，不碰注册表/用户目录 | `core::paths`（便携铁律） |
| 扩展宿主（非解码器插件） | manifest 发现/启停、进程外编排（命名管道 + 共享内存）、安装即同意、三振隔离、安装/卸载/远程清单；编辑型回写套成覆盖上屏，宿主只负责另存/还原；插件可自报动态热键（内置快捷键优先） | `extensions/` + `core::ext`，正本 `docs/扩展体系.md` |
| 色彩管理 | 解码器照实回报文件内嵌 ICC（ABI `icc_len`），宿主在**缩样之后**用系统 CMM（`mscms.dll`，感知意图）转 sRGB 上屏；无 profile 按 sRGB 原样显示，转换失败保留原像素并 warn。不做意图选择、不跟显示器 profile 联动 | `platform/color.rs` + `decoders/mod.rs` |

## 3. 解码器的职责边界（商品该做、框架不碰）

| 解码器负责 | 说明 |
|---|---|
| 把具体格式解成 RGBA8 | 宿主分配像素缓冲、解码器只写入（规避跨 DLL 释放崩溃） |
| 自述能力 | `iv_decoder_info()` 声明支持的扩展名与版本；元数据全在 DLL 内（无独立 JSON 清单） |
| 自述会不会降采样 | `iv_caps()` 的 `CAP_SCALED` + 单次请求的意图位 `REQ_ALLOW_SCALED`。**契约里没有"逐块进度"回调**（既没有 `iv_progress`，也没有回调指针），宿主拿不到"解到 40%"这种东西；首屏快是靠"这一次允许降档"，不是靠部分结果 |
| 可重入、可换、可并存 | 可随时被换、可多份并存（同 id 只留一份）；线程模型由契约规定（**同一份后端上串行调用**，解码器可重入不必 MT-safe）。★ 多开（m211）之后每窗一份私有后端，"同一枚 DLL 只被一条线程进入"这件事目前**没有保证也没有裁决**，见 `docs/架构总览.md` §二 那条未决边界 |
| 语言无关 | Rust / C / C++ 编的 DLL，满足 `abi/` 契约都能接（libwebp 先例：C 库直接编译进 DLL） |
| 选型自主 | 每格式用哪个库，由解码器仓库自己的候选清单与选型工具决定，框架不参与 |
| **对输入字节"推进且线性"** | 由文件长度字段驱动的循环不许原地踏步；递归 / 交叉引用用 visited 去重（只设深度上限不够——一个节点被 N 个条目指向时工作量是 `N^层数`）；轮数上界取自文件长度而非文件内的计数。正本见 [`解码器开发规范.md`](解码器开发规范.md) §六（宿主侧摘要；条文全文由解码器侧规范维护，不在本仓） |

### 3.1 替换是对用户开放的（2026-10-29 用户拍板，写下来免得被后人读成 bug）

解码器的 `id` 是**共享命名空间**：任何人都能编一枚自述 `id=common` 的 DLL 放进 `decoders/`，
版本比官方高就**由它接单**（宿主裁决"同 id 只留最高版"，见 `decoders::refresh_catalog`）。
官方那一套只是**基础功能支持**，不是特权。三条配套：

- 宿主**永远不许**加「官方优先 / 签名校验 / 白名单」这类裁决——那等于收回这条承诺，
  而且挡不住有心人（校验和只对随包 `decoders.json` 里那一条有效，用户手放的 DLL 根本没有清单）。
- 替换必须**看得见**：详情窗的解码器名 / 版本 / 作者 / 许可证 / 说明一律取自 DLL 自己的
  `iv_decoder_info()` 与 `iv_metadata`（作者缺席就如实显示「（未知）」）。
  ★ 我们给的是"看得见是谁在说"，**不是"验真"**——自述字段谁都能填。
- 范围限定：`deploy.py` 那道「随包清单 ↔ `decoders/*.dll` **同 id 同版本**」的门禁
  （m160 立、2026-11-04 用户裁定**不比字节**：MSVC 每次链接换 PDB GUID，同版本重编字节就变，
  拿 size 对账只会制造误报）——它**只管我们自己的发布目录**，不是对用户机器的约束；
  用户在机器上顶替官方解码器碰不到它。

## 4. "轻量"的硬定义（做到什么程度）

"轻量"不是口号，是可核验的硬指标：

| 维度 | 硬指标 | 当前状态 |
|---|---|---|
| **体积** | **不设硬数字目标**（用户拍板 2026-10-20：只要"小巧、不臃肿"，不为一个 MB 数动功能）；判据改成定性两条——① **不含任何第三方解码库**（解码库只住 `解码器仓库`，内置的只有 resvg/矢量文档重渲这类既有依赖），② 构成逐 crate 有账可查、能一眼指出"哪一块凭什么占这么多" | 现行字节数只认 §4.1 顶部那一行（机器闸 j12 核对）；构成见下 |
| **功能面** | 宿主只"看图"：打开 / 翻页 / 缩放 / 旋转 / 镜像 / 鸟瞰 / 导航；不做编辑、管理、批处理、媒体库。编辑由**进程外插件**提供（用户显式触发；通道已接通——宿主负责回写覆盖与「另存 PNG / 还原」，**第一方编辑插件不提供**，见 `docs/扩展体系.md`），不在宿主内实现 | 达标 |
| **依赖** | 不引重依赖链（如完整 image 栈外的重型库）；不引 `thiserror` / `anyhow` 之类"大而全"框架 | 手写最小 `core::error` |
| **复杂度** | 不堆设置项、不建独立事件总线 / 空层（不设第 6 层）、不引额外运行时 | 达标 |
| **自包含** | 不碰注册表 / 用户配置目录，exe 同级分发，删目录即干净卸载 | 便携铁律 |
| **性能** | 解码不卡 UI、渐进预览、速度不降（任何性能改动前后必须跑同一基准并复测） | `HISTORY.md` 与 `docs/架构总览.md` §七为基线 |

| **不可归 crate 的段** | 33.1 KB | 0.7% | `.pdata` 展开表 + `.reloc` 重定位这类 map 里没有符号行的段（本轮段表读数：`.pdata` 虚拟 193,296 B、`.reloc` 19,324 B、`.fptable` 256 B、`.rsrc` 5,704 B、`.data` 8,552 B；这一组按“**整段没有任何归账符号**”计，口径与段表不同，两组数不必相等，见脚本头的第 5 条）；随函数条数增长，别拿它的跨轮差值当增量。★ **勘误（m103）**：m102 那一行漏改了——脚本当时读 187.3 KB，这里仍写着上一轮的 206.1 KB；本轮按脚本重出为 206.3 KB，跨轮那 19 KB 是**符号区间覆盖度**在动，不是体积在动。m104 再重出为 206.4 KB——那 +0.1 KB 落在 `.pdata` 展开表（191,700→191,760），同口径，别当体积读。
★ **m128 这一行掉到 33.0 KB 不是体积缩水**：本轮的 map 里 `.pdata` **第一次有了 9,168 B 归账符号行**，
而这一组的口径是"整段有没有归账符号"——一旦有，整段 193,296 B 就不再计入 rest。差的那 ~174 KB
是**覆盖度**，不是代码变少了（同一轮段表里 `.pdata` 虚拟 192,504 → 193,296 B，反而多了 792 B）。
这是 K71 / m104 那条"分组读数不许跨轮引用"的又一个现行案例 |

三条读法：

1. **涨到 4.9 MiB 的主因不是某一次改动，是两件事的叠加**：内置 SVG（要"零解码器也开得了图标与 SVG"）
   占了近一半；`lto = false`（K53）比 fat LTO 多约 0.6 MB，是**买光栅性能**的代价
   （生产@200% 一帧 9.7 → 7.1 ms），当时已明写并接受，不是漂移。
2. **`debug = 1` 不占 exe**（事故当日配对：关掉后 5,016,064 → 5,018,112 B，多 2 KB 是段对齐噪声，
   PDB 则 21.6 → 7.9 MB）。行表只进 PDB，`strip = true` 已把调试段剥掉——
   所以**别拿体积当理由关掉崩溃取证要用的行表**。`.rdata` 里那 328 KB `$ip2state$` 单步状态表
   也不来自 debug 档位，关掉它一分不省。
3. **要继续瘦身，大块只有一条真路**：把 SVG 栈挪出 exe（变成一枚解码器 DLL）。账面能省 2.1 MB
   （按上表直接相减，**未实测**——真拆了要往回加宿主的 SVG 载入路径与 ABI 扩展），
   代价是"零解码器也开得了 SVG"这条内置能力没了——属**功能面裁决**，不是工程清理。
   要动它得先在 `待办.md` §9 立项并由用户拍板，本节只把账摆出来，不自行开工。
   小块仍可从**依赖的特性面**抠（m95 摘掉 `env_logger` 的 `auto-color` 实测 −43,520 B，
   连带整串终端着色依赖退出、代码零改动），但再往下的候选都是 10 KB 级，
   且要么削掉运行期日志过滤（`env_filter` 13.1 KB，`RUST_LOG` 就没了）、要么得改 `.3rd` 的 windui（toml 105 KB）——
   m95 逐项算过，**都不值当**。
4. **更早的逐段历史账**（资源段瘦身那一笔：`.rsrc` 305,664 → 4,992 B、`rupix.ico` 304,886 → 4,588 B、
   exe 4,175,040 → 4,074,496 B）**只记在本节**（2026-10-19 m46 把出处那份批次文档删了，数字就地落地）——
   否则下次问"图标资源什么时候瘦过"就无处可查。

## 5. 明确不做（边界清单，违反即越界）

> 来源：本宪章 §1 原则 + [`待办.md`](待办.md) 的"拒绝"清单 + [`架构总览.md`](架构总览.md) §九"明确不做" + [`../README.md`](../README.md) 的"明确不做"，收敛成一份战略级边界。功能项的具体裁决与理由以 `待办.md` 正本为准。

### 5.1 解码相关（框架边界）

- **不把任何第三方解码库编进 exe**：解码库只住解码器仓库，产物发到 `.build/decoders/`。
  ★ 2026-10-25 起这条**同时也管住系统解码器**：上一版登记在册的内置库 `wic`（操作系统自带
  的 `windowscodecs.dll`）已整层下线，见下一条。"零体积"因此重新名副其实：宿主里没有任何
  位图解码实现。（§4.1 账本里那"+10,752 B 绑定层"是 WIC 时代的历史行，随它一并作废。）
- **WIC：不接入（2026-10-25 用户裁决，本条**是第二次修宪**）——宿主不调用任何系统解码器**：
  - **来龙去脉**：2026-10-10 判弃的是**WIC 兜底**；2026-10-20 拍板让它以「可被点名的内置库」回归
    （`platform::wic`，`auto_claim=false`，只走设置页点名、不进默认仲裁、不做失败兜底）；
    **2026-10-25 用户裁决整层删除**：「我们这是便携式的看图工具，最好就不要调用太多系统的
    能力了」。代码侧 `platform::wic`、`decoders::Host::decode_builtin`、登记表里的 `wic` 条目、
    `Win32_Graphics_Imaging` 绑定与 `examples/wic_vs_decoder` 一并下线；端到端用例同步改成
    它的反面（`bitmaps_never_route_to_a_builtin_decoder`）。
  - **现行条文**：位图解码**只有解码器一条路**。内置登记表里允许出现的**只剩矢量**
    （今天 `resvg`，认领 `svg` / `svgz`）——矢量要按视口重渲，位图解码器的语义表达不了。
    想扩格式 = 加/换一枚 DLL，不动宿主。主路径与唯一路径都是解码器 DLL。
  - **不因"更快"回潮**：点名 WIC 的实测收益只在 BMP（0.64×），JPEG ≤6%、PNG/TIFF 反而慢
    1.4–1.5×，且不应用嵌入 ICC（带 profile 的图实测色差 mean 17.9 / max 100）。
    **速度从来不是接它的理由**——便携与跨机行为一致才是拒绝它的理由，那个理由不随数字变。
  - **同理 resvg（SVG）仍登记为一枚内置解码库**：内置不等于隐身，它在候选清单与
    「解码器 > 首选解码器」里看得见、可被点名。

- **不追求"纯 Rust 解码最优"**：纯 Rust 仅少数格式够用（EXR / JXL / 部分 PNG）；热门短板（JPEG/HEIC/AVIF）换 C 库 DLL 即可摸到 WIC 速度档，框架不变。
- **不做第二份能力清单文件**：解码器 id / 显示名 / 认领扩展名全内置在 DLL（`iv_decoder_info()`），能力真源只有 DLL 自述，传播只拷一个 DLL；发布/下载用的 `decoders.json` 只服务安装（id / 版本 / abi / 镜像地址；**不记哈希**），宿主**不拿它路由**。
- **不做系统级解码器兜底**：解码能力只来自两类来源——内置矢量（resvg，`svg` / `svgz`）与解码器 DLL；无外挂解码器即打不开对应格式（能力与清单不脱节）。"点名"与"兜底"的分别是硬的：兜底 = 系统 API 悄悄替解码器解出一张图，同一文件在两台机器上结果不同却无人知情；点名 = 用户在设置页里选了它，知情且可撤回。
- **不做第三方解码器的信任 / 分发 / 支持体系**：ABI 与《解码器开发规范》对外公开，任何人可以把 DLL 放进 `decoders/`，这是开放 ABI 的自然结果；但我们**不设解码器商店、不做签名/哈希固定、不提供"官方认证"或答疑承诺**，当前 8 个解码器 DLL（common/modern/raw/pro/classic/texture/doc/doc-legacy；后缀数以 `decoders.json` formats 计数为准，2026-10-29 为 152）都在解码器仓构建、由用户按需安装。加载失败 / ABI 不匹配时宿主只做退化显示 + 该格式不进清单。
- **解码超时熔断（2026-11-04 m212/m213 落地，替换旧「不做解码超时熔断」）**：隔离栈（`catch_unwind` / SEH）只拦本线程崩溃，**拦不住 worker 线程 panic 导致的挂死**——m213 实锤 `rav1d-safe 0.5.7` 多线程 AVIF 解码的 `overlapping DisjointMut` 竞争在 worker 线程 panic，等它的调用者只是 `recv` 一个永不来的结果。因此：(1) 解码器侧 AVIF/AVIFS 一律单线程（`zenavif::DecoderConfig::new().threads(1)`），从根源消除竞争；(2) 宿主侧 `core::decode::Worker` + `recv_timeout(decode_timeout_s)`（默认 20 秒、上限 600、0=关）做监督者，超时后丢弃该 worker、起新 worker、回可行动 Err；(3) 熔断只**本会话停用**该解码器（`decoders::add_disabled` 内存集），**不写 `decoders_disabled`**（脏的是本次进程不是这个解码器，重启自动恢复）；(4) 超时阈值经 `decode_timeout_s` ini 键可配，判据全程有效（`age_ms` 用户等多久 / `run_ms` 其中真在解多久，-1=还在排队）。
  ★ **但"检测"不等于"熔断"**：宿主有一枚**看门狗**（`core::decode_watchdog`，2026-10-28）登记在途解码，
  超过阈值（首报 10 s、之后每 +10 s 升报）就往日志写一行 `[decode-watchdog] file=… age_ms=…`。
  它**只记日志、不弹窗、不杀线程**——阈值没有现场数据校准，误报比不报更坏。
  ★ **现状口径（m212 起）**：解码真挂死时，**这张图给出一句可行动的失败**（"解码超时，已停用解码器
  「…」"），该 worker 被丢弃、新 worker 接着服务，**其余图照常打开**；本会话停用那枚解码器、
  重启自动恢复。看门狗那一行日志仍在，用来把"卡在哪一段"读出来（`age_ms` / `run_ms` / `phase`）。
  **不做独立解码进程**——多一个常驻进程 + IPC + 生命周期，与"轻量"硬约束冲突，代价大于收益（已封案）。

### 5.2 功能相关（产品边界）

- **不做视频 / 音频**：另一套播放管线，塞进看图器会让体积与复杂度失控。PDF 经解码器路线实现（m193/m194/m195，`doc` 这枚解码库的 `doc-pdf` 成员认领 `pdf` 后缀，页=帧模型翻页），属"多认一个格式"而非"做导出"，与本条不冲突。
- **不做"导出 / 格式转换"这条能力线（2026-10-28 用户裁决）**：宿主是看图器，不是转换器。
  具体口径：① 宿主不做"把 A 转成 B"的导出功能（转格式、转 PDF、转 SVG 一律没有）；
  ② **矢量格式一律由解码器按目标像素尺寸自己渲染**（"按 target 渲染"= 无损放大的技术内容），
  **不经任何中间格式**——宿主内置 resvg 只服务 `svg` / `svgz` 这两个原生 SVG 后缀，
  其余矢量格式由**一枚**矢量解码器 DLL 认领（内部用通用矢量栈，一次覆盖一批格式）；
  ②' ★ **2026-10-28 同步收口**：宿主侧那条"解码器交出矢量文档、宿主用自己的 resvg 渲染"
  （`HostExport`）的路线已**整条删除**（不再探测 `iv_export_svg`、不再有导出缓存与导出分支）。
  留着它就是**同一个格式挂着两条渲染路径**——换机器、换 DLL 版本、换字体栈时两边的像素可能不同，
  "同一文件跨机同结果"这条立宪理由会被自己破掉。符号与类型按 ABI 冻结保留在契约里，老解码器
  实现了它也不会出事（宿主只是不再调用）；
  ③ 因此"每格式写一个 →SVG 转换器"这条路线**不做**（那是 B 方案，已判废）；
  ④ PDF 全格式不做（宪章明令，与本条无关）；⑤ 将来若要让"能打开某个格式"，
  走的是**解码器**路线（认领后缀 + 自己渲染），宿主侧零改动——那是"多认一个格式"，不是"做导出"。
  ★ **"放大到 4000% 也无损"的技术通道 = ABI v6 的区域渲染**（2026-10-28 用户裁决扩到 v6）：
  宿主只向解码器要"**看得见的那一块**"，画布恒为一屏大小 ⇒ 倍率无上限；
  解码器按那块**重新光栅化**，不是位图插值放大。v6 是**加法式**升级（v5 的签名与结构体
  逐字节未动，v5 老 DLL 照常收载）。契约条文在 `vendor/rupix-abi/src/lib.rs` 的 `IvRegionReq` / `iv_render_region`，
  矢量路线的总体口径（一枚 DLL 自渲染、不经中间格式）见 `docs/架构总览.md` §五 与 §5.1 本条。
  ★ **文字必然要渲染**（2026-10-28 用户拍板）：矢量文档里的字**不许**因为找不到原字体就
  丢字、空字、留白或崩——字体优先级 = 文档内嵌 → 文档指定系统字体 → 兜底字体，
  并在解码器错误文案里记一句（用户看得见"已用兜底字体"）。
  ⇒ 由此产生的**跨机像素差异是已登记且已接受的唯一例外**（m153 §7.3 E2）：
  宁可两台机器差几个像素，也不给用户一张缺字的图。
- **不做网络 / 云盘 / 在线图库**：图片只从本地文件读，不为网络共享做专门功能或性能优化。
  **网络行为只有设置页的两张下载卡**：解码器卡与插件卡的**清单刷新 / 资产下载**：
  进页只读随包的 `<exe>/docs/decoders.json` 与 `<exe>/docs/plugins.json`（零网络，
  没网 / 永不联网都能打开这两页）；只有用户点「刷新」才在后台线程联网更新清单
  （成功才原子覆盖，失败保留旧清单并报原因），点「下载 / 升级」才拉对应 DLL / ZIP；
  切 Gitee / GitHub 只换地址列、不联网。**不上传任何数据**。
  除此之外不联网——无统计上报、无自动更新、无后台轮询
  （2026-10-26 m145 立 / m148 本地化，见 `main/AGENTS.md`「联网只有设置页两张下载卡」）。
- **宿主不做图像编辑 / 管理 / 批处理 / 媒体库**：RuPix 是"看"，不是"修"或"管"；插件可以自己提供编辑功能，但那不是宿主的能力，也不改变宿主的职责边界。
- **幻灯片放映：2026-10-12 判废删除，2026-10-31 用户重新拍板复活**，形态与那一版不同——
  **无音乐、无过渡动画、无定时器线程**（走已有的 16 ms 轮询），入口只有右键「操作」一项 +
  一个 ini 键，状态面是放映中持续亮起的那颗右箭头。带音乐 / 过渡动画的那一版仍在不做清单里；
  复活同时把"零新线程"写成了硬约束（当年删它就是因为间隔参数 + 双入口 + 轮询 + 状态机测试这串成本）。
- **不做强调色 / UI 缩放 / 多语言**：深色棋盘格已统一，无消费方。★ **界面主题已经做了**（m200：ini 键
  `ui_theme`，「选项」页「主题色」，只管看图窗口那一层；m223 改的名），所以这一条不能再写"不做主题"。
- **不做 KV / SQLite / GSettings / 自然序以外持久化**：配置即 `rupix.ini`（文件即文档），单 `core::paths` 落点。
- **不做以下已被逐项裁决拒绝的项**：窗口几何记忆 / 记住上次目录 / EXIF 开关 / 缩放步长 / 鼠标侧键翻页 / 文件列表排序 / 棋盘格颜色 / 背景色自定义 / auto_crop。完整清单与理由见 `待办.md` 的"已拍板不复活"。

### 5.3 架构相关（工程边界）

- **不引 `thiserror` / `anyhow`**：手写最小错误体系（`core::error`）。
- **不建独立事件总线 / 空层**：跨线程流只有一条时不开独立事件模块；不设 app / scripting 层（现五层，`extensions` 与 `decoders` 同层平级，不加第六层）。
- **不碰注册表 / 用户配置目录**：便携铁律，唯一落点 = exe 同级 `core::paths` 的 `OnceLock`。
- **多开 = 单进程多窗口（2026-11-04 m211 落地，替换旧「严格单实例」）**：全局只一个进程、一个托盘、一个单实例闸门（`windui::claim_instance` 启动闸门恒生效）。**窗口可以有多个**：每扇窗口一份运行期状态（`runtime::WinRt`），跨窗唯一只有 `Shared`（config/hub/窗口表）。二次启动的去路由 `allow_multiple` 决定：开新窗 / 就地换图；同一进程内可开多扇，空窗只从托盘开（画布右键菜单不再有「新建窗口」——想看图直接双击，那一项本来只能开出没图的窗）。关闭到托盘是"隐藏而非退出"；关最后一扇且无托盘时进程退出。机制详见 `docs/架构总览.md` 窗口模型一节。
- **不把解码库静态链进主 exe**（见 5.1）：AGPL 项目下静态链 LGPL 库必须以 DLL 形态提供，保留用户 relink 能力。
- ★ **宿主侧的改动不得触碰解码器接口**（2026-10-28 用户口径「解码器不再改动」）：
  宿主对解码器 ABI 的依赖面被**冻结在 9 个导出符号**上——
  必备 5 个（`iv_abi_version` / `iv_decoder_info` / `iv_probe` / `iv_render` / `iv_last_error`）
  + 可选 4 个（`iv_caps` / `iv_metadata` / `iv_render_raw` / `iv_render_region`）。
  机器闸 `core::abi::tests::host_abi_dependency_surface_is_frozen` 逐文件扫宿主源码：
  出现冻结集合外的 `iv_*` 符号 ⇒ **红灯** ⇒ 必须走既有流程
  （用户拍板 → 解码器仓改契约 → 加法式 bump ABI → 整份复制快照到 `vendor/rupix-abi/`）；
  退役符号（矢量导出）只许出现在测试代码里。
  ⇒ 换句话说：**宿主侧的新功能一律在宿主内部实现，不靠"让解码器多一个导出"**。

## 6. 新增格式 / 换解码库的标准流程（怎么做）

| 场景 | 怎么做 | 框架要不要动 |
|---|---|---|
| 新增一种图片格式 | 在解码器仓库内部写单库并接进发布档；扩展名/版本自述进 DLL（`iv_decoder_info`）；**不改宿主文档的清单** | **不动**宿主、不动 ABI |
| 替换某格式的解码库 | 解码器内部换（如 zune-jpeg → libjpeg-turbo）；框架只认 `vendor/rupix-abi`，不 bump ABI 即可换 | **不动** |
| 改解码路由 / 清单语义 | 动 `core::decode` 或 `core::formats` 的依赖倒置口，配 `ext` 组测试锁"清单与能力不脱节" | 仅 core，仅解码器接口 |
| 选每格式最快库 | 查 `HISTORY.md` 与 `docs/踩坑记录.md` 里的解码库选型记录（每格式最快库/语言/许可/能否静链） | 产物是选哪个 DLL |
| 多库横向评测 | 用宿主基准工具/解码器仓库内部的评测工作台（确定性语料 + PSNR/median 指标） | 不影响框架 |

**铁律**：解码库必须 `opt-level = 3`（workspace 默认 `z` 会让 JPEG 3MP 慢 4.6 倍）；冒烟 / 实测时解码器目录必须可寻址（设 `RUPIX_DECODERS_DIR` 绝对路径指向 `.build/decoders`，禁用 example 旁过期 DLL）。
