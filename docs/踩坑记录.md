## 一、构建与工具链

### K01 —— `seh_shim.c` 报 `C1034` 或 `LNK2019`

- **现象**：编译 `seh_shim.c` 报「找不到 `windows.h`」；或链接阶段报
  `GetExceptionCode` 未解析（LNK2019）。
- **根因**：构建脚本的子进程 INCLUDE 环境里没有 Windows SDK 路径；`GetExceptionCode`
  是宏（展开成 `_exception_code` 内建），不 include 就没有可解析的外部符号。
- **解法**：`seh_shim.c` **禁止** `#include <windows.h>` 与 `GetExceptionCode`——
  改用编译器内建 `_exception_code()`，需要的常量自己 `#define` 硬编码；
  注释写英文（中文注释在 GBK 代码页下触发 C4819）。
- **2026-10-17 复发一次**（同一文件加中文注释）：症状不是 C4819 警告而是
  `error C2059: 语法错误:“if”` + `C1004: 发现意外的文件尾`——**中文标点占偶数个 GBK 字节时
  会把行尾换行符吃掉**，于是下一行被并进注释，编译器在更远处才炸。报错位置离病灶很远，
  只看错误行会去改完全无关的地方。判据：`cl` 的 C2059/C1004 指向 `if`/文件尾而代码没问题，
  先查这个文件里最近加的非 ASCII 注释。

### K02 —— 改了 `seh_shim.c` 却仍链接到旧库（LNK1120 / LNK2019）

- **现象**：`.c` 改完了，报错指向**上一版**的符号，怎么重编都不变。
- **根因**：`build.rs` 没写 `println!("cargo:rerun-if-changed=seh_shim.c")`，
  cc 的产物缓存不失效，链接的还是旧 `seh_shim.lib`。
- **解法**：确认 `build.rs` 有这行；仍不生效就手动清
  `.temp/target/debug/build/rupix-*/out/*` 再构建。

### K03 —— 测试代码写空指针赋值过不了编译

- **现象**：测试里想制造访问违规，写 `*(0 as *mut u8) = 1` 被
  `#[deny(deref_nullptr)]` 直接拒掉。
- **根因**：该 lint 是编译期常量求值检查，与运行时意图无关。
- **解法**：用**非 0 的野指针**（`usize::MAX`）+ `std::ptr::write_volatile`
  触发访问违规，`platform::seh` 的测试即此写法。

### K04 —— 在 `./target` 里找不到构建产物

- **现象**：`cargo build` 完，`main/target/` 下没有预期产物，或目录莫名变大。
- **根因**：target 目录被写死重定向——`main/.cargo/config.toml` → `../.temp/target`；
  解码器工作区 → `.temp/decoder-target`（历史名 `target-ext` / `decoders-target`，`解码器仓库 target` 也已作废——
  源码仓库不放产物）。`main/target/` 是重定向生效前的残留。
- **解法**（现口径）：宿主产物在 `.temp/target`，解码器在 `.temp/decoder-target`；
  重定向键必须写在 `[build]`（写进 `[package]` 是无效键）；`main/target` 与
  `解码器仓库.temp_*.log` 属残留，可清理。

### K05 —— `cargo` 报 `os error 5 拒绝访问`，或测试跑着像卡死

- **现象**：构建偶发「拒绝访问」；`cargo test` 默认多线程跑法长时间无输出，
  看起来是假死。
- **根因**：杀软 / 索引服务在持锁——刚链接出来的测试二进制被占用，
  并行 runner 反复撞锁。
- **解法**：重跑；设 `CARGO_INCREMENTAL=0` 减少一类噪声；
  **跑测试固定加 `-- --test-threads=1`**（`build/5_test.bat` 已写死，单线程几秒跑完）。

### K06 —— 宿主与解码器 DLL 混用静态/动态 CRT 导致链接冲突

- **现象**：链接期符号冲突，或运行期堆/锁不一致。
- **根因**：宿主与解码器 DLL 必须一致地静态链接 CRT（`+crt-static`），
  混用会撞上两套运行时。
- **解法**：宿主与解码器 workspace 都开 `+crt-static`；`seh_shim.c` 用 `cc` 的
  `static_crt(true)` 对齐同一套。

### K07 —— 解码库用了 workspace 默认 `opt-level = z`，速度差好几倍

- **现象**：同一份解码库在 release 下比预期慢数倍（JPEG 3MP 实测差 4.6 倍）。
- **根因**：workspace 的 release profile 是体积优先的 `z`，热循环代码吃亏。
- **解法**：在 `Cargo.toml` 的 `[profile.release.package.*]` 给解码库 / resvg 相关
  crate 单独提 `opt-level = 3`；解码器侧同理按需提（见各解码器 `Cargo.toml` 注释）。

### K08 —— 冒烟 / 实测时「明明有解码器却一个格式都认不出」

- **现象**：示例或探针报「解码器目录为空 / 无人认领」，但 `.build/decoders` 里 DLL 齐全。
- **根因**：解码器目录默认取 **exe 同级**的 `decoders/`；示例 exe 在 `.temp/target` 下，
  旁边没有解码器目录。
- **解法**：设 `RUPIX_DECODERS_DIR` 指向 `.build/decoders`；或先把 DLL 拷到 exe 同级再跑。

### K09 —— 一条几十个文件的批处理命令静默失败

- **现象**：控制台里粘一大串文件操作，只成功了前几个，后面无声无息。
- **根因**：命令行长度 / 转义 / 引号在不同 shell 下行为不一致，失败不冒泡。
- **解法**：复杂操作落成脚本（`.bat` / `.ps1` / `.py`）再执行，脚本里逐条判错。

### K10 —— PowerShell 读不到输出 / 输出文件是乱码 / `&&` 报解析错误

- **现象**：前台跑 PowerShell 拿不到 stdout；用 `>` 重定向出来的文件是 UTF-16，
  别的工具读不了；写 `cmd1 && cmd2` 直接报错。
- **根因**：前台 stdout 缓冲与宿主管道的交互问题；`>` 走 PowerShell 自带编码；
  Windows PowerShell 5.1 不支持 `&&` / `||`。
- **解法**：要读输出就先写文件再读；需要重定向时显式
  `| Out-File -Encoding utf8` 或用 Bash；多步命令用 `;` 串联或拆成多条 /
  落成脚本；非要用 `&&` 就换 PowerShell 7。

### K11 —— 在 Bash 工具里跑 PowerShell 指令报 `command not found`

- **现象**：`Out-File` / `Write-Output` 在 Bash 工具里找不到命令。
- **根因**（2026-10-17 勘误）：本机该工具**实际执行的是 PowerShell 5.1**，不是 git bash——
  旧写法"该工具是 git bash"诊断错了，害得人按 bash 语法写、又白跑一轮。
  命令找不到的真因通常是**语法方向反了**：在 bash 会话里写 PowerShell  cmdlet，
  或在 PowerShell 里写 bash 的 `$()` / `Export` / `&&`。
- **解法**：**先探测当前 shell 再写命令**（`$PSVersionTable` 有输出即 PowerShell）；
  多行或复杂逻辑一律**落成纯 ASCII 的 `.ps1`**，用
  `powershell -NoProfile -ExecutionPolicy Bypass -File <path>` 执行（见 §四 与 K27）；
  需要 bash 语法时确认确实在 bash 会话里再写。
  备注：`git.exe` 装在非默认目录（`where git` 可查）；它在不在 PATH 里，与"终端是哪种
  shell"无关，别据此推断。

### K36 —— `idle_millis_is_safe` 测的是「你离开键盘多久」，整层集成门禁被它挡掉

- **现象**（2026-10-17 改名收尾复查时抓到）：`cargo test --release` 恒 1 红
  （`platform::working_set::tests::idle_millis_is_safe`），同一个测试二进制手动跑又绿。
  更严重的是 `5_test.bat` 第一层（`cargo test --release`）里 **lib 先跑、一红即中断**，
  `tests/*.rs` 执行次数 = 0；`full.bat` 第 5 步红灯停机、不部署。
  也就是说：**只要没人碰键盘，正式六步门禁永远过不去**——自动化 / 无人值守 / AI 跑门禁时
  100% 触发，而"门禁全绿"只能靠人守在手边手点。
- **根因**：断言写成 `assert!(m < 60_000 || m == u64::MAX)`，而 `m` 是 `GetLastInputInfo()`
  的**真实整机空闲毫秒**——本来就是可以几小时的东西，拿 60 秒当上限等于在断言键盘状态。
  取证：同一二进制依次报 `87s → 109s → 123s → 167s`，与对话期间无键鼠输入的时长严格同步递增。
- **★ 顺带发现：那个哨兵分支是死码**。`idle_millis` 用 `GetTickCount().wrapping_sub(dwTime)`
  算差，两个 tick **同纪元**，结果只可能是真实空闲时长，永远不等于 `u64::MAX`；
  真失败走 `else` 才返回 MAX。所以旧断言的后半句一直在验不可达分支。
- **★ 第一版修法也会红（别再试）**：想改成不变量 `idle ≤ uptime` 是**错的**——
  `GetTickCount()` 是 32 位 tick、约 49.7 天回绕，机器跨轮后 uptime 显示成回绕余数，
  本机实测 `idle=139609` 而 `uptime=630021312`，照样误红。
- **解法**：断言换成**同基代数恒等式**——调用前后各取一次 tick（`t0`/`t1`）并独立复取
  `LASTINPUTINFO.dwTime`，要求 `idle ∈ [t1-last, t0-last]`。同基 `wrapping_sub` 天然消回绕，
  判据与"是否有人在用键盘"彻底无关，同时仍保住原意（探测不 panic + 读数与时间基自洽）。
  验证：三次各隔 45 秒（累计空闲 >300 秒）复跑全绿，随后 `cargo test --release`
  **172 lib + 14 集成（docs_consistency / config_compat / config_pipeline_e2e）首跑全绿**。
- **教训口径**：单测里凡读**外部世界状态**（时钟、键鼠、网络、开机时长、磁盘余量）的断言，
  必须写成"**与自身取样同基的恒等式 / 单调关系**"，不能写成"当下应该是个小值"；
  否则测的是环境而不是代码，还会连累整层门禁。
- **★ 姊妹缺口（同轮发现）：写在文档里的门禁，没人执行就等于没有**。`main/AGENTS.md` §九 第 3 行、
  `RuPix-Decoder/AGENTS.md` §七（第 176 行）**两边早已写明** `cargo fmt --check` 须 exit 0，
  但 6 个 `.bat` 与 `RuPix-Decoder/build.ps1` 里**零处执行**——所以两处漂移一直无人拦，
  直到本轮复查手跑才现形；其中一处在 `abi/src/lib.rs`，格式一动宿主逐字节快照就脱钩。
  已补：`main/build/2_scan.bat` 加第 `[3/3]` 步（宿主 fmt）、`RuPix-Decoder/build.ps1` 在编译前加
  fmt 检查；两侧文档口径同步改成"已被流水线执行"。判据同 K31 那句老话——**不会红的门禁不是门禁**。

### K27 —— PowerShell 读无 BOM 的中文文件读出乱码（`鐗堟湰鍘嗗彶…`）


- **现象**：仓库里的 `.md` / `.ps1`（UTF-8 **无 BOM**、含中文）用 PowerShell 5.1 一读，
  中文全是 `鐗堟湰鍘嗗彶` 这类乱码；更糟的是执行无 BOM 的中文 `.ps1` 时中文串按 ANSI 解释，
  **脚本逻辑静默错**（不只是显示难看）。
- **根因**：Windows PowerShell 5.1 在没有 BOM 时按当前 ANSI 代码页（GBK）解码；
  `-File` 执行同样如此（PowerShell 7 才默认 UTF-8）。本仓文件默认 UTF-8 无 BOM。
- **解法**：① 读中文文档内容用显式 UTF-8 的工具（`Get-Content -Encoding UTF8`，或直接
  用能正确解码 UTF-8 的读取工具）；② 落成 `.ps1` 的脚本**保存为 UTF-8 with BOM**
  （或用纯 ASCII 注释与字符串）；③ 此为 K10 的兄弟坑——K10 管输出去向，本条管输入解码。

### K31 —— `cargo` / `gate.py` 报 `rustup could not choose a version of cargo to run`

- **现象**：本机直接跑 `cargo build` 或 `python build/gate.py run ext`，报
  `error: rustup could not choose a version of cargo to run, because one wasn't specified
  explicitly, and no default is configured.`——可 `rustup toolchain list` 明明有 stable。
- **根因**：rustup 的**默认工具链没配置**（全局 settings 缺 `default_toolchain`），
  而各处脚本又直接裸调 `cargo`。开发机的全局状态不该是构建前提。
- **解法**：① 脚本入口显式固定工具链——`RuPix-Decoder/build.ps1` dot-source
  本仓审计工具 后自动设 `RUSTUP_TOOLCHAIN`；`main/build/gate.py` 在
  `subprocess.run` 的 `env` 里 `setdefault("RUSTUP_TOOLCHAIN", "stable-x86_64-pc-windows-msvc")`；
  ② 手动跑 cargo 前设 `$env:RUSTUP_TOOLCHAIN = "stable-x86_64-pc-windows-msvc"`
  （`rustup default stable` 会改全局配置，非必要不用）。
- **同类**：凡"脚本内部调 cargo / cl / cmake"的地方都要自己兜底环境——这正是规范 §六第 9 条
  （工具链锁版本，"在我机器上编得出来"不算数）的正面落地。
- **★ 2026-10-17 补漏（宿主 bat 侧是漏网之鱼）**：六步流水线的 `.bat` 从来没设过
  `RUSTUP_TOOLCHAIN`，`1_check_env.bat` 的 `for /f 'cargo --version'` 因此**抓到空串照样打
  `[OK]`**、紧接着判"rust host is not MSVC"，`full.bat` 第 1 步 rc=1 **在这台机器上根本起不来**。
  修法：`_common.bat`（所有编号步骤与 `full.bat` 共用）`if not defined RUSTUP_TOOLCHAIN`
  则钉 `stable-x86_64-pc-windows-msvc`（值与 `解码器仓库工具toolchain.ps1` 一致，不覆盖调用方、
  不动全局 rustup）；同时给 `1_check_env.bat` 加"**空串即 [ERROR]**"守卫——这道检查此前会
  静默吞掉失败，而 `[OK]` 后跟空值本身就是它自己的现场照片。

### K32 —— stb 解截断的无压缩 PSD **不报错**：EOF 的 `get8` 返回 0，静默补零出一张全零图

- **现象**（#53 stb 解码器验收）：一个只剩 26+14 字节头、像素平面全被删掉的 `.psd`，
  `stbi_load_from_memory` 返回**成功**，"解出"一张尺寸正确、全 0 像素的图。
  若解码器直接转报 OK，宿主会把"文件已损坏"显示成一张正常打开的黑图。
- **根因**：`stb_image.h` 的 `stbi__psd_load` raw 分支是 `*p = stbi__get8(s)` 逐字节读，
  **EOF 时 `get8` 返回 0 且不置错误**（`stbi__getn` 才查长度，这条路径没用它）。
  不是 stb 的 bug，是它的错误处理粒度——但"静默出错"的后果全在调用方。
- **解法**：解码器自己算**期望字节数**预检——无压缩 PSD 的数据长 = 定头 40 +
  `w*h*channelCount*(depth/8)`，短了就是截断 → `ERR_CORRUPT`（RLE 压缩后的长度
  无法从头推算，跳过预检，靠 stb 自己的 RLE 越界检查）。**教训**：第三方库
  "不报错"不等于"数据对"，验收时必须问"喂残缺输入它会怎样"。
- **同类**：K28（PIL 裁判失真）同族——工具在特定输入下的行为必须实测，不能默认严谨。

### K33 —— image 的 PnmEncoder 对 Rgb8 也出 **P7(PAM)**：stb 只认 P5/P6，"编码器选错"伪装成"库不解"

- **现象**（#53 选型 bench）：stb 解不了 harness 生成的**任何** PNM 语料，
  报 `unknown image type`——差点写成"stb 不支持 PNM"的结论。
- **根因**：`DynamicImage::write_to(Pnm)` 即使对 `ImageRgb8` 也走
  `PnmSubtype::ArbitraryMap`（P7/PAM 头 `P7\nWIDTH…DEPTH…MAXVAL…TUPLTYPE…`），
  而 stb 的 `stbi__pnm_test` 只认 **P5/P6** 的魔数。是**语料编码器选错形态**，
  不是库的能力缺口——现实世界的 PNM 主流恰恰是 P5/P6。
- **解法**：显式 `PnmEncoder::new(w).with_subtype(PnmSubtype::Pixmap(SampleEncoding::Binary))`
  出 P6 后重跑，6/6 bit-exact，stb 0.74×（慢于 core，按纪律不认领）。
- **教训**：bench 出现"某库全败"时，先查**语料本身是不是该库定义的输入形态**
  （对照库源码的 test/load 函数），再下能力结论。"编码器选错 → 库背锅"与
  K28 的"裁判工具失真"是同一类事故的两个方向。

### K34 —— `canonicalize()` 返回 `\\?\` verbatim 路径，`cl.exe` 的 `-I` 不认（cc-rs C1083）

- **现象**：`cc` crate 的 build.rs 里 `root.canonicalize()` 后 `.include(&stb_dir)`，
  MSVC 报 `C1083: 无法打开包括文件: "stb_image.h"`，cc-rs exit 2。
- **根因**：Windows 上 `canonicalize()` 返回 `\\?\E:\…` 形式的 **verbatim 路径**，
  `cl.exe` 的命令行不接受这个前缀（它能被 API 层接受，过不了命令行词法）。
- **解法**：用 `Path::ancestors()` 逐级上溯取干净绝对路径（含 `..` 段没关系，
  OS 自己规范化），**不要 canonicalize**。两个 build.rs（bench harness / stb 解码器）
  已按此写法并留注释。
- **同类**：Windows 路径进外部工具（cl / link / rc）前，先问一句"这路径词法
  它吃得吗"；UNC、verbatim、8.3 短名都是同类雷。

## 二、UI 线程与窗口

### K12 —— 「点了一下，窗口无声消失」

- **现象**：交互过程中窗口直接没了，没有错误框、没有控制台输出。
- **根因**：所有交互跑在 `extern "system"` 的 `wnd_proc` 里，**panic 展开不出去 = abort**。
  最常见写法是 `if let Some(x) = cell.borrow().f() { … cell.borrow_mut() }`——
  `Ref` 活到整个语句结束，块内 `borrow_mut` 立刻 `RefCell already borrowed`。
- **解法**：先把结果绑到局部变量再判断：`let opt = cell.borrow().f(); if let Some(x) = opt { … }`。
  取证看 exe 同级 `crash.log`（`platform::panic_guard` 写入消息 + 线程 + 源码位置）。

### K13 —— 设置里勾了「启动置顶」，窗口却没置顶

- **现象**：启动时的窗口动作（置顶 / 全屏）其中一个不生效，菜单里勾选态也不对。
- **根因**：`EventOutcome::window_op` 是 `Option<WindowOp>` **单槽**，
  同一次分发里第二个 op 把第一个顶掉（启动首帧同时要发置顶 + 不透明度）。
- **解法**：多个窗口动作排成 `Vec<StartOp>` 队列，16ms 轮询**一帧只发一个**
  （`runtime/mod.rs` 的 `startup_ops` 就是这个模式）。

### K14 —— 半透明窗口设置没上屏 / 菜单糊成一片

- **现象**：`UpdateLayeredWindow` 返回成功但窗口不变；或 80% 不透明度下深色菜单看不清。
- **根因**：ULW 是**逐像素 alpha**，`pptDst` / `psize` 不显式传就不落屏；
  `LWA_ALPHA` 整窗生效，菜单是画在画布上的浮层，会跟着一起变透明。
- **解法**：`pptDst` / `psize` 永远显式传；菜单展开期间整体临时回 100%
  （判据 `ctx.menu_open()`），收起后恢复。

### K15 —— 新增持久化时把文件写到了 CWD / `%APPDATA%`

- **现象**：从快捷方式或别的目录启动时，配置写到了意料之外的位置。
- **根因**：CWD 随启动方式变化；外部用户目录违背便携定位。
- **解法**：任何持久化一律走 `core::paths`（exe 同级 `OnceLock`：`rupix.ini` /
  `crash.log` / `temp/decode-cache`）；写失败 = 只读介质 → 静默降级为纯内存会话（只 warn）。

## 三、解码、清单与日志

### K16 —— 手写了一份格式清单，过段时间和解码器能力对不上

- **现象**：某后缀明明有解码器能解，目录里翻不到；或反过来，清单里有打不开的后缀。
- **根因**：清单正源是**各解码器 `iv_decoder_info()` 自述的动态并集**
  （`core::formats::declared_exts()`），手写第二份必然漂移。
- **解法**：不写第二份清单；新增格式只改解码器自述；`cargo test --lib ext` 锁
  「清单与能力不脱节」。`docs/图片格式与后缀名.md` 的扩展名列照抄源码，核对以源码为准。

### K17 —— `--decode-trace` 打开了却什么都不输出

- **现象**：设了 `RUPIX_DECODE_TRACE=1`，控制台没有 `[decode-trace]` 行。
- **根因**：输出走 `log::debug!`，而 `main.rs` 的 env_logger 默认过滤级别是 `warn`。
- **解法**：同时设 `RUST_LOG=debug`（或 `RUST_LOG=rupix=debug`）再跑。

### K18 —— 换个后缀名就打不开 / 无后缀文件打不开

- **现象**：文件内容没问题，改名或去掉后缀后报「不认识这个文件」。
- **根因**：无魔数格式（TGA 一类）靠 `iv_probe` 的 `ext` 尾参认领；
  `ext == NULL` 时解码器只按魔数认领——这是**故意的语义**（显式打开的兜底路径）。
- **解法**：正常后缀的文件直接打开；确实需要时用显式打开路径触发魔数嗅探兜底；
  解码器侧不要在 `ext == NULL` 时硬认内容。

### K28 —— 用 PIL 当 PNG 独立裁判，隔行（Adam7）样本"解不出来"

- **现象**：校验解码器解码结果时，拿 PIL 开路参照，非隔行 PNG 一致，**隔行 PNG**（Adam7）
  那张 PIL 直接失败/给不出像素，一度误以为是我们解码器解错了。
- **根因**：PIL 对隔行 PNG 的解码支持不完整，**它不能当隔行样本的裁判**（我们的解码器与
  core 的 `image` 路线反倒是一致的）。
- **解法**：隔行 PNG 的独立校验改用系统 **WIC** 转储（本仓审计工具
  经 `WICImagingFactory` 逐像素转储）；测试样本用 encoder 现场造，别依赖 PIL 生成隔行图。
  通用教训：**参照工具自己也会错**，裁判要选实现独立、口径明确的那个（WIC/系统栈）。

## 四、解码库选型与解码器实测

### K19 —— `jxr` 依赖解析到 0.3.0 后编译期直接拒绝

- **现象**：`jxr` / `jxr-core` / `j2k-core` 报 `requires rustc 1.99.0`（本机 1.97.0）。
- **根因**：不带上界的写法（裸 `"*"` 或 caret）解析到更新的大版本，MSRV 超出本机。
- **解法**：`jxr = "=0.2.1"` 锁死上界；给任何新依赖都显式带上界，别用裸 `"*"`。
  （顺带注意：JPEG XR 与 JPEG 2000 共用 `j2k-core`，两个解码器可能重复链接它。）

### K20 —— 按名字搜到的 crate 根本不是图像库

- **现象**：`cargo add --dry-run` 能加进来，实际完全不是那个格式的解码器。
- **根因**：名字对上不等于库对上——`xpm` 是包管理器、`ani` 是动漫命令行工具、
  `dpx` 是 Dropbox 客户端、`ras` 是 AirPlay 服务。
- **解法**：判定「能不能解这个格式」必须读 `description` 与 README（许可证要看
  `.crate` 包里真实 `Cargo.toml` 的 `license` 字段，不信 README、不信站点页）。

### K21 —— 「库已选定」被当成「已经能用」

- **现象**：文档里标了选型，实际接入时才发现解码错误、慢得不可接受或覆盖率不够。
- **根因**：存在性 / 许可证 / 能编译 ≠ 解码正确性 / 速度 / 覆盖率；
  有些库还没有编码器（构造不了「编码→解码」往返测试，手上也没有真实样本）。
- **解法**：接入前先拿真实样本跑通 `decoder_smoke`，再更新能力表；
  无样本的格式先造样本（例如用系统自带编码器生成一张）再验收。

### K22 —— 查询阶段谎报尺寸，渲染阶段崩或图错

- **现象**：HEIC/AVIF 打开报「尺寸超硬顶」或像素错乱。
- **根因**：ABI 是「查询 → 宿主一次性分配 → 渲染」两阶段，**没有重试**；
  容器里的 `ispe` 会撒谎（且报的是旋转前尺寸），解码器若照抄就会给宿主错误的 `bytes_needed`。
- **解法**：解码器在查询阶段回报**转正后的真实**宽高与 `bytes_needed`；宿主侧按
  `budget_bytes`（= `MAX_PIXELS`×4 字节）与 `MAX_PIXELS`（40MP）在查询与渲染两侧校验，
  SVG 路径另有 `MAX_EDGE`（16384）边长上限。

### K23 —— 某些 RAF 打开全黑

- **现象**：compressed RAF 解码结果整屏纯黑，别的格式正常。
- **根因**：元数据声明的白电平远高于实际峰值，按元数据线性化归一后全部压到 0。
- **解法**：raw 解码器按**观测峰值**兜底重归一（元数据与观测冲突时以观测为准）。

### K29 —— 16bit 图"取高字节" vs `image` 的 ÷257：逐字节断言会红，但图没错

- **现象**：PNG 解码器对 16bit 灰度/RGB 样本做"与 `image` 路线逐字节相等"的 parity 断言，
  整片红；可放大看像素，肉眼根本分不出差异。
- **根因**：`png` crate 的 `STRIP_16` 取**高字节**（`0x10B3` → `0x10` = 16），而 `image` 的
  16→8 走 **÷257 四舍五入**（→ 17）。两者差 ≤1 LSB——`libpng` 同样丢低字节，
  即"高字节"是行业口径，`image` 才是少数派。
- **解法**：16bit 族的 parity 断言写成两条——"等于源数据高字节" + "与 `image` 之差 ≤1 LSB"；
  8bit 族仍要求逐字节相等。**凡宣称"与 core 逐字节一致"，先问清是不是 16bit 降位链路**。

### K30 —— GIF 首帧合成成本吃光解码优势（选型 1.18× 的冠军，发布配置复测反而慢 2.2%）

- **现象**：G1 选型 gif crate 直调比 `image` 快 1.18×（裸帧口径）；照发布代码路径实现
  （首帧 = 画布合成 + 探帧）后复测，**反而比 `image` 慢 2.2%**——不达标，冠军不能发。
- **根因**：对"必须输出整幅画布"的格式（GIF/APNG 首帧），合成成本与解码成本同量级：
  整屏画布的 memset + blit（3MP ≈ 12MB 内存往返）把裸帧优势全吃掉。而 `image` 在
  `帧矩形 == 逻辑屏幕` 时走 **in-place 分支**（直接在帧缓冲上合成、没有第二份画布），
  第一版实现却无条件"分配画布 + blit"。
- **解法**：**整屏帧零拷贝快路径**——帧矩形 == 屏幕时直接 `read_into_buffer(宿主缓冲)`，
  透明像素清零（等价"保留画布原值"）；只有局部帧矩形才走画布 + blit。修完复测
  **74.25 vs 86.62 = 1.17×**，与选型倍率复现（本仓基准记录）。
- **同类教训（通用）**：**G1 选型的对照配置必须与被测的发布代码路径逐字一致**——
  否则"选型 1.18×"可以带着 -2.2% 的发布回归上线（PNG 也有同款"口径差"前科，
   §9.6/§9.7）。对画布类格式做 G1 时，
  先看 core 侧有没有 in-place / 零拷贝优化可对齐。

## 五、windui 框架用法

### K24 —— 列表"扫描到了"却整块不可见：scroll 里放 weight 子节点

- **现象**：设置 → 解码器页点「刷新」（2026-10-16 前叫「重新扫描」），计数行显示「7 个解码器」，
  但解码器信息行与开关**一行都没有**；日志里 DynList 也确实重建出了行。
- **根因**：`Element::list_signal(...).weight(1.0)` 被放在了外层 `Element::scroll()` 里。
  windui 滚动容器按**无限高度**测量子元素（`measure_scroll` 发 `Unbounded`），而
  `measure_linear` 对权重子节点两遍都跳过：第一遍 `is_weight()` 直接 `continue`，
  第二遍瓜分剩余空间要求 `!main_unbounded`——主轴无限时权重子**永远量不到**，
  `measured_of` 取默认 0，arrange 只好按 0 高排版。行建出来了，容器高 0，整体裁剪掉。
- **解法**：让权重子节点的父链一路有**确定高度**——`list_signal` 自带内部滚动，
  页面本体用 `col().fill() … .child(list.weight(1.0))`（API 指南范式），别外包 `scroll`。
  回归测试 `ui::settings::tests::decoders_page_rows_survive_layout` 把真实
  `decoders_page` 搬上无头 Tree，钉住「行数对 + 容器高度 > 0」。
- **同类**：重建子树里含 `weight` 正文的表格别用 `list_signal`，换 `host_signal`（普通 col）。
- **附（同日晚，实机才暴露的续坑）**：列表一旦可见，固定行高 `ROW_H` 里塞不下的**长文字
  会换行**——`Core Raster Formats` 的说明折成 2 行，第二行直接压到下一行 `JPEG XL` 标题上。
  固定行高的列表行里，长文案一律 `.max_lines(1).truncate(Truncate::End)` 单行省略，
  别指望 measure 替你把行高撑开（`.height(ROW_H)` 是硬约束）。

### K25 —— 离屏 GDI 渲染（依赖 `windows` crate）必须放 platform，不能图省事放 ui

- **现象**：分层体检 `build/layering_scan.py` 报 `src/ui/pin.rs: ui 层禁引外部 crate windows`
  （use 形态），门禁红——📌 图钉的离屏渲染原本整段写在 `ui/pin.rs`。
- **根因**：图钉渲染调用 `windows` 的 GDI（`CreateDIBSection` / `SetWorldTransform` /
  `DrawTextW` 等），而 ui 层按五层门禁**禁止**引 `windows`（平台 API 只能经 platform 取用）。
- **解法**：GDI 引擎整段搬到新建的 `platform/pin_glyph.rs`——pub 入口
  `render_pin_rgba(upright, r, g, b)`，裸 RGB 入参，**不**依赖 windui 的 `Color`；
  `SIZE` 常量从 ui 提到 platform 并 `pub` 导出供 ui 复用。`ui/pin.rs` 退化为薄封装：
  把 windui `Color` 拆成 RGB 喂平台、把返回的 `SIZE×SIZE` RGBA 字节包成 windui `Image`
  （`render_pins` 仍是 chrome 调用的 ui 侧入口，签名不变）。功能测试
  `platform::pin_glyph::tests::pin_bitmaps_render_both_postures`（两姿态位图 + 绿像素断言）
  随引擎一并迁入 platform 层。
- **同类**：任何「在 ui 里想直接调 Win32」的冲动，先问 platform 有没有现成封装；没有就建一个
  platform 模块，ui 只做 windui 那一层的活。分层体检是字符串静态扫描（use 形态 + 裸 `windows::`
  路径都查），不是建议，是红线。

## 六、输入边界与工作量

### K26 —— EXIF 递归有深度上限，却依然能被 3MB 文件卡死整个窗口

- **现象**：打开一张构造的 TIFF（或 JPEG 内嵌 APP1）后，属性窗「拍摄信息」永远出不来，
  窗口直接「未响应」，CPU 满载、进程不崩、再也回不来。`catch_unwind`、SEH 隔离层、
  解码器三振黑名单**全部无效**——这里没有异常，只有一个跑不完的循环；而且 `read_exif`
  是在 **UI 线程**同步调用的（`ui/settings/metadata.rs` 里 `EXIF_LAST_PATH` 那段），根本不在
  `sv-decode` 解码线程上，解码器侧的隔离层碰不到它。
- **根因**：`platform::exif::walk` 只有 `MAX_DEPTH = 3`。**深度上限防的是链式成环，
  防不了菱形重入**：TIFF 允许任意多个条目指向**同一个**子 IFD 偏移。IFD0 的 65535 条
  `0x8769` 全指 A、A 全指 B、B 全指 C，递归次数就是 `N^层数 ≈ 2.8e14`，而构造这个文件
  只需要三个 IFD（约 3MB）——每个 IFD 不过 `2 + 12N + 4` 字节。
- **解法**：`walk` 加 `visited: &mut HashSet<(usize, bool)>`，进函数即 `insert`，
  已存在即 `return`。key 必须带上 `in_gps`：同一偏移可能同时被 `0x8769`(ExifIfd) 和
  `0x8825`(GPSInfo) 引用，两类上下文采集的字段集不同（GPS 分支只认 `0x0001..0x0006`
  且不再下钻），只按偏移去重会互相顶掉字段。修完工作量回到**对文件长度线性**。
  回归测试 `platform::exif::tests::diamond_sub_ifd_is_walked_once` 断言
  `visited.len() == 4`——去重一失效就红（不是靠计时），并再走一遍 `parse_tiff`
  确认最深层字段没因为去重而丢。
- **同类**：凡「循环/递归次数由输入字节决定」的手写解析器，防环要用**可达集合**，
  不是**深度上限**；深度上限保护的是栈，不是工作量。判据按调用线程分档：跑在解码线程上
  的挂死只废掉图像显示，跑在 UI 线程上的挂死废掉整个软件——所以 `read_exif` 这种
  UI 线程同步解析必须保证工作量对输入长度线性。**超时熔断救不了它**：熔断守的是
  `sv-decode` 线程，UI 线程挂住时没有任何机制能把它捞出来。

### K35 —— 滚动条画得出来却滚不动：`list_signal` 覆盖了 `scroll()` 的 ScrollWidget

- **现象**（2026-10-15 用户报）：设置 → 解码器页，列表右侧**有**垂直滚动条，但滚轮不滚、
  拖滑块也不动，无法向下滑动。
- **根因**：`Element::list_signal` 的容器是 `Self::scroll().fill()`，而 `scroll()` 的本职就是
  装上 `ScrollWidget`（滚轮 + 滚动条拖动）。紧接着构造器 `set_widget(Box::new(DynList { .. }))`
  挂上重建行的 widget——`set_widget` 是**覆盖**语义（`self.widget = w`），`ScrollWidget` 被静默
  丢掉。`DynList::on_event` 恒 `false`，于是滚轮与拖动再无人处理。
  框架自己在 `Element::widget` 的 `debug_assert!` 里警告过这种行为（"该节点已有控件，再挂会
  把它静默替换掉"），而 `set_widget` 作为内部入口恰好绕过那道守卫。
- **★ 迷惑点**：`Layout::Scroll` 还在，`measure_scroll` / `arrange_scroll` 照跑，`content_h` /
  `view_h` / `max_scroll` 全算对，**滚动条也照常画出来**（实测 20 行时 `max_scroll = 636`），
  只有 `scroll_y` 恒为 0。**布局全对、事件全丢**——所以沿布局方向排查会一无所获。
- **解法**：新增 `dyn_list::DynListWithScroll`，组合而非替换——`on_update` / `measure` / `paint`
  走 `DynList`、`on_event` 走 `ScrollWidget`，共用同一个 widget 槽位；`list_signal` 改挂它。
  `host_signal` 的容器是普通 `col`、无可滚容器，仍挂纯 `DynList`（给它装 `ScrollWidget` 会
  让不可滚的列容器吞掉滚轮、外层反而失灵）。详见 `patches/PATCHES.md` 补丁 08。
- **★ 测试口径（比修复更值得记）**：布局类回归"行可见 + 容器有高度"**抓不到**这类 bug——
  那两样恰恰都是好的。要抓必须①**塞够行数强制溢出**（3 行装得下，压根不触发滚动），
  ②**真的派发事件**去验 `scroll_y` 变化，而不是只看布局数字。
  回归见 `ui::settings::tests::decoders_page_list_actually_scrolls`；已做负向验证
  （还原 `set_widget(Box::new(widget))` 后该测试立刻变红）。

### K37 —— 空格预览两轮翻车：`RegisterHotKey` 吞键 + 回注二次吞；消费链随主窗隐藏停摆

- **现象**（2026-10-17 用户报）：开着「空格预览」、主窗收进托盘后——①资源管理器/桌面
  选中图片按空格**没反应**，开不出预览；②拼音输入法按空格**选不中候选词**。两处现象
  合起来说明空格确已被接管（键没到目标手里），但接管方的后续动作全部没落地。
- **根因一（吞键回注是死路）**：`RegisterHotKey(VK_SPACE)` 命中后系统**吃掉原始按键**、
  只投递 WM_HOTKEY。一轮对"非接管场景"的补救是 `SendInput` 回注空格——但注入事件走
  同一条键盘管线：vkCode 仍是空格，**再次命中自家热键**、再次被系统吃掉，只把
  WM_HOTKEY 又发了一遍（防环时间戳挡住的只是旗标自触发这个次生灾害）。回注的键永远
  到不了想让它去的应用——打字场景的空格**结构性消失**，与窗体显隐状态无关。
- **根因二（托盘停摆）**：旗标消费挂在 `App::on_interval`、解码成品投递挂在
  `App::channel`——windui 通道回调只在窗口的**帧**里排空，而隐藏/最小化的窗口不产生
  WM_PAINT（框架源码亲注的实测口径："TICK 照跑而 CHANNEL 8 秒一条不来"）。收进托盘
  （= 本功能的主场景）后：轮询消费得到旗标也没人来收成品，预览永远不开，空格照吞。
- **定论**：单键"裸键全局监听"必须走 QuickLook 原始模式——`WH_KEYBOARD_LL` 低级钩子
  在回调内甄别、**从不吞键、从不回注**：不是我们的场景键原样路过；是我们的场景也只是
  "额外做一件事"，键本身继续发给前台（前台是资源管理器列表时空格本就无动作，代价为零）。
  IME 安全靠 `IsCursorActivated` 双判据：可见插入符 **或** GTF 标志置位（组词期应用
  标准光标常被 IME 顶替为 null，光看 caret 会漏判——`shell_selection::is_typing_context`
  已同步加 flags）。重活（外壳 COM、解码、开窗）一律 `PostMessage` 出钩子再干；钩子回调
  超 `LowLevelHooksTimeout` 会被系统**静默摘钩**。
- **解法**：整体重做为 `platform::spacehook.rs`（钩子 + 独立消息线程 + 原生分层预览窗），
  一轮的「全局热键」平台模块与「预览编排」UI 模块随之删除。预览窗不再经 windui/单例键/通道
  ——"隐藏窗口不产帧"这一族问题从结构上不再存在；Esc 在预览窗自己的键盘焦点里处理，
  一轮"预览期临时注册全局 Esc"（吞全系统 Esc 的动作）一并消解。
- **★ 教训**：①"注册热键吞键靠回注补"这类系统级管线假设必须**真机全系统实测**才能验收
  ——单测与合成事件测的是回调层，测不到注入事件与热键表的相互作用；方案 D2 那句
  "QuickLook 用同类方案验证多年"是事实性误判（QuickLook 从来就是低级钩子，且从不吞键）。
  ②功能链路挂在"窗口可见才会跑"的载体（帧/通道/重绘）上，对常驻托盘类软件是
  隐藏地雷；主场景恰是隐藏态时，这类链路必须在隐藏状态下端到端跑一遍才算测过。

### K38 —— 外壳取件的四处真机盲区与探针三重假阴性：桌面不在 `IShellWindows` 枚举里、标签窗登记的是子窗、部分窗口不吐 `IWebBrowser2`、Items 口径与 `/select` 现场不可信

- **现象**（2026-10-17，二轮重做部署后用户真机报"空格预览开了但没效果"；随后探针取证）：
  判定链（类名白名单 / 打字判据 / 钩子链）单测全绿、注入空格回调可达，预览就是不开
  ——断点在**取件环节**（`foreground_selected_file` 返回 `None`），部分前台形态 100% 复现。
- **根因一（桌面）**：一轮断言"桌面也是一枚外壳窗口、`IShellWindows` 枚举天然覆盖"，
  **真机证伪**——该枚举只含资源管理器窗，桌面窗口（Progman 下的 `SHELLDLL_DefView`）
  从不在列表里。桌面必须走 `IShellWindows::FindWindowSW(SWC_DESKTOP, SWFO_NEEDDISPATCH)`
  单独一跳拿桌面浏览器的 IDispatch（QuickLook `getSelectedFromDesktop` 同款）。前置守卫
  = 前台类名 Progman/WorkerW **且内含 `SHELLDLL_DefView`**：Win10/11 贴壁纸层会生成同名
  WorkerW 但没有图标视图，不加守卫会把壁纸层当桌面、拿到错误的选择集。
- **根因二（Win11 部分窗口不吐 `IWebBrowser2`）**：顶层浏览窗的 IDispatch 在部分窗口
  （不同版本/不同创建方式下表现漂移）**cast 不出 `IWebBrowser2`**（上一轮真机日志出现过）。
  旧代码把"cast 失败"当"不是资源管理器"直接 `continue`，三跳正路一步没走就返回 `None`。
  修法：cast 失败**不挡路**——句柄留 0，靠 `IServiceProvider→IShellBrowser::GetWindow`
  用浏览器自己的窗口句柄补判匹配（QuickLook `Shell32.cpp:168` 的 `psb->GetWindow` 同款）。
  本轮复测部分窗口 cast 正常——行为随窗口而异，补判必须作为常态防御保留。
- **根因三（Win11 标签式窗口）**：`IShellWindows` 条目登记的 HWND 可能是**标签子窗**
  （`ShellTabWindowClass`）而非最外层 frame，只比 frame 全数漏配。取前台 frame 之下的
  ShellTabWindowClass 子窗一并匹配（QuickLook `Shell32.cpp:143` fallback 同款）。
- **根因四（取件 API 口径，真正的兼容面大头）**：一轮走 `IFolderView::Items(SVGIO_SELECTION)`
  ——但 QuickLook 全程只用 **`IShellView::GetItemObject(SVGIO_SELECTION)` 取 IDataObject、
  按 `CF_HDROP` 取首项**，从不碰 Items。本机实测：Explorer 文件夹视图的选择集为空时
  Items 直接抛 `0x80070490`（ERROR_NOT_FOUND），`GetItemObject` + `CF_HDROP` 则表现良好
  （稳定窗口上双路实测都通，但主路换成 QuickLook 同款以对齐兼容面）。修法：主路 =
  `GetItemObject` + `CF_HDROP` + `DragQueryFileW`，Items 降为桌面 defview 的兜底。
- **★ 探针现场的三重假阴性（比"取件 API 坏了"更常见，先排除再动手）**：
  ①**`explorer /select` 的新窗口可能从不注册 `IShellWindows`**——真机实测窗口稳定在前台
  30s 仍无条目（mini_take6 逐秒采样），而用户手动打开的窗口注册正常；拿 `/select` 窗口
  当"真实用户窗口"取证，会把系统行为误判成产品故障；
  ②**窗口在前台 ≠ 选择集就绪**：/select 的选中异步完成，800ms/1.8s 下 Items 报
  0x80070490（"没有选择集"），3s 才稳；
  ③**前台会丢**：/select 后数秒前台即被其它窗口抢走（Chrome_WidgetWin_1 等），"对着
  GetForegroundWindow 匹配"的探针测的是新前台——要对**枚举到的稳定 CabinetWClass
  窗口**取证（mini_take5 式），不要依赖前台。
- **★ 排障方法论**（比修复更值得记，本轮全程用它二分定位）：
  ①**多环链路先把变量钉死在最可疑的一环**——`mini_take` 系列探针"不装钩子、不碰
  spacehook，直接调取件函数"，一次回答"是判定断了还是取件断了"；
  ②**逐跳打印**（`select_diag` 探针）把 IShellWindows 每个条目的 HWND / 匹配结果 /
  各级 QueryService 成败全量打出来，哪一跳 None 一目了然——盲改判定链是打地鼠；
  ③**探针样本别放系统 Temp**：Temp 动辄数万文件，explorer 打开它要在异步加载里挣扎
  数秒——放小目录（`.temp/probe_samples`），目录选错 = 白绕一大圈。
- **解法**：`shell_selection::foreground_selected_file` 改为 QuickLook `GetCurrentSelection`
  同款**双路分派**——资源管理器窗走枚举匹配（frame + tab 子窗 + 新家族 GetWindow 三重
  兼容），桌面走 `FindWindowSW(SWC_DESKTOP)` 独立一跳；取件主路 = `GetItemObject` +
  `CF_HDROP`（QuickLook 同款），Items 只做桌面兜底。判定链（spacehook 类名白名单）
  不变。全链路回归探针 = `examples/space_probe`（八步逐环 PASS/FAIL，含缓存命中时长
  对比与"前台未注册时降级验 API 存活"）；稳定窗口取证 = `examples/mini_take5`。

### K39 —— 空格预览的格式过滤漏了内置 SVG：`declared_exts` 只有解码器自述，内置格式永远不在表里

- **现象**（2026-10-17，用户真机）：`space_preview=1` 开启后 PNG 选中按空格正常预览，
  **SVG 选中按空格完全无反应**。
- **根因**：`on_space` 的取件过滤口径 = `declared_exts()`（解码器自述扩展名并集）并排除 raw 类。
  而 SVG/SVGZ 是**内置解码**（`core::decode::decode_one` 直接路由到 `SvgDecodeFn`，

  取件环节跳过 → 静默返回（设计如此：取不到合格图片键原样放行，用户无感）。
  PNG 有 png 解码器认领、恰好不在缺口里，"PNG 能开 SVG 不能开"的对比极具迷惑性——
  不是解码失败，是格式判定环节就挡了。
- **解法**：判据唯一真源收口到 `core::formats::is_previewable`：
  内置（svg/svgz）∪ 解码器自述，且排除裸数据参数类（is_raw）；spacehook 改用这一个函数。
  注意 `gallery::is_image_ext_str`（主窗"算不算图片"）一直是 `BUILTIN_EXTS ∪ declared_exts`
  的正确口径——空格预览此前漏的只是"内置"这一半，主窗一直是对的，所以"主窗能开 SVG
  空格不行"的矛盾本身就是定位线索。`is_builtin_ext` 与 `gallery::BUILTIN_EXTS` 双处同源，
  改内置认领时两边一起动。
  （**m116 注**：那两条"两边"后来都被收口掉了——内置认领自 m56 起**只有 `formats::BUILTIN_DECODERS` 一处**
  （判据 `auto_claim`，清单由 `formats::builtin_exts()` 派生），本句的"两边一起动"**已作废**；
  而 `gallery::is_image_ext_str` 与它服务的 `gallery::is_image_ext` 是**零读者的死函数**，m116 已删，
  主窗"算不算图片"现在只有 `gallery::is_image_ext_in`（一次取好清单再逐个判）那一形。）
- **复现/验证**：`formats::is_previewable` 单测锁"未装入格式来源（SOURCE 空）时内置 SVG
  仍可预览、解码器清单恒空"——K39 回归锁：不允许退回"只查解码器自述"。真机验证：选中
  SVG/SVGZ 按空格开/收。

### K40 —— 空格预览窗悬停呈忙光标（旋转圆圈）：原生窗类注册忘了设 `hCursor`

- **现象**（2026-10-17 用户真机）：空格预览开窗后，鼠标悬停在图片上时，光标变成
  **旋转圆圈**（Windows 11 的忙光标形态），首次悬停尤其明显。
- **根因**：预览窗是原生分层窗（spacehook 自管，不经 windui），窗口类注册时
  `WNDCLASSW.hCursor` 字段走 `..Default::default()` = NULL。DefWindowProc 对
  `WM_SETCURSOR` 的默认应答是 `SetCursor(lpCursor)`——lpCursor 取 wParam = 类光标
  = NULL → `SetCursor(NULL)` 回落系统默认光标，Windows 11 下这个回落路径呈现忙光标。
  windui 主窗不受影响：它的 wnd_proc 有自己的 `WM_SETCURSOR` 应答链（`Widget::cursor()`
  默认 `Arrow`）。
- **解法**：两层一起——① 类注册显式 `LoadCursorW(NULL, IDC_ARROW)` 作 `hCursor`；
  ② `preview_wnd_proc` 处理 `WM_SETCURSOR`：无条件 `SetCursor(IDC_ARROW)` 应答并返回 1，
  把任何来源的忙态光标都清成箭头。两层互为兜底。
- **同类**：任何自建原生窗（不经框架）都要记得注册类时设 `hCursor`；Windows 11 下
  NULL 类光标的 `SetCursor(NULL)` 呈现比旧版更刺眼（旋转圆圈），而忙态会"粘"在
  预览窗上持续转。

### K41 —— EXIF 解析：注释里写着「12MB 上限」，代码里没有；轮数取自文件内 `count`

- **现象**（2026-10-17 全函数审计，主代理逐行复验）：属性窗翻页到一张超大 TIFF/PSD 时
  UI 线程同步读整个文件（内存暴涨 + 数十秒无响应）；另有构造文件把 IFD 的 `count` 写成
  65535，使解析工作量对文件长度**不是线性**，UI 线程冻结分钟级。
- **根因**（两条独立）：
  1. `read_exif` 的文档注释声称 12MB 上限，函数体直接 `std::fs::read` 整文件——**上限只
     存在于注释里**。
  2. `walk` 的每层轮数 `for _ in 0..count` 取自段落字节，而 K26 补的 `visited` 去重只消掉了
     `N^层数` 的递归爆炸，**没给轮数上界**：总工作量 ≈ 访问数 × min(count, 段落长/12)。
     规范§六 第 10 条的后半句「轮数上界取自文件长度而非文件内的计数」当时没落到实现上。
- **解法**：① `read_head(path, EXIF_READ_CAP)` 用 `File` + `take` **只读文件头 12MiB**
  （不是整读后再截断——那正是要避免的）；② 引入 `exif_budget(len) = min(EXIF_MAX_ENTRIES,
  len/2)`，`walk` 每处理一条扣一格、扣光即 `return`，预算成为轮数的真上界。
  合法文件条目数必然 ≤ `len/12`，所以 `len/2` 永不咬到正常文件（既有 15 条端到端测试全过）。
- **已知缺口（诚实记录）**：WebP 的 `EXIF` chunk 常落在文件**尾部**，>12MiB 的 WebP 读不到
  拍摄信息——宁可少显示，也不冻结 UI 线程。
- **★ m104 补（同一枚闸的第二档）**：那道 12 MiB 闸本身后来成了代价——属性窗开着时每换一张图，
  UI 线程同步读满 12 MiB（临时探针逐档取最小、热缓存：**256 KiB 23–25 µs / 4 MiB 1.4–1.7 ms /
  12 MiB 4.2–4.7 ms**，跑在测试二进制里，只用来说明"白付多少字节"）外加一次 12 MiB 分配，而落点不是猜的：
  本机 **94 枚**带 EXIF 标记的真文件里，最深的一枚**非 HEIC** 在 **19,087 B**，超过 256 KiB 的只有两枚
  HEIC（那容器今天根本不解）。现在默认档 256 KiB，WebP 单独保留 12 MiB（它的 EXIF 在尾部，见上一条缺口）。
  教训是同一课的另一面：**兜底上限要按"实际需要量"分档定，兜底值不会因为"它是兜底"就自动合理**；而收紧
  必须两端各钉一条用例（头内必须读得到 / 头外必须照实为空 / WebP 尾部必须还读得到），否则"少读点字节"
  就是悄悄砍功能。★ 同时**照实登记一条新收的缺口**：JPEG/PNG/TIFF 的 EXIF 落在 256 KiB 之后现在显示为空，
  这类文件的全网发生率没测过——用例钉住的是行为，不是发生率。全文。
- **同类**：**「注释/规范/文档声称有闸」不等于有闸**。凡是文档里的数字、上限、禁令，落点必须是
  可运行的检查（代码判定、脚本或单测），否则按「不存在」处理。本轮同形问题另有两处：
  §八.1 的 `unwrap/panic` 红线**没有任何机器执行**（属待补门禁）、`thumbs.rs` 文档写「最久未用
  淘汰」而实现只在 put 时打戳（实为 FIFO）。

### K42 —— 外壳选中项：`STGMEDIUM` 未校验 `tymed` 就当 `HDROP` 用

- **现象**：空格预览取资源管理器/桌面选中文件时，特定命名空间下整个进程**无声消失**。
- **根因**：`dao.GetData(&fe)` 成功后直接 `HDROP(med.u.hGlobal.0)` 并立刻 `DragQueryFileW`，
  全程不回看 `med.tymed`、不判空句柄。请求里写的 `tymed` 只是**期望**，不是**保证**；
  第三方命名空间 / OneDrive / 回收站视图的 `IDataObject` 可以合法返回别的 TYMED。
  句柄类型混淆后的 AV 落在 `extern "system"` 回调里 = abort（见 §七「UI 线程 panic = 窗口消失」同族）。
- **解法**：取用之前先校验 `med.tymed == TYMED_HGLOBAL.0 as u32` 且 `hGlobal` 非空，
  不合则 `ReleaseStgMedium` 后**放弃接管**（返回 None，空格照旧不吞键）。注意
  **先记下 `tymed` 再归还**——Release 之后字段内容不再可信。
- **同类**：凡跨进程/COM 边界拿回来的结构，**每个判别字段都要回看**（`tymed` / `cbSize` /
  句柄非空），"我请求的是什么"与"对方给的是什么"是两件事。字段宽也不对称：
  `STGMEDIUM.tymed` 是 `u32`、`TYMED_HGLOBAL.0` 是 `i32`，必须显式收口。

### K43 —— `pin_glyph`：`&mut [u8]` 横跨 GDI 绘制存活（noalias 假设被违反）

- **现象**：置顶图钉可能整幅全透明（图标消失）；`cargo test`（debug）**抓不到**，
  是否发作取决于 release 优化强度与编译器版本——潜伏型。
- **根因**：`slice::from_raw_parts_mut(bits, size)` 造出的 `&mut [u8]` 被留到函数末尾读回，
  中间横跨 `DrawTextW` 等 GDI 调用，而字形像素正是 GDI 经 `hdc` 写进**同一块** DIB 内存。
  `&mut` 在 LLVM 眼里是 noalias，优化器有权认定没人动过它，于是把预填的 `G=0` 直接折进
  之后的 `px[1]` 读。
- **解法**：预填用**块作用域**收掉可变引用；读回阶段在绘制完成后**另建**只读切片
  （`from_raw_parts(bits as *const u8, size)`）。同项目 `spacehook.rs` 处理同类 DIB 内存
  用的是 `write_bytes` / `copy_nonoverlapping`，本可避免。
- **同类**：凡「指针指向的内存被第三方 API 写」的场景，不要让 Rust 的可变借用跨过那次调用；
  写用短命借用或裸指针，读在写之后重新构造。

### K44 —— 托盘「退出」绕过 `on_close_request`：防抖窗口里的偏好静默丢失

- **现象**（2026-10-17 运行顺序专项）：改完设置不到 5 秒就从**托盘菜单**退出，下次启动配置
  回到旧值。走窗口 ×（Alt+F4）退出则正常。
- **根因**：配置是**防抖落盘**的（`mark_dirty` 置脏 + 16ms 轮询 `poll_save` 到期才写，
  5s trailing），权威兜底 `flush_save` 只挂在 `.on_close_request(...)` 上。而托盘「退出」调的是
  框架 `TrayCtx::quit() → quit_app() → DestroyWindow`——**`DestroyWindow` 派发的是
  `WM_DESTROY`，不经过 `WM_CLOSE`**，那条回调根本不执行。两个入口说的是同一件事
  （"退出"），却只有一条走了决策链。
- **解法**：把兜底落盘从"某个关窗回调里"挪到 **`App::run()` 返回之后**——退出路径有几条不重要，
  重要的是它们**都**要经过这一个点。同处补一句 `spacehook::set_enabled(false)`：低级键盘钩子
  挂在系统钩子链上，收权不该赌"进程消亡时系统替我摘"；投递本身走控制线程（摘钩必须在装配它的
  那条线程上做，见 `spacehook::post_enable`），控制线程已停时投递失败无害、不退化于现状。
- **同类**：凡「多条入口 → 同一个收尾动作」的结构，兜底要放在**汇合点**上，不是放在其中一条
  入口的回调里。看图器里的对应汇合点有三个：`App::run()` 返回（退出）、`Gallery::from_file`
  （换目录）、`Viewer::install`（解码落地）——需要"必然执行一次"的事情挂这三处之一。

### K45 —— 我给预读加的字节上限是**算错账**加出来的（同日回退）

- **现象**（2026-10-17 用户真机追问）：让我验「超大图不再为预读常驻内存」，用户答
  「我没有大图，并且『目录翻页』是什么意思？」——**无法复现的验收项，通常说明它压根不会触发**。
- **根因**：我写 `PREFETCH_MAX_BYTES = 32 MiB` 时的推导是「40MP 档整图一份 = 160MB，两份 = 320MB」，
  于是判定必须再加一条字节闸。但预读存的**不是原图档**：[`Self::request_prefetch`] 的框是
  `视口逻辑尺寸 × dpi`，解码器出来就经 `fit_to` 收到该框内——4K 满屏 3840×2160 × 4 B
  ≈ **31.6 MiB，恰好落在我那道 32 MiB 门槛之下**。所以闸门在现实配置里永不触发，是一段
  带错误注释的死代码；而它一旦撞到（5K+ 视口），效果是**把预读整个关掉**，比不加更糟。
- **解法**：回退。真正的内存账写回 `cache_prefetch` 的注释里：**最坏驻留 = `PREFETCH_CAP` ×
  视口档**（4K 约 63 MiB，1080p 约 17 MiB），这个数由份数封顶已经是确定值，不需要第二条闸。
  将来真要压这块内存，动的应是 `PREFETCH_CAP` 或视口档本身。
- **同类**：加「上限」之前先把那份内存的**真实尺寸来源**算清楚——原图档、视口档、文件档三者
  差一到两个数量级。判据算错的上限比没有上限更危险：它在注释里冒充一道防线，且真撞到时是
  静默关掉一项功能。**验收项写不出「怎么触发」，就是设计阶段的红灯。**

### K46 —— 「正在看的那张优先」写在注释里，代码里却没有优先级

- **现象**（2026-10-17 用户真机）：打开 105 MB 的 6055×6055 TIFF，**放大后画面不清**，用户直接
  怀疑「我们对大图做了阉割」。
- **先排除嫌疑，再找根因**：`examples/zoom_sharp_probe.rs` 打三档**上屏位图的真实尺寸**，
  TIFF / JPEG / PNG 三个 100 MB 级样本全部 PASS（899×899 → 6055×6055 → 6055×6055）——
  按需重解链路是通的，没有阉割。慢在**取队顺序**：`decode_loop` 是单线程 FIFO，而队列里常态
  躺着最多 3 张在途缩略图（`thumbs::MAX_INFLIGHT`）+ 刚装完图顺手发的预读（在途最多 1 条）
  （`Viewer::apply` 成功后立刻 `request_prefetch`），用户刚按下的那次缩放重解排在它们**后面**。
  实测 2 张缩略图在前：主图重解 **0.37s → 1.98s**；插队修复后同场景 **0.25s**。
- **`main_floor` 不是优先级**：它只在请求**被取出之后**判 `seq < floor` 作废，管不了「排在前面
  那张正在解」。世代令牌解决的是「过期结果别盖新图」，从来不能解决「新请求排在后台活儿后面」——
  两件事名字很像（都叫"取消/让路"），注释里那句"不能让缩略图把正在看的那张挤到队列后面去"
  恰好是**愿望被当成了实现**。
- **第一版实现踩在 std mpsc 上**：插队要"取之前看一眼队里有没有 `Main`"，只能非阻塞轮询；
  `Receiver::try_recv` 在**发送端已 drop 且队里还有货**时返回 `Disconnected` 并把接收端**永久判死**，
  剩下的请求静默丢失（rust-lang/rust#34087）。四条请求只解出一条，三条单测当场红灯。
  改用自持的 `Mutex<VecDeque<Req>> + Condvar`（`decode::Queue`）：顺序可控、丢不了，
  `Decoder` 释放时 `close()` 叫醒工作线程。
- **同类**：① 凡「用户动作应当优先于后台填充」的结构，要问优先级在**取队那一刻**生效还是只在
  **入队那一刻**生效——只在入队时排序的"优先级"等于没有。② 需要窥视队首的调度不要用 std mpsc。
  ③ 观感类报障（糊 / 慢 / 卡）先做**可测量的判据**再动手：本轮若从"是不是阉割"倒推，就会去动
  `MAX_PIXELS`、预读这些其实无辜的地方。

### K47 —— 解码缓存只按"龄"清理 = 长会话等于没有上限（实测 7.5 GB） **［2026-10-19 已根治：整套磁盘解码缓存撤除，见 K68 与 `HISTORY.md`］**

- **现象**（2026-10-17 给大图探针跑盘后）：`temp/decode-cache` 攒到 **7.5 GB / 126 条**，
  而设置页的"缓存清理"档位明明不是"不清理"。
- **根因**：`dcache::cleanup(max_age_days)` 只在**启动时**跑一遍，判据又只有 mtime 龄。
  缓存存的是**未压缩 RGBA**（一张 40MP 原图档 = 160 MB），于是"一天不关程序翻几百张大图"
  这条路径上没有任何东西挡着。按龄与按总量是**两种独立的账**，只做其一等于另一个没有闸——
  与 K41"注释声称有闸 ≠ 有闸"同族。
- **解法**：补 `MAX_CACHE_BYTES`（2 GiB）总量闸，按同一份 mtime 簿记从最旧淘汰、**删到刚好
  达标即停手**（不做"腾出一半空间"式的激进回收，那会把明天还要看的图赶出去，白丢一次解码）。
  清理跑两遍：按龄（受档位开关控制）+ 按总量（**不受开关控制**——"不清理"说的是"别动我的
  缓存命中"，不是"请把盘吃满"）。写入侧另有 `TRIM_STRIDE`（256 MB）步长复查，长会话也突破不了。
  设置页文案同步成「占用 X，上限 Y」，让用户看得见它不是无界的。
- **顺带抓到自己**：第一版把 `cleanup_with(age, cap)` 的测试写好后，实现体里仍写死
  `MAX_CACHE_BYTES`——**测试当场红灯**。上限做成参数不只是为了小数值好测，它是逼实现把
  "这条闸到底用哪个数"说清楚。
- **同类**：任何"按时间清理"的缓存，都要单独问一句**单次会话内**能长多大；只有龄闸的缓存
  在"开着程序不动"的用法里等于无上限。同理，凡是把某个开关理解成"这一整套动作都跳过"的
  实现，都要检查有没有一条底线不该被它跳过。
